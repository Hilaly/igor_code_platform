# Создание файлового агента

Файловый агент — это постоянная роль: системные инструкции плюс отбор доступных tools и skills.
Формат сам по себе не делает роль надёжной. Сначала ограничь ответственность агента, затем выдай
ему минимальные возможности для этой ответственности.

**Главный принцип:** одна миссия, явные границы, least privilege и проверяемый контракт результата.

## Рабочий процесс

1. **Сформулируй одну миссию.** Заверши предложение: «Этот агент отвечает за …». Если в нём два
   независимых результата, раздели роли.
2. **Опиши границы.** Перечисли входные артефакты, допустимые изменения и явные нецели. Не заставляй
   модель угадывать, можно ли менять соседние модули, сеть или внешние системы.
3. **Задай условия остановки.** Укажи, когда агент обязан спросить пользователя, сообщить blocker
   или отказаться от необратимого действия.
4. **Выдай минимальные tools.** Начни с allowlist. `include: ["*"]` оправдан у намеренно общего
   агента, но автоматически разрешит и будущие совпавшие инструменты.
5. **Подключи только нужные skills.** Используй plugin-qualified id для plugin-owned скила и
   короткий id для standalone. Не подключай весь каталог «на всякий случай».
6. **Опиши workflow.** Минимум: что прочитать, как изменить, чем проверить, что вернуть. Правила
   должны объяснять решения и ограничения, а не пересказывать названия tools.
7. **Определи output contract.** Например: результат, изменённые файлы, выполненные проверки,
   непроверенные риски и blockers.
8. **Выбери model и `thinking-level` только при необходимости.** Отсутствие поля оставляет выбор
   вызывающей стороне. Parser проверяет у `model` только непустую строку; существование
   `provider/model` определяется runtime-каталогом.
9. **Проверь роль на сценариях.** Дай нормальную задачу, неоднозначную задачу и запрос за пределами
   scope. Агент должен выполнить первую, уточнить вторую и не расширить полномочия в третьей.

## Минимальный специализированный агент

```markdown
---
name: code-reviewer
description: Reviews an existing code change and reports correctness, regression, and verification risks without modifying files
tools:
  include: ["read", "bash"]
  exclude: ["*-write", "*-delete"]
skills:
  include: ["code-review"]
  exclude: []
thinking-level: medium
---

Ты проверяешь уже подготовленное изменение и не редактируешь файлы.

1. Прочитай правила проекта и итоговый diff.
2. Проверь затронутые тесты, типы и публичные контракты.
3. Сообщи findings по убыванию важности с точными путями.
4. Если blocker не позволяет проверить вывод, назови его вместо предположения.

В конце перечисли выполненные команды и непроверенные риски.
```

Имена tools зависят от включённых плагинов. Перед использованием примера сверь allowlist с
фактическим runtime-каталогом.

## Проверка перед завершением

- mission помещается в одно предложение;
- scope и нецели явно названы;
- destructive или внешние действия имеют stop/escalation rule;
- allowlist минимален, wildcard обоснован;
- instructions требуют фактической проверки, а не обещания «должно работать»;
- output contract перечисляет evidence и ограничения;
- `name` совпадает с директорией;
- parser diagnostics отсутствуют;
- три сценария роли дали ожидаемое поведение.

## Частые ошибки

- **Описание говорит только «помогает с кодом».** Пользователь не понимает специализацию, а каталог
  не помогает выбрать роль. Назови результат и ограничения.
- **`include: ["*"]` используется по привычке.** Новый плагин может незаметно расширить полномочия.
- **Skills дублируются в системном prompt.** Роль должна ссылаться на reusable knowledge, а не
  копировать его и создавать две расходящиеся версии.
- **Нет нецелей и stop conditions.** Агент оптимизирует задачу шире намерения автора.
- **Нет проверки и output contract.** Агент может сообщить об успехе без evidence.
- **Жёстко задана модель без причины.** Это снижает переносимость и мешает вызывающей стороне
  выбрать доступную модель.
