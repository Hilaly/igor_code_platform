# Создание скила

Скил — не архив заметок, а компактная точка входа в повторяемую работу. Модель сначала видит только
`name`, `description` и `location`; тело и соседние ресурсы она читает после того, как description
совпал с задачей.

**Главный принцип:** сначала спроектируй условия активации и проверяемый результат, затем пиши
инструкции. Формально корректный, но не найденный или бесполезный скил не решает задачу.

## Рабочий процесс

1. **Назови повторяемую задачу.** Не создавай скил для одноразовой истории или правила конкретного
   репозитория — последнее живёт в его `AGENTS.md` или документации.
2. **Определи тип.**
   - Reference: точный формат, API или доменные сведения.
   - Workflow: последовательность действий с проверяемым результатом.
   - Discipline: правило поведения, которому агент склонен находить исключения.
3. **Собери 2–3 реальных запроса.** Они дают слова для имени и description и показывают, где
   общеизвестных знаний модели недостаточно.
4. **Выбери имя.** Используй lowercase hyphen-case без `_`; имя директории и поле `name` обязаны
   совпадать.
5. **Напиши description как условие применения.** Начинай с `Use when`, перечисляй наблюдаемые
   ситуации и артефакты. Не прячь triggers в тело: до активации модель его не видит.
6. **Выбери степень свободы.**
   - Высокая: эвристики, когда допустимо несколько решений.
   - Средняя: шаблон или псевдокод с параметрами.
   - Низкая: исполняемый скрипт для хрупкой и строго повторяемой операции.
7. **Собери минимальный `SKILL.md`.** Оставь основной принцип, workflow, проверку и типовые ошибки.
   Тяжёлый reference вынеси в `references/`, исполняемую механику — в `scripts/`, входные шаблоны и
   файлы результата — в `assets/`.
8. **Проверь механику.** Убедись, что parser принимает файл без diagnostics, а все относительные
   ссылки разрешаются от директории скила.
9. **Проверь поведение.** Для workflow/reference выполни реальные задачи. Для discipline сначала
   зафиксируй нарушение без скила, затем повтори тот же сценарий со скилом и закрой найденные
   обходные пути.

## Минимальный пример

```markdown
---
name: code-review
description: Use when reviewing a code change before publication, especially when tests, types, generated files, or the final diff may have been missed.
compatibility: Requires git
allowed-tools: read bash
---

# Проверка изменения

Сначала изучи итоговый diff, затем запусти относящиеся к изменению тесты и typecheck.

## Проверка

Сообщи найденные проблемы по убыванию важности. Если проблем нет, перечисли фактически выполненные
команды и непроверенные риски.
```

`allowed-tools` сейчас только метаданные: поле не ограничивает runtime-набор инструментов и не
заменяет правила подтверждения операций.

## Проверка перед завершением

- description начинается с `Use when` и содержит слова из реальных запросов;
- имя переносимо и совпадает с директорией;
- тело не повторяет длинный reference;
- каждая упомянутая локальная ссылка существует;
- scripts были реально запущены на representative input;
- model-invocable скил содержит полезную инструкцию или ссылки на полезные ресурсы;
- diagnostics просмотрены через панель проекта или `GET /api/projects/:id/file-resources`;
- хотя бы один реалистичный запрос выполнен с этим скилом.

## Частые ошибки

- **Description пересказывает workflow.** Модель может решить, что метаданных достаточно, и не
  прочитать тело. Описывай условия применения, а действия оставляй внутри.
- **Всё лежит в одном огромном файле.** Это отменяет progressive disclosure. Вынеси справочник или
  автоматизацию в соседний ресурс.
- **Скил повторяет общеизвестные советы.** Оставляй только специфический контракт, неочевидный
  workflow или reusable asset.
- **Пустое тело считается готовым скилом.** Parser это допускает, но такой model-invocable скил
  обычно ничего не добавляет.
- **`allowed-tools` принимают за sandbox.** До появления runtime enforcement это информационное
  поле, а не граница безопасности.
- **Discipline-скил пишут без baseline.** Тогда неизвестно, какое реальное нарушение и какие
  рационализации должна исправлять инструкция.
