# Контракт агентного рантайма (Pi)

Что именно предоставляет Pi и на что мы опираемся. Документ описывает чужой код, поэтому он
устаревает не от наших изменений, а от чужих релизов — механика та же, что у
[runtime-checks.md](runtime-checks.md): при обновлении Pi документ перечитывается, иначе он
тихо превращается в ложь.

**Проверено по исходникам:** [earendil-works/pi](https://github.com/earendil-works/pi),
коммит `cee5ff7`, версия пакетов 0.82.1, лицензия MIT, `engines.node >= 22.19.0`.
`@earendil-works/pi-ai` стоит зависимостью `packages/agent-runtime-pi` и закреплён **точной
версией без `^`**: документ описывает конкретный релиз, и молчаливый minor превратил бы его в ложь
раньше, чем это заметит тест.
**Что мы с этим делаем:** [architecture.md](architecture.md) — Pi за нашим интерфейсом, сессией
владеет ядро; [hooks.md](hooks.md) — как события Pi отдаются плагинам.

## Сессии

Сессия — не линейный лог сообщений, а **дерево записей**: есть ветвление, форк от произвольной
записи, компакция и навигация по дереву. Записи типизированы: сообщение, смена модели, смена
набора инструментов, компакция, суммаризация ветки, метка, произвольная пользовательская запись.

Ключевое для нас: **хранилище сессий — это интерфейс.**

```ts
interface SessionStorage {
  getMetadata(): Promise<TMetadata>;
  getLeafId(): Promise<string | null>;
  setLeafId(leafId: string | null): Promise<void>;
  createEntryId(): Promise<string>;
  appendEntry(entry: SessionTreeEntry): Promise<void>;
  getEntry(id: string): Promise<SessionTreeEntry | undefined>;
  getEntries(options?: SessionEntryCursorOptions): Promise<SessionTreeEntry[]>;
  // …плюс поиск по типу, метки, статистика, путь до корня
}

interface SessionRepo {
  create(options): Promise<Session>;
  open(metadata): Promise<Session>;
  list(options?): Promise<TMetadata[]>;
  delete(metadata): Promise<void>;
  fork(source, options): Promise<Session>;
}
```

В комплекте идут реализации на JSONL-файлах и в памяти. **Берём готовую JSONL-реализацию Pi и
направляем её в директорию данных** ([data-directory.md](data-directory.md)) — своей не пишем.

Их JSONL-реализация привязывает сессию к рабочей директории: в метаданных лежит `cwd`, а
`list({ cwd })` фильтрует по нему. То есть привязка сессии к папке — не наша выдумка, она есть в
рантайме; проектом эту папку делаем мы ([sessions-and-projects.md](sessions-and-projects.md)).

Типы записей дерева: сообщение, смена модели, смена уровня ризонинга, смена активного набора
инструментов, компакция, суммаризация ветки, метка, имя сессии, лист, произвольная запись
(`custom`) и произвольное сообщение (`custom_message`). Последние два — точки, куда приложение
кладёт своё: `custom` в контекст модели по умолчанию не попадает, для него задаётся проектор.

### Что можно делать с живой сессией

Точка входа — `AgentHarness`. Всё это уже есть в рантайме, писать нам не нужно.

| Возможность                | Как в Pi                                                              |
| -------------------------- | --------------------------------------------------------------------- |
| Запуск турна               | `prompt(text, { images })`                                            |
| Запуск скила               | `skill(name, additionalInstructions)`                                 |
| Запуск шаблона промпта     | `promptFromTemplate(name, args)`                                      |
| Стиринг                    | `steer(text, { images })` — вклинивается между турнами агента         |
| Догоняющее сообщение       | `followUp(text, { images })` — агент берёт его вместо остановки       |
| Сообщение к будущему турну | `nextTurn(text, { images })` — уходит в начало следующего `prompt`    |
| Режим разбора очередей     | `setSteeringMode`, `setFollowUpMode`: «всё сразу» или «по одному»     |
| Прерывание                 | `abort()` — возвращает то, что выкинул из очередей                    |
| Ожидание простоя           | `waitForIdle()`                                                       |
| Смена модели               | `setModel` — пишется в дерево сессии, работает и посреди турна        |
| Смена уровня ризонинга     | `setThinkingLevel`, значения `off … max`                              |
| Набор инструментов         | `setTools`, `setActiveTools` — полный набор и активный отдельно       |
| Скилы и шаблоны промптов   | `setResources`                                                        |
| Компакция                  | `compact(customInstructions)` — и больше ничего, см. ниже             |
| Навигация по дереву        | `navigateTree(entryId, { summarize, label })` — с суммаризацией ветки |
| Дописать сообщение         | `appendMessage` — в сессию, без запроса к модели                      |
| Форк                       | `SessionRepo.fork(source, { entryId, position })` — новая сессия      |
| Список и удаление          | `SessionRepo.list`, `delete`                                          |
| Имя сессии                 | `appendSessionName`                                                   |
| Метки записей              | `Session.appendLabel` — **не на harness**, см. ниже                   |
| Статистика                 | `getSessionStats`: сообщения, токены с разбивкой по кэшу, стоимость   |
| Чтение дерева              | `getEntry`, `getEntries` с курсором, `getBranch`, `findEntries(type)` |

#### Изображения в сообщении человека

Четыре пути из пяти принимают `options.images` штатно; у `appendMessage` такого параметра нет, и
содержимое ему платформа собирает руками — в том же порядке, в котором его складывает сам рантайм:
сначала текстовый блок, затем изображения. Нормализатор при этом один на все пять: раздельные
реализации быстро разошлись бы в порядке блоков и в том, что считается сообщением без текста.

Рантайм всегда ставит текстовый блок первым, даже пустой. В ленту такой блок не попадает — иначе она
рисовала бы абзац, которого человек не писал; провайдеру он тоже не доезжает: адаптер выбрасывает
пустые текстовые блоки перед отправкой. Именно поэтому сообщение из одних картинок законно.

**Модель проверяется до похода к провайдеру, и неизвестная считается текстовой.** Capability лежит в
`Model.input` и берётся оттуда — отдельного реестра для этого не нужно. Проверяется и само сообщение,
и действующая ветка: после первой картинки текстовая модель не годится даже для чисто текстового
продолжения, потому что новый контекст всё равно понесёт изображение. Ветка при этом читается только
тогда, когда выбранная модель текстовая, — годная модель за проверку не платит.

Fail closed выбран потому, что у провайдера нет безопасного «попробуем и посмотрим»: он либо ответит
невнятной ошибкой, либо молча выбросит картинку, и человек решит, что модель её посмотрела.

### Контекст: чего в рантайме нет

Разобрано по распакованному пакету перед срезом 10b. Таблица выше называет вызовы, но не говорит их
границ, а границы здесь дорогие — из них следует, сколько кода пишем мы.

- **Автокомпакции нет вовсе.** `shouldCompact(contextTokens, contextWindow, settings)` экспортирована
  и реализована — `contextTokens > contextWindow - reserveTokens`, — но **внутри пакета не вызывается
  ни разу**. Ни флага, ни порога, ни таймера, ни фонового вызова: решение «пора» и вызов `compact()`
  целиком на приложении.
- **`compact()` не принимает параметров, кроме инструкций.** `reserveTokens` и `keepRecentTokens`
  берутся из `DEFAULT_COMPACTION_SETTINGS` (16384 и 20000) жёстко. Единственный способ задать свои —
  собрать компакцию самому (`prepareCompaction` со своими настройками плюс `compact`) и вернуть её из
  хука `session_before_compact`; тогда рантайм запишет её с `fromHook: true`. Так и сделано
  ([sessions-and-projects.md](sessions-and-projects.md)), и у этого пути есть три оговорки, которые
  видны только на запущенном коде:
  - **`prepareCompaction` читает из настроек только `keepRecentTokens`.** Поле `enabled` она
    игнорирует — то есть `enabled: true` в нашем вызове ничего не включает и выключателем не
    является. `reserveTokens` доезжает до дела позже, параметром `generateSummary`, где становится
    `maxTokens = 0.8 * reserveTokens`.
  - **Наш хук зовут уже после того, как рантайм подготовил компакцию своими константами.**
    `harness.compact()` сам делает `prepareCompaction(branchEntries, DEFAULT_COMPACTION_SETTINGS)` и
    бросает `AgentHarnessError("compaction", "Nothing to compact")` при `undefined` — **до** вызова
    хука. Значит наши параметры способны только сузить то, что дефолты уже разрешили начать, а ветка
    «наша подготовка ничего не нашла» на тех же записях недостижима.
  - **Одна компакция разрезанного турна — до двух запросов к модели**, а не один:
    `generateSummaryWithUsage` для истории плюс `generateTurnPrefixSummary` для префикса турна.
    Для очереди походов к модели это значит, что слот компакции стоит дороже слота турна.
  - `prepareCompaction` возвращает `undefined` ровно в двух случаях: ветка пуста либо её последняя
    запись уже `compaction`. Никакого порога внутри неё нет — порог целиком наш.
- **Отменить компакцию или суммаризацию снаружи нечем.** `signal` в нагрузке обоих
  `session_before_*` — это `new AbortController().signal`, который никто не дёргает. `abort()`
  относится к турну и на эти операции не действует.
- **Метка не операция harness.** Публичного метода у `AgentHarness` нет: метка ставится
  `Session.appendLabel(targetId, label)`, а снимается тем же вызовом с `undefined`. Действующее
  значение — свёртка всех записей `label` по `targetId`, потому что файл только дописывается.
  Опция `label` у `navigateTree` **записи `label` не создаёт** — она уходит в нагрузку хука
  `session_before_tree` и больше никуда.
- **`navigateTree` не говорит, куда переехал лист.** `NavigateTreeResult` — это `cancelled`,
  `editorText` и `summaryEntry`, и всё. Новый лист приходится спрашивать `getLeafId()` после
  перехода, а вычислить его из цели нельзя: у реплики человека и у `custom_message` листом
  становится **родитель** цели, у всего прочего — сама цель.
- **Одна ситуация, два класса ошибки.** `getBranch(неизвестный id)` бросает
  `SessionError("not_found")`, а `navigateTree(неизвестный id)` — `AgentHarnessError`
  с кодом `invalid_argument`. Ловить приходится оба.
- **Вниз по дереву рантайм не ходит.** Ни `getChildren`, ни списка листьев, ни списка веток:
  `getBranch` идёт от записи вверх по `parentId`, а всё остальное — плоский `getEntries()`. Дерево
  для показа строит приложение.
- **`getBranch()` обрывается на компакции.** Путь идёт вверх до ближайшей записи `compaction` и
  останавливается на ней — это ровно то, что увидит модель. Полной истории до настоящего корня
  готовым методом не получить: её надо собирать обходом `parentId` через `getEntry`.
- **`getEntries({ afterEntrySeq })` — включающий индекс в плоском массиве, а не «после seq».**
  Реализация — `entries.slice(afterEntrySeq ?? 0, …)`, и поля `seq` у записей не существует вовсе.
  Имя параметра обещает не то, что он делает.
- **Метрик контекста на harness нет.** Ни текущего числа токенов, ни доли заполнения, ни события о
  приближении к пределу. Считается своими руками:
  `estimateContextTokens((await session.buildContext()).messages)` — эвристика «символов делить на
  четыре», не токенизатор, — а `contextWindow` живёт на `Model` из `pi-ai`.
- **`getSessionStats()` считает по всему файлу, а не по ветке**, и молча пропускает записи, у которых
  в `usage` не всё числа. Для вопроса «сколько заплачено» это верно, для «сколько влезет» — нет.
- **Событие о смене листа даёт только `navigateTree`.** `session_tree` эмитится оттуда; прямой
  `Session.moveTo()` или `setLeafId()` не сообщает ничего. Обычная дозапись двигает лист молча, и
  события «запись добавлена» тоже нет.

### Типы записей дерева: одиннадцать

`message`, `thinking_level_change`, `model_change`, `active_tools_change`, `compaction`,
`branch_summary`, `custom`, `custom_message`, `label`, `session_info`, `leaf`. `parentId` есть у
всех — он `string | null`, и `null` только у корня. Файл **строго только дописывается**: ни удаления,
ни правки записи нет ни на одном уровне API, поэтому «снять метку» и «переставить лист» — это тоже
новые записи.

Форк копирует записи **с теми же `id` и `parentId`**, то есть идентификатор записи уникален внутри
сессии, но не между сессией и её форком. Форк без `entryId` копирует **весь файл со всеми ветками**,
а не текущую ветку.

Фазы harness — `idle`, `turn`, `compaction`, `branch_summary`, `retry`. `prompt`, `skill`,
`promptFromTemplate`, `compact` и `navigateTree` требуют `idle` и иначе бросают `busy`; `steer` и
`followUp`, наоборот, требуют не-`idle`. Это ограничение видно снаружи, поэтому состояние сессии
придётся показывать в интерфейсе, а не прятать.

Чего в Pi нет: **архива**. Есть удаление, есть список — понятия «убрано с глаз, но не потеряно»
нет, это наш слой.

### Базовые инструменты

`pi-agent-core` даёт фабрики четырёх инструментов: `bash`, `read`, `write`, `edit`. Они
параметризуются средой исполнения (`ExecutionEnv` — файловая система плюс шелл), реализация на
Node в комплекте. Это и есть «агент из коробки умеет править файлы и bash»: возможность приходит
из рантайма, а не из плагинов.

Инструменты, добавленные результатом другого инструмента, поддержаны отдельным полем результата
(`addedToolNames`). Платформа эту возможность для скилов не использует: файловый скил активируется
только чтением и не меняет набор инструментов.

## Хуки

В Pi они называются событиями. Точка подписки — `AgentHarness`:

- `subscribe(listener)` — весь поток событий, вернуть ничего нельзя; обработчик получает
  `AbortSignal`;
- `on(type, handler)` — подписка на конкретный тип, у части типов возвращаемое значение влияет
  на ход работы; `AbortSignal` обработчику **не передаётся**.

Оба возвращают функцию отписки. Списки ниже полные: сверены по `AgentHarnessEventResultMap`,
`AgentHarnessOwnEvent` и `AgentEvent`.

Событий три группы: 8 перехватывающих и 14 уведомительных у самого harness плюс 10 событий цикла
агента. **В типе `on()` перечислены только 22 события harness** — события цикла агента приходят
исключительно в `subscribe()`, то есть перехватить их нельзя по устройству.

### Перехватывающие: 8

| Событие                   | Что приходит                                                                 | Что можно вернуть                                                          | Что это даёт                          |

| `context`                 | `messages`                                                                   | `{ messages }`                                                             | переписать контекст перед запросом    |
| `before_provider_request` | `model`, `sessionId`, `streamOptions`                                        | `{ streamOptions? }`                                                       | пропатчить параметры стрима           |
| `before_provider_payload` | `model`, `payload`                                                           | `{ payload }`                                                              | переписать сырой запрос к провайдеру  |
| `tool_call`               | `toolCallId`, `toolName`, `input`                                            | `{ block?, reason? }`                                                      | **запретить вызов инструмента**       |
| `tool_result`             | `toolCallId`, `toolName`, `input`, `content`, `details`, `isError`, `usage?` | `{ content?, details?, isError?, usage?, terminate? }`                     | подменить результат, оборвать цикл    |
| `session_before_compact`  | `preparation`, `branchEntries`, `customInstructions?`, `signal`              | `{ cancel?, compaction? }`                                                 | отменить или подсунуть свою компакцию |

| `tool_execution_start`  | инструмент вызван: id вызова, имя, аргументы                          |
| `tool_execution_update` | частичный результат инструмента                                       |
| `tool_execution_end`    | инструмент отработал: результат и признак ошибки                      |

Это тот поток, из которого рисуется живой ход сессии в интерфейсе. Перехвата у него нет: вернуть
из `subscribe()` ничего нельзя, а в `on()` этих типов не существует.

**Отписка во время активного турна.** Обработчики лежат в `Set`, обход — `for…of`. Проверено
запуском на Node 24.18.0: обработчик, отписанный до того, как обход до него дошёл, не вызывается;
обработчик, подписавшийся во время обхода, вызывается в этом же событии.

## Агенты и скилы: чем это поддержано в Pi

Агенты — настраиваемые сущности, а скилы — файловые инструкции, которые модель подключает по
необходимости. Настройки живой сессии и вычисляемый системный prompt ложатся на существующий
контракт Pi, но формат каталога и его обновление принадлежат платформе.

**Настройки агента** задаются в `AgentHarnessOptions` и меняются на живой сессии: `setModel`,
`setThinkingLevel`, `setTools(tools, activeToolNames?)`, `setActiveTools`, `setResources`,
`setStreamOptions`. Уровень ризонинга — перечисление `ThinkingLevel`: `off`, `minimal`, `low`,
`medium`, `high`, `xhigh`, `max`. Инструкции — `systemPrompt`, строкой или колбэком.

Платформа передаёт `systemPrompt` колбэком и вычисляет его заново на границе каждой операции
модели. Основные инструкции агента сохраняются целиком. Для файлового агента после них через пустую
строку добавляется папка, в которой лежит выбранный `AGENT.md`:

```xml
<agent_data>
  <directory>/absolute/path/to/agent</directory>
</agent_data>
```

Это runtime provenance, а не текст определения: parser переносит абсолютный путь `AGENT.md`, демон
передаёт его `dirname`, а программный агент без файла не получает ни блока, ни пустой обёртки.
Следующей непустой секцией идёт детерминированно отсортированный XML-каталог применимых скилов:

```xml
<available_skills>
  <skill>
    <name>code-review</name>
    <description>Проверяет изменение перед публикацией</description>
    <location>/absolute/path/to/code-review/SKILL.md</location>
  </skill>
</available_skills>
```

В записи находятся только `name`, `description` и абсолютный `location`; XML-метасимволы в них и в
`agent_data.directory` экранируются. Пустой набор не добавляет ни обёртку, ни лишние переводы строк.
Итоговый порядок непустых секций всегда один: инструкции, `<agent_data>`, `<available_skills>`.
Инструкции, папка агента и весь набор скилов заменяются на живой сессии целиком, поэтому следующая
операция модели видит актуальные определения после hot reload без пересоздания harness.

Встроенный `starter.generic` сам читает `AGENTS.md` в корне проекта обычным инструментом `read`, а перед
изменением файлов в подкаталоге — более близкий применимый `AGENTS.md`, если он есть. Отсутствие
файла не останавливает работу. Ядро не ищет `AGENTS.md`, не подмешивает его содержимое в
`systemPrompt` и не заводит для проектных инструкций отдельный loader.

Это progressive disclosure: полный `SKILL.md` не попадает в системный prompt. Когда задача
соответствует описанию, модель читает файл по `location` обычным доступным инструментом `read`, а
соседние scripts, references и assets — отдельными чтениями по необходимости.

`disable-model-invocation: true` оставляет скил в реестре и диагностике платформы, но полностью
исключает его из каталога модели. Отдельного инструмента `activate_skill`, вызова Pi
`AgentHarness.skill()`, slash-команд вроде `/skill:name` и специальных сообщений для активации нет.
Поле `allowed-tools` не меняет runtime-набор инструментов. Прочитанный `SKILL.md` остаётся обычным
результатом `read`: runtime не закрепляет его в контексте, и обычная компакция Pi вправе свернуть
или удалить его наравне с другими результатами чтения.

**Разделение «есть инструмент» и «инструмент активен» встроено.** Полный набор живёт в `tools`,
доступный модели — в `activeToolNames`. Платформа задаёт оба списка независимо от каталога скилов.

**Смена инструментов посреди турна поддержана намеренно.** `setTools` и `setActiveTools` при
`phase !== "idle"` не пишут в сессию сразу, а откладывают запись; `prepareNextTurn` сбрасывает
отложенное и заново собирает снимок турна. Новый активный набор виден модели начиная со следующего
запроса внутри того же турна. Смена активного набора попадает в дерево сессии записью
`active_tools_change`, поэтому восстанавливается при перечитывании сессии.

**Ресурсы Pi для скилов намеренно не используются.** У Pi есть `resources.skills`,
`AgentHarness.skill()` и дженерики ресурсов, но они задают другую механику явного вызова. Граница
платформы принимает только разрешённые метаданные скила и строит собственный model-driven каталог;
наружу типы скилов Pi не выходят.

## Авторизация в LLM-провайдерах

Хранилище кредов внедряется приложением, по умолчанию оно вообще in-memory:

```ts
interface CredentialStore {
  read(providerId: string): Promise<Credential | undefined>;
  list(): Promise<readonly CredentialInfo[]>;
  modify(providerId, fn): Promise<Credential | undefined>; // единственный путь записи
  delete(providerId: string): Promise<void>;
}
```

Запись только через `modify` — это сериализованный read-modify-write, внутри которого Pi делает
обновление OAuth-токена, чтобы параллельные запросы не обновили его дважды.

Логин оркестрирует приложение: `Models.login(providerId, type, interaction)`, `logout`,
`getAuth`, `checkAuth`.

### Диалог входа: четыре вопроса и четыре сообщения

```ts
interface AuthInteraction {
  signal?: AbortSignal; // гасит вход целиком
  prompt(prompt: AuthPrompt): Promise<string>; // select возвращает id варианта
  notify(event: AuthEvent): void;
}
```

| `AuthPrompt.type` | Что это                                             |
| ----------------- | --------------------------------------------------- |
| `text`            | обычная строка                                      |
| `secret`          | ключ; в журнал он не попадает никогда               |
| `select`          | выбор из списка; ответом уезжает `id`, а не подпись |
| `manual_code`     | код, который человек забирает у провайдера руками   |

| `AuthEvent.type` | Что это                                                      |
| ---------------- | ------------------------------------------------------------ |
| `info`           | сообщение, возможно со ссылками                              |
| `auth_url`       | ссылка, по которой человек входит у провайдера               |
| `device_code`    | код устройства, адрес ввода, интервал опроса и срок годности |
| `progress`       | «ждём провайдера»                                            |

Событий именно **четыре**: `info` в прежней редакции этого документа был пропущен.

**У каждого вопроса свой `AuthPrompt.signal`, и он не то же самое, что `AuthInteraction.signal`.**
Первый гасит **вопрос**, второй — вход целиком. Нужен он для гонки: провайдер спрашивает код руками
и одновременно поднимает колбэк-сервер, а выигравший гасит проигравшего. Значит перевод обязан
отклонить ждущего и **оставить попытку жить** — отклони он вход, успешный вход по колбэку падал бы
вместе с отменённым вопросом.

### Окружение — тоже источник креда

Второе внедряемое приложением:

```ts
interface AuthContext {
  env(name: string): Promise<string | undefined>;
  fileExists(path: string): Promise<boolean>; // поддерживает ведущий `~`
}
```

Через него провайдер добирается до `ANTHROPIC_API_KEY`, профилей AWS и ADC-файла gcloud. По
умолчанию Pi берёт настоящие `process.env` и `node:fs`. Мы порт всё равно объявляем своим типом:
без него ambient-кред не проверить тестом, а это самая дешёвая сквозная проверка авторизации.

`AuthResult.source` и `AuthCheck.source` — человекочитаемая подпись источника: `ANTHROPIC_API_KEY`,
`OAuth`, `stored credential`, `~/.aws/credentials`. Она приходит от рантайма и показывается
человеку как есть: своя таблица подписей разошлась бы с провайдером на первом переименовании.

### Статус спрашивается через `checkAuth`, а не через `getAuth`

Разница не косметическая, и она видна снаружи:

| Вызов                   | Что делает при протухшем OAuth-креде           |
| ----------------------- | ---------------------------------------------- |
| `checkAuth(providerId)` | одно чтение хранилища, сети нет                |
| `getAuth(providerId)`   | обновление токена: сеть плюс запись в `modify` |

Замерено (docs/runtime-checks.md, проверка 30). То есть `getAuth` на отрисовке вью провайдеров
ходил бы в сеть и писал бы на диск. Вторая причина та же по духу: `ApiKeyAuth.resolve` у Pi вправе
исполнять команды, а рядом с ним объявлен `ApiKeyAuth.check` — «проверка без побочных эффектов».
**Оговорка, которую надо знать:** `check` не реализован ни у одного из 38 встроенных провайдеров, и
`checkAuth` сегодня везде сводится к `resolve`. Гарантии «статус ничего не исполняет» контракт не
даёт — провайдер с ключом из команды её нарушит.

`getAuth` отклоняется `ModelsError` с кодом `oauth` (обновление токена не удалось; сохранённый кред
цел, лечится повторным входом) или `auth` (не удалось разрешить ключ либо отказало хранилище).
Ненастроенный провайдер — не отказ: `getAuth` и `checkAuth` отдают `undefined`.

### Кто как входит

`ProviderAuth` обязан иметь хотя бы одно из `apiKey` и `oauth`.

- **`ApiKeyAuth.login` необязателен.** Его отсутствие — признак провайдера, который берёт кред
  только из окружения. Среди встроенных таких нет ни одного, зато у `openai-codex` нет `apiKey`
  вовсе: вход только по подписке (docs/runtime-checks.md, проверка 31).
- **`OAuthAuth.loginLabel`** — подпись кнопки входа («Sign in with SuperGrok or X Premium») в
  отличие от `name`, называющего способ («Anthropic (Claude Pro/Max)»).

Вывод, важный для [data-directory.md](data-directory.md): `~/.pi/agent/auth.json` — хранилище их
CLI, а не библиотеки. Конфликта с требованием «всё внутри нашей директории данных» нет.

### Кэш списков моделей — второе внедряемое хранилище

Про него легко не узнать: он не упомянут ни в описании авторизации, ни рядом с провайдерами.

```ts
interface ModelsStore {
  read(providerId: string): Promise<ModelsStoreEntry | undefined>;
  write(providerId: string, entry: ModelsStoreEntry): Promise<void>;
  delete(providerId: string): Promise<void>;
}

interface ModelsStoreEntry {
  models: readonly Model[];
  lastModified?: number; // из Last-Modified каталога провайдера
  checkedAt?: number;
  etag?: string; // хранится дословно, с кавычками, и уезжает обратно как If-None-Match
}
```

По умолчанию он в памяти, то есть за пределы нашей директории данных Pi не пишет и без нас. Своя
реализация нужна не ради правила, а ради экономии: иначе динамический список читается из сети на
каждый старт демона ([data-directory.md](data-directory.md)).

**Обновления одного провайдера у рантайма нет.** `Models.refresh()` обходит все настроенные
динамические провайдеры разом, сам обновляя перед этим OAuth-токены, и возвращает
`{ aborted, errors }` — ошибка провайдера не отклоняет обход. Отсюда форма нашего маршрута
([web-api.md](web-api.md)): один `POST /api/providers/refresh` без сегмента провайдера. Провайдеру
при обходе достаётся `RefreshModelsContext` с уже разрешённым кредом и хранилищем, суженным до него
одного, — каталоги чужих провайдеров провайдеру недоступны.

### Модели и провайдеры

Вью «Модели и провайдеры» из [vision.md](vision.md) опирается на готовое: `getProviders`,
`getModels(provider?)`, `getModel`, `refresh()` для провайдеров с динамическим списком,
`checkAuth(providerId)` — настроен ли провайдер, `getAvailable()` — модели тех провайдеров, у
которых авторизация полна. `builtinModels()` из `@earendil-works/pi-ai/providers/all` отдаёт
**38 провайдеров** — посчитано запуском, а не по каталогу файлов: модулей в `providers/` больше,
чем провайдеров в сборке.

Список моделей читается синхронно и без сети: `provider.getModels()` у статического провайдера
отдаёт зашитый в пакет каталог, у динамического — пустой список до первого `refreshModels()`.

**Кастомные провайдеры поддержаны рантаймом.** Провайдер — это объект с `id`, `name`, `baseUrl`,
методами авторизации и списком моделей; собирается фабрикой `createProvider` и добавляется в
коллекцию через `setProvider`. Своего механизма нам не потребуется.

## Где их контракт трётся о наши требования

Это не претензии к Pi. У них расширения живут в одном процессе с агентом, у нас плагины — в
воркерах и их много. Отсюда три места, которые ядру придётся закрывать самому.

1. **Обработчики вызываются с `await` внутри турна, последовательно.** Это относится и к
   перехватывающим хукам, и к наблюдателям из `subscribe()`: обход идёт по одному, следующий
   ждёт предыдущего. Плагин в воркере означает, что каждый вызов — межпоточный, а зависший плагин
   вешает турн агента. Нужен таймаут и заранее решённый ответ на случай молчания плагина.
2. **Исключение в любом обработчике роняет турн** (`normalizeHookError` →
   `AgentHarnessError("hook")`) — включая наблюдателя, который ничего не возвращает. Против
   требования «падение плагина не задевает остальных»: ядро обязано оборачивать обработчики
   плагинов, а не отдавать их в `on()` и `subscribe()` напрямую. Отдельный случай — `turn_end`:
   там ошибка наблюдателя перевыбрасывается уже после сброса отложенных записей сессии, то есть
   запись не теряется, но турн всё равно падает.
3. **Побеждает последний обработчик.** `emitHook` идёт по подписчикам и возвращает последний
   результат, отличный от `undefined`. «Последний» — это порядок подписки, то есть у нас порядок
   загрузки плагинов: два плагина на `tool_call` дают результат, зависящий от того, кто
   подписался позже. Для их одного расширения это нормально, для наших плагинов правила слияния и
   приоритета придётся определять нам.
4. **Наблюдатель задерживает возврат в `idle`.** Слушатели `agent_end` и `turn_end` входят в
   settlement прогона: harness становится `idle` только после того, как они отработали. Значит
   медленный наблюдатель плагина делает сессию занятой, а `prompt` в это время бросает `busy` —
   наблюдение за ходом сессии влияет на её доступность, хотя ничего не возвращает.
5. **Перехватывающему обработчику не передаётся `AbortSignal`.** Он есть у наблюдателей и в
   полезной нагрузке двух `session_before_*`. Значит своим таймаутом мы прекращаем **ожидание**
   ответа, но не работу плагина: отменить сам обработчик нечем, и он допишет своё в пустоту.

## Каких хуков не хватает нам

То, чего в Pi нет по определению, потому что это наш слой, а не их.

Все утверждены. Как сводятся ответы нескольких подписчиков одного хука и что делает таймаут — в
[hooks.md](hooks.md).

- **Запрос разрешения у пользователя.** У Pi есть `tool_call` с `block`, но нет способа спросить
  человека. Хук в ядре есть; ядро его никуда не проксирует — диалог с пользователем делает
  плагин ([architecture.md](architecture.md)).
- **Сбор инструментов** — `tools_collect`. В Pi инструменты задаются при создании harness. У нас
  набор динамический: его приносят несколько плагинов, и он пересобирается при каждой загрузке,
  выгрузке и перезагрузке любого из них.
- **Жизненный цикл сессии** — `session_created`, `session_closed`. Pi не знает о создании и
  закрытии: `AgentHarness` ему кто-то даёт готовым.
- **`before_session_start` с правом отказа** — единственное место, где можно применить политику
  до того, как сессия начала тратить деньги. Отказ приходит вызвавшему запуск плагину отличимо от
  сбоя.
- **Конец турна со стоимостью** — `turn_finished` с `usage`. Отдельного события нет, а без него
  негде считать лимиты и бюджет. Сам `usage` при этом берётся у рантайма — своего отчёта мы не
  заводим ([hooks.md](hooks.md)).

## Чего этот документ не покрывает

- **Хуки** прочитаны по исходникам и почти не запускались. Исключений два: семантика отписки во
  время турна и `session_before_compact` — **первый хук harness, который платформа действительно
  вешает** (срез 10b). Остальные семь перехватывающих по-прежнему не запускались ни разу.
- **Фаза `retry`** в типе есть, но `agent-harness.js` её никогда не присваивает.
- **Настоящий OAuth-вход** — см. ниже.

Срез 10b добавил к запускаемому компакцию, суммаризацию ветки и метки. Подтвердилось запуском всё,
что записано выше про компакцию через хук, включая `fromHook: true` в записи дерева; метка ставится
и снимается дозаписью, действующее значение — свёртка.

Срез 10a добавил к запускаемому форк, три очереди сообщений, имя сессии, статистику и удаление
([runtime-checks.md](runtime-checks.md)). Подтвердилось: `position` по умолчанию `before` и
отказывает `SessionError("invalid_fork_target")` на всём, кроме сообщения человека; `at` берёт путь
включительно; стиринг, положенный в очередь во время обращения к модели, уезжает в контекст
**следующего круга того же турна**, а не следующего турна; `abort()` чистит очереди стиринга и
догоняющего, но не очередь к следующему турну; `getSessionStats` — обход записей в памяти, никакого
хука конца турна для неё не нужно.

Прогоняется запуском на каждом `make check`: авторизация и каталог провайдеров, а с срезом 9a —
турн целиком (`packages/agent-runtime-pi/src/pi-harness.test.ts`, [runtime-checks.md](runtime-checks.md),
проверка 32). Подтвердилось всё, что этот документ утверждает про турн: последовательность событий
цикла агента, дельты в `message_update`, запись сообщений в дерево сессии на `message_end`, отказ
