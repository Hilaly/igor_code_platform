# Директория данных

Всё состояние платформы лежит в одной директории: перенос установки — это копирование её одной, и
ничего не остаётся в `$HOME`. Путь приходит первым позиционным аргументом запуска, по умолчанию
`~/.sovereign_platform`; в dev-режиме это `apps/daemon/.sovereign-dev` ([runbook.md](runbook.md)). Отсутствующая директория создаётся при
старте вместе с родительскими.

## Что в ней лежит сейчас

| Файл                  | Кто пишет          | Назначение                                                                                       |
| --------------------- | ------------------ | ------------------------------------------------------------------------------------------------ |
| `daemon.lock`         | платформа          | признак работающего демона, он же защита от второго на тех же данных                             |
| `config.json`         | человек, платформа | параметры поведения; интерфейс платформы может менять файл, значения перечитываются живьём       |
| `preferences.json`    | платформа          | предпочтения пользователя; править руками не запрещено                                           |
| `account.json`        | платформа          | учётная запись владельца: хеш пароля и параметры его счёта                                       |
| `login-sessions.json` | платформа          | серверные записи сессий входа                                                                    |
| `projects.json`       | платформа          | записи проектов ([sessions-and-projects.md](sessions-and-projects.md))                           |
| `credentials.json`    | платформа          | креды LLM-провайдеров ([models-and-providers.md](models-and-providers.md))                       |
| `model-catalogs.json` | платформа          | кэш динамических списков моделей ([models-and-providers.md](models-and-providers.md))            |
| `user-providers.json` | платформа          | постоянные определения пользовательских LLM-провайдеров                                          |
| `model-aliases.json`  | платформа          | алиасы моделей со списком кандидатов ([model-routing.md](model-routing.md))                      |
| `sessions/`           | платформа          | записи сессий агента ([sessions-and-projects.md](sessions-and-projects.md))                      |
| `sessions-archived/`  | платформа          | те же записи, убранные с глаз; раскладка внутри та же                                            |
| `plugins/`            | человек            | папка на плагин; сюда кладут внешние плагины ([plugins.md](plugins.md))                          |
| `plugin-storage/`     | платформа          | хранилище ключ-значение, по файлу на плагин ([plugins.md](plugins.md))                           |
| `plugin-files/`       | платформа          | папка на плагин: вложения, кэш, своя база плагина                                                |
| `agents/`             | человек            | пользовательские файловые агенты ([file-resources.md](file-resources.md))                        |
| `skills/`             | человек            | пользовательские файловые скилы ([file-resources.md](file-resources.md))                         |
| `commands/`           | человек            | пользовательские шаблоны промптов ([file-resources.md](file-resources.md))                       |
| `work/`               | человек            | папка эфемерного проекта; в неё пишет пользователь и агент                                       |
| `tmp/`                | платформа          | временные файлы инструментов: полный вывод усечённой команды bash ([bash-tool.md](bash-tool.md)) |
| `runtime/`            | платформа          | то, что продакшн-артефакт кладёт на диск, чтобы работать ([toolchain.md](toolchain.md))          |
| `builtin/`            | платформа          | встроенные плагины, распакованные из артефакта ([toolchain.md](toolchain.md))                    |

Оба файла настроек необязательны: отсутствующий равен пустому, значения по умолчанию живут в коде.
Папки `plugins/` и `commands/` создаются при старте пустыми: иначе положить в них плагин или шаблон
некуда. Папка `work/` — тоже, и
по той же причине: эфемерный проект есть всегда, а «есть всегда» без папки на диске означало бы, что
первая же сессия в нём падает.

`agents/` и `skills/` — нативные пользовательские корни. Внутри них одна директория на определение:
`agents/<name>/AGENT.md` и `skills/<name>/SKILL.md`. Их формат и правила обхода описаны в
[file-resources.md](file-resources.md). Отдельный межклиентский корень `~/.agents/skills` не входит
в директорию данных и не переезжает вместе с ней. Нативный `skills/` имеет precedence 200 и
перекрывает межклиентский корень с precedence 100; `agents/` имеет precedence 100. Оба корня
необязательны и наблюдаются живьём: демон замечает создание отсутствующей папки, изменения и
удаление определений и соседних ресурсов. Символические ссылки не используются как корни и не
переносят наблюдение на внешние цели.

## `runtime/`

Каталог существует только у продакшн-артефакта; при запуске из исходников его не заводится вовсе
([toolchain.md](toolchain.md)). Внутри — каталог на версию платформы:

```
runtime/0.1.0/plugin-worker.js     собранный бутстрап воркера плагина
runtime/0.1.0/package.json         зависимости, которые в артефакт не вшиваются
runtime/0.1.0/node_modules/        то, что по нему поставил npm — сегодня только esbuild
```

**Каталог принадлежит платформе.** Правки в нём затираются: оба файла переписываются на каждый старт,
потому что принадлежат артефакту, а он мог смениться, не сменив версию платформы. Каталоги прошлых
версий удаляются — иначе директория данных росла бы на каждое обновление на размер нативного бинаря.

Готовится он **после захвата лока**, поэтому одновременно этого не делают два процесса, и **до**
первого обхода плагинов: воркер без бутстрапа не поднимется. Установка зависимостей ходит в сеть —
это единственное место, где артефакт это делает, и работа без сети не является обязательным
требованием (решение владельца продукта, [toolchain.md](toolchain.md)). Провал установки директорию
данных не портит и демон не роняет.

## `builtin/`

Каталог тоже существует только у продакшн-артефакта. Внутри — каталог на версию платформы, и внутри
него обычный корень плагинов, ничем не отличающийся от `plugins/` репозитория:

```
builtin/0.1.0/.sovereign-builtin                        отпечаток распакованной нагрузки
builtin/0.1.0/starter/package.json                      манифест плагина, как он лежит в репозитории
builtin/0.1.0/starter/node_modules/@sovereign/sdk/      SDK, собранный сборкой артефакта
builtin/0.1.0/subagents/src/browser.tsx                 исходники, из которых демон соберёт браузер
```

**Каталог версии появляется целиком или не появляется.** Содержимое пишется в соседний временный
каталог и встаёт на место переименованием: оборванная распаковка не имеет права оставить каталог,
который следующий старт сочтёт готовым. Прошлые версии и брошенные временные каталоги удаляются.

**Распаковано или нет — решает отпечаток нагрузки, а не версия платформы.** Между двумя сборками
артефакта версия не меняется, и по одной версии вторая сборка молча работала бы с содержимым первой.
Отпечаток совпал — распаковки нет; разошёлся — каталог версии заменяется целиком, вместе с любыми
правками, сделанными в нём руками ([runtime-checks.md](runtime-checks.md), проверка 40).

**Каталог принадлежит платформе.** Способ изменить встроенный плагин — скопировать его в `plugins/`
директории данных, где он перекроет встроенный по правилу источников ([plugins.md](plugins.md)).

Распаковка идёт **после захвата лока** и **до** первого обхода плагинов, там же, где готовится
`runtime/`. В сеть она не ходит: зависимости встроенных плагинов приезжают внутри нагрузки, и
установка считает их привезёнными.

`plugin-storage/` и `plugin-files/` создаются по надобности, а не при старте: класть в них человеку
нечего — пишет туда платформа. Имя внутри обоих — ключ плагина `<источник>:<id>` с `%3A` вместо
двоеточия: двоеточие в имени файла незаконно на Windows, а идентификаторы плагина и проекта состоят
из `[a-z0-9-]`, поэтому кодировать больше нечего и кодирование обратимо — то же `%3A` уже стоит в
маршруте `PUT /api/plugins/:key/preferences`.

```
plugin-storage/builtin%3Atasks.json   { "values": { "last-seen": { "id": "42" } } }
plugin-files/builtin%3Atasks/         что положил плагин
```

**Ключ хранилища — источник плюс идентификатор**, а не только идентификатор: перекрытие — это другой
плагин, и черновик из папки проекта не имеет права работать с боевыми данными встроенного
([plugins.md](plugins.md)). **Негодный файл хранилища не перезаписывается,** как `projects.json` и
`credentials.json`: плагин получает отказ с причиной, в журнал уходит `error`, соседние плагины
работают. Безвозвратное удаление проекта уносит файлы и папки его плагинов — `project%3A<id>%3A*`.

**Каталога собранных браузерных ассетов здесь нет и не будет** — решение владельца продукта
2026-08-08. Демон собирает браузерную часть плагина в память и оттуда же её отдаёт
([ui-extension-model.md](ui-extension-model.md)): сборка занимает единицы миллисекунд, а файл на
диске был бы копией того, что и так пересобирается при каждом старте плагина, — с собственным
жизненным циклом, инвалидацией и мусором после удалённого плагина.

**Всё это — файлы и папки. Базы данных в директории данных нет** («Почему так» ниже). Конкретные
имена файлов фиксируются вместе с реализацией своего раздела, а не заранее.

## `sessions/`

Записи сессий агента, по файлу на сессию, формат — JSONL: одна json-запись на строку, файл только
дописывается и никогда не переписывается. Раскладку и формат задаёт агентный рантайм
([agent-runtime-contract.md](agent-runtime-contract.md)): своей реализации хранилища у нас нет,
готовая направлена в эту папку.

```
sessions/
  --Users-me-code-demo--/            папка на рабочую директорию, путь в имени
    2026-07-29T09-11-04-512Z_0199….jsonl
```

Первая строка файла — заголовок с идентификатором, моментом создания и рабочей директорией; в его
поле `metadata` платформа кладёт своё: идентификатор проекта, идентификатор агента и `folderKey`.
Дальше идут записи дерева: сообщения, смена модели, смена уровня ризонинга, смена набора
инструментов.

**Модель и уровень ризонинга в заголовке не хранятся.** Они меняются на живой сессии, а заголовок
дописанного файла не переписывается — текущее значение выводится из последней записи о смене. Это и
есть причина, по которой append-only формат ничего не стоит: у него нет изменяемых полей.

**Битый файл сессии не отменяет остальные,** в отличие от `projects.json`: сессия выпадает из списка
с названной причиной, прочие работают. Оборванная последняя строка — штатное свойство JSONL и
главная причина, по которой формат выбран: падение посреди дозаписи теряет одну запись, а не файл.

## `sessions-archived/`

Тот же корень с той же раскладкой внутри, только для сессий, убранных с глаз. **Архивация — это
перемещение файла между двумя корнями**, а не запись где бы то ни было: где лежит файл, то и есть
состояние ([sessions-and-projects.md](sessions-and-projects.md), «Почему так»).

Корень именно сосед `sessions/`, а не папка внутри неё: рантайм берёт папки первого уровня корня за
папки рабочих директорий, и вложенный `archived/` притворился бы одной из них.

Перемещается файл, а не папка рабочей директории: опустевшая папка остаётся в прежнем корне. Сессий
в ней рантайм больше не видит, и вреда от неё нет — удалять её означало бы гоняться с созданием
новой сессии в той же папке.

Восстановить архивную сессию руками можно тем же перемещением обратно; демон при этом должен быть
остановлен — файл сессии он держит открытым.

## `daemon.lock`

Создаётся при старте атомарно, содержит `pid`, момент захвата, имя хоста и порт. Смысл файла — не
дать двум демонам открыть одни и те же данные: делимый ресурс здесь директория, а не порт.

Что происходит при повторном старте на занятой директории:

| Состояние лока                                 | Поведение                                          |
| ---------------------------------------------- | -------------------------------------------------- |
| процесс с этим `pid` жив                       | отказ старта с указанием `pid` и порта работающего |
| `hostname` чужой (директория на сетевом диске) | отказ: проверить процесс на другой машине нечем    |
| процесс мёртв (`kill -9`, падение машины)      | лок считается протухшим и перезахватывается        |
| файл не читается или неполон                   | отказ; лечится удалением файла руками              |

Штатное завершение (`Ctrl+C`, `SIGTERM`) удаляет файл, но только если в нём наш `pid`: чужой лок
платформа не снимает.

Возможен ложный отказ старта — система переиспользовала `pid` мёртвого демона, и живым оказался чужой
процесс. Лечение то же: удалить `daemon.lock` руками, убедившись, что демон действительно не запущен.

## Настройки

Файлов два, и делит их автор записи: `config.json` — параметры развёртывания и поведения,
`preferences.json` — предпочтения пользователя. Порта и пути к директории данных в них нет: это
параметры развёртывания, они приходят аргументами запуска.

`config.json` правит человек редактором, но платформа тоже пишет в него — по явному действию
пользователя из вью настроек, маршрутом `PUT /api/config` ([web-api.md](web-api.md)). Запись
сохраняет неизвестные ключи и порядок: файл, написанный более новой версией платформы или руками, не
обедняется записью из интерфейса. Параметры, требующие перезапуска, записываются, но не применяются —
диагностика «применится после перезапуска» работает одинаково для правки руками и правки из
интерфейса.

Тело `PUT /api/config` — непустое подмножество известных полей; прежний полный документ остаётся
допустимым. Платформа читает последний документ на диске и накладывает на него только названные поля,
поэтому пропущенная настройка не откатывается к умолчанию и не затирается устаревшей формой.
Незнакомые поля тела и документа на диске сохраняются для совместимости с новой версией, но тело,
которое называет только незнакомые поля, отклоняется. Нечитаемый или отвергнутый файл на диске запись
не чинит, а отказывается делать — там чужая правка, и стирать её нельзя.

**Отказ файловой системы называется вслух.** Директория данных без права записи, кончившееся место,
чужая блокировка — всё это ловится на самой записи и возвращается причиной, а не исключением: иначе
человек, у которого не сохраняется форма, видел бы `internal error`, тогда как чинить это ему.
Правило общее для всех трёх пишущих маршрутов настроек ([web-api.md](web-api.md)), потому что и файл
у них общий механизм записи.

Правка руками и partial-запись из интерфейса идут одновременно, и побеждает последний `rename`.
Каждый контрол интерфейса пишет только свой ключ: выбор уровня журнала сразу, число — после `Enter`
или blur. Пока числовой текст не завершён, внешний снимок не затирает его; после отказа интерфейс
показывает причину демона и перечитывает авторитетный снимок. Общей формы, врезки о коллизии и действия
«Взять из файла» больше нет. Как именно — в [ui-kit.md](ui-kit.md).

Примеры:

```json

```

([architecture.md](architecture.md)). Значение по умолчанию — `4`, названо владельцем продукта.
Предел определяет не машина, а лимит частоты запросов у провайдера, поэтому под свой тариф его
правят файлом.

`maxConcurrentAgentTurns` — сколько из этих слотов вправе занять агентские сессии, то есть субагенты
([subagents.md](subagents.md)). Не второй предел рядом с первым, а **доля внутри него**: человеку
всегда остаётся `maxConcurrentTurns` минус это число, и разлёт субагентов не отодвигает его
сообщение в конец очереди. Умолчание `3` при общих `4` оставляет человеку один слот при любом числе
субагентов. Доля выше общего предела не отказ — очередь берёт меньшее из двух, иначе правка двух
ключей в одном файле зависела бы от их порядка.

`compactionThreshold` — доля контекстного окна модели, после которой компакция запускается сама
([sessions-and-projects.md](sessions-and-projects.md)). `0` выключает автопорог, и это умолчание,
названное владельцем продукта: компакция стоит денег и необратимо меняет разговор. **Доля, а не
число токенов** — окна моделей различаются на порядок, и одно и то же абсолютное число означало бы
на разных моделях совершенно разное. Верхняя граница строгая: порог, равный целому окну, не сработал
бы никогда, потому что запрос к модели отклонится раньше.

`compactionReserveTokens` и `compactionKeepRecentTokens` — сколько токенов окна оставить под ответ
модели и какой хвост разговора не трогать. Умолчания совпадают с зашитыми в Pi: своя компакция
заведена ради управляемости, а не ради других чисел
([agent-runtime-contract.md](agent-runtime-contract.md)).

`hookTimeoutMilliseconds` — сколько платформа ждёт обработчик хука в воркере плагина
([hooks.md](hooks.md)). Одно значение на все хуки; исход истёкшего ожидания зависит от вида хука и от
критичности, объявленной подпиской. Умолчание `5000` — предположение, а не измерение.

`pluginToolTimeoutMilliseconds` — сколько ждёт вызов инструмента, объявленного плагином. Отдельная
величина, потому что **инструмент — не хук**: хук ждут внутри турна и он обязан быть быстрым, а
инструмент модель зовёт как работу. По истечении модель получает результат-ошибку с названным
автором, и турн продолжается.

`pluginRouteTimeoutMilliseconds`, `pluginRouteBodyLimitBytes` и `publicRouteRequestsPerMinute` —
маршруты плагина ([web-api.md](web-api.md)). Третье значение относится только к публичным маршрутам:
это единственная поверхность платформы, открытая наружу, и без лимита частоты один такой маршрут
превращает демон в мишень. Ждать здесь приходится живому HTTP-соединению, поэтому величина своя, а не
инструментальные две минуты.

`maxImageBytes`, `maxImagesPerMessage`, `maxMessageImageBytes` и `maxSessionImageBytes` — пределы на
изображения в сообщениях агенту ([sessions-and-projects.md](sessions-and-projects.md)). Считаются в
**декодированных** байтах, а не в длине base64: тогда одно и то же число значит одно и то же для
файла с диска, вставки из буфера и восстановленной сессии.

Пределы нужны потому, что изображение лежит прямо в файле сессии: без них один разговор со
скриншотами вырастает до размера, который перестаёт читаться. Последний считается по всему файлу,
включая брошенные ветки, — местом заплачено и за них.

Три из них связаны между собой: `maxMessageImageBytes` не меньше `maxImageBytes`, а
`maxSessionImageBytes` не меньше `maxMessageImageBytes`. Файл или правка, нарушающие это, отвергаются
целиком: предел одной картинки выше предела сообщения означал бы, что первая же принятая картинка не
влезает в сообщение, куда её кладут. Равенство законно.

```json
{
  "plugins": {
    "data:hello": { "enabled": true, "disabledContributions": ["hello.panel"] }
  },
  "appearance": { "colorScheme": "imperium", "variant": "system", "scale": "larger" },
  "locale": "ru"
}
```

`appearance` и `locale` — раздел, которым владеет оболочка: она читает и пишет его целиком одним
маршрутом ([web-api.md](web-api.md)), поэтому оба поля обязательны в теле записи. Значение вне
перечисленных **отвергает разбор целиком**, а не подставляет значение по умолчанию: правка руками
тогда не применяется вовсе, из интерфейса — получает `400`. Отсутствующее поле — не ошибка, у него
есть значение по умолчанию. `appearance.scale` двигает базовый кегль, шаг отступов и высоту контролов
одной осью ([ui-kit.md](ui-kit.md)).

Отсутствие записи о плагине — не «выключен», а «решения не было»: встроенный работает сразу, любой
другой ждёт включения. Подробности — в [plugins.md](plugins.md).

Параметров, требующих перезапуска, сейчас нет. Появится такой — он обязан сказать об этом
диагностикой, а не тихо расходиться с файлом.

### Перечитывание на живом демоне

Оба файла применяются без перезапуска: правка подхватывается за десятки миллисекунд. Наблюдается вся
директория, а не сами файлы, поэтому посторонний файл рядом (`.DS_Store`, временный файл редактора,
лок) события не вызывает — он отфильтровывается по имени. Подробности замеров — в
[runtime-checks.md](runtime-checks.md), проверки 12 и 14.

Перечитывание идемпотентно: если содержимое совпало с текущим, не происходит ничего.

### Что бывает не так

| Что в файле            | Что делает платформа                                                               |
| ---------------------- | ---------------------------------------------------------------------------------- |
| файла нет              | значения по умолчанию                                                              |
| битый JSON             | файл не применяется и не затирается, действует прежний снимок, в лог — диагностика |
| неверное значение поля | то же: применяется файл целиком или не применяется вовсе                           |
| неизвестный ключ       | диагностика, остальное применяется                                                 |

Платформа никогда не перезаписывает `config.json` своим представлением о нём: иначе опечатка в
редакторе уничтожала бы остальные настройки.

## Учётная запись и сессии входа

Два файла, и оба пишет только платформа: `account.json` и `login-sessions.json`. Права — `0600`,
запись атомарна (временный файл и `rename`), как у `preferences.json`: под ней лежат хеш пароля и
хеши токенов. Как устроен сам вход — в [authentication.md](authentication.md).

`account.json` — одна запись, потому что пользователь один:

| Поле                         | Что в нём                        |
| ---------------------------- | -------------------------------- |
| `passwordHash`               | scrypt-хеш пароля, base64        |
| `salt`                       | соль, base64, 16 байт            |
| `parameters.cost`            | `32768`                          |
| `parameters.blockSize`       | `8`                              |
| `parameters.parallelization` | `1`                              |
| `parameters.keyLengthBytes`  | `64`                             |
| `createdAt`                  | момент создания записи, ISO-8601 |

Параметры лежат рядом с хешем, а не в коде: поднять их со временем, не ломая существующий вход, можно
только зная, каким набором посчитан этот хеш. Пока файла нет, API отвечает «требуется регистрация» и
принимает создание записи; после этого — только вход.

**Негодный `account.json` не перезаписывается.** Под ним единственный пароль владельца, и затереть
его значило бы запереть человека снаружи, поэтому платформа отвечает `409` и ждёт человека
([web-api.md](web-api.md)).

Негодным файл считается не только когда это не json. Проверяется и содержимое: `cost` обязан быть
степенью двойки не меньше четырёх, набор целиком — требовать не больше гигабайта на счёт хеша,
длина ключа — не больше килобайта, а `passwordHash` — декодироваться ровно в `keyLengthBytes` байт.
Требования не придирка: `scrypt`
бросает на непригодном наборе, а base64 в Node молча проглатывает мусор, поэтому без этих проверок
поправленный руками файл давал бы на входе `500` вместо честного «файл негоден».

`login-sessions.json` — список записей:

```json
{
  "sessions": [
    {
      "id": "8Qk2…",
      "tokenHash": "TmV2ZXI…",
      "createdAt": "2026-07-28T09:11:04.512Z",
      "expiresAt": "2026-08-27T09:11:04.512Z"
    }
  ]
}
```

На диске лежит SHA-256 токена в base64, самого токена нет: копия директории данных не даёт живых
сессий. Срок жизни записи — 30 суток, и он обязан быть явным: сессии переживают перезапуск демона,
потому что лежат файлом.

**Негодный `login-sessions.json`, в отличие от настроек, не отказ.** Он читается как пустой набор с
диагностикой в журнал: худшее, что это стоит, — новый вход, и требовать за это ручного вмешательства
незачем.

Имя `login-sessions.json`, а не `sessions.json`, выбрано намеренно: сессия агента
([sessions-and-projects.md](sessions-and-projects.md)) — другая сущность, и в одной директории данных
им нельзя выглядеть одинаково.

Наблюдатель настроек этих файлов не касается: он фильтрует по имени и знает только `config.json` и
`preferences.json`. Править их руками незачем — единственный штатный случай это сброс забытого пароля
(«Ручное восстановление» ниже).

## Проекты

`projects.json` — список записей ([sessions-and-projects.md](sessions-and-projects.md)):

```json
{
  "projects": [
    {
      "id": "b7Kq3xv9pQdT",
      "name": "Платформа",
      "folder": "/Users/owner/code/platform",
      "folderKey": "/users/owner/code/platform",
      "archived": false,
      "createdAt": "2026-07-29T09:11:04.512Z"
    }
  ]
}
```

`folder` — путь, каким его показывают человеку; `folderKey` — тот же путь после нормализации, по
нему держится правило «один путь — один проект». Ключ лежит в файле, а не считается при чтении:
пересчёт менял бы идентичность живой записи под ней самой.

Ни доступности папки, ни числа сессий в файле нет. Доступность — свойство мира, а не записи: её
считает наблюдатель по таймеру. Число сессий считается на лету по снимку хранилища и в файл
проектов не записывается: иначе число стало бы устаревшим после создания, удаления или архивации
сессии.

**Эфемерного проекта в файле нет вовсе** — что слово «эфемерный» и значит. Его запись синтезируется
на лету поверх папки `work/`, идентификатор у неё постоянный (`work`), и переименовать, архивировать
или удалить её нельзя.

**Негодный `projects.json` — отказ, как настройки, а не пустой набор, как сессии входа.** Пустой
набор означал бы, что платформа молча забыла список проектов, а следом бодро создала «новые» проекты
на тех же папках — проверять уникальность стало бы не с чем. Файл не перезаписывается, все маршруты
проектов отвечают `409` ([web-api.md](web-api.md)), в журнал идёт `error`. Одна негодная запись
роняет файл целиком: выборочное чтение означало бы, что платформа сама решила, какой из проектов
человека забыть. Так же обрабатываются две записи на одну папку и запись, занявшая
зарезервированный идентификатор `work`.

## Креды провайдеров

`credentials.json` — **набор именованных ключей на провайдера**
([models-and-providers.md](models-and-providers.md)):

```json
{
  "credentials": {
    "anthropic": {
      "keys": [
        {
          "id": "key-1",
          "label": "личный",
          "credential": { "type": "api_key", "key": "sk-ant-…" }
        },
        { "id": "key-2", "label": "рабочий", "credential": { "type": "oauth", "access": "…" } }
      ],
      "selected": "key-1"
    }
  }
}
```

**Выбранный ключ — тот, которым провайдер представлен целиком:** проверка авторизации, обновление
списка моделей и обновление OAuth-токена идут через него. Сессия агента выбирает ключ из набора сама
([models-and-providers.md](models-and-providers.md)), и в файле её выбор не хранится.

**Форму значения платформа не знает и знать не хочет.** Её знает только
`packages/agent-runtime-pi`: для ядра кред — непрозрачный блоб, и это записано типом (`unknown`), а
не обещанием. Своя у платформы только обёртка ключа — `id` и `label`. Отсюда и проверка при чтении:
платформа сверяет, что `credential` вообще объект, и на этом останавливается.

**Файл прежней формы — одиночный кред вместо набора — читается как единственный ключ `key-1` с
пустой подписью.** Прежняя форма узнаётся по полю `type`, которое есть у любого креда рантайма и
которого нет у набора; на чтении файл не переписывается, новую форму сохраняет первая же запись.

Идентификатор ключа — `key-1`, `key-2`, … по первому свободному номеру, а не uuid: файл правят
руками, и в нём должно быть видно, о каком ключе речь. Освободившийся номер достаётся следующему
ключу — идентификатор адресует живой ключ, а не хранит историю удалённых.

Файл пишется в режиме `0600`, как и остальные, — там лежит настоящий ключ.

**Единственный путь записи — сериализованный read-modify-write**, взаимное исключение по
идентификатору провайдера. Внутри него агентный рантайм обновляет OAuth-токен сетевым запросом:
второй писатель обновил бы токен дважды, и симптом выглядел бы как случайный отвал авторизации.
Замок по провайдеру, а не общий, потому что зависший сетевой запрос одного провайдера иначе
блокировал бы запись для всех остальных. **Замок остался по провайдеру, а не по ключу:** набор
меняется целиком — удаление ключа сдвигает выбранный, — и замок по ключу пришлось бы брать вместе с
замком по набору. Цена: два ключа одного провайдера обновляют токен по очереди, а не разом, и
стоит это одного сетевого запроса раз в несколько часов.

**Цель записи на время входа переключается** на добавляемый ключ (`withKeyTarget`): иначе вход
вторым ключом переписал бы первый. Вход в одного провайдера идёт по одному, поэтому целей не бывает
двух сразу. Обновление OAuth-токена, попавшее ровно в окно входа, промахнётся мимо выбранного ключа
— но не испортит его: оно записывает токен только поверх своего же креда, а его в цели входа нет.
Пропущенное обновление повторится на следующем запросе.

**Удаление ключа не оставляет набор без выбранного:** ушёл выбранный — выбирается первый оставшийся,
ушёл последний — запись провайдера исчезает целиком.

**Негодный `credentials.json` — отказ, и файл не перезаписывается**, как `projects.json`, но по
более резкой причине: под ним лежат OAuth-токены, а взять их заново неоткуда, кроме как сходив к
провайдеру. Пишущие маршруты отвечают `409`, в журнал идёт `error`. Отличие от проектов: **список
провайдеров всё равно отдаётся** — каталог от файла не зависит, статус авторизации у всех
показывается как «сказать нечем», и пустое вью здесь чинить файл не помогает
([web-api.md](web-api.md)).

Негодным считается и набор, испорченный правкой руками: два ключа с одним идентификатором, пустой
список ключей, выбранный ключ, которого в наборе нет. Каждый случай отказывает файл целиком и
называет виновника — выборочное чтение означало бы, что платформа сама решила, какой из ключей
человека забыть.

**Значение креда в журнал не попадает никогда.** В записи есть идентификатор провайдера и факт
записи или удаления — этого хватает, чтобы понять, что произошло, и по этому же признаку журнал
проверяется тестом.

## Алиасы моделей

`model-aliases.json` — имя со списком совместимых моделей ([model-routing.md](model-routing.md)):

```json
{
  "aliases": [
    {
      "id": "opus-5",
      "name": "Opus 5",
      "candidates": [
        { "providerId": "anthropic", "modelId": "claude-opus-4-5" },
        { "providerId": "openai", "modelId": "gpt-5.6-sol" }
      ]
    }
  ]
}
```

Порядок кандидатов — порядок обхода, и он значим. Политика негодного файла та же, что у
пользовательских провайдеров: отказ, файл не переписывается, пишущие маршруты отвечают `409`. Список
собрал человек, и молчаливо забыть его платформа права не имеет.

## Кэш списков моделей

`model-catalogs.json` — по записи на провайдера, чей список моделей приходит из сети:

```json
{
  "catalogs": {
    "radius": { "models": [], "etag": "\"a1b2\"", "checkedAt": 1785000000000 }
  }
}
```

Форма записи, как и у креда, платформе непрозрачна: её знает `packages/agent-runtime-pi`. Смысл
файла один — не ходить в сеть за списком на каждый старт демона, а `make dev` перезапускает демон на
каждую правку файла.

**Политика негодного файла здесь обратная кредам: испорченный читается как пустой и свободно
перезаписывается.** Это кэш. Худшая цена ошибки — один лишний сетевой запрос, а отказ заставил бы
человека чинить руками файл, который платформа умеет собрать сама. В журнал идёт `warn`, а не
`error`: платформа работает в полную силу, теряется только экономия.

Встроенный провайдер с динамическим списком сегодня ровно один
([runtime-checks.md](runtime-checks.md), проверка 31) — по-настоящему файл оправдывают кастомные
провайдеры плагинов.

## Пользовательские провайдеры

`user-providers.json` хранит `{ "providers": [...] }` с определениями, созданными в UI. Ключей API
в нём нет: они лежат отдельно в `credentials.json`. Файл пишется атомарно с правами `0600`;
негодный JSON или одна негодная запись блокируют изменения и не перезаписываются пустым списком.
Удаление провайдера согласованно очищает его записи из `credentials.json` и
`model-catalogs.json`.

## Ручное восстановление

Директория текстовая намеренно: это способ починить платформу, когда интерфейс не открывается.

- **Демон не стартует, жалуясь на лок.** Убедиться, что демон не запущен, и удалить `daemon.lock`.
- **Интерфейс не поднимается из-за настройки.** Править `preferences.json` руками — это
  предусмотренный путь, а не обходной.
- **Не видно, что не так с файлом.** Диагностика идёт в журнал демона: `logLevel` в `config.json`
  ставится в `debug`, и это применяется без перезапуска.
- **Проекты не открываются, платформа жалуется на `projects.json`.** Файл негоден, и платформа его
  не чинит: она отказывается писать поверх, чтобы не стереть список проектов. Причина — в журнале
  демона; чинится правкой файла руками при остановленном демоне. Крайний случай — удалить файл: это
  теряет записи проектов, но не папки — папку пользователя платформа не удаляет никогда.
- **Провайдер не логинится, платформа жалуется на `credentials.json`.** Файл негоден, и поверх него
  платформа не пишет: под ним OAuth-токены. Список провайдеров при этом виден, а статус у всех —
  «сказать нечем». Причина — в журнале демона; чинится правкой файла руками при остановленном
  демоне. Крайний случай — удалить файл: это разлогинивает во всех провайдерах сразу, и войти в
  каждого придётся заново.
- **Забыт пароль.** Удалить `account.json` руками — это удаляет учётную запись, и платформа снова
  просит её создать. Войти заново придётся регистрацией: другого пароля у платформы нет
  ([authentication.md](authentication.md)). Сессии удалять не нужно: сессия подтверждает учётную
  запись, поэтому без `account.json` не действует ни одна выданная cookie, а регистрация нового пароля
  вычищает `login-sessions.json`. Если сессии надо снять и не создавая пароль заново, демон
  останавливается и файл удаляется вместе с `account.json`: набор сессий живёт в памяти процесса, и
  правка файла на ходу ничего не изменит.

Правка руками при работающем интерфейсе может потеряться: побеждает тот, кто записал последним, а
переключатель в браузере пишет тот же файл.

## Почему так

### Одна директория и лок на неё

Демон запускается из терминала и, по замыслу, больше не глушится. Второй демон на той же директории
данных недопустим: два процесса писали бы в одни и те же файлы состояния. Порт для защиты не
годится — он не мешает поднять второй демон на другом порту поверх тех же данных. Делимый ресурс
здесь директория, её и надо защищать.

Захват — атомарное эксклюзивное создание файла (`fs.open(path, "wx")`, за ним `O_CREAT|O_EXCL`). Это
единственный примитив блокировки, который в Node работает одинаково на всех целевых платформах.
Оба примитива проверены запуском ([runtime-checks.md](runtime-checks.md), проверка 8).

**`flock` или блокировка дескриптора.** Правильный способ на POSIX: лок снимается ядром вместе с
процессом, протухших локов не бывает вовсе. Но в Node нет встроенного `flock`, а на Windows его нет
как понятия — пришлось бы тянуть нативную зависимость ради одной функции.

**Занять порт и считать это локом.** Не защищает директорию: два демона на разных портах спокойно
откроют одни и те же данные.

**Лок в общесистемном месте (`/var/run`, `%TEMP%`).** Ломает главное правило — всё состояние внутри
директории данных. К тому же локов должно быть столько, сколько директорий данных, а не один на
машину.

Из правила «ничего за пределами директории данных» следует критерий выбора библиотек: любая новая
зависимость, которая хранит состояние, проверяется на возможность указать ей путь. Не умеет — не
берём или оборачиваем. Именно поэтому у Pi мы внедряем свои реализации хранилищ, а его CLI с
`~/.pi/agent/` не используем ([agent-runtime-contract.md](agent-runtime-contract.md)).

Проверка на протухание удаляет чужой файл, поэтому делает ровно одну повторную попытку: иначе два
одновременно стартующих демона по очереди сносили бы лок друг друга.

### Всё состояние файлами, базы данных нет

**Правило одно и без исключений: любое состояние платформы лежит файлом или папкой в директории
данных.** То, что правит человек, — JSON. То, что пишет платформа и что растёт — дерево записей
сессии агента, — JSONL по файлу на сессию, дописыванием в конец. Атомарность записи обеспечивается
записью во временный файл и переименованием — одной реализацией на всех, кто пишет: `preferences.json`,
`account.json` и `login-sessions.json`.

Причина в том, ради чего эта директория текстовая: **способ починить платформу здесь — открыть файл
редактором** («Ручное восстановление» выше). База выделила бы кусок состояния, к которому этот способ
неприменим, и сделала бы это ровно там, где чинить приходится чаще всего.

Конкуренции за файл сессии не возникает по построению: одновременный турн в одной сессии рантайм
отклоняет с `busy` ([agent-runtime-contract.md](agent-runtime-contract.md)), поэтому писатель у файла
всегда один.

**SQLite (`node:sqlite`) для сессий и хранилищ плагинов.** Так и было записано в этом документе —
и записано ошибочно: решение принял агент, а стояло оно со статусом «Утверждено»
([master-spec.md](master-spec.md)), которого владелец продукта не давал. Отвергнуто владельцем
продукта. Замеры при этом верны и остаются в силе: 10 000 записей в транзакции за 20 мс, выборка по
индексу за 1.6 мс ([runtime-checks.md](runtime-checks.md), проверка 10) — производительность никогда
не была здесь вопросом. Цена варианта: бэкап перестаёт быть копированием папки и требует `backup()`,
запись сессии становится нечитаемой без инструмента, а миграции и `user_version` появляются с первого
дня. Взамен он давал выборку отдельных записей внутри огромной сессии и поиск по содержимому — ни то,
ни другое на одном пользователе не является ограничением.

**`better-sqlite3` вместо встроенного модуля.** Быстрее и API богаче, но это нативная сборка на
машине пользователя — против ставки на возможности рантайма и лишний барьер для установки. Отпало
вместе с самой базой.

**Внешняя СУБД.** Локальный однопользовательский демон, который «запускается и больше не глушится»,
не может требовать поднятого рядом сервера.

Цена принятого варианта названа честно:

- **«Список сессий» — это обход файлов.** На сотнях сессий дёшево, на тысячах станет заметно. Это
  первое место, куда надо смотреть, если чтение начнёт тормозить.
- **Транзакции на несколько сущностей нет.** Безвозвратное удаление проекта вместе с его сессиями —
  это несколько файлов, и падение посередине оставляет осиротевшие записи. Уборка таких остатков —
  обязанность реализации, а не «этого не случится».
- **Сводная статистика по токенам и стоимости считается обходом всех сессий.**

Страховка на случай, если по сессиям решение окажется неверным: `SessionStorage` у Pi внедряется
приложением ([agent-runtime-contract.md](agent-runtime-contract.md)), то есть это наш интерфейс.
Подмена его реализации на базу не заденет ничего, что лежит выше.

### Два файла настроек, а не один

Смешивание означало бы, что каждое нажатие переключателя в интерфейсе перезаписывает файл, в котором
лежат параметры развёртывания, а правка руками в этот момент теряется. Плюс диффы становятся
нечитаемыми: параметры тонут в списке выключенных вкладов.

**Один файл с разными секциями.** Меньше файлов и одно место, куда смотреть. Отвергнуто по причине
выше.

**Предпочтения в базе.** Обсуждалось, пока база предполагалась. Отпало вместе с ней, но довод стоит
удержать: предпочтения обязаны открываться редактором — выключить рукой плагин, из-за которого
интерфейс не поднимается, ровно тот сценарий, для которого настройки лежат текстом.

**Хот-релоад только `config.json`, предпочтения — исключительно через API.** Отвергнуто: файл,
который платформа пишет, но чужую правку игнорирует, — ловушка. Пользователь правит, ничего не
происходит, а следующая запись платформы затирает правку без следа.

### Перечитывание: наблюдаем директорию, а не файлы

**`fs.watch` на самих файлах.** Естественный первый вариант. Отвергнуто по измерению: наблюдатель на
файле умирает после первой же атомарной замены — он держит старый inode, а `rename` подставляет новый
([runtime-checks.md](runtime-checks.md), проверка 12). Ошибка была бы незаметной: первый релоад
проходит.

**Опрос по `stat` (`watchFile`).** Замену переживает, но опрашивает диск постоянно и добавляет
задержку. Оставлен как запасной путь для сетевых файловых систем, где события не приходят.

**Своё расширение поверх наблюдателя, чтобы отличать свою запись от чужой.** Отвергнуто: различать
нечем, а идемпотентное перечитывание делает вопрос ненужным.

Следствия: директория наблюдается целиком, поэтому фильтр по имени — обязательная часть реализации, а
не оптимизация; валидация нужна на каждом перечитывании и с внятным откатом к прежнему снимку;
неизвестный ключ — диагностика, а не ошибка, иначе понижение версии платформы перестанет стартовать
на файле, написанном более новой.

### Порт и путь — аргументы запуска, а не настройки

Сначала аргумент был один — путь к директории данных, — а порт предполагался в `config.json`.
Владелец продукта поправил: ни порт, ни пути в конфиге не задаются.

**Порт в `config.json`.** Отвергнуто владельцем продукта; кроме его решения против работает то, что
порт понадобился бы до чтения файла, а хот-релоад конфига на него всё равно не распространяется.
Переключатель, который меняет порт под собой же, оборвал бы соединение, которым его нажали.

**Жёсткая константа в коде.** Самое простое и предсказуемое: закладка в браузере всегда одна.
Отвергнуто: два экземпляра на одной машине становятся невозможны, а порт, занятый чужим процессом, —
отказ старта без выхода.

**Свободный порт от ОС.** Конфликтов не бывает никогда. Отвергнуто: адрес меняется между запусками,
постоянной закладки не существует.

**Переменная окружения.** Отвергнуто: не видна в команде запуска, теряется при переносе установки и
нигде не документирует сама себя. В dev-режиме `SOVEREIGN_PORT` остаётся временным решением, и это
расхождение держится видимым в [runbook.md](runbook.md).

### Вью настроек пишет `config.json` через платформу

Разделение файлов по автору записи прямо говорило: `config.json` пишет человек, платформа только
читает. Требование владельца продукта — править настройки платформы из интерфейса — в эту
формулировку не укладывалось.

**Оставить `config.json` только на чтение, из интерфейса править лишь предпочтения.** Ноль изменений
и никакой потерянной правки. Отвергнуто владельцем продукта: он назвал правку настроек платформы
содержанием вью, а не его украшением.

**Показывать файл текстом и сохранять целиком.** Интерфейс как редактор в браузере. Отвергнуто
владельцем; и это не снимает вопроса — писать в файл платформе всё равно пришлось бы.

**Перенести всё в `preferences.json` и оставить `config.json` пустым.** Убрало бы противоречие
целиком. Отвергнуто: файлы разделены именно потому, что нажатие переключателя не должно
перезаписывать файл с параметрами развёртывания.

Цена: одновременная правка руками и из интерфейса становится штатным сценарием, побеждает последний
`rename`, и это надо честно показывать в интерфейсе — файл мог измениться под открытой формой. Права
на файл становятся частью работоспособности интерфейса: `config.json` только для чтения на диске даёт
ошибку записи, которую надо показать внятно. И правка настроек через интерфейс — не полная гарантия:
вью настроек можно переопределить плагином, и последней гарантией остаётся правка файлом.
