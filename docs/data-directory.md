# Директория данных

Всё состояние платформы лежит в одной директории: перенос установки — это копирование её одной, и
ничего не остаётся в `$HOME`. Путь приходит первым позиционным аргументом запуска, по умолчанию
`~/.sovereign_platform`; в dev-режиме это `apps/daemon/.sovereign-dev` ([runbook.md](runbook.md)). Отсутствующая директория создаётся при
старте вместе с родительскими.

## Что в ней лежит сейчас

| Файл                  | Кто пишет | Назначение                                                              |
| --------------------- | --------- | ----------------------------------------------------------------------- |
| `daemon.lock`         | платформа | признак работающего демона, он же защита от второго на тех же данных    |
| `config.json`         | человек   | параметры поведения; платформа только читает                            |
| `preferences.json`    | платформа | предпочтения пользователя; править руками не запрещено                  |
| `account.json`        | платформа | учётная запись владельца: хеш пароля и параметры его счёта              |
| `login-sessions.json` | платформа | серверные записи сессий входа                                           |
| `plugins/`            | человек   | папка на плагин; сюда кладут внешние плагины ([plugins.md](plugins.md)) |

Оба файла настроек необязательны: отсутствующий равен пустому, значения по умолчанию живут в коде.
Папка `plugins/` создаётся при старте пустой: иначе положить плагин некуда.

Решено, но ещё не реализовано: записи проектов и записи сессий агента
([sessions-and-projects.md](sessions-and-projects.md)), папка `work` эфемерного проекта, креды
LLM-провайдеров ([models-and-providers.md](models-and-providers.md)), хранилища плагинов
([plugins.md](plugins.md)), каталог `builtin/<версия>/` с распакованными встроенными плагинами
([toolchain.md](toolchain.md)).

**Всё это — файлы и папки. Базы данных в директории данных нет** («Почему так» ниже). Конкретные
имена файлов фиксируются вместе с реализацией своего раздела, а не заранее.

## `daemon.lock`

Создаётся при старте атомарно, содержит `pid`, момент захвата, имя хоста и порт. Смысл файла — не
дать двум демонам открыть одни и те же данные: делимый ресурс здесь директория, а не порт.

Что происходит при повторном старте на занятой директории:

| Состояние лока                                 | Поведение                                          |
| ---------------------------------------------- | -------------------------------------------------- |
| процесс с этим `pid` жив                       | отказ старта с указанием `pid` и порта работающего |
| `hostname` чужой (директория на сетевом диске) | отказ: проверить процесс на другой машине нечем    |
| процесс мёртв (`kill -9`, падение машины)      | лок считается протухшим и перезахватывается        |
| файл не читается или неполон                   | отказ; лечится удалением файла руками              |

Штатное завершение (`Ctrl+C`, `SIGTERM`) удаляет файл, но только если в нём наш `pid`: чужой лок
платформа не снимает.

Возможен ложный отказ старта — система переиспользовала `pid` мёртвого демона, и живым оказался чужой
процесс. Лечение то же: удалить `daemon.lock` руками, убедившись, что демон действительно не запущен.

## Настройки

Файлов два, и делит их автор записи: `config.json` — параметры развёртывания и поведения,
`preferences.json` — предпочтения пользователя. Порта и пути к директории данных в них нет: это
параметры развёртывания, они приходят аргументами запуска.

`config.json` правит человек редактором, но платформа тоже пишет в него — по явному действию
пользователя из вью настроек. Запись сохраняет неизвестные ключи и порядок: файл, написанный более
новой версией платформы или руками, не обедняется записью из интерфейса. Параметры, требующие
перезапуска, записываются, но не применяются — диагностика «применится после перезапуска» работает
одинаково для правки руками и правки из интерфейса.

Поля на сегодня:

| Файл               | Поле                                            | Значения                               | По умолчанию         | Применение |
| ------------------ | ----------------------------------------------- | -------------------------------------- | -------------------- | ---------- |
| `config.json`      | `logLevel`                                      | `debug` \| `info` \| `warn` \| `error` | `info`               | живьём     |
| `config.json`      | `maxConcurrentTurns`                            | целое число больше нуля                | `4`                  | живьём     |
| `preferences.json` | `plugins.<источник>:<id>.enabled`               | `true` \| `false`                      | зависит от источника | живьём     |
| `preferences.json` | `plugins.<источник>:<id>.disabledContributions` | список идентификаторов вкладов         | пусто                | живьём     |
| `preferences.json` | `appearance.colorScheme`                        | идентификатор цветовой схемы           | `base`               | живьём     |
| `preferences.json` | `appearance.variant`                            | `light` \| `dark` \| `system`          | `system`             | живьём     |
| `preferences.json` | `appearance.scale`                              | `smaller` \| `default` \| `larger`     | `default`            | живьём     |
| `preferences.json` | `locale`                                        | языковой тег (`en`, `ru`, …)           | `en`                 | живьём     |

Примеры:

```json
{ "logLevel": "debug", "maxConcurrentTurns": 8 }
```

`maxConcurrentTurns` — сколько турнов исполняется одновременно; остальные ждут в очереди
([architecture.md](architecture.md)). Значение по умолчанию — `4`, названо владельцем продукта.
Предел определяет не машина, а лимит частоты запросов у провайдера, поэтому под свой тариф его
правят файлом.

```json
{
  "plugins": {
    "data:hello": { "enabled": true, "disabledContributions": ["hello.panel"] }
  },
  "appearance": { "colorScheme": "imperium", "variant": "system", "scale": "larger" },
  "locale": "ru"
}
```

`appearance` и `locale` — раздел, которым владеет оболочка: она читает и пишет его целиком одним
маршрутом ([web-api.md](web-api.md)), поэтому оба поля обязательны в теле записи. Значение вне
перечисленных **отвергает разбор целиком**, а не подставляет значение по умолчанию: правка руками
тогда не применяется вовсе, из интерфейса — получает `400`. Отсутствующее поле — не ошибка, у него
есть значение по умолчанию. `appearance.scale` двигает базовый кегль, шаг отступов и высоту контролов
одной осью ([ui-kit.md](ui-kit.md)).

Отсутствие записи о плагине — не «выключен», а «решения не было»: встроенный работает сразу, любой
другой ждёт включения. Подробности — в [plugins.md](plugins.md).

Параметров, требующих перезапуска, сейчас нет. Появится такой — он обязан сказать об этом
диагностикой, а не тихо расходиться с файлом.

### Перечитывание на живом демоне

Оба файла применяются без перезапуска: правка подхватывается за десятки миллисекунд. Наблюдается вся
директория, а не сами файлы, поэтому посторонний файл рядом (`.DS_Store`, временный файл редактора,
лок) события не вызывает — он отфильтровывается по имени. Подробности замеров — в
[runtime-checks.md](runtime-checks.md), проверки 12 и 14.

Перечитывание идемпотентно: если содержимое совпало с текущим, не происходит ничего.

### Что бывает не так

| Что в файле            | Что делает платформа                                                               |
| ---------------------- | ---------------------------------------------------------------------------------- |
| файла нет              | значения по умолчанию                                                              |
| битый JSON             | файл не применяется и не затирается, действует прежний снимок, в лог — диагностика |
| неверное значение поля | то же: применяется файл целиком или не применяется вовсе                           |
| неизвестный ключ       | диагностика, остальное применяется                                                 |

Платформа никогда не перезаписывает `config.json` своим представлением о нём: иначе опечатка в
редакторе уничтожала бы остальные настройки.

## Учётная запись и сессии входа

Два файла, и оба пишет только платформа: `account.json` и `login-sessions.json`. Права — `0600`,
запись атомарна (временный файл и `rename`), как у `preferences.json`: под ней лежат хеш пароля и
хеши токенов. Как устроен сам вход — в [authentication.md](authentication.md).

`account.json` — одна запись, потому что пользователь один:

| Поле                         | Что в нём                        |
| ---------------------------- | -------------------------------- |
| `passwordHash`               | scrypt-хеш пароля, base64        |
| `salt`                       | соль, base64, 16 байт            |
| `parameters.cost`            | `32768`                          |
| `parameters.blockSize`       | `8`                              |
| `parameters.parallelization` | `1`                              |
| `parameters.keyLengthBytes`  | `64`                             |
| `createdAt`                  | момент создания записи, ISO-8601 |

Параметры лежат рядом с хешем, а не в коде: поднять их со временем, не ломая существующий вход, можно
только зная, каким набором посчитан этот хеш. Пока файла нет, API отвечает «требуется регистрация» и
принимает создание записи; после этого — только вход.

**Негодный `account.json` не перезаписывается.** Под ним единственный пароль владельца, и затереть
его значило бы запереть человека снаружи, поэтому платформа отвечает `409` и ждёт человека
([web-api.md](web-api.md)).

Негодным файл считается не только когда это не json. Проверяется и содержимое: `cost` обязан быть
степенью двойки больше единицы, набор целиком — требовать не больше гигабайта на счёт хеша, а
`passwordHash` — декодироваться ровно в `keyLengthBytes` байт. Требования не придирка: `scrypt`
бросает на непригодном наборе, а base64 в Node молча проглатывает мусор, поэтому без этих проверок
поправленный руками файл давал бы на входе `500` вместо честного «файл негоден».

`login-sessions.json` — список записей:

```json
{
  "sessions": [
    {
      "id": "8Qk2…",
      "tokenHash": "TmV2ZXI…",
      "createdAt": "2026-07-28T09:11:04.512Z",
      "expiresAt": "2026-08-27T09:11:04.512Z"
    }
  ]
}
```

На диске лежит SHA-256 токена в base64, самого токена нет: копия директории данных не даёт живых
сессий. Срок жизни записи — 30 суток, и он обязан быть явным: сессии переживают перезапуск демона,
потому что лежат файлом.

**Негодный `login-sessions.json`, в отличие от настроек, не отказ.** Он читается как пустой набор с
диагностикой в журнал: худшее, что это стоит, — новый вход, и требовать за это ручного вмешательства
незачем.

Имя `login-sessions.json`, а не `sessions.json`, выбрано намеренно: сессия агента
([sessions-and-projects.md](sessions-and-projects.md)) — другая сущность, и в одной директории данных
им нельзя выглядеть одинаково.

Наблюдатель настроек этих файлов не касается: он фильтрует по имени и знает только `config.json` и
`preferences.json`. Править их руками незачем — единственный штатный случай это сброс забытого пароля
(«Ручное восстановление» ниже).

## Ручное восстановление

Директория текстовая намеренно: это способ починить платформу, когда интерфейс не открывается.

- **Демон не стартует, жалуясь на лок.** Убедиться, что демон не запущен, и удалить `daemon.lock`.
- **Интерфейс не поднимается из-за настройки.** Править `preferences.json` руками — это
  предусмотренный путь, а не обходной.
- **Не видно, что не так с файлом.** Диагностика идёт в журнал демона: `logLevel` в `config.json`
  ставится в `debug`, и это применяется без перезапуска.
- **Забыт пароль.** Удалить `account.json` руками — это удаляет учётную запись, и платформа снова
  просит её создать. Войти заново придётся регистрацией: другого пароля у платформы нет
  ([authentication.md](authentication.md)). Сессии удалять не нужно: сессия подтверждает учётную
  запись, поэтому без `account.json` не действует ни одна выданная cookie, а регистрация нового пароля
  вычищает `login-sessions.json`. Если сессии надо снять и не создавая пароль заново, демон
  останавливается и файл удаляется вместе с `account.json`: набор сессий живёт в памяти процесса, и
  правка файла на ходу ничего не изменит.

Правка руками при работающем интерфейсе может потеряться: побеждает тот, кто записал последним, а
переключатель в браузере пишет тот же файл.

## Почему так

### Одна директория и лок на неё

Демон запускается из терминала и, по замыслу, больше не глушится. Второй демон на той же директории
данных недопустим: два процесса писали бы в одни и те же файлы состояния. Порт для защиты не
годится — он не мешает поднять второй демон на другом порту поверх тех же данных. Делимый ресурс
здесь директория, её и надо защищать.

Захват — атомарное эксклюзивное создание файла (`fs.open(path, "wx")`, за ним `O_CREAT|O_EXCL`). Это
единственный примитив блокировки, который в Node работает одинаково на всех целевых платформах.
Оба примитива проверены запуском ([runtime-checks.md](runtime-checks.md), проверка 8).

**`flock` или блокировка дескриптора.** Правильный способ на POSIX: лок снимается ядром вместе с
процессом, протухших локов не бывает вовсе. Но в Node нет встроенного `flock`, а на Windows его нет
как понятия — пришлось бы тянуть нативную зависимость ради одной функции.

**Занять порт и считать это локом.** Не защищает директорию: два демона на разных портах спокойно
откроют одни и те же данные.

**Лок в общесистемном месте (`/var/run`, `%TEMP%`).** Ломает главное правило — всё состояние внутри
директории данных. К тому же локов должно быть столько, сколько директорий данных, а не один на
машину.

Из правила «ничего за пределами директории данных» следует критерий выбора библиотек: любая новая
зависимость, которая хранит состояние, проверяется на возможность указать ей путь. Не умеет — не
берём или оборачиваем. Именно поэтому у Pi мы внедряем свои реализации хранилищ, а его CLI с
`~/.pi/agent/` не используем ([agent-runtime-contract.md](agent-runtime-contract.md)).

Проверка на протухание удаляет чужой файл, поэтому делает ровно одну повторную попытку: иначе два
одновременно стартующих демона по очереди сносили бы лок друг друга.

### Всё состояние файлами, базы данных нет

**Правило одно и без исключений: любое состояние платформы лежит файлом или папкой в директории
данных.** То, что правит человек, — JSON. То, что пишет платформа и что растёт — дерево записей
сессии агента, — JSONL по файлу на сессию, дописыванием в конец. Атомарность записи обеспечивается
записью во временный файл и переименованием — одной реализацией на всех, кто пишет: `preferences.json`,
`account.json` и `login-sessions.json`.

Причина в том, ради чего эта директория текстовая: **способ починить платформу здесь — открыть файл
редактором** («Ручное восстановление» выше). База выделила бы кусок состояния, к которому этот способ
неприменим, и сделала бы это ровно там, где чинить приходится чаще всего.

Конкуренции за файл сессии не возникает по построению: одновременный турн в одной сессии рантайм
отклоняет с `busy` ([agent-runtime-contract.md](agent-runtime-contract.md)), поэтому писатель у файла
всегда один.

**SQLite (`node:sqlite`) для сессий и хранилищ плагинов.** Так и было записано в этом документе —
и записано ошибочно: решение принял агент, а стояло оно со статусом «Утверждено»
([master-spec.md](master-spec.md)), которого владелец продукта не давал. Отвергнуто владельцем
продукта. Замеры при этом верны и остаются в силе: 10 000 записей в транзакции за 20 мс, выборка по
индексу за 1.6 мс ([runtime-checks.md](runtime-checks.md), проверка 10) — производительность никогда
не была здесь вопросом. Цена варианта: бэкап перестаёт быть копированием папки и требует `backup()`,
запись сессии становится нечитаемой без инструмента, а миграции и `user_version` появляются с первого
дня. Взамен он давал выборку отдельных записей внутри огромной сессии и поиск по содержимому — ни то,
ни другое на одном пользователе не является ограничением.

**`better-sqlite3` вместо встроенного модуля.** Быстрее и API богаче, но это нативная сборка на
машине пользователя — против ставки на возможности рантайма и лишний барьер для установки. Отпало
вместе с самой базой.

**Внешняя СУБД.** Локальный однопользовательский демон, который «запускается и больше не глушится»,
не может требовать поднятого рядом сервера.

Цена принятого варианта названа честно:

- **«Список сессий» — это обход файлов.** На сотнях сессий дёшево, на тысячах станет заметно. Это
  первое место, куда надо смотреть, если чтение начнёт тормозить.
- **Транзакции на несколько сущностей нет.** Безвозвратное удаление проекта вместе с его сессиями —
  это несколько файлов, и падение посередине оставляет осиротевшие записи. Уборка таких остатков —
  обязанность реализации, а не «этого не случится».
- **Сводная статистика по токенам и стоимости считается обходом всех сессий.**

Страховка на случай, если по сессиям решение окажется неверным: `SessionStorage` у Pi внедряется
приложением ([agent-runtime-contract.md](agent-runtime-contract.md)), то есть это наш интерфейс.
Подмена его реализации на базу не заденет ничего, что лежит выше.

### Два файла настроек, а не один

Смешивание означало бы, что каждое нажатие переключателя в интерфейсе перезаписывает файл, в котором
лежат параметры развёртывания, а правка руками в этот момент теряется. Плюс диффы становятся
нечитаемыми: параметры тонут в списке выключенных вкладов.

**Один файл с разными секциями.** Меньше файлов и одно место, куда смотреть. Отвергнуто по причине
выше.

**Предпочтения в базе.** Обсуждалось, пока база предполагалась. Отпало вместе с ней, но довод стоит
удержать: предпочтения обязаны открываться редактором — выключить рукой плагин, из-за которого
интерфейс не поднимается, ровно тот сценарий, для которого настройки лежат текстом.

**Хот-релоад только `config.json`, предпочтения — исключительно через API.** Отвергнуто: файл,
который платформа пишет, но чужую правку игнорирует, — ловушка. Пользователь правит, ничего не
происходит, а следующая запись платформы затирает правку без следа.

### Перечитывание: наблюдаем директорию, а не файлы

**`fs.watch` на самих файлах.** Естественный первый вариант. Отвергнуто по измерению: наблюдатель на
файле умирает после первой же атомарной замены — он держит старый inode, а `rename` подставляет новый
([runtime-checks.md](runtime-checks.md), проверка 12). Ошибка была бы незаметной: первый релоад
проходит.

**Опрос по `stat` (`watchFile`).** Замену переживает, но опрашивает диск постоянно и добавляет
задержку. Оставлен как запасной путь для сетевых файловых систем, где события не приходят.

**Своё расширение поверх наблюдателя, чтобы отличать свою запись от чужой.** Отвергнуто: различать
нечем, а идемпотентное перечитывание делает вопрос ненужным.

Следствия: директория наблюдается целиком, поэтому фильтр по имени — обязательная часть реализации, а
не оптимизация; валидация нужна на каждом перечитывании и с внятным откатом к прежнему снимку;
неизвестный ключ — диагностика, а не ошибка, иначе понижение версии платформы перестанет стартовать
на файле, написанном более новой.

### Порт и путь — аргументы запуска, а не настройки

Сначала аргумент был один — путь к директории данных, — а порт предполагался в `config.json`.
Владелец продукта поправил: ни порт, ни пути в конфиге не задаются.

**Порт в `config.json`.** Отвергнуто владельцем продукта; кроме его решения против работает то, что
порт понадобился бы до чтения файла, а хот-релоад конфига на него всё равно не распространяется.
Переключатель, который меняет порт под собой же, оборвал бы соединение, которым его нажали.

**Жёсткая константа в коде.** Самое простое и предсказуемое: закладка в браузере всегда одна.
Отвергнуто: два экземпляра на одной машине становятся невозможны, а порт, занятый чужим процессом, —
отказ старта без выхода.

**Свободный порт от ОС.** Конфликтов не бывает никогда. Отвергнуто: адрес меняется между запусками,
постоянной закладки не существует.

**Переменная окружения.** Отвергнуто: не видна в команде запуска, теряется при переносе установки и
нигде не документирует сама себя. В dev-режиме `SOVEREIGN_PORT` остаётся временным решением, и это
расхождение держится видимым в [runbook.md](runbook.md).

### Вью настроек пишет `config.json` через платформу

Разделение файлов по автору записи прямо говорило: `config.json` пишет человек, платформа только
читает. Требование владельца продукта — править настройки платформы из интерфейса — в эту
формулировку не укладывалось.

**Оставить `config.json` только на чтение, из интерфейса править лишь предпочтения.** Ноль изменений
и никакой потерянной правки. Отвергнуто владельцем продукта: он назвал правку настроек платформы
содержанием вью, а не его украшением.

**Показывать файл текстом и сохранять целиком.** Интерфейс как редактор в браузере. Отвергнуто
владельцем; и это не снимает вопроса — писать в файл платформе всё равно пришлось бы.

**Перенести всё в `preferences.json` и оставить `config.json` пустым.** Убрало бы противоречие
целиком. Отвергнуто: файлы разделены именно потому, что нажатие переключателя не должно
перезаписывать файл с параметрами развёртывания.

Цена: одновременная правка руками и из интерфейса становится штатным сценарием, побеждает последний
`rename`, и это надо честно показывать в интерфейсе — файл мог измениться под открытой формой. Права
на файл становятся частью работоспособности интерфейса: `config.json` только для чтения на диске даёт
ошибку записи, которую надо показать внятно. И правка настроек через интерфейс — не полная гарантия:
вью настроек можно переопределить плагином, и последней гарантией остаётся правка файлом.
