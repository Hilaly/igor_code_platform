# Проверки рантайма

Утверждения о возможностях Node, на которых стоят решения по архитектуре. Проверены запуском,
а не взяты из документации. Прогоняются заново при смене мажорной версии Node: если проверка
перестала проходить, затронутое решение нужно пересматривать.

Проверки 28–32 — про чужой пакет, а не про Node: они перепрогоняются при обновлении Pi
([agent-runtime-contract.md](agent-runtime-contract.md)).

**Проверено на:** Node v24.18.0, macOS arm64, 2026-07-26; проверки 21 и дальше — 2026-07-27;
проверка 26 и дальше — 2026-07-29. Проверка 24 сделана в браузере (Chrome, тот же день),
остальные — в Node. Проверка 36 — 2026-08-08.
**Связанные решения:** [toolchain.md](toolchain.md).

## 1. TypeScript исполняется без транспайлера

```bash
printf 'const id: string = "demo";\nconsole.log("ok:", id);\n' > /tmp/t.ts && node /tmp/t.ts
```

Результат: `ok: demo`. Флаги не нужны, стирание типов включено по умолчанию.

## 2. Нестираемый синтаксис в режиме по умолчанию не работает

```bash
printf 'enum Level { Debug, Info }\nconsole.log(Level.Info);\n' > /tmp/e.ts && node /tmp/e.ts
```

Результат: `ERR_UNSUPPORTED_TYPESCRIPT_SYNTAX: TypeScript enum is not supported in strip-only mode`.
Так же ведут себя `namespace` и parameter properties (`constructor(private x: T)`).

## 3. Встроенный трансформ снимает это ограничение

```bash
node --experimental-transform-types /tmp/e.ts
```

Результат: `1`. Транспайлер внутри Node, внешних зависимостей не требуется. Флаг помечен
экспериментальным и печатает предупреждение.

## 4. Флаг можно включить только для воркера

Хост-процесс запускается без флага, воркер получает его через `execArgv`:

```js
new Worker(pluginUrl, { execArgv: ["--experimental-transform-types"] });
```

Результат: код с `enum` и parameter properties исполняется внутри воркера, хост-процесс при этом
экспериментальных флагов не несёт. Значит режим исполнения TypeScript можно выбирать для плагинов
отдельно от самого демона.

## 5. Лимит памяти на воркер действительно убивает воркер, а не процесс

Воркер с `resourceLimits: { maxOldGenerationSizeMb: 32 }` в бесконечном цикле аллокаций:

```js
new Worker(hogUrl, { resourceLimits: { maxOldGenerationSizeMb: 32 } });
```

Результат:

```
worker died: Error | Worker terminated due to reaching memory limit: JS heap out of memory
worker exit code: 1 | host alive, rss 62 MB
```

Хост-процесс пережил событие и остался в пределах своей памяти. Это опорный факт для модели
изоляции «воркер на плагин»: лимит — не декларация, а рабочий предохранитель.

## 6. SQLite доступен из коробки

```bash
node -e 'const {DatabaseSync}=require("node:sqlite"); new DatabaseSync(":memory:").exec("create table t(a)")'
```

Результат: работает без флагов и без нативных зависимостей.

## 7. Пакет воркспейса резолвится в исходниках через симлинк pnpm

Node не стирает типы в файлах внутри `node_modules`, а pnpm кладёт туда симлинк на пакет
воркспейса. Вопрос — какой путь увидит Node.

```bash
cd apps/daemon && node -e 'import("@sovereign/protocol").then((m) => console.log(m.healthPath))'
```

Результат: `/api/health`. Node разворачивает симлинк в реальный путь (`packages/protocol/src`),
то есть файл оказывается вне `node_modules` и стирание типов применяется.

Это опорный факт для потребления внутренних пакетов исходниками
([repository-structure.md](repository-structure.md)): без него
потребление пакетов исходниками не работало бы и потребовалась бы сборка в `dist`.

## 8. Примитивы лок-файла работают без нативных зависимостей

Опора для лока на директорию данных ([data-directory.md](data-directory.md)): единственность демона
защищается лок-файлом, а не `flock`.

```js
await open(path, "wx"); // второй такой же вызов на существующем файле
process.kill(pid, 0); // проверка живости процесса
```

Результат:

```
первый захват: ok, второй: EEXIST
живой pid: жив | свой pid: жив
убитый pid: ESRCH | заведомо свободный: ESRCH
```

Эксклюзивное создание атомарно, живость процесса проверяется без сторонних пакетов.

**Проверено только на macOS.** `O_EXCL` и сигнал `0` есть на всех целевых платформах, но на
Linux и Windows это утверждение из документации, а не из запуска. Перепроверить, когда появится
вторая платформа в работе.

## 9. Браузер даёт шесть соединений на источник, и SSE-потоки их занимают

Опора для «одно SSE-соединение на клиента» ([web-api.md](web-api.md)): почему поток к
демону один, а не по одному на сессию агента.

Тестовый сервер на `http://127.0.0.1:8899` отдавал `/sse` (поток), `/ping` (обычный JSON) и
страницу, которая открывает N потоков и затем делает один `fetch("/ping")` с таймаутом 4 с.

| Открыто SSE-потоков | Обычный запрос к тому же источнику |
| ------------------- | ---------------------------------- |
| 3                   | ответ за 11 мс                     |
| 6                   | не прошёл за 4000 мс               |

Шесть потоков открылись успешно — упёрся именно седьмой запрос, и это был обычный `fetch`, а не
поток. То есть переполнение пула ломает не только события, а весь HTTP к этому источнику.

Пока первая вкладка держала шесть потоков, страница того же источника во второй вкладке не
загрузилась вовсе. Это согласуется с тем, что пул соединений общий для источника, а не отдельный
на вкладку: «шесть» — это шесть на весь браузер, а не шесть на вкладку.

**Проверено на:** Chrome, HTTP/1.1, `http://127.0.0.1`. По TLS и HTTP/2 лимит был бы другим, но
браузеры не включают HTTP/2 без TLS, а демон слушает `http://localhost`.

## 10. Встроенный SQLite годится как хранилище состояния

> **Замер верен, решение отменено.** Он делался под выбор SQLite для машинного состояния; владелец
> продукта этот выбор отверг, всё состояние платформы лежит файлами
> ([data-directory.md](data-directory.md)). Цифры ниже остаются фактом о рантайме и говорят, что база
> отвергнута не из-за производительности.

Проверка 6 показала только то, что модуль есть. Вопрос был в другом: можно ли на нём держать дерево
записей сессии — то есть упираются ли запись пачкой и выборка по индексу.

```js
import { DatabaseSync } from "node:sqlite"; // 10 000 записей в одной транзакции
```

Результат:

```
sqlite: 10000 записей в транзакции за 20 мс
sqlite: выборка по типу — 3334 записей за 1.6 мс
```

Про зрелость модуля: на 24.18.0 `require("node:sqlite")` не печатает ничего, на 22.22.2 тот же
вызов даёт `ExperimentalWarning`. Экспортируется `DatabaseSync`, `StatementSync`, `Session`,
`constants`, `backup` — то есть горячий бэкап базы делается штатным средством, без остановки демона.

## 11. Хеш пароля считается встроенным scrypt

Опора для входа по паролю ([authentication.md](authentication.md)): пароль хранится как
scrypt-хеш, и `argon2` с нативной сборкой в ядро не тянется.

```js
import { scryptSync, timingSafeEqual } from "node:crypto"; // N=2^15, r=8, p=1, 64 байта
```

Результат:

```
scrypt N=2^15: 69 мс, совпадение: true, чужой пароль: false
```

69 мс — это не медленно, а по построению: столько стоит одна проверка пароля, и во столько же
обходится одна попытка подбора.

## 12. Хот-релоад конфигурации: наблюдать надо директорию, а не файл

Опора для хот-релоада настроек ([data-directory.md](data-directory.md)): `config.json` и
`preferences.json` перечитываются на живом демоне. Оба пишутся атомарно — временный файл плюс
`rename`, — и вопрос в том,
переживает ли наблюдатель такую замену.

```js
watch(file, cb); // против watch(dir, cb) при записи через temp + rename
```

Результат:

```
watch(файл), 1-я замена: ["rename:preferences.json"]
watch(файл), 2-я замена: []
watch(директория), три замены: [".tmp", "preferences.json", "preferences.json"] × 3
watch(отсутствующий файл): ENOENT
watchFile, две замены: ["mtime новый size=7", "mtime новый size=8"]
```

**Наблюдатель на самом файле отрабатывает один раз и молча замолкает:** он держит старый inode, а
`rename` подставляет новый. Наблюдатель на директории переживает любое число замен, но шумит —
на одну запись приходит три события, включая событие про временный файл. Значит фильтр по имени и
подавление дребезга обязательны, а не желательны. `watchFile` (опрос по `stat`) замену переживает,
но требует постоянного опроса.

Отдельно проверено, что атомарность записи действительно защищает читателя: 179 конкурентных чтений
файла на 2 МБ, который в это же время непрерывно перезаписывался, — ни одного битого JSON и ни одного
`ENOENT`. Читателю не нужен лок, ему достаточно `readFileSync`.

Событие от собственной записи демона ничем не отличается от события от правки руками — различать их
нечем, поэтому перечитывание обязано быть идемпотентным.

**Проверено только на macOS.** `fs.watch` опирается на механизм уведомлений конкретной ОС, поэтому
на Linux и Windows проверку надо прогнать заново; на сетевых файловых системах события могут не
приходить вовсе, и там остаётся `watchFile`.

## 13. Сохранять поток событий на диск не дорого; дорого его хранить

> **Мерилось на SQLite, а базу с тех пор отвергли** ([data-directory.md](data-directory.md)). Вывод
> замера от носителя не зависит и остаётся в силе: ограничением является объём, а не скорость. Сам
> вопрос — сохранять ли поток событий на диск вместо окна в памяти — по-прежнему открыт, и решать его
> придётся уже файлом.

Проверка 10 мерила запись пачкой в базу **в памяти**. Вопрос был другой: можно ли сохранять поток
событий, который уходит на фронтенд по SSE, вместо окна в оперативной памяти — то есть сколько стоит
запись **на диск**, причём такая, после которой событие сразу можно догнать.

Замер: `node:sqlite`, база файлом, `journal_mode = WAL`, полезная нагрузка — реальное доменное
событие (212 байт JSON) и дельта вывода агента (167 байт).

```
запись по одному событию, synchronous=FULL:    2000 шт за 125 мс = 16 031 событий/с
запись по одному событию, synchronous=NORMAL: 20000 шт за 269 мс = 74 393 событий/с
коммит раз в 10 событий:                      50000 шт за 165 мс = 303 574 событий/с
коммит раз в 100 событий:                     50000 шт за  83 мс = 604 443 событий/с
догон с индекса 199500: 500 событий за 0.2 мс
догон с индекса 100000: 100 000 событий за 63.4 мс
догон с индекса 0:      200 000 событий за 104.5 мс
200 000 доменных событий на диске: 40.4 МБ = 212 байт на событие
200 000 дельт вывода на диске:     31.8 МБ = 167 байт на дельту
чтение вторым соединением во время записи: 200 успешных, 0 ошибок
удаление 150 000 событий: 155 мс, размер 40.4 → 71.2 МБ (без VACUUM)
```

**Пропускная способность не является ограничением.** Даже в самом строгом режиме — своя транзакция на
каждое событие и честный `fsync` — это 16 тысяч событий в секунду. Микропачка (коммит раз в 10–100
событий) даёт сотни тысяч, но она и не нужна: платформа не производит таких потоков.

**Догон с индекса — это индексная выборка по первичному ключу,** и на типичном случае (клиент отстал
на несколько сотен событий) он занимает доли миллисекунды. Дорог только полный проигр с нуля, и то
100 мс на 200 тысяч.

**Ограничение не в скорости, а в объёме.** 212 байт на доменное событие, 167 на дельту вывода агента.
Час генерации на 50 дельтах в секунду — это порядка 30 МБ, то есть решение «что попадает в поток»
определяет рост базы, а не производительность.

**`DELETE` не освобождает место.** Удаление 150 000 событий из 200 000 **раздуло** файл с 40.4 до
71.2 МБ, потому что удаление тоже пишется в WAL. Retention — это не одна инструкция `DELETE`: нужен
чекпойнт WAL, иначе чистка истории увеличивает занятое место вместо того, чтобы уменьшать.

**Проверено на:** macOS, APFS, SSD, один писатель. На сетевой файловой системе и на вращающемся диске
числа будут другими — там значима именно стоимость `fsync`, которая здесь получилась дешёвой.

## 14. Наблюдатель встаёт не мгновенно, и события этого окна теряются

Найдено при реализации хранилища настроек: тест на атомарную замену падал раз в два-три
прогона, причём событие не задерживалось, а не приходило вовсе. Замер — запись сразу после `watch()`
при разном числе наблюдателей, поставленных в том же всплеске, и при разной паузе перед записью:

```
наблюдателей до 0, пауза  0 мс: да да да да
наблюдателей до 3, пауза  0 мс: да да да НЕТ
наблюдателей до 6, пауза  0 мс: НЕТ НЕТ да НЕТ
наблюдателей до 6, пауза  5 мс: НЕТ НЕТ НЕТ да
наблюдателей до 6, пауза 10 мс: да да да да
наблюдателей до 6, пауза 30 мс: да да да да
```

**`watch()` возвращает управление раньше, чем наблюдатель начинает получать события.** Изменение,
попавшее в это окно, теряется насовсем. Окно тем шире, чем больше наблюдателей ставится одновременно:
одиночный наблюдатель не пропустил ни одной записи, шесть подряд — большинство. Момент готовности
наблюдателя в API не выражен никак: `watch()` не даёт ни колбэка, ни события об этом.

Следствия:

- **Читать надо после постановки наблюдателя, а не до.** Тогда правка, потерянная не успевшим встать
  наблюдателем, всё равно попадает в первый снимок. Остаточное окно — изменение, случившееся после
  чтения и до готовности наблюдателя, — этим порядком не закрывается, но становится минимальным.
- **Тест не имеет права полагаться на одну запись.** Запись повторяется, пока наблюдатель не
  отзовётся, иначе тест проверяет гонку с постановкой наблюдателя, а не поведение кода.
- Пауза «10 мс достаточно» — это наблюдение на одной машине, а не гарантия. Гарантии здесь нет вовсе;
  запасной путь на случай, когда события не приходят, — тот же `watchFile` из проверки 12.

**Проверено на macOS**, Node 24.18.0. За `fs.watch` там стоит FSEvents; на Linux (inotify) и Windows
поведение надо мерить отдельно.

## 15. Бутстрап и плагин видят разные экземпляры одного пакета

Контракт SDK говорит: бутстрап воркера инициализирует состояние модуля SDK и только потом импортирует код
плагина. Проверка — что именно считать «состоянием модуля», когда у внешнего плагина в `node_modules`
лежит своя копия `@sovereign/sdk`. Раскладка повторяет реальную: демон резолвит пакет по симлинку
(как pnpm), плагин — по собственной копии. Бутстрап пишет хост двумя способами, плагин читает оба:

```
sameInstance: false
плагин видит состояние модуля:      null
плагин видит символ в globalThis:   "host-through-global"
```

**Копия пакета — это другой модуль со своим состоянием.** Внутри репозитория обе стороны резолвятся в
один реальный путь (проверка 7) и общее состояние работает — но ровно до первого внешнего плагина,
который принёс `@sovereign/sdk` с собой. Модульная переменная в этой раскладке молча пуста.

**`globalThis[Symbol.for(...)]` доходит до любой копии,** и у каждого воркера свой `globalThis`:
плагин видит только своего хоста, в главном потоке символа нет вовсе. Поэтому хэндл хоста живёт там,
а не в переменной модуля.

## 16. `terminate()` снимает воркер, что бы плагин ни делал

Выгрузка плагина устроена как «попроси, потом сними» ([plugins.md](plugins.md)), и вопрос был в том, есть ли случай,
когда снять не получается. Замер — три плагина: вежливый, с `deactivate`, возвращающим никогда не
разрешающееся обещание, и с пустым бесконечным циклом. Плюс стоимость старта воркера, который ставит
хост и импортирует плагин:

```
старт воркера с плагином, мс: [38,16,15,17,20]
штатная выгрузка, мс: 1        код выхода: 1
зависший deactivate, мс: 152   код выхода: 1
занятый цикл, мс: 152          код выхода: 1
```

**`terminate()` снимает и зависшее обещание, и цикл без единой точки передачи управления.** Значит
таймаут на `deactivate` — это вся необходимая защита: за ним всегда есть чем закончить.

**Холодный старт воркера с плагином — 38 мс, последующие 15–20 мс.** Разница между первым и
остальными — прогрев самой платформы, а не плагина. Сотня плагинов при старте демона обойдётся в
пару секунд, и это довод в пользу параллельного подъёма, если она когда-нибудь наберётся.

**Код выхода после `terminate()` — 1, а не 0,** и это не признак ошибки плагина: различать штатную
выгрузку и падение по коду выхода нельзя, нужен собственный признак.

## 17. Рекурсивный наблюдатель первым событием перечисляет всё поддерево

Установка зависимостей плагина предупреждает про петлю «установка → перезагрузка → установка» и требует исключить
`node_modules` из наблюдения. Замер проверял, достаточно ли этого. Рекурсивный `fs.watch` по корню
источника, внутри — папка плагина с `node_modules`:

```
правка двух вложенных файлов: rename src/worker.js, rename src/deep/helper.js
npm install: 4 события, вне node_modules — только package-lock.json

первое событие после постановки наблюдателя (запись одного файла в node_modules):
  rename hello, rename hello/node_modules, rename hello/node_modules/left,
  rename hello/src, rename hello/node_modules/left/index.js, rename hello/package-lock.json
последующие события: ровно тот файл, который записали
```

**Вложенные файлы видны, и путь приходит относительный** — по первому сегменту понятно, какой плагин
трогали.

**`package-lock.json` пишется в корень плагина, а не в `node_modules`.** Исключения одного
`node_modules` мало: без второго имени установка зависимостей перезагружала бы плагин.

**Первое событие приходит пачкой на всё поддерево** — со всеми папками и всеми давно лежащими
файлами, хотя изменился один файл. Дальше события точные. Значит фильтра по имени недостаточно:
правкой считается только то, что моложе момента постановки наблюдателя, а событие о папке правкой не
считается вовсе — файл внутри неё придёт своим событием.

**Проверено на macOS**, Node 24.18.0, за `fs.watch` там FSEvents. На Linux (inotify) пачка, скорее
всего, выглядит иначе — правило «моложе наблюдателя» от этого не ломается, но проверить надо отдельно.

## 18. Прокси Vite отдаёт SSE по кадру, а не пачкой

Это условие работоспособности потока в разработке ([web-api.md](web-api.md)): буферизующий прокси
превратил бы поток в один ответ в конце, и догон по индексу проверить было бы нечем. Замер — один и
тот же источник (событие раз в 300 мс, в нагрузке момент отправки), прочитанный напрямую и через
прокси:

```
напрямую 127.0.0.1:8787:  7, 0, 0, 1, 0, 1, 1, 0, 2, 1 мс
через localhost:5273:     9, 2, 2, 1, 1, 2, 1, 2, 1, 1 мс
```

**Кадры приходят по одному, задержка прокси — 1–2 мс.** Первый кадр дороже остальных в обоих
случаях: это установка соединения, а не буферизация.

**Через прокси надо ходить на `localhost`, а не на `127.0.0.1`.** Vite слушает только `[::1]:5273`,
и запрос на IPv4-петлю получает `ECONNREFUSED`. К поведению SSE это отношения не имеет, но стоило
часа поиска.

## 19. Обратного давления у SSE-сокета нет

`response.write()` возвращает `false`, когда буфер полон, но писать это не мешает. Вопрос был в том,
что делает демон, если клиент перестал читать. Замер — клиент, который открыл поток и не читает
ничего:

```
запись № 246, 108 мс:  write() вернул false, в буфере 65 740 байт
0,4 с:   173 МБ в буфере, RSS 511 МБ
1,4 с:   871 МБ в буфере, RSS 2 032 МБ
5,1 с: 2 094 МБ в буфере, RSS 4 175 МБ
```

**Ничто не останавливается само: буфер растёт, пока не кончится память.** Одной зависшей вкладки
достаточно, чтобы убить демон за секунды. Значит порог отцепления медленного клиента — не
оптимизация, а условие живучести; поток следит за `writableLength` после каждой записи и рвёт
соединение, а не копит.

**`false` от `write()` приходит на 65 КБ** — это размер буфера сокета, а не признак беды: клиент,
который читает, проглатывает эти килобайты немедленно.

## 20. Журнал в шине стоит дешевле, чем всё остальное

Журнал был назван самым частым источником событий, и путь требовалось измерить целиком. Замер —
запись логгера, доставка трём подписчикам, сериализация кадра SSE и отправка в читающий сокет:

```
собрать запись                             86 мс   2 315 784 зап/с
собрать и разослать трём подписчикам       89 мс   2 235 049 зап/с
плюс сериализация кадра SSE               164 мс   1 223 088 зап/с
весь путь через читающий сокет            349 мс     573 487 зап/с
```

**Полный путь — около 570 тысяч записей в секунду**, то есть журнал на уровне `debug` не является
нагрузкой ни при каком реальном числе плагинов. Дорога здесь только сериализация: она вдвое дороже
самой рассылки.

**Кадр весит около 200 байт** (37,9 МБ на 200 000 кадров). Отсюда глубина окна догона: тысяча
событий — это порядка 200 КБ памяти, и торговаться за неё не о чем.

> Дописано позже: журнал на шине больше не публикуется
> ([logging.md](logging.md)), поэтому первые три строки
> замера описывают путь, которого нет. Вывод про вес кадра остаётся: по нему выбрана глубина окна
> догона, и события ядра сериализуются так же.

## 21. Проверка нагрузки по схеме дешевле, чем путь публикации вокруг неё

Проверку по схеме требовалось измерить: она идёт на каждой публикации. Замер — `zod` 4.4.3,
типовая нагрузка события в семь полей (строки, число, перечисление, массив), полный путь публикации
события плагина: разрешение вклада в реестре, сборка события и синхронная рассылка подписчикам шины.

```
1 объявление, 1 подписчик      без проверки 13 874 918 публ/с   с проверкой 5 165 267 публ/с
50 объявлений, 1 подписчик     без проверки  6 400 597 публ/с   с проверкой 3 583 630 публ/с
50 объявлений, 3 подписчика    без проверки  6 788 156 публ/с   с проверкой 3 642 081 публ/с
```

**Проверка стоит около 120 наносекунд на публикацию** — при том, что самый частый источник событий
в системе, журнал, проходит весь свой путь на 573 тыс. записей/с (проверка 20). То есть проверка не
является нагрузкой ни при какой мыслимой частоте событий, и делать её условной не за чем.

**Поиск объявления в реестре стоит столько же, сколько проверка.** Реестр — плоский список, и
пятьдесят объявлений вместо одного стоят примерно тех же ста наносекунд. При тысячах вкладов
разрешение придётся индексировать по имени, но до этого далеко и оптимизировать сейчас нечего.

**Нагрузка, не прошедшая проверку, стоит в полсотни раз дороже прошедшей** — 154 тыс. отказов/с
против 8,8 млн проверок/с на той же схеме: цена в сборке объекта ошибки. Значение это имеет только
для того, кто ошибся: проверка идёт в воркере публикатора ([event-bus.md](event-bus.md)), и плагин, публикующий мусор в
цикле, замедляет себя, а не демон.

## 22. Доставка события в воркеры стоит в разы дороже самой шины

Событие с шины уходит подписанным воркерам через `postMessage`, то есть через структурное
клонирование на каждого. Замер — та же нагрузка в семь полей, 100 000 событий, 1, 3 и 10
подписанных воркеров; «отправка» — время в потоке демона, «все получили» — пока последний воркер не
подтвердил счёт.

```
 1 воркер     отправка  107 мс (931 670 соб/с)   все получили  151 мс (662 460 соб/с)
 3 воркера    отправка  710 мс (140 780 соб/с)   все получили  711 мс (140 729 соб/с)
10 воркеров   отправка 4585 мс ( 21 812 соб/с)   все получили 4585 мс ( 21 811 соб/с)
```

**Цена одного сообщения растёт с числом получателей:** 1,1 мкс при одном воркере, 2,4 при трёх, 4,6
при десяти. Дело не в получателях — они успевают, «все получили» совпадает с «отправкой», — а в
отправляющем потоке: он сериализует каждому и на это время занят.

**Отсюда подтверждение исключению `core.log`.** Журнал идёт через шину со скоростью 573
тыс. записей/с (проверка 20), а фан-аут на десять воркеров тянет 22 тысячи событий в секунду. То
есть на журнале это не «дорого», а «невозможно»: демон встал бы на сериализации.

> Дописано позже: журнал убран с шины целиком ([logging.md](logging.md)), и
> исключать его из доставки больше не нужно. Измерение от этого не меняется, но вывод из него теперь
> сильнее: цифры выше — одна из причин, по которым журналу на шине не место вовсе.

**Предел на число подписчиков не нужен.** При реальных частотах прикладных событий — единицы и
десятки в секунду — даже десять воркеров стоят десятые доли миллисекунды. Предел понадобился бы
плагину, публикующему тысячи событий в секунду, и это разговор про такого плагина, а не про
платформу.

## 23. Фронтовая шина не является узким местом, узкое место — разбор кадра

Оставался открытым вопрос, нужна ли подписка на уровне протокола или хватает тупой отдачи
всего: у `EventSource` и внутренней шины обратного давления нет, а поток отдаёт события плагинов
наравне с событиями ядра. Замер — путь кадра целиком, как его проходит браузер: `JSON.parse` тела
`data:` плюс синхронная рассылка подписчикам фронтовой шины
([apps/web/src/events/bus.ts](../apps/web/src/events/bus.ts)). Нагрузка — типовое событие плагина в
шесть полей с массивом, 200 000 кадров, подписчик читает тип кадра.

```
1 подписчик     138 мс  1 450 331 кадр/с      только JSON.parse   134 мс  1 487 885 кадр/с
3 подписчика    145 мс  1 378 343 кадр/с
10 подписчиков  148 мс  1 347 169 кадр/с
30 подписчиков  163 мс  1 226 282 кадр/с
```

**Рассылка бесплатна по сравнению с разбором.** Тридцать подписчиков вместо одного стоят 18% времени,
а сам `JSON.parse` — 97% всего пути. Фан-аута, который есть в демоне при доставке в воркеры (проверка
22), здесь нет: подписчики живут в том же realm, и копий кадра не делается.

**Подписка на уровне протокола не нужна.** Отсечь ненужное на сервере значило бы экономить те самые
проценты на рассылке, а не 97% на разборе, — и разбирать кадр всё равно пришлось бы, чтобы узнать его
тип. Тупая отдача всего остаётся в силе; вернуться к вопросу стоит, если появится плагин, публикующий
десятки тысяч событий в секунду, — тогда экономить надо будет на сериализации в демоне, а не на шине.

**Чего замер не покрывает:** ре-рендер React на кадр. Шина переваривает миллион кадров в секунду, но
подписчик, дёргающий состояние на каждом, упрётся в отрисовку задолго до этого. Это ограничение
подписчика, а не шины, и меряется оно вместе с вью, которая так делает.

## 24. Смена цветовой схемы стоит миллисекунды и не требует ре-рендера

Схема применяется записью восемнадцати CSS-переменных в корень документа
([packages/ui-kit/src/tokens/apply.ts](../packages/ui-kit/src/tokens/apply.ts)) — так тема доезжает и
до чужого компонента, перекрасить который платформа не может ([ui-kit.md](ui-kit.md)). Замер сделан в браузере на
живой оболочке: 12 переключений подряд, в каждом пишутся все переменные и тут же вынуждается пересчёт
раскладки (`getBoundingClientRect`), чтобы в цифру попала не только запись, но и работа движка.

```
оболочка как есть,   57 элементов   первое 1,6 мс, дальше 0,1–0,3 мс
плюс 2000 элементов, 2058 всего     первое 3,7 мс, дальше 2,7–3,2 мс
```

**Ре-рендера React нет вовсе.** Дерево не перестраивается: меняются значения переменных, на которые
ссылаются классы кита. Поэтому цена зависит от числа элементов на странице, а не от размера
компонентов или глубины дерева, и растёт линейно — полторы микросекунды на элемент.

**Переключение остаётся мгновенным на любой мыслимой странице.** Три миллисекунды на две тысячи
элементов — это меньше кадра; чтобы выйти за 16 мс, страница должна нести больше десяти тысяч
элементов, и тогда проблемой будет уже не смена темы.

**Первое переключение дороже последующих** — в нём движок пересчитывает стили впервые после загрузки.
Значения это имеет только для замера: пользователь платит эту разницу один раз.

## 25. Ре-рендер на кадр упирается не в шину, а в число панелей на странице

Долг из проверки 23: шина переваривает миллион кадров в секунду, но подписчик, дёргающий состояние
React на каждом кадре, упрётся в отрисовку куда раньше. Мерить это стало чем только со вью плагинов —
она так и делает: кадр жизненного цикла заменяет строку плагина, то есть ведёт к ре-рендеру.

Замер в браузере на живой вью: снимок берётся у демона и размножается, кадры (`core.plugin.lifecycle`
с настоящим статусом) публикуются в фронтовую шину, подписчик применяет кадр и обновляет состояние.
Раскладка вынуждается после каждого коммита (`getBoundingClientRect`), как в проверке 24. Три прогона
по 150 кадров после прогрева.

```
                     кадр за кадром, свой коммит      пачка в одной задаче
5 панелей, 3 вклада    0,5–0,7 мс   ~1700 коммитов/с   150 кадров: 0,2–0,4 мс шина + один коммит
20 панелей             1,8–2,6 мс   ~550 коммитов/с    150 кадров: 0,2–0,5 мс шина + один коммит
60 панелей             ~7,1 мс      ~140 коммитов/с    150 кадров: 0,4–1,4 мс шина + один коммит
```

**React сводит пачку сам.** Сто пятьдесят кадров, пришедших в одной задаче, стоят один коммит: цена
пачки — это время шины плюс одна отрисовка. Своего батчинга писать не нужно, и в этом срезе он не
написан.

**Опасен не поток, а кадры по одному.** Кадр из сети приходит своей задачей, сводить их React не
может, и тогда потолок — цена коммита: на настоящем наборе (пять плагинов) это больше тысячи кадров в
секунду, на шестидесяти панелях — сто сорок. События ядра редкие: переходы плагинов и смены набора
вкладов исчисляются единицами, а события плагинов вью вообще не касаются (`isPluginStreamEvent`).
Запас — три порядка.

**Цена линейна по числу панелей,** а не по числу кадров: 0,12 мс на панель. Вью, показывающая сотни
плагинов, будет стоить кадр отрисовки на каждый коммит — тогда и понадобится либо виртуализация
списка, либо сведение кадров в окно. Заводить это сейчас не под что.

**Замер сделан на dev-сборке** (Vite и React в режиме разработки) и без учёта отрисовки на экран:
продакшн-сборка быстрее, поэтому цифры — потолок сверху, а не оценка «как у пользователя».

## 26. `realpath` канонизирует регистр только в нативном варианте

Проверка под правило «один путь — один проект» ([sessions-and-projects.md](sessions-and-projects.md)):
можно ли положиться на один `realpath` вместо своей складки регистра.

```js
mkdirSync("/tmp/SovereignCase");
realpathSync.native("/tmp/sovereigncase"); // /private/tmp/SovereignCase
realpathSync("/tmp/sovereigncase"); // /private/tmp/sovereigncase
realpathSync.native("/tmp/SovereignCase/nope/deeper"); // бросает ENOENT
realpathSync.native("/etc/hosts/inside"); // бросает ENOTDIR
```

Три факта разом:

- **`realpathSync.native` возвращает написание, как оно лежит на диске**, а `realpathSync` — как
  спросили. Разные функции при одинаковом имени: JS-вариант идёт по компонентам через `lstat` и
  регистр не сверяет. Поэтому в коде стоит `.native`.
- **Одного `realpath` для правила всё равно не хватает.** У несуществующей папки написания на диске
  нет вовсе, а папка проекта не обязана существовать: проект, созданный до появления папки, и
  проект, созданный после, получили бы разные ключи на одну папку. Регистр и форму юникода
  приходится складывать самим, поверх `realpath`.
- **`realpath` на несуществующем пути бросает `ENOENT`, а на пути сквозь файл — `ENOTDIR`.**
  Значит нужен частичный разбор: подниматься `dirname` до существующего префикса и приписывать
  хвост обратно.

Заодно видно, что `/tmp` — симлинк на `/private/tmp`: «`/tmp/x` и `/private/tmp/x` — один проект»
это не теория, а первый тест-кейс.

**Проверено на macOS** (APFS, корневой том регистронезависим), Node v24.18.0, 2026-07-29. На
регистрозависимом томе складка регистра соврёт в другую сторону — это записано в бэклоге.

## 27. `fs.watch` не сообщает об отмонтировании тома под папкой

Проверка под выбор способа следить за доступностью папки проекта
([sessions-and-projects.md](sessions-and-projects.md)). Настоящий том, а не `mv` и не `chmod`: те
дают `ENOENT` и `EACCES`, но не воспроизводят случай, ради которого наблюдатель нужен.

```bash
hdiutil create -size 10m -fs APFS -volname SovereignProject /tmp/sovereign-project.dmg
hdiutil attach /tmp/sovereign-project.dmg && mkdir /Volumes/SovereignProject/proj
```

Наблюдатель на `/Volumes/SovereignProject/proj`, затем `detach`, затем `attach`:

```
запись файла до отмонтирования: rename:before.txt
detach:                         (ничего — ни события, ни error, ни close)
attach:                         (ничего)
запись файла после возврата:    rename:after.txt
```

**Наблюдатель молчит и об исчезновении тома, и о его возврате.** Он при этом не ломается — после
возврата тома снова отдаёт события, — он просто не про это: `fs.watch` рассказывает об изменениях
**внутри** папки, а исчезновение самой папки изменением внутри неё не является. Наблюдатель на
самой точке монтирования (`/Volumes/SovereignProject`) `rename` отдаёт, но папка проекта — это
обычно поддиректория, и чтобы поймать её исчезновение наблюдателем, пришлось бы следить за её
родителем, то есть за `/Volumes` или за `~/code` — чужой директорией, к проекту отношения не
имеющей.

Отсюда опрос по таймеру. Замер на живом демоне с интервалом 5 с: от `hdiutil detach` до
`core.projects.changed` в SSE-потоке — **0,2 с и 10,9 с в двух прогонах**, то есть один интервал
или два. Второй случай объясняется тем, что точка монтирования какое-то время после `detach` ещё
существует папкой и `stat` на ней успевает пройти. Возврат тома состояние восстанавливает сам:
наблюдатель не одноразовый.

**Проверено на macOS** (APFS-образ), Node v24.18.0, 2026-07-29. За `fs.watch` там стоит FSEvents; на
Linux и Windows поведение при отмонтировании надо мерить отдельно.

## 30. Статус авторизации стоит 0,4 мс, но побочно-эффектным быть вправе

`checkAuth` по всем 38 провайдерам с пустым окружением — **0,4 мс**, 47 спрошенных переменных
окружения и один спрошенный файл (`~/.config/gcloud/application_default_credentials.json`). Сети
нет. Для снимка провайдеров это бесплатно.

Важная оговорка: у Pi есть `ApiKeyAuth.check` — «необязательная проверка без побочных эффектов,
нужная там, где `resolve()` вправе исполнять команды», — и **не реализована она ни у одного из 38
встроенных провайдеров**. То есть `checkAuth` сегодня везде сводится к `resolve()`. Ходить за
статусом всё равно надо через `checkAuth`, а не через `getAuth`: `getAuth` вдобавок обновляет
OAuth-токен, то есть лезет в сеть и пишет в хранилище. Но обещания «статус ничего не исполняет»
контракт Pi не даёт, и провайдер с ключом из команды это обещание нарушит.

Заодно измерено: один `checkAuth` делает **два** `read()` в хранилище кредов. Хранилище обязано
быть дешёвым на чтение — файл читается один раз при создании стора, а не на каждый вызов.

Ambient-кред виден именно так, и источник у Pi уже подписан:

```
checkAuth("anthropic") при ANTHROPIC_API_KEY: {"source":"ANTHROPIC_API_KEY","type":"api_key"}
```

## 31. «Ambient-only» — свойство контракта Pi, а не встроенных провайдеров

Считалось, что провайдер без интерактивного входа отличается отсутствием `ApiKeyAuth.login`. Так и
есть по типам, но по факту:

```
apiKey.login есть у:              37 из 38
ambient-only (apiKey без login):  0
вообще без apiKey:                openai-codex (только oauth)

```

Следствий два. Первое: пустой список способов входа во вью означает не «ambient-only», а «войти

## 34. Фан-аут событий рантайма на `message_update` платится только при живой подписке

`message_update` публикуется на каждую дельту стриминга — это самый горячий путь, на который срез 11a
поставил вызов диспетчера хуков. Замер: 200 000 дельт на вызов диспетчера, `node --experimental-strip-types`,
Node 24.18, Apple Silicon.

```
подписчиков нет вовсе:                    0,03 мкс на дельту
подписчик есть, но на другое событие:     0,02 мкс на дельту
подписчик на message_update:              0,41 мкс на дельту
51 подписка, одна из них на это событие:  0,42 мкс на дельту
501 подписка, одна из них на это событие: 1,77 мкс на дельту
```

Вторая половина цены — переход границы воркера. Нагрузка `message_update` несёт **накопленное**
сообщение целиком, поэтому цена одной дельты растёт вместе с ответом модели (структурное
клонирование, 20 000 дельт на размер):

```
сообщение 40 символов:     2,6 мкс на дельту
сообщение 400 символов:    2,6 мкс на дельту
сообщение 4 000 символов:  3,0 мкс на дельту
сообщение 40 000 символов: 9,7 мкс на дельту
```

Выводы, из которых сделан код:

- **Без подписчика рантайм не платит почти ничего** — 30 нс на дельту, то есть 3 мкс на сотню дельт.
  Проверять `subscribed` перед наблюдением поэтому незачем: нагрузка наблюдательного события — это
  само событие Pi, собирать её не нужно, и экономить проверкой нечего. У перезаписывающих событий
  проверка есть, и там она экономит настоящую работу — сбор нагрузки без `signal` и слияние поправок.
- **Цена растёт с числом подписок, но не с их числом на это событие:** фильтр обходит весь список на
  каждое событие. До полусотни подписок это не видно (0,42 мкс против 0,41), на пятистах — вчетверо
  дороже. Индекс по имени события заводить рано: полтысячи подписок означали бы десятки плагинов, и
  до них есть что делать. Но именно здесь он и понадобится.
- **Дорогая часть — не наш код, а клонирование накопленного сообщения.** Ответ на 40 000 символов
  стоит 10 мкс на дельту; при сотне дельт в секунду это миллисекунда в секунду, то есть терпимо. Своей
  нагрузки для этого события мы не изобретаем: она контракт Pi (docs/hooks.md).

Не измерено: цена подписки на `message_update` у плагина, который в обработчике делает работу.
Наблюдателя не ждут, но воркер у плагина один, и занятый обработчик задержит его собственные вызовы.

## 35. Подписки плагинов доезжают до агента, и сверять их надо по изменению набора вкладов

Проверено живьём, на собранном демоне с двойником модели и плагином, объявляющим инструмент и девять
подписок ([runbook.md](runbook.md), «Хуки и инструменты плагина живьём»). Подтвердилось всё
перечисленное в [hooks.md](hooks.md):

```
инструмент:         имя стоит в записи tools-change рядом с bash/read/write/edit,
                    модель его зовёт, результат приезжает из воркера записью tool-result
цепочка перезаписи: второе звено видит вход, изменённый первым (first: true в журнале плагина)
отказ на старте:    409 со списком из двух отказов, у каждого автор-вклад; сессии нет вовсе
таймаут advisory:   outcome "skipped", турн доигрывает, дольше ровно на величину таймаута
таймаут critical:   outcome "aborted-the-turn", турн падает с причиной, называющей автора
и то и другое:      событием core.hook.timed-out в потоке и записью warn в журнале
наблюдатель:        зависший на turn_end не задерживает возврат в idle
исключение:         бросающий обработчик оставляет турн живым, ошибка уходит в журнал ядра
трата турна:        turn_finished несёт usage типом рантайма — плагин читает totalTokens
```

**Живьём нашлась ошибка проводки, которой не было ни в одном тесте.** Сверка подписок стояла в конце
обхода плагинов, а вклады попадают в реестр между `activate` и `running` — то есть **позже**, чем
возвращается применение. Подписки регистрировались только если после активации случалось второе
приведение (например, человек создавал проект), а на чистом старте демона не регистрировались вовсе —
и ни один хук не работал, молча. Сверка перенесена туда, где набор вкладов **изменился**, — в
публикатор смены вкладов, тот же, которым область плагинов сообщает об этом остальным. Регрессия
закрыта тестом на настоящем супервизоре с настоящей фикстурой; на прежней проводке он падает.

Мораль общая: **точка «после того как я попросил» и точка «когда это случилось» — разные точки**, и
для асинхронного применения совпадать они не обязаны.

## 36. Конвейер браузерного кода плагина работает целиком, и ломается он на сборке

Проверено живьём на демоне из исходников с плагином `browsered` в директории данных: точка входа
`src/browser.tsx`, `*.module.css` рядом, импорты `react`, `@sovereign/ui-kit` и стилей
([runbook.md](runbook.md), «Браузерная часть плагина живьём»).

```
жизненный цикл:   discovered → building → starting → running, записями plugin lifecycle
сборка:           7 мс от building до starting, размер бандла 2537 байт с преамбулой интеропа
статус:           browser.revision, browser.entry и browser.styles в GET /api/plugins
ассет с сессией:  200, content-type text/javascript; charset=utf-8,
                  cache-control private, max-age=31536000, immutable
ассет без сессии: 401
протухшая:        404 с текстом «there is no revision … any more, reload the page»
имя класса:       .data_browsered_badge_badge — ключ плагина в имени, как задумано
правка стиля:     новая ревизия, прежняя ещё отдаётся 200
перезапуск:       ревизия та же (u9A5buRpiQKu), прежняя ревизия уже 404 — память демона
```

**React в бандле — тот же объект, что у хоста.** Проверено на бандле, скачанном по HTTP с живого
демона: `useState` из плагина и `useState` хоста — одна и та же функция, а не две копии одного
имени. Это то самое ограничение, ради которого сборку вообще забрали в демон
([ui-extension-model.md](ui-extension-model.md)).

**Живьём нашлась ошибка, которой не было ни в одном тесте.** Подмена пути `*.module.css` шла без
проверки существования файла, поэтому отсутствующий стиль доезжал до `onLoad` esbuild и превращался
в `ENOENT` со стеком по нашим модулям и по внутренностям esbuild. Этот текст едет в интерфейс
причиной отказа плагина, то есть автор плагина получил бы пятнадцать строк чужих кадров вместо
строки со своим импортом. Тесты сборки не ловили этого, потому что проверяли **несуществующий
`.tsx`** — его перехватывает штатный резолвер esbuild, а до нашего плагина он не доходит. Починка:
несуществующий файл отдаётся обратно esbuild, и тот пишет обычное «Could not resolve» с местом
импорта. Регрессия закрыта проверкой, которая падает на прежнем коде.

Вторым тем же прогоном нашлось, что в dev-режиме ассеты плагина не доезжали до страницы вовсе: прокси
Vite знал только про `/api`. Тот же случай, что и с переездом маршрутов плагина под `/api`
(«Маршруты и хранилище плагина живьём» в runbook) — dev-режим это второй путь, и он обязан быть в
проверке, а не подразумеваться.

Мораль: **проверка ошибки на удобной ошибке ничего не проверяет.** Отсутствующий `.tsx` и
отсутствующий `.module.css` не доходили даже до одного и того же кода.

## 37. Демон бандлится в один файл целиком, наружу остаётся только esbuild

Проверено сборкой и запуском до всякого кода среза 16: вопрос был не «красиво ли это», а поедет ли
`apps/daemon/src/main.ts` через esbuild одним файлом, если наружу оставить только сам `esbuild`.
Повод для сомнений был конкретный — `ws` внутри Pi объявляет опциональные нативные аддоны
(`bufferutil`, `utf-8-validate`), а такие зависимости обычно и ломают бандл.

```
сборка:        bundle, platform node, format esm, target node24, external: ["esbuild"]
результат:     7,0 МБ одним файлом, 354 мс, предупреждений ноль
запуск:        демон поднялся, /api/health отвечает, защищённый маршрут без cookie даёт 401
плагины:       три фикстуры прошли discovered → building → starting → running
воркер:        бутстрап, собранный вторым entry point (9,0 КБ), поднимает воркеры плагинов
сборка плагина: браузерный бандл собран внешним esbuild, ассет отдан 200 text/javascript
```

Опциональные аддоны `ws` бандл не сломали: esbuild оставил их обычными `require`, до которых
исполнение не доходит. Ничего сверх `esbuild` во внешние выносить не пришлось — набор
рантайм-зависимостей директории данных состоит из одной записи ([toolchain.md](toolchain.md)).

**Отдельно проверен отказ, и он оказался не тем, который нужен.** Запуск бандла без `esbuild` рядом
падает целиком — `ERR_MODULE_NOT_FOUND` на старте процесса, код возврата 1:

```
Error [ERR_MODULE_NOT_FOUND]: Cannot find package 'esbuild' imported from …/sovereign.js
```

Причина в том, что `plugin-browser-build.ts` импортирует `esbuild` статически на верхнем уровне.
Пока сборщик лежал в `node_modules` рядом с исходниками, это было бесплатно; в артефакте он приезжает
в директорию данных **после** старта процесса, и статический импорт превращает «браузерную часть
плагина не собрать» в «продукт не запускается». Отсюда требование к срезу: импорт сборщика —
динамический и по пути из директории данных, а его отсутствие обязано быть отказом плагина, а не
отказом демона.

Мораль та же, что у проверки 36: **проверять надо и удачный путь, и отказ.** Удачный путь работал с
первого раза, а нашлась ровно та ошибка, из-за которой продукт не запустился бы у человека без сети.

**Без `npm` в `PATH` продукт остаётся живым.** Отдельный прогон с `env -i` и `PATH` из одного `node`:

```
журнал:     error «the runtime dependencies of the artifact are not installed»,
            reason «npm was not found in PATH»
демон:      жив, GET / → 200, /api/health отвечает
плагин:     failed, reason «the browser bundler is not available: Cannot find module 'esbuild'»
```

Это и есть цена решения «работа без сети не обязательна» ([toolchain.md](toolchain.md)): отказ
локализован в плагине с браузерной частью и назван, а не превращён в неработающий продукт. До
динамического импорта тот же случай давал `ERR_MODULE_NOT_FOUND` и код возврата 1 (проверка 37).

**Dev-режим не изменился ни в чём.** Тем же прогоном на демоне из исходников: `GET /` отвечает
json-отказом `404` (интерфейс отдаёт Vite), каталог `runtime/` не заводится вовсе, встроенные
`starter` и `subagents` читаются из репозитория.

## 39. Node не стирает типы под `node_modules`, а в разработке это не видно

Проверено до всякого кода среза 16b: пакет с точкой входа `./src/index.ts`, положенный настоящими
файлами в `node_modules`, и запуск обычным `node --experimental-transform-types`.

```
Error [ERR_UNSUPPORTED_NODE_MODULES_TYPE_STRIPPING]: Stripping types is currently unsupported
for files under node_modules, for "file:///…/node_modules/@fake/lib/src/index.ts"
```

**В репозитории этого отказа нет, и не по случайности.** pnpm кладёт в `plugins/starter/node_modules/`
симлинк на `packages/sdk`, Node разрешает симлинки до настоящего пути, и файл оказывается **вне**
`node_modules`. Распакованный плагин симлинков не содержит: вшей мы SDK исходниками, встроенные
плагины не стартовали бы у пользователя, продолжая работать у нас.

Отсюда решение среза: SDK едет плагину **собранным** ([toolchain.md](toolchain.md)). Проверено тем же
способом — SDK, собранный esbuild-ом в ESM со вшитым `zod`, положен настоящими файлами в
`node_modules` фикстуры, и настоящий воркер `starter` из репозитория на нём загружается и отдаёт
свой `activate`.

## 41. Отказ провайдера приезжает строкой, а кода ответа у него нет

Проверялось ради маршрутизации: чтобы перейти на следующий ключ, надо знать, кто виноват
([model-routing.md](model-routing.md)).

- **`onResponse` на провалившемся запросе не зовётся вовсе.** В `api/anthropic-messages.js` он стоит
  **после** `await retryProviderRequest(...)`, а клиент бросает исключение раньше: на `429` и `401`
  до него не доходит. То же в `api/openai-responses.js`.
- **Наружу отказ уходит текстом.** `catch` в том же файле кладёт `error.message` в
  `AssistantMessage.errorMessage` и пушит событие `error`; ни статуса, ни заголовков в событии нет.
- **Клиенты Anthropic и OpenAI начинают сообщение кодом ответа** — `429 {"type":"error",…}`. Это
  единственное, на что можно опереться, поэтому код ищется в начале строки, а не по всей.
- **`StreamOptions.apiKey` закорачивает разрешение авторизации целиком** (`auth/resolve.js`:
  `if (overrides?.apiKey !== undefined && provider.auth.apiKey)` — сохранённый кред не читается).
  Подмена ключа на запрос — объявленный контракт Pi, а не обход.
- **`ModelsStreamTransforms.transformHeaders` применяется последним** над собранными заголовками
  (`models.js`, `applyAuth`): поставленные им заголовки перебивают всё, что собрал рантайм.

Проверено запуском на настоящем `AgentHarness`: турн, чей первый запрос отказал с `429`, доигрывает
вторым ключом и доходит до `done`; отказ после первой дельты текста не переигрывается
(`packages/agent-runtime-pi/src/agent-session.test.ts`).

## Чего эти проверки не покрывают

- Поведение при тысячах циклов `terminate`/`spawn` — утечки на длинной дистанции не измерялись.
- Работу нативных аддонов в зависимостях плагинов.
- Поведение SSE за настоящим обратным прокси: проверен только прокси Vite из режима разработки.
- Работу собранного бандла плагина в настоящей странице: проверка 36 сделана в Node на бандле,
