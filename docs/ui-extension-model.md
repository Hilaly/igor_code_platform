# Модель расширения интерфейса

Что платформа обязана предоставить, чтобы плагин мог добавлять элементы в интерфейс и
переопределять существующие компоненты. Устройство кита и оболочки — в [ui-kit.md](ui-kit.md),
контракт плагина — в [plugins.md](plugins.md).

Отправной точкой был подробный набросок модели, написанный агентом в другом репозитории. Он не
является нормативным: из него взято направление, а трёхуровневая модель исполнения, рантайм-контракты
на схемах, язык условий видимости и обвязка изоляции отвергнуты — см. «Почему так».

## Требование

В поставке — базовый интерфейс. Плагин может:

- добавить элемент в существующий интерфейс;
- переопределить существующий компонент;
- занять целую страницу своим приложением;
- опубликовать внутри своего интерфейса места, которые расширит другой плагин.

Безопасность браузерного слоя в задачи модели не входит: включённый плагин доверен, и границей
является включение ([plugins.md](plugins.md)).

## Один ярус рендеринга

**Браузерный UI плагина исполняется одним способом: доверенным компонентом в realm хоста.** Плагин
владеет содержимым выданного ему контейнера — любой DOM, Canvas, WebGL, свои библиотеки. Хост владеет
пространством, размещением и жизненным циклом.

**Изоляции браузерного кода плагина платформа не предоставляет и не имитирует.** Плагин находится в
доверенной базе браузерного приложения; единственная граница — включён он или нет.

Встроить внешнюю страницу по-прежнему можно: плагин ставит `<iframe>` внутри своего контейнера,
потому что владеет своим DOM. Платформенного механизма для этого не требуется.

## Три сущности

| Сущность      | Что это                                                                                                     |
| ------------- | ----------------------------------------------------------------------------------------------------------- |
| **Место**     | публичная точка расширения: id, владелец, тип контекста, кардинальность, заменяемость, встроенный провайдер |
| **Вклад**     | заявка плагина на место: id, ссылка на компонент или команду, группа и порядок                              |
| **Экземпляр** | живое размещение, созданное хостом: своё состояние, свой жизненный цикл                                     |

Кардинальность места — одно из: одиночное (может быть заменяемым), коллекция (упорядоченный
список), вкладки (несколько открытых экземпляров), действие или значок (без состояния размещения).

Один компонент может быть размещён в нескольких местах и иметь несколько независимых экземпляров.

**Места однородны.** Место, опубликованное ядром, и место, опубликованное плагином, устроены
одинаково. Поэтому плагин может расширять интерфейс другого плагина, и для этого не нужно ни
отдельной подсистемы, ни объявления зависимостей: достаточно того, что владелец места объявил его
публично. Ядро привилегий в этой модели не получает.

## Оболочка

Оболочка принадлежит ядру и **не заменяется**: она состоит из трёх областей — левая панель (верх,
основная часть, низ), центральная страница, правая панель с вкладками. Заменяемо всё, что внутри неё.

Вкладок ядра у правой панели нет: внешний вид и диагностика переехали на страницу настроек
(`/settings`). Полоса вкладок и контейнер остаются — это место, куда плагины приносят свои вкладки
(механизм — срез 12); до тех пор панель показывает заглушку.

Хост владеет: границами и размерами областей, полосой вкладок, фокусом и переходами между
областями, маршрутизацией, сохранением раскладки, заглушками на случай отсутствия или ошибки плагина.

Плагин владеет содержимым выданного ему контейнера.

## Добавление и замена

- Вклад по умолчанию **добавляется** рядом с остальными.
- **Заменить** можно только место, объявленное заменяемым. У такого места обязателен встроенный
  провайдер: он поведение по умолчанию и он же — то, к чему хост возвращается, если выбранный
  провайдер выключен, не загрузился или упал при отрисовке. Вью базовой поставки — настройки,
  плагины, проекты, чаты с агентами, модели и провайдеры — как раз такие места: встроенный провайдер
  у них ядро ([architecture.md](architecture.md)).
- Замена никогда не следует из совпадения маршрута, id или порядка загрузки.
- Если провайдеров несколько, побеждает **более частный источник** плагина: папка проекта перекрывает
  директорию данных, та — встроенный ([plugins.md](plugins.md)). Отдельного выбора провайдера
  пользователем нет: он выбирает, какой плагин включён и откуда взят.
- Если источник равный, **не применяется ни один** из конфликтующих вкладов: место показывает
  встроенного провайдера, публикуется диагностика с перечислением конфликтующих вкладов, лечится
  выключением одного из них. Правило общее для всех видов вкладов: так же разрешается коллизия имён
  инструментов, схем и каталогов локали.
- Порядок в коллекции детерминирован: группа, затем порядок, затем id. Появление нового плагина не
  переставляет существующие элементы.

## Места базовой поставки

Имена мест — публичный контракт ([public-contract.md](public-contract.md)). Форма вклада описана в
[plugins.md](plugins.md), здесь — сам набор и то, что каждое место показывает.

| Место                      | Кардинальность | Заменяемо | Контекст (`subject`)                 |
| -------------------------- | -------------- | --------- | ------------------------------------ |
| `core.session.chat`        | одиночное      | да        | `sessionId`                          |
| `core.session.new`         | одиночное      | да        | —                                    |
| `core.settings.projects`   | одиночное      | да        | `view: list \| detail`, `projectId`  |
| `core.settings.providers`  | одиночное      | да        | `view: list \| detail`, `providerId` |
| `core.settings.plugins`    | одиночное      | да        | `view: list \| detail`, `pluginKey`  |
| `core.sidebar.sections`    | коллекция      | нет       | `page` — вид открытой страницы       |
| `core.view.header.actions` | действие       | нет       | `page` — вид открытой страницы       |

Контекст места — это **две разные вещи в одном объекте**, и разделены они намеренно:

```ts
type PlaceContext = {
  /** В контексте какого проекта место рисуется. У оконного места его нет. */
  project?: string;
  /** Что место показывает: сессия, провайдер, ключ плагина, вид страницы. */
  subject?: Readonly<Record<string, string>>;
};
```

По `project` решается, вправе ли вклад из папки проекта занять место; `subject` — предмет отрисовки.
Вью настроек проектов показывает проект, но рисуется **вне** контекста проекта: слив этих двух вещей
в одно поле отдал бы оконное вью плагину из папки открытого проекта.

Контекст нарочно не повторяет пропсы вью базовой поставки. Пропсы — внутреннее дело `apps/web`
(у вью провайдеров их дюжина, почти все — колбэки), и объявить их публичными значило бы заморозить
внутренности приложения. Плагин-провайдер добирает данные публичными сервисами SDK.

**Встроенный провайдер места ядра — узел самого хоста, а не имя экспорта.** Поле `builtIn` есть у
объявления **плагина**, которому иначе нечем указать на своё вью; ядро своё вью пишет рядом и в
бандле по имени его не ищет.

**Условия видимости у вклада нет.** Компонент решает это сам, вернув `null`: в том же realm предикат
не нужен, а декларативный через границу воркера не проезжает («Почему так»).

## Разрешение провайдера

Считается **в браузере**, чистой функцией из `@sovereign/protocol`. Порядок всегда один: сначала
отфильтровать непроектные вклады и вклады текущего проекта, затем сгруппировать их по
`kind:id`, в каждой группе оставить единственного лидера с максимальным рангом источника и только
после этого отобрать вклады с нужным `placeId`. Равный верхний ранг означает спор identity: такая
группа не применяется целиком.

Вклад из `project:<id>` применим только там, где `context.project` равен этому `id`, а у оконного
места `project` нет вовсе. Если после разрешения identity несколько разных component ids претендуют
на одно одиночное место с одинаковым максимальным рангом, не применяется ни один: место показывает
встроенного провайдера и публикует диагностику.

Выключенные вклады до этого шага не доходят: в действующем наборе снимка их нет.

У коллекции и полосы действий спора не бывает — вклады складываются в ряд. Порядок: группа, затем
`order`, затем идентификатор вклада. Ранг источника в порядке не участвует: вклад из папки проекта не
обязан стоять первым только потому, что он специфичнее.

## Загрузчик бандла в браузере

Место знает про вклад из снимка, а про код — ничего: код лежит в бандле по адресу с ревизией.
Загрузчик между ними устроен так:

- **Ключ кеша — ключ плагина вместе с ревизией.** Смена ревизии сама по себе означает новый
  `import()`, поэтому правка плагина доезжает до открытой страницы без её перезагрузки.
- **Стили ждут вместе с модулем.** Есть `styles` — сначала вставляется `<link>` и ожидается его
  `load`, иначе первый кадр чужого компонента едет без оформления.
- **Лист стилей прежней ревизии снимается ровно тогда, когда своя загрузилась.** Раньше — место
  мигнёт неоформленным; никогда — два листа одного плагина одинаково специфичны, и побеждал бы
  порядок вставки.
- **Завершение применяется только к текущей попытке загрузки.** Каждый запуск имеет
  свой token: сравнивать только revision нельзя, потому что тот же content hash может вернуться после
  исчезновения плагина. Опоздавший `load` или `error` прежней попытки снимает только свой
  `<link>` и не начинает `import()`; кеш удаляет прежние листы только из собственного набора, не по
  общему DOM-селектору.
- **Ошибка stylesheet или последующего `import()` снимает `<link>` этой ревизии** до того, как
  кеш опубликует отказ. Незагрузившийся или неприменимый CSS в документе не остаётся.
- **Отказ кешируется вместе с успехами** и сбрасывается приходом новой ревизии: иначе провал сети
  повторялся бы на каждой отрисовке.
- **Плагин без бандла — это не отказ, а ожидание.** Между правкой исходников и готовой сборкой
  плагин какое-то время в состоянии `building` и `browser` у него нет; место на это время держит
  встроенного провайдера молча. Провалившаяся сборка видна во вью плагинов состоянием самого плагина.
- **Пока бандл едет, в месте стоит встроенный провайдер,** а не пустота: иначе место мигало бы на
  каждой пересборке плагина.

`PlaceRuntimeProvider` владеет своим кешем и при размонтировании вызывает `dispose()`: кеш забывает
загрузки и подписчиков и снимает только созданные им `<link>`. Любой опоздавший callback такого
кеша после этого не публикует результат и не трогает стили нового provider mount.

Диагностика (спор, пропавший экспорт, провал загрузки, падение отрисовки) публикуется **один раз на
текст**: снимок плагинов приезжает на любое изменение любого плагина, а причина остаётся той же.

Экземпляр живёт в границе ошибки: упавший компонент не размонтирует соседей по коллекции и не роняет
оболочку, а заменяемое место возвращается к встроенному провайдеру. Граница заводится заново на
каждую ревизию — пересобранный плагин обязан получить попытку заново.

## Переключение вкладов

Любой вклад включается и выключается отдельно от плагина — это правило всей платформы, а не только
интерфейса ([plugins.md](plugins.md)). Здесь важны две его стороны:

- выключенный вклад не участвует в разрешении провайдеров и в сборке динамических списков; правило
  источников применяется к тому, что осталось, второго правила перекрытия не появляется;
- **вью базовой поставки не выключаются, а заменяются,** и не как исключение, а потому что они живут
  в ядре ([architecture.md](architecture.md)): у вклада в ядре нет переключателя. Переключается вклад
  плагина, который вью переопределяет, и его выключение возвращает встроенное. Если переопределение
  оказалось работающим, но негодным, восстановление идёт правкой `preferences.json`.

## Страницы и маршруты

- Маршруты ядра стабильны; плагин их не захватывает.
- Маршруты ядра: `/` (заглушка), `/settings/projects`, `/settings/projects/:projectId`,
  `/settings/providers`, `/settings/providers/:providerId`, `/settings/plugins`
  (страница входа и моделей), `/sessions/:sessionId`, `/settings/:section` (страница настроек),
  `/p/<pluginId>/<pageId>/*` (неймспейс плагина). Список разделов настроек закрыт: раздел, которого
  ядро не знает, — неизвестная страница, а не запрос.
- Корень `/p/` принадлежит страницам целиком. Именно поэтому HTTP-маршруты плагина живут под `/api/p/`
  ([web-api.md](web-api.md)): два вида адресов с одним префиксом различить по форме нельзя, а
  разрешать спор порядком загрузки — значит сделать поведение случайным.
- Плагину выдаётся неймспейс `/p/<pluginId>/<pageId>/*`. Часть пути после базы принадлежит плагину:
  он строит внутри свою навигацию, получая от хоста базовый путь, относительный путь, параметры и
  фасад навигации.
- Заменяемая страница ядра остаётся на своём маршруте: маршрут отображает заменяемое место, а
  провайдер выбирается по общим правилам. Маршрут при замене не перерегистрируется.
- Плагин выключен, а его страница открыта — показывается заглушка с возвратом, а не общий «не
  найдено». Включили обратно — страница восстанавливается на том же URL.

## Команды

Действие — отдельная сущность от места, где нарисована кнопка. У команды есть id с неймспейсом,
метаданные для отображения, условие доступности и обработчик — в браузере или в воркере плагина.

Одна и та же команда вызывается из кнопки, контекстного меню, палитры команд, горячей клавиши или
другим плагином. Меню и панели инструментов — это места с кардинальностью «действие», а не
привязка к элементам DOM.

## Регистрация и жизненный цикл

- Плагин при старте объявляет свои места, компоненты, страницы, вклады и команды. Хост проставляет
  неймспейс, проверяет набор целиком и публикует одним снимком.
- Метаданные вклада (заголовок, значок, размещение) доступны до загрузки его кода — поэтому
  оболочка рисует элемент, не загружая тяжёлый бандл, и по ним же проверяются коллизии.
- Код активируется лениво: при открытии страницы, при первом показе компонента, при первом вызове
  команды.
- Выключение и перезагрузка снимают живые рендереры, но сохраняют размещения, выбранных провайдеров
  и небольшое состояние — чтобы после включения интерфейс вернулся в то же состояние.
- Ошибка одного экземпляра не размонтирует соседние и не роняет оболочку.
- Вклад, адресованный ещё не появившемуся месту, не является ошибкой: он ждёт. Место исчезло —
  вклад снова ждёт, не теряя сохранённого размещения.
- Отказ в регистрации виден в интерфейсе управления плагинами: вклад, молча выброшенный при загрузке,
  выглядит для пользователя как сломанный плагин без объяснений.

## Браузерные ассеты

**Браузерные исходники плагина собирает демон.** Автор плагина шага сборки не имеет: он кладёт папку
с исходниками, всё остальное делает платформа.

- **Результат отдаётся по URL, содержащему ревизию** сборки. Ассеты ревизии неизменяемы и кешируются
  браузером бессрочно; новая правка плагина — это новая ревизия и новый URL, а не сброс кеша.
- **Singleton-зависимости хоста в бандл плагина не собираются.** `react`, `react-dom`,
  `@sovereign/ui-kit` и остальные общие библиотеки помечаются внешними и резолвятся в экземпляр
  хоста. Внутренности `apps/web` плагину недоступны — он получает публичные сервисы SDK.
- **Для кита это не предпочтение, а требование.** Его стили — CSS Modules с хешированными именами
  классов ([ui-kit.md](ui-kit.md)): плагин, собравший свою копию кита, получит классы с другими
  хешами и ни одного подходящего правила в загруженных стилях, то есть компоненты без оформления.
- **Сборщик демона обязан уметь CSS Modules.** Иначе автор плагина не может писать стили тем же
  способом, каким они написаны в ките, и у нашего кода появляется дорога, которой нет у него.
- **Перезагрузка плагина — это новая ревизия плюс подмена снимка реестра вкладов,** без перезагрузки
  страницы.
- **Ошибка сборки — событие жизненного цикла плагина,** видимое в интерфейсе, а не исключение в
  журнале: для пользователя это единственный признак, что плагин не заработал.

### Что делает сборка

Сборщик — esbuild, прямая зависимость демона ([toolchain.md](toolchain.md)). Точка входа одна — путь
из `sovereign.browser` ([plugins.md](plugins.md)); плагин без этого поля не собирается вовсе.

Выход **плоский**: `browser.js`, `browser.css` и карты кода к ним, и ничего больше. Кода-сплиттинга
нет, мелкие ассеты (`svg`, `png`, `woff2`) инлайнятся в `data:`. Плоскость — не побочность, а условие
адресации: в адресе ассета один сегмент под имя файла.

Собранного кода на диске не появляется: результат живёт в памяти демона
([data-directory.md](data-directory.md)).

Локальные имена CSS-классов **не минифицируются**, хотя всё остальное минифицируется: на эти имена
смотрит человек, отлаживающий чужой интерфейс в инспекторе.

Типы esbuild не проверяет и проверять не будет — это трансформация, а не компилятор. Плагин с
ошибкой типов соберётся и упадёт в браузере; проверка типов — дело автора плагина.

### Когда собирается и сколько ревизий живёт

Сборка идёт **при старте плагина и до подъёма воркера**, отдельным состоянием жизненного цикла
`building` ([plugins.md](plugins.md)): `discovered → [installing] → building → starting → running`.
Плагин без `sovereign.browser` через это состояние не проходит вовсе.

Цена такого порядка названа вслух: **сломанный `*.module.css` уносит плагин целиком** — вместе с его
инструментами и хуками, которые к интерфейсу отношения не имеют.

Ревизий одного плагина демон помнит **две** — текущую и предыдущую. Больше одной потому, что старый
ES-модуль из кеша браузера выгрузить нельзя: страница, открытая до перезагрузки плагина, продолжает
жить на прежней ревизии и вправе дозапросить её карту кода. Не больше двух потому, что между двумя
перезагрузками плагина страница либо обновилась, либо ей всё равно пора. Перезагрузка плагина
предыдущую ревизию сохраняет; выключение и исчезновение плагина с диска забывают обе.

### Модули хоста

Общие библиотеки не попадают в бандл: вместо каждой из них сборка подставляет заглушку, читающую
глобальный реестр `globalThis.__sovereignHostModules__`. Реестр заполняет веб-приложение до первого
`import()` плагина, ключ и состав — публичный контракт ([public-contract.md](public-contract.md)).

Список внешних: `react`, `react-dom`, `react-dom/client`, `react/jsx-runtime`,
`react/jsx-dev-runtime`, `@sovereign/ui-kit`.

Подмена ловит спецификатор от любого импортёра, поэтому чужой React, приехавший транзитивной
зависимостью плагина, перехватывается тоже. Модуля нет в реестре — заглушка бросает ошибку с именем
модуля, а не отдаёт `undefined` вглубь чужого кода.

Заполняется реестр в точке входа веб-приложения, до первого рендера: заглушка читает его в момент
загрузки модуля плагина, поэтому «до» здесь буквальное. Полноту реестра сторожит проверка, идущая от
того же списка спецификаторов, — пропущенный модуль иначе виден только в браузере у пользователя.
`react/jsx-dev-runtime` указывает на боевой рантайм: браузерный код плагина собирается в продовом
режиме, и отдельный dev-рантайм был бы обещанием, которого сборка не выполняет.

### Контракт CSS Modules

У хоста стили собирает Vite, у плагина — esbuild. Это разный код в разных процессах, и «свести их в
один» нельзя. Сводится подмножество, которое обе стороны обрабатывают одинаково; за расхождением
следят тесты с обеих сторон.

| Правило                                                      | Почему                                                                                                                    |
| ------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------- |
| Импорт только default: `import styles from "./x.module.css"` | ровно это объявляет `vite/client`, на который опирается кит; имя с дефисом именованным экспортом быть не может в принципе |
| Имена классов — как написаны, camelCase не добавляется       | проверено на обоих конвейерах; правило фиксирует совпадение, чтобы смена умолчания упала тестом                           |
| `composes` и `:global` разрешены                             | поддерживают оба; порядок токенов в `composes` различается, но на каскад не влияет                                        |
| На форму имени класса опираться нельзя                       | у хоста `_<локальное>_<хеш>_<строка>`, у плагина `<ключ плагина>_<файл>_<локальное>`                                      |
| Уникальность имён между плагинами обеспечивает платформа     | у esbuild в имени класса нет хеша вовсе — см. «Почему так»                                                                |
| CSS плагина — отдельный файл, подключает его хост            | ни Vite, ни esbuild не вшивают ссылку на стили в JS                                                                       |

Префикс класса — base64url-кодировка **всего** ключа плагина: заменить каждый «небезопасный» символ
одним дефисом нельзя — `project:foo-bar:widget` и `project:foo:bar-widget` тогда сошлись бы в одно
имя.

## UI-кит

Примитивы интерфейса живут в `packages/ui-kit` — публичном пакете, отдельном от `sdk`. Наша оболочка
и встроенные компоненты собираются только из него, поэтому плагин может собрать то же самое из тех же
деталей ([ui-kit.md](ui-kit.md)).

## Обновления и состояние

Изменения реестра вкладов и жизненного цикла плагинов приходят на фронтенд единственным
SSE-соединением и раздаются внутренней шиной ([web-api.md](web-api.md)). Поллинга нет.

Состояние делится на три уровня:

| Уровень             | Что в нём                                                    | Где живёт                             |
| ------------------- | ------------------------------------------------------------ | ------------------------------------- |
| Раскладка хоста     | размеры панелей, открытые вкладки, выбранные провайдеры мест | локально в браузере                   |
| Небольшое состояние | выделение, раскрытые секции, позиция прокрутки               | в экземпляре до unmount/reload        |
| Доменные данные     | всё, что плагин считает своими данными                       | хранилище плагина в директории данных |

## Почему так

### Один ярус рендеринга вместо трёх

Набросок предлагал три уровня исполнения браузерного кода плагина: декларативные описания,
рендерящиеся хостом; доверенный компонент в realm хоста; изолированный iframe — вместе с отдельным
credential-free origin, sandbox-политиками, проверкой origin, nonce-рукопожатием, двусторонним RPC со
схемами и будущей моделью разрешений. Этот набор границ имеет смысл там, откуда он взят: расширения
ставятся из публичного каталога, исполняются в другом процессе и по умолчанию недоверенные. У нас
модель доверия другая, и владелец продукта сформулировал прямо: безопасность браузерного слоя не
является задачей этой модели.

**Iframe как уровень изоляции.** Отвергнуто не из-за трудоёмкости, а из-за несогласованности:
песочница в браузере защищала бы от кода, которому мы этой же галочкой отдали диск, сеть и креды.
Вместе с ним отпадают отдельный origin со своим CSP, sandbox-политики, проверка origin и nonce,
двусторонний RPC, caller principal и модель разрешений — самая опасная часть кода в проекте, не
закрывающая ни одной реальной угрозы.

**Декларативный уровень (UI как сериализуемое описание, рендерит хост).** Существует ради безопасного
исполнения недоверенного UI. При бинарном доверии это второй, более слабый способ делать то же, что
делает компонент, плюс собственный язык виджетов, который надо спроектировать, версионировать и
документировать — и который будет отставать от возможностей компонента всегда.

**Рантайм-контракты на JSON Schema** (`contractId`, content hash, согласование мажора и минора).
Валидация контракта в рантайме нужна, когда контракт пересекает границу процесса или realm. У
единственного same-realm яруса контракт — это типы в SDK, и проверяет их компилятор.

**Статический индекс вкладов с хешем содержимого.** Обоснование в наброске — «код не должен протащить
скрытую метадату при активации» — это модель угроз каталога расширений. Нужное свойство (показать
элемент до загрузки тяжёлого кода) даёт обычное поле в манифесте.

**`when` как декларативный язык выражений над ключами контекста.** Мини-язык с парсером и
вычислителем нужен, когда код расширения живёт в другом процессе. В том же realm условие видимости —
обычный предикат.

**Отдельная идентичность для плагинов из рабочей директории.** В наброске это отдельная подсистема
из-за неоднозначности одинаковых id в разных областях. У нас перекрытие разрешается **до**
регистрации: три источника, побеждает более частный.

**Учёт ссылок на «поколения» браузерного кода, пометка провайдера нездоровым, окна удержания.**
Ответы на масштаб с чужими плагинами. Достаточно: упавший провайдер заменяется встроенным и даёт
диагностику, а накопление старых модулей в памяти лечится предложением перезагрузить страницу.

Цена принятого варианта, названная честно: плохой плагин может испортить интерфейс, прочитать
содержимое страницы и уехать с ним куда угодно. Он и так может это сделать из своего воркера.
Правила вида «не лезь в чужой DOM, не цепляйся за внутренности хоста селекторами» остаются
соглашением в документации, а не механизмом; формулировать их как защиту нельзя — это создаст ложное
чувство изоляции. Второй порт и второй origin при этом не нужны, и веб-слой демона остаётся одним
слушателем.

### Расширение через именованные места, замена — явная

**Перехват маршрута или замена модуля целиком.** Ближе всего к тому, что просто реализовать.
Отвергнуто: намерение не выражается (совпадение маршрута ничего не говорит о том, что автор хотел
заменить именно это), конфликт двух плагинов оказывается спрятан в порядке загрузки, а замена части
страницы требует дублировать всё остальное на ней.

**Произвольные слоты по строковому имени или DOM-анкоры.** Максимальная гибкость на короткой
дистанции. Отвергнуто: строка не описывает ни кардинальность, ни контракт контекста, ни политику
замены; плагин начинает зависеть от внутренностей чужого компонента, и любая правка страницы ломает
сторонний код молча.

**Только аддитивные вклады, без замены.** Существенно проще и безопаснее. Не выполняет продуктовое
требование: переопределение существующих компонентов заявлено прямо.

**Замена без обязательного встроенного провайдера.** Позволяла бы ядру не иметь своей реализации для
заменяемых мест. Отвергнуто: тогда выключение плагина оставляет интерфейс без части, а мы обязаны
уметь вернуться в рабочее состояние в любой момент.

Цена: список заменяемых мест — публичный контракт, добавить новое дёшево, убрать дорого; у каждого
заменяемого места обязана быть встроенная реализация, значит базовый интерфейс не может быть пустым
каркасом; место — это ещё и обещание про контекст, менять его форму так же дорого, как менять
публичный API.

### Разрешение провайдера считается в браузере

**В снимке демона.** Демон посчитал бы победителя один раз, а браузер только рисовал бы. Отвергнуто:
контекст — какой проект сейчас открыт и что показывает место — знает только браузер, а `/api/plugins`
один на всё окно и перечисляет объявления **всех** контекстов сразу. Демону пришлось бы либо считать
ответ для каждого возможного контекста, либо принимать контекст параметром запроса — то есть
пересчитывать снимок на каждый переход по страницам.

Правило при этом живёт в `packages/protocol`, а не в `apps/web`: спрашивающих про него больше одного
— место рисует провайдера, а вью плагинов показывает человеку, кем занято место. Разъехавшись, они
объясняли бы разное про одно и то же.

Цена: демон не знает, кто занял место, и в его журнале этого нет. Спор виден человеку диагностикой в
браузере — там же, где он случился.

### Плагин из папки проекта не заменяет оконное вью

Решение владельца продукта. Проектный вклад применяется только там, где контекст — этот проект;
оконное вью настроек он не занимает, хотя его источник и специфичнее.

**Разрешить проектному вкладу оконное место.** Формально последовательнее: ранг источника один и тот
же везде. Отвергнуто: человек, открывший один проект, получил бы подменённое вью настроек плагинов —
общее для всех проектов — кодом из папки этого проекта. Это ровно тот же дефект, который живая
проверка среза 12a нашла на цветовых схемах и каталогах локали.

Цена: у вью настроек проектов в контексте есть `projectId` предметом, но нет `project` контекстом, и
разница между этими двумя полями обязана быть понятной автору плагина — иначе она выглядит опечаткой.

### Встроенный провайдер — поле объявления места

**Соглашение по имени экспорта** (например, «экспорт с именем места»). Отвергнуто: заменяемое место
без встроенного провайдера обязано отвергаться **при регистрации**, а проверить соглашение можно
только загрузив бандл — то есть в браузере и по факту. Поле проверяется реестром, и отказ виден во
вью плагинов рядом с остальными причинами «плагин не работает».

**Отдельный вид вклада на замену.** Отвергнуто: у одиночного заменяемого места провайдер один по
определению кардинальности, а у коллекции и действия вклады складываются. Второй флаг рядом с
кардинальностью означал бы два способа сказать одно.

### Условие видимости отложено

Вклад мог бы нести предикат или декларативное условие над ключами контекста. Не заведено: компонент
живёт в том же realm и решает это сам, вернув `null`, а декларативный мини-язык нужен только тогда,
когда код вклада исполняется за границей процесса. Заводить его «на будущее» значит проектировать
язык без единого потребителя ([backlog.md](backlog.md)).

### Оболочка не заменяется

**Заменяемая оболочка целиком.** Максимальная свобода плагину. Отвергнуто по механике отката:
заглушку об ошибке рисует оболочка, поэтому у провайдера оболочки нет точки возврата — падение
некому показать. Пришлось бы держать вторую, аварийную оболочку, то есть тот же встроенный провайдер,
но с обязанностью работать в момент, когда сломано размещение.

**Оболочка как обычное заменяемое место со встроенным провайдером.** Формально укладывается в общую
модель. Отвергнуто: плагин, забравший оболочку, распоряжается размещением всех остальных вкладов,
включая вклады конкурирующих плагинов. Это превращает один плагин в платформу внутри платформы.

Цена: форма оболочки становится долгоживущим решением — добавить область (например, нижнюю панель)
можно, а переставить существующие — это изменение публичного контракта размещений.

### Браузерный код собирает демон

Жёсткое техническое ограничение, а не предпочтение: **React-хуки работают только при одном экземпляре
React на страницу.** Плагин, притащивший свою копию React, получит сломанные хуки и пустой контекст —
не в редком случае, а сразу. Второе ограничение: браузер не исполняет TypeScript и TSX, а хот-релоад
объявлен базовой функциональностью ядра.

**Плагин приносит собранный бандл.** Снимает с нас сборщик целиком. Отвергнуто: противоречит поставке
исходниками и требует от автора настроенного окружения сборки — превращает «положил папку» в
«настроил проект».

**Плагин тянет свой React.** Автономность бандла и никакой связи версий. Отвергнуто по факту: хуки
перестают работать, в памяти две копии библиотеки, контексты хоста плагину не видны.

**Отдавать исходники браузеру без трансформации.** Браузер не понимает TS/TSX, а import map на каждый
файл лишает контроля над кешированием и превращает загрузку плагина в сотни запросов.

**Собирать плагины в момент установки, а не в демоне.** Убирает сборщик из горячего пути. Отвергнуто:
хот-релоад по правке файла всё равно требует сборки на живой системе, то есть сборщик в демоне нужен
независимо, и второй путь сборки — лишняя сущность.

**Import map вместо глобального реестра модулей.** Бандл плагина выглядел бы честным ESM с обычными
`import "react"`. Отвергнуто по цене: карту надо вписывать в `index.html` **до** первого модульного
скрипта, а адреса в проде — хешированные имена чанков, значит нужен свой плагин Vite и вторая карта
для dev; на каждый спецификатор — файл-реэкспорт и запись в `manualChunks`; и главное — собранный так
бандл нельзя импортировать из Node, то есть проверить его можно только живым браузером. Глобальный
объект не зависит от конвейера сборки фронтенда вовсе и проверяется исполнением в обычном тесте.

Цена принятого варианта названа вслух: преамбула CommonJS-интеропа в каждом бандле (около килобайта);
`import * as React` даёт синтезированный объект, а не Module Namespace, поэтому `export * from "react"`
из плагина не сработает; реестр — изменяемый глобальный объект, что соответствует уже принятой модели
доверия («граница — включение»); состав реестра и мажорная версия React становятся публичным
контрактом.

**Собирать лениво — по первому запросу браузера, а не при старте плагина.** Демон без открытой
страницы не тратил бы ни миллисекунды. Отвергнуто: ошибка сборки — событие жизненного цикла, а не
ответ на HTTP-запрос, и при ленивой сборке плагин с опечаткой в TSX числился бы `running` до тех пор,
пока кто-нибудь не откроет страницу. Сборка стоит 2–12 мс — экономить тут нечего.

**Поднимать воркер, а потом собирать браузерный код.** Плагин с ошибкой в TSX сохранял бы инструменты
и хуки. Отвергнуто: вклады, которые воркер объявляет в `activate`, ссылаются на экспорты бандла, и
без бандла реестр наполнился бы мёртвыми ссылками. «Полуживое» состояние потребовало бы второго
понятия в интерфейсе — навсегда, ради случая, который чинится правкой одного файла.

**Уникальность имён CSS-классов оставить сборщику.** Отвергнуто по факту запуска: **у esbuild в имени
класса нет хеша вовсе** — имя это `<файл>_<локальное имя>`, а уникальность обеспечена счётчиком
внутри одной сборки. Два плагина с одинаковым `badge.module.css`, собранные по отдельности, оба
получили бы `.badge_badge` и молча перекрыли бы друг друга. Поэтому base64url-кодированный ключ
плагина въезжает в имя файла, из которого esbuild составляет имя класса, — шаблона имени класса
esbuild не предоставляет.

Второй факт запуска: **`minify: true` схлопывает и локальные имена CSS до одной буквы** (`.o`, `.l`).
Поэтому минификация включена по частям — `minifyWhitespace` и `minifySyntax` без `minifyIdentifiers`.

Цена: демон получает зависимость-сборщик; версия React становится частью публичного контракта
([public-contract.md](public-contract.md)); старый ES-модуль после перезагрузки плагина остаётся в
памяти браузера — выгрузить модуль из кеша браузера нельзя, поэтому число накопленных ревизий надо
ограничивать и предлагать перезагрузку; ассеты плагинов идут с того же origin, что и API, и делят с
SSE-соединением пул из шести соединений на источник ([runtime-checks.md](runtime-checks.md),
проверка 9).
