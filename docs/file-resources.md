# Файловые агенты и скилы

Агенты и скилы можно объявлять Markdown-файлами с YAML-frontmatter. Каждое определение занимает
отдельную директорию: имя директории задаёт его идентичность, entry-файл задаёт метаданные и текст,
а лежащие рядом файлы служат ресурсами определения.

## Общие правила

Имя обязательно совпадает с именем директории, имеет длину от 1 до 64 символов и состоит из
строчных латинских букв, цифр, `_` и `-`. Дефис не может быть первым или последним; `--` запрещён.
Подчёркивание допустимо в обоих форматах, но скил с `_` получает warning
`nonstandard-underscore`: строгие клиенты Agent Skills могут его не принять.

Frontmatter разбирается как YAML 1.2. Повтор ключа и синтаксическая ошибка недопустимы, неизвестные
поля игнорируются. Ошибка одного определения локальна: остальные директории продолжают читаться.

У файлов плагина корни фиксированы: `<plugin-directory>/agents` и
`<plugin-directory>/skills`. Loader всегда считает их от обнаруженной директории конкретной копии
плагина — встроенной, пользовательской или проектной. Отдельного общего built-in-корня для агентов
и скилов нет. Файловый агент получает полное имя `<plugin-id>.<name>`; например,
`plugins/base-agent/agents/agent/AGENT.md` регистрирует `base-agent.agent`.

Standalone-определения не принадлежат плагину, не запускают worker и сохраняют короткий
идентификатор `<name>`. Корни обходятся в таком порядке; числовой precedence определяет победителя
при одинаковых kind и идентификаторе:

| Порядок | Корень                        | Scope   | Kind  | Source      | Precedence |
| ------- | ----------------------------- | ------- | ----- | ----------- | ---------- |
| 1       | `<project>/.sovereign/agents` | project | agent | `sovereign` | 200        |
| 2       | `<project>/.sovereign/skills` | project | skill | `sovereign` | 400        |
| 3       | `<project>/.agents/skills`    | project | skill | `agents`    | 300        |
| 4       | `<data-directory>/agents`     | user    | agent | `sovereign` | 100        |
| 5       | `<data-directory>/skills`     | user    | skill | `sovereign` | 200        |
| 6       | `~/.agents/skills`            | user    | skill | `agents`    | 100        |

Проектные корни существуют только у неархивного проекта с доступной папкой. Эфемерный проект
`work` подчиняется тому же правилу и участвует, пока доступен. Корня `.agents/agents` нет:
межклиентский формат предоставляет только скилы.

## `AGENT.md`

Агент лежит по пути `<agents-root>/<name>/AGENT.md`. Поля `name` и `description` обязательны, как и
непустой Markdown-body с инструкциями. Необязательны `tools`, `skills`, `model` и
`thinking-level`. Поддерживаемые уровни thinking: `off`, `minimal`, `low`, `medium`, `high`,
`xhigh`, `max`.

```markdown
---
name: code-agent
description: Работает с кодом проекта
tools:
  include: ["*"]
  exclude: ["dangerous-*"]
skills:
  include: ["review-*"]
  exclude: []
model: provider/model
thinking-level: medium
---

Сначала прочитай затрагиваемые файлы, затем внеси минимальное изменение.
```

Оба селектора состоят из массивов строк `include` и `exclude`; отсутствующая сторона селектора
становится пустым массивом. Полностью отсутствующий `tools` или `skills` становится
`{ include: [], exclude: [] }`: это означает «ничего», а не неявный `*`. Для разрешения всего
набора автор пишет `include: ["*"]` явно.

Перед каждой операцией модели selectors применяются заново к текущему набору проекта: `tools` — к
собранным именам инструментов, `skills` — к разрешённым идентификаторам скилов. Plugin-owned скил
выбирается квалифицированным `id` (`github.review`), standalone — коротким (`review`). Сначала
применяется `include`, затем из результата вычитается `exclude`; запрет всегда побеждает разрешение.
Горячее добавление скила поэтому делает его доступным на следующей операции, а удаление целиком
убирает его из каталога действующего harness. Скил с `disable-model-invocation: true` в каталог
модели не передаётся даже при совпавшем selector.

## `SKILL.md`

Скил лежит по пути `<skills-root>/<name>/SKILL.md`. Обязательны строковые `name` и `description`;
описание содержит не больше 1024 символов. Markdown-body может быть пустым. Поддерживаются
необязательные поля:

- `license` — непустая строка;
- `compatibility` — непустая строка не длиннее 500 символов;
- `metadata` — YAML mapping из строк в строки;
- `allowed-tools` — одна строка, разбираемая по пробельным разделителям в `string[]`;
- `disable-model-invocation` — boolean, по умолчанию `false`.

```markdown
---
name: code_review
description: Проверяет изменение перед публикацией
license: MIT
compatibility: Requires git
metadata:
  author: sovereign
allowed-tools: read bash
disable-model-invocation: false
---

Пройди тесты, типизацию и изучи итоговый diff.
```

`location` загруженного скила — абсолютный путь к его `SKILL.md`. Относительные пути из Markdown
разрешаются от содержащей его директории. `allowed-tools` распознаётся, проверяется и сохраняется как
нормализованный список, но пока не меняет доступный runtime-набор инструментов и не вводит особых
правил подтверждения вызовов.

`disable-model-invocation: true` тоже распознаётся и сохраняется. Такой скил остаётся в реестре и
диагностике, но не попадает в XML-каталог системного prompt и потому недоступен для самостоятельной
активации моделью. Остальные применимые скилы представлены модели только именем, описанием и
абсолютным `location`; полный `SKILL.md` она читает обычным `read` по необходимости.

## Обнаружение и соседние ресурсы

Обход каждого корня плоский. Определениями считаются только `<root>/<name>/AGENT.md` и
`<root>/<name>/SKILL.md`; поиск глубже одного уровня не выполняется. Директория без entry-файла не
считается определением. Вложенный `AGENT.md` или `SKILL.md` не запускает второй parser.

Символическая ссылка вместо директории определения или entry-файла запрещена и получает
`unsupported-symlink`; цель ссылки не читается. После такой ошибки обход продолжается. Соседние
файлы, директории и ссылки не индексируются, не валидируются и не сканируются ради квоты. Поэтому
платформа не обещает наблюдение за внешней целью ссылки среди ресурсов.

Watcher плагина следит за всем каталогом плагина, но помечает как изменение файловых ресурсов только
путь, чей первый сегмент внутри плагина — `agents` или `skills`. Standalone-сервис наблюдает каждый
существующий корень рекурсивно, а для отсутствующего корня — ближайшего существующего родителя без
рекурсии, чтобы заметить появление пути и переставить watcher. Поэтому создание, правка, удаление
entry-файла или любого соседнего `scripts`, `references` либо `assets` сразу заменяет полный снимок
корня. Переходы valid → invalid → valid и появление → удаление отражаются без перезапуска демона;
обычный повторный scan неизменного снимка ревизию не повышает, а реальное файловое событие повышает
её и при неизменных разобранных метаданных.

Символические ссылки вместо корня, директории определения или entry-файла не разыменовываются.
Появление ссылки вызывает новый scan и диагностику `unsupported-symlink` для определения, но её
внешняя цель под наблюдение не попадает. Замена списка проектов или доступности полностью
переставляет standalone watchers; при остановке демона закрываются и watchers, и debounce timer.

Размер проверяется до чтения только для entry-файла. Допустимо не больше 1 048 576 байт; большее
значение даёт `entry-too-large`. Размер соседних ресурсов этим ограничением не связан.

## Диагностика

Диагностика содержит severity, стабильный code, сообщение и путь к entry-файлу. Основные коды:

- `invalid-frontmatter` — нет delimiters, YAML синтаксически неверен, повторяет ключ или не является
  mapping;
- `invalid-name`, `name-directory-mismatch` — неверное имя или несовпадение с директорией;
- `missing-description`, `missing-instructions` — нет обязательного содержания;
- `invalid-selector`, `invalid-thinking-level` — неверное поле агента;
- `invalid-description`, `invalid-compatibility`, `invalid-metadata`, `invalid-allowed-tools`,
  `invalid-disable-model-invocation` — неверное поле скила;
- `unsupported-symlink`, `entry-too-large`, `invalid-entry`, `unreadable-entry` — entry нельзя
  безопасно прочитать;
- `nonstandard-underscore` — предупреждение о переносимости, определение остаётся корректным.

## Почему так

### Одна директория на определение

Инструкции могут ссылаться на scripts, references и assets относительными путями. Отдельная
директория сохраняет эти связи и не смешивает одноимённые ресурсы разных агентов или скилов.
Рекурсивный поиск отвергнут: вложенный файл невозможно однозначно отличить от ресурса родительского
определения.

### Строгий YAML через зависимость `yaml`

Ручной parser frontmatter отвергнут: он либо принимает не весь YAML, либо незаметно расходится с
семантикой YAML 1.2 и проверкой повторных ключей. `yaml` даёт документ с явными parse errors и
режимом `uniqueKeys`, чтобы ошибка оставалась локальной и превращалась в диагностику, а не в
исключение из общего обхода.

### Лимит только на entry-файл

Entry разбирается платформой целиком при discovery, поэтому лимит 1 МиБ ограничивает обязательную
стоимость сканирования. Соседние ресурсы читаются только по необходимости обычными инструментами;
обходить их заранее ради той же квоты означало бы нарушить progressive disclosure и дорого
сканировать произвольные деревья.

### Standalone-сервис рядом с loader плагинов

Standalone-файлам нужен тот же parser и единый реестр вкладов, но не жизненный цикл исполняемого
кода. Запускать для них plugin worker отвергнуто: Markdown-определение не объявляет программу и не
должно получать изоляцию, RPC и состояние включения плагина. Сервис поэтому живёт в той же области
демона, атомарно заменяет снимок каждого корня и независимо управляет файловыми watchers.
