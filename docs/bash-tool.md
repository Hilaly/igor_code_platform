# Инструменты bash, job-output, job-kill

Bash — инструмент исполнения команд агента: `bash`, `job-output` и `job-kill` объявляет встроенный
плагин `starter` (plugins/starter/src/tools.ts), исполнение живёт в его воркере
(plugins/starter/src/bash.ts). Это **вклад плагина, а не инструмент рантайма**: выключил starter —
bash пропал; заменил starter одноимённым плагином из директории данных — bash заменился, не трогая
ядро ([plugins.md](plugins.md)).

## Почему bash переехал из рантайма

Раньше bash приходил из `pi-agent-core` вместе с `read`, `write`, `edit`. Его исполнение
(`NodeExecutionEnv.exec`) копило stdout/stderr команды в строки **без лимита, пока жив процесс**:
зависшая команда с таймаутом в сотни секунд линейно раздувала память демона (замерено ~12 МБ/с,
два параллельных агента — до 30+ ГБ, мак умирал; запись в [backlog.md](backlog.md)). У рантайма
нет ни лимита вывода, ни потолка таймаута, ни убийства дерева процессов — а у плагина всё это есть.
`read`/`write`/`edit` работают файловой системой, не `exec`, и остались в рантайме.

## Контракт для модели

### `bash`

```json
{
  "command": "<строка, обязательна>",
  "timeout": "<секунды, необязательно>",
  "run_in_background": "<true, необязательно>"
}
```

- Каждый вызов — свежая оболочка (`bash -c`): `cd`, переменные и функции между вызовами не
  переживают. Рабочая директория — папка проекта сессии.
- Окружение команды наследует окружение демона с принудительными `NO_COLOR=1`, `TERM=dumb`,
  `PAGER=cat`, `GIT_PAGER=cat`: цвет и пейджеры калечат вывод.
- Результат — текст: stdout, затем секция `[stderr]`, затем маркеры исхода. Ненулевой код выхода —
  **маркер `[exit code: N]`, а не ошибка**: инструмент не «сломался», и решает модель.
  Таймаут — `[timed out after N seconds]`, смерть от сигнала — `[killed by signal: SIG]`.
- Пустой результат — `(no output)`.

### Ограничения исполнения

- **Вывод bounded.** Хвост каждого потока (64 КБ) держится в памяти; переполнение уезжает в файл
  `<dataDirectory>/tmp/bash-*.log`, и результат получает пометку
  `[output truncated; full output: <путь>]`. Файл не удаляется автоматически
  ([data-directory.md](data-directory.md)).
- **Потолок таймаута — таймаут вызова плагина** (`pluginToolTimeoutMilliseconds` из `config.json`,
  по умолчанию 120 с) минус запас 2 с на передачу ответа воркером. Команда, которая просит больше
  или не указывает таймаут, исполняется с потолком; если модель просила больше — в результат
  добавляется `[timeout clamped to N seconds by the platform]`. Дольше потолка — только
  `run_in_background`.
- **Убийство деревом.** Команда живёт в своей process group (`detached`); таймаут и `job-kill`
  шлют SIGTERM всей группе, затем SIGKILL по grace 3 с. Потомок с унаследованным pipe не держит
  ожидание вечно: после `exit` закрытие канала ждётся тот же grace.

### `job-output` и `job-kill`

- `bash` с `run_in_background: true` возвращает `background job <id> started` сразу; команда бежит
  без таймаута.
- `job-output {jobId}` читает вывод **дельтой с прошлого раза** и статус:
  `[status: running|completed|killed]`; для завершённых — маркеры исхода. Читать, пока не
  `completed`, — нормальный способ дождаться фоновой работы.
- `job-kill {jobId}` убивает дерево задания (SIGTERM → SIGKILL). Повторный kill —
  `already finished`; чужое или неизвестное задание — ошибка.

## Жизненный цикл заданий

- Задание принадлежит сессии, которая его запустила: `job_output`/`job_kill` другой сессии его не
  видят.
- Задание умирает вместе с сессией (хук `session_closed`), с выгрузкой плагина (`deactivate`
  шлёт SIGKILL всем деревьям — иначе они осиротели бы) и с остановкой демона (вместе с воркером).
- Задания **не переживают перезапуск демона**: реестр в памяти воркера, и после рестарта модель
  получает `unknown job <id>`.
- Архив сессии задание не убивает: архив — «убрано с глаз», а не закрытие
  ([sessions-and-projects.md](sessions-and-projects.md)).

## Почему так

- **Плагин, а не ядро.** Ограничения исполнения — это политика, а не механика рантайма: ядро
  остаётся минимальным, а владелец может заменить или выключить bash своим плагином, не пересобирая
  платформу. Цена — bash зависит от включённого starter, и это видно из интерфейса плагинов.
- **Синхронный вызов плюс фоновый флаг, а не второй инструмент.** Один инструмент с
  `run_in_background` — тот же выбор, что в других платформах: модель уже знает `bash`, и фоновый
  режим не требует нового ментального контракта.
- **Постоянной оболочки на сессию нет.** Состояние (cwd, переменные) между вызовами не
  переживает: оно не хранится в файле сессии, не восстанавливается после перезапуска демона и
  усложняет параллельные турны. Это отдельная продуктовая фича, а не ограничение bash.
- **Foreground ограничен таймаутом вызова плагина.** Вызов инструмента плагина идёт демон →
  воркер с таймаутом `pluginToolTimeoutMilliseconds`, и отмены воркеру при таймауте не приходит:
  команда, не уложившаяся в него, осталась бы доживать с потерянным ответом. Поэтому потолок —
  существующий параметр конфига, а не новый.
- **Слив синхронный.** `writeSync` на чанке 64 КБ стоит микросекунды, асинхронная цепочка записей
  потребовала бы собственную очередь с лимитами.
- **Файлы в `<dataDirectory>/tmp` не чистятся автоматически.** Уборка по возрасту — фоновая
  работа с собственным жизненным циклом; пока выводы малы, файл удаляется вместе с сессией руками
  или живёт до следующей уборки машины.
