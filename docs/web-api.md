# Веб-API

Всё, что интерфейс и плагины получают от демона по HTTP. Демон слушает петлю
(`127.0.0.1:8787` по умолчанию), в dev-режиме запросы идут через прокси Vite —
[runbook.md](runbook.md).

Типы ответов лежат в `@sovereign/protocol` и импортируются обеими сторонами: расхождение сервера и
клиента ловит компилятор, а не человек.

## Из чего состоит

Разовый вопрос — обычный HTTP-запрос, поток изменений — одно SSE-соединение. Второго соединения на
вкладку нет: все события ядра и плагинов идут в одном потоке, поллинга нет ни короткого, ни
длинного.

| Маршрут                                 | Что делает                                           | Доступ       |
| --------------------------------------- | ---------------------------------------------------- | ------------ |
| `GET /api/health`                       | Жив ли демон и сколько работает                      | открыт       |
| `GET /api/login-session`                | Состояние входа                                      | открыт       |
| `POST /api/login-session`               | Вход по паролю                                       | открыт       |
| `DELETE /api/login-session`             | Выход                                                | нужна сессия |
| `POST /api/account`                     | Создать учётную запись первым входом                 | открыт       |
| `GET /api/plugins`                      | Снимок состояния плагинов                            | нужна сессия |
| `PUT /api/plugins/:key/preferences`     | Включить или выключить плагин и отдельные его вклады | нужна сессия |
| `GET /api/preferences`                  | Выбранная цветовая схема, вариант и локаль           | нужна сессия |
| `PUT /api/preferences`                  | Записать этот выбор                                  | нужна сессия |
| `GET /api/projects`                     | Проекты в работе и, отдельным списком, архивные      | нужна сессия |
| `POST /api/projects`                    | Создать проект на папке                              | нужна сессия |
| `PUT /api/projects/:id`                 | Переименовать, архивировать или восстановить         | нужна сессия |
| `DELETE /api/projects/:id`              | Удалить проект безвозвратно, если нет сессий         | нужна сессия |
| `GET /api/providers`                    | Провайдеры LLM и статус авторизации у каждого        | нужна сессия |
| `GET /api/providers/:providerId/models` | Модели одного провайдера                             | нужна сессия |
| `POST /api/providers/refresh`           | Перечитать динамические списки моделей               | нужна сессия |
| `GET /api/agents`                       | Агенты, включённые прямо сейчас                      | нужна сессия |
| `GET /api/sessions`                     | Сессии агента, фильтр `?projectId=`                  | нужна сессия |
| `POST /api/sessions`                    | Создать сессию                                       | нужна сессия |
| `GET /api/sessions/:sessionId`          | Одна сессия вместе с её состоянием                   | нужна сессия |
| `GET /api/sessions/:sessionId/entries`  | Записи дерева, курсор `?after=`                      | нужна сессия |
| `POST /api/sessions/:sessionId/turns`   | Запустить турн                                       | нужна сессия |
| `DELETE /api/sessions/:sessionId/turns` | Прервать турн                                        | нужна сессия |
| `GET /api/events`                       | Поток событий                                        | нужна сессия |

`:key` — ключ плагина `<источник>:<id>`, в пути он кодируется: двоеточие обязано быть `%3A`.
`:id` — идентификатор записи проекта, а не его папка: путь длинный, содержит юникод и меняет
написание от регистра, а идентификатор переживает и то, и другое.

Маршруты собраны в таблицу, а не разложены по веткам `if`. Разбор пути, лимит тела
(64 КБ), коды и форма отказа общие для всех: отказ — это всегда `{"error": "..."}` с текстом для
человека.

| Код   | Когда                                                                         |
| ----- | ----------------------------------------------------------------------------- |
| `400` | Тело не разбирается, не той формы или пароль короче минимума                  |
| `401` | Нужна сессия; либо пароль не тот                                              |
| `403` | Браузер назвал изменяющий запрос межсайтовым                                  |
| `404` | Нет такого маршрута или такого плагина                                        |
| `405` | Маршрут есть, метод другой; в заголовке `Allow` — какие есть                  |
| `409` | Файл на диске не читается, и записать поверх — стереть чужое; состояние не то |
| `413` | Тело больше лимита                                                            |
| `415` | Изменяющий запрос не назвал себя `application/json`                           |
| `500` | Обработчик упал; причина ушла в журнал, наружу подробности не идут            |

`409` отвечают пять разных случаев: файл настроек, `account.json` или `projects.json` не читается
([data-directory.md](data-directory.md)), вход до создания учётной записи («требуется регистрация»),
повторная регистрация («учётная запись уже есть»), попытка изменить эфемерный проект и создание
второго проекта на занятую папку. Общее у них то, что запрос сам по себе верен, а состояние
платформы не то, которого он ждёт.

**У одного отказа тело шире `{"error"}`.** Создание проекта на занятую папку отдаёт ещё и поле
`conflict` — целую запись занявшего проекта. Спецификация требует «отклоняется с указанием на
существующий» ([sessions-and-projects.md](sessions-and-projects.md)), а строкой текста интерфейс не
подсветит нужную строку списка. Общая форма при этом остаётся: поле `error` есть и здесь, и клиент,
который читает только его, ничего не теряет.

## Что требуется от изменяющего запроса

`POST`, `PUT` и `DELETE` проверяются диспетчером до всякой сессии — два условия, оба про форму
запроса, а не про то, кто спрашивает:

- **Заголовка `Sec-Fetch-Site: cross-site` или `same-site` быть не должно** — иначе `403`. Заголовок
  ставит браузер, страница его не подделает; у запроса из терминала его нет вовсе, и это не повод
  отказывать.
- **`Content-Type` обязан быть `application/json`** (параметры вида `; charset=utf-8` допустимы) —
  иначе `415`. У `DELETE` тела нет, и от него заголовок не требуется.

Проверка стоит до проверки сессии намеренно: ответ на негодный запрос не должен зависеть от наличия
cookie, иначе отказ рассказывал бы о состоянии входа.

## Проверка сессии

**Проверка живёт в диспетчере, одним местом на все маршруты,** включая SSE-поток и будущие маршруты
плагинов: маршрут не может случайно оказаться незащищённым, потому что защита не в обработчике
([authentication.md](authentication.md)).

Порядок в диспетчере: разбор пути → `404`/`405` → форма изменяющего запроса (`403`/`415`, «Что
требуется от изменяющего запроса» выше) → проверка сессии → чтение тела.

- **`404` и `405` отвечают и без сессии.** Таблица маршрутов ядра публична, скрывать её незачем, а
  разница «нет адреса»/«не тот метод» полезна и до входа.
- **Тело без сессии не читается вовсе:** буферизовать килобайты для того, кто получит отказ,
  незачем.
- Отказ — `401` с телом `{"error":"the request needs a session"}`.

**Открытость объявляется полем маршрута** — необязательным `access?: "open"`. Его отсутствие значит
«нужна сессия», поэтому забытое поле делает новый маршрут защищённым, а не открытым. Сама функция
проверки в опциях диспетчера, наоборот, **обязательна**: значение по умолчанию означало бы, что
забытая проводка открывает API целиком и молча.

Открытых маршрутов четыре: состояние входа, вход, создание учётной записи и `GET /api/health`. Выход в
этот список не входит — закрывать сессию, которой нет, незачем. Проба «жив ли демон» обязана работать
до входа: иначе неотвеченный запрос перестал бы отличать лежащий демон от закрытой сессии, — а отдаёт
она ровно то, что и так видно по факту ответа.

## Вход и сессия

```bash
curl -c jar -X POST http://localhost:5273/api/account \
  -H 'content-type: application/json' -d '{"password":"correct horse"}'
```

`POST /api/account` — первый вход: учётной записи ещё нет. Тело — `{"password":"..."}`, пароль
короче шести символов отвергается разбором в `@sovereign/protocol` с `400`. Ответ —
`{"state":"authenticated"}` и `Set-Cookie`: сессия открывается сразу, потому что вход отдельным
запросом стоил бы ещё одного счёта хеша подряд, а человек только что доказал, что знает пароль.

`POST /api/login-session` — обычный вход, то же тело и тот же ответ. Неверный пароль даёт `401` с
`{"error":"the password is not right"}` — одна формулировка и на неверный пароль, и на торможение
подбора: различать их в ответе значило бы рассказывать подбирающему, что он нащупал
([authentication.md](authentication.md)).

`GET /api/login-session` отвечает `{"state": ...}` без всякой сессии — интерфейс обязан узнать состояние до
того, как что-то показывать:

| `state`                 | Что значит                    |
| ----------------------- | ----------------------------- |
| `registration-required` | Учётной записи ещё нет        |
| `unauthenticated`       | Запись есть, живой сессии нет |
| `authenticated`         | Живая сессия есть             |

`DELETE /api/login-session` — выход: отвечает `{"state":"unauthenticated"}` и гасит cookie. Защита при этом
не в погашенной cookie, а в удалённой серверной записи — сохранённая копия cookie мертва вместе с
ней.

**Cookie** — `sovereign_session`: `HttpOnly`, `SameSite=Strict`, `Path=/`, `Expires` совпадает со
сроком серверной записи. Без срока закрытие браузера выкидывало бы из интерфейса при живой сессии.
Флага `Secure` нет: по `http` браузер такую cookie не отправил бы вовсе
([authentication.md](authentication.md)). Разбор и сборка заголовка — библиотекой `cookie`: это ровно
та скучная и опасная часть, которую здесь берут готовой («Почему так» ниже).

## Снимок и поток

Событие говорит, что состояние изменилось; спрашивать «как сейчас» надо у владельца состояния
([event-bus.md](event-bus.md)). Поэтому у потока есть пара — `GET /api/plugins`:

```json
{
  "revision": 2,
  "plugins": [
    {
      "key": "data:hello",
      "id": "hello",
      "source": "data",
      "state": "running",
      "contributionProblems": ["the contribution identifier \"Board Panel\" must match …"]
    }
  ],
  "contributions": [
    { "id": "hello.board", "pluginKey": "data:hello", "kind": "custom" },
    {
      "id": "tracker.task.created",
      "pluginKey": "data:tracker",
      "kind": "event",
      "payloadSchema": { "type": "object", "properties": { "id": { "type": "string" } } }
    }
  ],
  "switchedOffContributions": [
    { "id": "hello.panel", "pluginKey": "data:hello", "kind": "custom", "title": "Panel" }
  ],
  "conflicts": [],
  "enablement": {
    "data:hello": { "enabled": true, "disabledContributions": ["hello.panel"] }
  }
}
```

Статусы здесь те же самые, что уходят событием `core.plugin.lifecycle`: снимок и поток собираются из
одного источника, иначе догон по индексу не имел бы смысла. У вклада вида `event` рядом лежит
описание схемы нагрузки: это и есть ответ на вопрос «какие события существуют и кто их публикует».

- **`contributions`** — действующий набор: то же, что в событии `core.plugin.contributions`.
- **`switchedOffContributions`** — объявленное, но выключенное человеком. В действующий
  набор такой вклад не входит и не участвует ни в чём, включая перекрытие, — но переключатель ему
  нужен, иначе включить его обратно было бы нечем.
- **`conflicts`** — вклады, на которые претендуют несколько плагинов одного источника: не применяется
  ни один ([plugins.md](plugins.md)). Диагностика обязана быть видна в интерфейсе, а журнал наружу не
  отдаётся вовсе ([logging.md](logging.md)).
- **`enablement`** — действующее решение о включении по ключу плагина: не содержимое
  `preferences.json`, а результат. У плагина без записи оно выведено по источнику, поэтому
  политика по умолчанию остаётся в демоне. Форма записи та же, что тело `PUT` ниже: интерфейс читает и
  пишет одно и то же. Плагина, отказанного до чтения манифеста, здесь нет — его ключ это путь к папке,
  и переключать там нечего.
- **`contributionProblems`** в статусе — почему объявленный вклад не появился: кривой идентификатор,
  занятый неймспейс `core`, двойное объявление
  ([plugins.md](plugins.md)). Поле в статусе, а не в снимке,
  потому что статус ходит и потоком: вклады применяются перед переходом в `running`, и событие
  жизненного цикла уносит причину с собой.

`revision` — версия набора вкладов; по ней видно, изменился ли набор с прошлого события. **Свежесть
снимка ею мерить нельзя:** ревизия живёт в памяти процесса и сбрасывается вместе с перезапуском
демона, как и индексы потока.

Порядок для клиента: сначала открыть поток, потом запросить снимок. Наоборот — потеряешь события,
случившиеся между ответом и подпиской.

## Поток событий

`GET /api/events` — SSE. Каждое событие получает монотонный индекс в поле `id`, а телом `data:`
идёт кадр целиком:

```
id: 18
data: {"index":18,"time":"2026-07-27T07:06:07.923Z","type":"core.plugin.lifecycle","payload":{"key":"data:hello","state":"starting"}}
```

Тип и время лежат внутри `data`, а не в полях SSE: клиент разбирает один json, а не сначала кадр,
потом его нагрузку.

События ядра:

| Тип                         | Когда                                               |
| --------------------------- | --------------------------------------------------- |
| `core.plugin.lifecycle`     | Переход состояния плагина                           |
| `core.plugin.contributions` | Действующий набор вкладов изменился                 |
| `core.preferences.changed`  | Изменились цветовая схема, вариант или локаль       |
| `core.sessions.changed`     | Список сессий или состояние одной из них изменились |
| `core.stream.gap`           | Пропущенного уже нет, состояние надо перезапросить  |

У `core.preferences.changed` нагрузки нет: событие говорит «изменилось», а состояние спрашивается у
владельца — `GET /api/preferences` ([event-bus.md](event-bus.md)). О записях
плагинов из того же файла рассказывают события жизненного цикла и набора вкладов.

**Правка записи плагина, ничего не изменившая по факту, событием не сопровождается.** Выключение
вклада, который и так был перекрыт, или запись `enabled: true` уже запущенному плагину не меняют ни
состояния, ни набора — значит и публиковать нечего. Клиент, который показывает записанное решение,
видит своё собственное изменение из ответа `PUT`; правку файла руками такого рода он не заметит до
следующего запроса снимка ([backlog.md](backlog.md)).

**Журнала демона в потоке нет.** Записи уходят в `stdout` и наружу по HTTP не отдаются вовсе
([logging.md](logging.md)): событие шины — это событие
предметной области, а запись журнала им не является. Диагностика читается в терминале, где запущен
демон.

Неймспейс `core.*` принадлежит ядру, занять его плагин не может ([event-bus.md](event-bus.md)).

Набор вкладов приходит целиком, а не приращением: подписчик, пропустивший одно приращение, остался
бы с испорченной картиной навсегда.

**События плагинов идут тем же потоком и нумеруются наравне с событиями ядра.** Отличает их поле
`plugin` — кто опубликовал; тип несёт полное имя с неймспейсом публикатора:

```
id: 73
data: {"index":73,"time":"2026-07-27T08:12:08.713Z","type":"tracker.task.created","payload":{"id":"15"},"plugin":{"key":"data:tracker","id":"tracker","source":"data"}}
```

Перечня таких типов нет и быть не может: плагин в поставку не входит. Что существует сейчас,
отвечает снимок `/api/plugins` — вклады вида `event` со схемой нагрузки. Нагрузку проверил воркер
публикатора ([event-bus.md](event-bus.md)), ядро её не разбирает.

## Сессии агента

Полное описание сущности — в [sessions-and-projects.md](sessions-and-projects.md); здесь то, что
видно на проводе.

```bash
curl -b jar localhost:5273/api/agents
# {"agents":[{"id":"base-agent.agent","title":"Base agent","source":"builtin","skills":[]}]}

curl -b jar -X POST localhost:5273/api/sessions -H 'content-type: application/json' \
  -d '{"projectId":"b7Kq3xv9pQdT","agentId":"base-agent.agent","model":"anthropic/claude-opus-4-5"}'
# {"id":"0199…","projectId":"b7Kq…","folder":"/Users/me/code/demo","phase":"idle", …}

curl -b jar -X POST localhost:5273/api/sessions/0199…/turns -H 'content-type: application/json' \
  -d '{"text":"создай hello.txt со словом привет"}'
# {"sessionId":"0199…","turnId":"turn-1","phase":"turn"}
```

**Модель называется как `<провайдер>/<модель>`.** Идентификатор модели сам вправе содержать `/`
(так устроены каталоги вроде OpenRouter), поэтому строка режется по **первому** разделителю — в
идентификаторе провайдера `/` не бывает.

**`phase` в ответе на запуск турна — не украшение.** При исчерпанном пределе одновременных турнов
она равна `queued`: турн принят, но ещё не начат ([architecture.md](architecture.md)). Значения:
`idle`, `queued`, `turn`, `compaction`, `branch-summary`, `retry`.

**Ноль агентов — законный ответ `GET /api/agents`, а не отказ:** единственный плагин с агентом могли
выключить.

Отказы создания сессии — `409` с причиной: проект архивный, папка проекта пропала, такого агента
никто не включал, у агента нет модели по умолчанию и её не назвали, названной модели нет в каталоге.
Неизвестный проект — `404`.

**Прерывание — `DELETE` над коллекцией турнов**, а не отдельный маршрут: прерывать нечего, кроме
того, что идёт. Ответ `{"sessionId":…,"interrupted":false}` означает «прерывать было нечего» и
ошибкой не является. Ещё не начатый турн снимается с очереди, идущий — прерывается рантаймом.

Записи дерева читаются курсором: `seen` в ответе — значение для следующего `?after=`. Курсор
считается в записях рантайма, поэтому одна запись рантайма может дать в ответе больше одной нашей.

### Кадр дельты турна

Живой ход турна агента едет тем же соединением и тоже отдельным классом кадра
([sessions-and-projects.md](sessions-and-projects.md)):

```json
{
  "time": "2026-07-29T09:11:04.512Z",
  "frame": "session-delta",
  "sessionId": "0199-…",
  "turnId": "t-7",
  "delta": { "kind": "message-delta", "messageId": "t-7:0", "channel": "text", "text": "при" }
}
```

**Индекса у кадра нет, и `id:` в SSE он не пишет.** Это единственное отличие от кадра шага входа, и
оно принципиальное: дельт на один ответ модели сотни. Займи они позиции в нумерации — тысяча кадров
окна догона выродилась бы в один ответ модели, а все события шины до него стали бы недостижимы.
Клиент, запомнивший такой `id`, к тому же попросил бы продолжить с позиции, которой в нумерации
не существует, и получил бы ложный `core.stream.gap`.

Корректности это не стоит ничего: после разрыва клиент перечитывает записи сессии маршрутом
`GET /api/sessions/:sessionId/entries`, а не доигрывает дельты. Догонять поток токенов бессмысленно —
он уже не живой, а его результат целиком лежит в дереве сессии.

Виды дельт: `phase`, `message-start`, `message-delta`, `message-end`, `tool-start`, `tool-end`,
`turn-end`, `turn-aborted`, `turn-failed`. Идентификатор сообщения здесь синтетический и живёт ровно
один турн: запись дерева получает свой идентификатор только в момент, когда она дописана, то есть
уже после последней дельты.

### Переподключение

Позиция передаётся заголовком `Last-Event-ID` — браузерный `EventSource` шлёт его сам — или
параметром `?lastEventId=`, если заголовок ставить неоткуда.

- **Без позиции** соединение начинается с текущего конца: истории свежий клиент не получает.
- **С позицией** приходит ровно пропущенное.
- **Позиции уже нет** — приходит `core.stream.gap` с тем, что просили, и тем, что осталось. Это
  сигнал перезапросить снимок, а не повод показывать неполные данные.

Индексы **сбрасываются при перезапуске демона**: индекс из прошлой жизни демона тоже даёт
`core.stream.gap`.

**Браузерный `EventSource` переподключается сам не всегда.** Пока сервер отвечает как положено —
повторяет; на HTTP-ошибку он закрывается навсегда, а именно её отдаёт прокси Vite, пока демон лежит.
Поэтому клиент ведёт позицию сам и переоткрывает поток с `?lastEventId=` — [ui-kit.md](ui-kit.md),
раздел про оболочку.

**Подписки на уровне протокола нет и не планируется.** Поток отдаёт всё, а фильтрует клиент: замер
показал, что рассылка по подписчикам стоит 3% пути кадра, а разбор json — 97%
([runtime-checks.md](runtime-checks.md), проверка 23): отсекать на сервере значило бы экономить
проценты и всё равно разбирать кадр, чтобы узнать его тип.

Окно догона живёт в памяти процесса и хранит последнюю тысячу событий. События ядра редкие —
переходы плагинов и изменения набора вкладов, — поэтому тысяча кадров покрывает часы работы, а не
секунды. Архивом поток от этого не становится: пережить перезапуск демона он не умеет.

**Клиент, который перестал читать, отцепляется.** Обратного давления у сокета нет
([runtime-checks.md](runtime-checks.md), проверка 19): не читающий клиент набирает гигабайты в
буфере демона за секунды. Порог — мегабайт неотданного, то есть тысячи кадров; разрыв уходит в
журнал.

Простаивающее соединение держится комментарием-пингом раз в пятнадцать секунд.

**Выход обрывает живой поток.** Проверка сессии стоит на входе в соединение, а соединение живёт
часами, поэтому у потока есть `disconnect` по идентификатору сессии: закрытие серверной записи —
выходом или истечением срока — рвёт поток, а не оставляет его дожить до конца процесса. Проверено
запуском: открытый `curl -N /api/events` завершается в тот же момент, когда проходит
`DELETE /api/login-session`.

## Переключение плагина

```bash
curl -b jar -X PUT http://localhost:5273/api/plugins/data%3Ahello/preferences \
  -H 'content-type: application/json' \
  -d '{"enabled":true,"disabledContributions":["hello.panel"]}'
```

Тело — та же запись, что лежит в `preferences.json`: файл остаётся источником истины
([data-directory.md](data-directory.md)), а API — вторым способом его изменить. Демон дописывает названный плагин, не трогая остальные записи, и
перезапись атомарна.

Ответ подтверждает записанное и **не содержит состояния плагинов**: подъём идёт своим чередом, и
снимок этого момента назвал бы ещё прежнее состояние, споря с переходами, которые клиент уже
получил потоком. Что произошло дальше — видно в потоке.

Правка файла руками и запрос через API — один и тот же путь применения. Кто записал последним, тот
и прав; это записано в [data-directory.md](data-directory.md) и не лечится.

## Внешний вид и локаль

```bash
curl -b jar -X PUT http://localhost:5273/api/preferences \
  -H 'content-type: application/json' \
  -d '{"appearance":{"colorScheme":"imperium","variant":"dark","scale":"larger"},"locale":"ru"}'
```

Тело — тот же раздел, что лежит в `preferences.json`. **Оба ключа обязательны:** запись заменяет весь
раздел, и тело без локали молча вернуло бы английский интерфейс тому, кто менял только тему. Записи
плагинов этот маршрут не отдаёт и не трогает — у них свой.

Внутри `appearance` поля необязательны и берут значения по умолчанию, а вот значение вне перечисленных
([data-directory.md](data-directory.md)) даёт `400` с диагностикой и не пишет файл вовсе: раздел
применяется целиком, и половина верных полей хуже внятного отказа.

Ответ — записанное. Дальше оно приезжает всем открытым вкладкам событием
`core.preferences.changed`, включая ту, которая его записала: правку файла руками и запись через API
различать незачем.

## Проекты

```bash
curl -b jar http://localhost:5273/api/projects
curl -b jar -X POST http://localhost:5273/api/projects \
  -H 'content-type: application/json' \
  -d '{"folder":"~/code/platform","name":"Платформа"}'
curl -b jar -X PUT http://localhost:5273/api/projects/b7Kq3xv9pQdT \
  -H 'content-type: application/json' \
  -d '{"name":"Платформа","archived":true}'
curl -b jar -X DELETE http://localhost:5273/api/projects/b7Kq3xv9pQdT
```

Снимок — два списка, `projects` и `archived`: архивные показываются отдельно, и клиент читает в той
форме, в которой рисует. Поле `archived` при этом есть и у записи — тело записи и есть тело `PUT`.

**Папка нормализуется до сравнения** ([sessions-and-projects.md](sessions-and-projects.md)): `~`
разворачивается, `.` и `..` снимаются, симлинки раскрываются, на macOS складывается регистр и форма
юникода. В ответе два поля: `folder` — путь для человека, `folderKey` — то, по чему шло сравнение.
Относительный путь даёт `400`: демон запускается из произвольной директории, и развернуть такой путь
обязан тот, кто знает, относительно чего.

**Переименование, архивация и восстановление — один `PUT` целой записью.** Отдельного
`POST /api/projects/:id/archive` нет: он читался бы лучше в терминале, но завёл бы третий и
четвёртый пути и разъехался бы с формой чтения. Оба поля тела обязательны — тело без `archived`
разархивировало бы проект тому, кто менял только имя. Папку `PUT` не принимает вовсе: она задаётся
при создании и не меняется.

**Эфемерный проект (`id` = `work`) не принимает ни `PUT`, ни `DELETE`** — `409` на любое изменение,
включая переименование. Записи на диске у него нет, а имя даёт локализация интерфейса.

**Удаление безвозвратно и удаляет только запись проекта, если `sessionCount = 0`.** Папку
пользователя платформа не удаляет никогда; подтверждение спрашивает интерфейс, а не маршрут.
Если `sessionCount > 0`, маршрут отвечает `409` и не меняет ни запись проекта, ни записи сессий:
индивидуальное удаление сессий и безопасный каскад появятся в срезе 10.

`availability` — состояние папки на этот момент: `available` или `missing`. Оно меняется само по
себе, поэтому смену приносит событие `core.projects.changed`, а не ответ запроса
([event-bus.md](event-bus.md)). `sessionCount` считается для снимка по JSONL-заголовкам сессий:
сравнивается `folderKey`, поэтому записи дерева читать не требуется.

## Провайдеры и модели

```bash
curl -b jar http://localhost:5273/api/providers
curl -b jar http://localhost:5273/api/providers/anthropic/models
```

`:providerId` — идентификатор провайдера у агентного рантайма (`anthropic`, `openai`), он же
идентификатор кастомного провайдера, зарегистрированного плагином
([models-and-providers.md](models-and-providers.md)).

**Моделей в снимке провайдеров нет.** У 38 встроенных провайдеров их больше тысячи
([runtime-checks.md](runtime-checks.md), проверка 28), а список провайдеров показывает не их. Модели
берутся отдельным запросом по одному провайдеру.

`auth` — статус авторизации, и состояний у него три:

| `auth.kind`    | Что значит                                                         |
| -------------- | ------------------------------------------------------------------ |
| `configured`   | кред есть; `type` — ключ или подписка, `source` — откуда он взялся |
| `unconfigured` | креда нет                                                          |
| `unknown`      | сказать нечем: `credentials.json` не читается                      |

`source` приходит от рантайма и показывается как есть: `ANTHROPIC_API_KEY`, `OAuth`,
`stored credential`. Для креда из окружения это единственное, по чему человек поймёт, почему из
провайдера не выйти.

`logins` — способы интерактивного входа. Пустой список значит «войти нечем»: кред берётся только из
окружения. У встроенных провайдеров таких нет, но у `openai-codex` нет входа по ключу — вью обязано
показывать доступное, а не считать ключ всегда возможным.

**Обновление динамических списков — одно на всех, а не по провайдеру.** `POST /api/providers/refresh`
без тела. Это не наш выбор формы, а форма рантайма: он умеет обойти все настроенные динамические
провайдеры разом, сам обновив перед этим OAuth-токены, а обновления одного провайдера у него нет
вовсе. Разбирать его оркестрацию ради фильтра значило бы переписать её у себя
([agent-runtime-contract.md](agent-runtime-contract.md)). В ответе — по итогу на каждый динамический
провайдер (`providerId`, `modelCount`, `error`, если не приехало) и `aborted` на весь обход. **Ошибка
провайдера не отказ маршрута:** его прежний список остаётся в силе, и сказать об этом надо, а не
уронить весь ответ. Следом публикуется `core.providers.changed` ([event-bus.md](event-bus.md)).

**Негодный `credentials.json` не отменяет ответ:** `GET /api/providers` отвечает `200`, кладёт беду
в `problem` и ставит всем `auth.kind: "unknown"`. Это намеренное отличие от проектов, где негодный
файл даёт `409` на все маршруты: список проектов **живёт** в негодном файле, а каталог провайдеров
от него не зависит вовсе. Пустое вью провайдеров чинить файл не помогает, а вью с честным «сказать
нечем» — помогает ([data-directory.md](data-directory.md)). Список моделей от кредов не зависит и
подавно: он лежит в пакете рантайма.

**Выход отдаёт нынешний статус провайдера, а не пустой ответ.** Причина — ловушка «нажал выход,
ничего не изменилось»: кред из окружения платформе не принадлежит, убрать его нечем, и провайдер
останется настроенным. Ответ говорит об этом прямо, а не оставляет человека гадать. Логаут при живой
попытке входа сначала отменяет её: иначе идущий вход дописал бы кред обратно уже после удаления.

## Интерактивный вход в провайдера

Вход — это диалог: провайдер показывает ссылку или код устройства, спрашивает ключ, сообщает
прогресс. Разложен он на три части.

```bash
curl -b jar -X POST http://localhost:5273/api/provider-logins \
  -H 'content-type: application/json' -d '{"providerId":"anthropic","method":"oauth"}'
curl -b jar -X POST http://localhost:5273/api/provider-logins/a1b2/answer \
  -H 'content-type: application/json' -d '{"stepId":"a1b2-1","value":"sk-ant-…"}'
curl -b jar -X DELETE http://localhost:5273/api/provider-logins/a1b2
```

### Кадр шага входа

Шаги едут **кадром существующего SSE-соединения**:

```json
{
  "index": 42,
  "time": "2026-07-29T09:11:04.512Z",
  "frame": "login-step",
  "attemptId": "a1b2",
  "providerId": "anthropic",
  "step": { "kind": "prompt", "prompt": { "stepId": "a1b2-1", "kind": "secret", "message": "…" } }
}
```

**Это не событие шины.** Событие шины — уведомление всем подписчикам, а шаг входа адресован одному
инициатору и ждёт ответа; запрос-ответ по шине запрещён ([event-bus.md](event-bus.md)). До плагинов
шаг через шину не доходит. Кадр различается **значением** поля `frame` — тем же приёмом, каким кадр
события плагина различается наличием `plugin`, — и в типах протокола объединение кадров шины и кадры
не с шины разделены: подписчик шины формы этого кадра не принимает вовсе. Проверяется именно
значение, а не наличие поля: классов кадра больше одного.

Нумерация общая, кадр попадает в окно догона. **Корректность на окно не опирается:**
переподключившаяся вкладка перечитывает `GET /api/provider-logins` и восстанавливает диалог из
снимка — там лежит всё сказанное и вопрос, который ждёт ответа.

**Кадр уходит только у попытки, начатой этой стороной.** Шаги попытки, которую начал плагин, едут в
его воркер и никуда больше: окажись они ещё и в потоке, у одного вопроса стало бы два отвечающих. В
снимке попытка плагина при этом видна, с `answerable: false` — человек должен понимать, почему
провайдер занят.

### Отказы

| Код   | Когда                                                                   |
| ----- | ----------------------------------------------------------------------- |
| `409` | в этого провайдера уже входят — в теле `conflict` с идущей попыткой     |
| `409` | шаг больше не ждёт ответа: форма отправлена дважды или ответ на прошлый |
| `409` | попытку начал плагин, и отвечает на неё он                              |
| `409` | `credentials.json` не читается: вход всё равно нечем будет сохранить    |
| `404` | такой попытки нет — она кончилась, истекла или её отменили              |

**Второй вход в того же провайдера отклоняется, а не отменяет первый.** Автоотмена убивала бы
наполовину пройденный диалог у того, кто его ведёт.

**Попытки не переживают перезапуск демона** — реестр в памяти намеренно: на той стороне диалога
после перезапуска уже никого нет. Не переживают они и выход из платформы: попытки закрывшейся сессии
гаснут, попытки плагинов живут.

## Маршруты плагинов

Решено, кода нет ([plugins.md](plugins.md), «Чего ещё нет»).

**Плагин объявляет свои HTTP-маршруты.** Обработчик исполняется в воркере плагина. Своего порта или
сокета плагин не открывает: все запросы приходят на единственный слушатель и проходят через
диспетчер ядра. Ветки маршрутов снимаются при выгрузке и перезагрузке плагина.

**Проверка сессии остаётся в диспетчере,** то есть распространяется и на маршруты плагинов: маршрут
чужого кода не может случайно оказаться незащищённым, потому что защита не в обработчике.

**API ядра публично.** Браузерная часть любого плагина читает состояние ядра — сессии, проекты,
плагины, провайдеров — тем же API, которым пользуются встроенные вью. Проксировать состояние ядра
через собственный воркер не нужно.

**Обновления идут шиной, чтение — запросом.** Браузер узнаёт об изменениях из SSE-потока и
перечитывает состояние. Публикация в шину из браузера — тоже запрос через ядро, отдельной лазейки для
неё не появляется.

**Публичный маршрут — отдельный вид вклада,** а не флаг у обычного маршрута: «маршрут» и «публичный
маршрут» — разные вещи, и написать второе, имея в виду первое, нельзя случайно. Диспетчер пропускает
проверку сессии только для этого вида.

- **Аутентификация публичного маршрута — забота плагина.** Платформа своей схемы не навязывает:
  GitHub подписывает тело своим ключом, другой сервис носит токен в заголовке, третий не умеет ни
  того, ни другого. Обработчик получает запрос как есть и решает сам.
- **Публичные маршруты видны человеку.** Это единственная поверхность платформы, открытая наружу, и
  вью плагинов обязано показывать её списком: какой плагин что открыл. Вклад переключается, как любой
  другой, — закрыть маршрут можно, не выключая плагин целиком.
- **Лимит частоты и лимит тела для этого вида — часть механизма, а не пожелание:** иначе один
  публичный маршрут превращает демон в мишень.
- **Журнал обязан различать вызовы извне и вызовы из интерфейса,** иначе в логах не видно, что
  действие пришло снаружи.

Каждый запрос к маршруту плагина — это сериализация в воркер и обратно, поэтому лимит тела и таймаут
ответа входят в контракт: без них зависший плагин держит соединение, а их всего шесть на источник.

## Чего ещё нет

- **Маршрутов плагинов** (`/p/<pluginId>/...`) и вида вклада «публичный маршрут»: регистрировать в
  них пока нечего.
- **Публикации в шину из браузера** — она тоже идёт запросом через ядро, но маршрута для неё ещё нет:
  потребителя нет.
- **Отдачи браузерных ассетов**: в dev-режиме это делает Vite, в продакшне будет делать демон
  ([toolchain.md](toolchain.md)).

## Почему так

### SSE, поллинга нет

Веб-интерфейс должен показывать то, что происходит прямо сейчас: агент печатает ответ, вызывает
инструмент, плагин упал и перезапускается. Всё это порождает сервер, а не пользователь. Отдельно
играет замысел: демон работает сутками, и опрос сервера — это постоянный фоновый трафик и пробуждения
процесса всё время, пока открыта вкладка, независимо от того, происходит ли что-нибудь.

**Поллинг.** Отвергнут владельцем продукта. Независимо от этого он плохо ложится на замысел: цена
растёт со временем работы демона, а не с активностью пользователя.

**WebSocket.** Даёт двунаправленный канал, но поток от клиента к серверу не нужен: команды редки и
укладываются в обычный HTTP. Взамен пришлось бы тащить свой слой протокола поверх сокета, свой
реконнект и отдельную возню с проксированием. SSE — обычный HTTP-ответ, а `EventSource`
переподключается сам.

**Длинный поллинг.** Тот же поллинг, только с большими таймаутами.

Следствие, определившее вход: признак аутентификации едет в cookie — `EventSource` не умеет задавать
заголовки, а класть токен в query-параметр нельзя ([authentication.md](authentication.md)).

### Одно соединение на клиента

Проверка запуском закрыла вопрос гранулярности: браузер держит шесть HTTP/1.1-соединений на источник,
и пул общий на весь браузер, а не на вкладку. Шесть SSE-потоков занимают его целиком, после чего
перестают работать и обычные запросы, и загрузка страниц того же источника
([runtime-checks.md](runtime-checks.md), проверка 9).

**Поток на сессию агента.** Отвергнуто: пять-шесть открытых сессий исчерпывают пул и парализуют весь
интерфейс, причём молча.

**Локальный HTTPS ради HTTP/2.** Снял бы лимит, но добавил самоподписанный сертификат,
предупреждение браузера при первом входе и возню с доверием к сертификату — ради удобства, которое
даёт одна строчка мультиплексирования на фронте.

Цена: появляется точка, через которую проходят все серверные события, — удобно для отладки, но она же
единственная точка отказа. Разрыв — это разрыв для всего интерфейса сразу, а не для одной вьюхи.

### Все события в потоке, с индексом, фильтрует клиент

**Подписка на уровне протокола:** клиент объявляет, какие типы событий и какие сессии ему нужны.
Трафик минимален. Отвергнуто владельцем продукта; кроме его решения против работает то, что на
сервере появляется состояние на каждое соединение, а каждый новый тип события требует ответа на
вопрос, как он попадает в подписку. Замер подтвердил: рассылка по подписчикам стоит 3% пути кадра.

**Полный перезапрос состояния при каждом разрыве, без индексов.** Проще всего. Отвергнуто: короткий
сетевой сбой превращался бы в перезагрузку всего интерфейса, а SSE и так умеет догонять — не
пользоваться этим значит платить за отказ от готового механизма.

Индекс задаёт полный порядок **в потоке**. Это не обещание про порядок на серверной шине: там порядок
между разными воркерами по-прежнему не гарантирован ([event-bus.md](event-bus.md)).

Сервер обязан хранить окно последних событий — состояние, которого раньше в веб-слое не было, и оно
живёт в памяти процесса. Демон перезапустился — окно пусто, любой клиент получает `core.stream.gap` и
пересинхронизируется. Для dev-режима с `node --watch` это штатный случай, а не редкий.

### `node:http` со своим табличным диспетчером

Состав того, что обслуживает HTTP-слой, решил вопрос: небольшой фиксированный API ядра, SSE-поток
(сырой `ServerResponse`, живущий часами), маршруты плагинов, появляющиеся и исчезающие при каждой
перезагрузке любого плагина, браузерные ассеты по URL с ревизией и отдача файлов потоком. Большая
часть этого — динамика.

Проверено запуском (Fastify 5.10.0, Hono 4.12.32, sirv 3.0.2, Node 24.18.0):

| Проверка                                    | Результат                                |
| ------------------------------------------- | ---------------------------------------- |
| Fastify: маршрут после `listen()`           | `FST_ERR_INSTANCE_ALREADY_LISTENING`     |
| Fastify: повторная регистрация того же пути | `FST_ERR_DUPLICATED_ROUTE`               |
| Hono: маршрут после старта                  | добавляется, отвечает `200`              |
| Hono: тот же путь второй раз                | отвечает **прежний** обработчик          |
| Hono: API снятия маршрута                   | отсутствует                              |
| sirv: `ETag` и `If-None-Match`              | `200` с etag, затем `304`                |
| sirv: `Range: bytes=0-99`                   | `206`, `content-range: bytes 0-99/10000` |
| sirv: `immutable` вместе с `maxAge`         | `public,max-age=31536000,immutable`      |
| sirv: `GET /../../etc/hosts`                | `404`                                    |

**Fastify.** Схемы на маршрут, `@fastify/static`, `@fastify/cookie`, инкапсуляция — всё это применимо
только к маленькой фиксированной части, потому что динамика всё равно уходит за wildcard и наш
диспетчер. Платить фреймворком за меньшую часть работы смысла нет, а динамику он не принимает вовсе.

**Hono.** Маленький, стандартные `Request`/`Response`. Отвергнут по результату проверки: снять
маршрут нельзя, повторная регистрация оставляет живым старый обработчик — после перезагрузки плагина
отвечала бы его прошлая ревизия. Это не ошибка, а тихо устаревший код, то есть худший исход. Плюс
адаптер между Web-потоками и потоками Node ложится ровно на два места, где контроль над потоком нужен
больше всего.

**Express 5.** Против Fastify не даёт ничего, типы слабее.

**Писать раздачу файлов самим.** `Range`, `304`, нормализация пути — известный источник дыр, а
проверка показала, что узкая библиотека это уже делает правильно. Поэтому скучные и опасные части
берём библиотеками: `sirv` — раздача файлов, `cookie` — разбор и сборка заголовка.

SSE пишется в `ServerResponse` напрямую — без прослоек, которые могут буферизовать поток. По той же
причине прокси Vite в dev-режиме не должен буферизовать ответ ([runtime-checks.md](runtime-checks.md),
проверка 18).

Цена: маршрутизация, отображение ошибок в коды, лимиты тела и таймауты — наши, а валидацию входа надо
звать явно, забытый вызов компилятор не поймает. Гасится тем, что таблица маршрутов ядра маленькая и
покрыта тестами. Взамен диспетчер стал единственным местом, где применяется проверка сессии: новый
маршрут не может случайно оказаться незащищённым («Проверка сессии» выше).

### Два замка на изменяющем запросе

`SameSite=Strict` закрывает всё, что стоит за сессией: межсайтовый запрос приходит без cookie и
получает `401`. Но маршруты входа открыты по необходимости — состояние входа и сам вход обязаны
работать до всякой сессии, — и вот там чужая страница вправе **отправить** запрос, даже не имея права
прочитать ответ. На демоне, в который владелец ещё не входил, это значило бы, что пароль платформе
назначает кто угодно, чью страницу владелец открыл: одного `POST /api/account` достаточно, дальше
машина принадлежит не ему. Окно узкое — до первого входа, — но исход в нём полный.

Отсюда две проверки, и каждая закрывает слепое пятно другой:

- **`Sec-Fetch-Site`** — единственный признак межсайтовости, который нельзя подделать со страницы: его
  ставит браузер, а не код. Слепое пятно: старые браузеры его не присылают вовсе.
- **Обязательный `application/json`** — это не про разбор тела, а про предзапрос. Запрос с
  `text/plain` считается «простым» и уходит без предзапроса, поэтому CORS его не останавливает; с
  `application/json` предзапрос обязателен, а на `OPTIONS` мы не отвечаем. Слепое пятно: против
  запроса не из браузера не помогает, но там и межсайтовости нет.

**Список доверенных `Origin`.** Отвергнуто: список пришлось бы откуда-то брать и настраивать —
интерфейс приезжает то с порта Vite через прокси, то из туннеля, — а сверх двух проверок выше он не
добавил бы ничего.

**Свой CSRF-токен в теле.** Классический способ, и он не нужен: `SameSite=Strict` делает ровно это
для маршрутов за сессией, а для открытых маршрутов токен пришлось бы сначала выдать неизвестному —
то есть выдать и атакующему.

Цена: клиент обязан ставить `content-type` на каждый изменяющий запрос, включая `curl` в примерах и
тестовые обвязки. Забытый заголовок отвечает `415`, а не молчаливой ошибкой разбора, поэтому цена
видна сразу.

### Маршруты плагина и публичное API ядра

**Только вызов процедуры в свой воркер, маршрутов у плагина нет.** Один механизм и одинаковый стиль
на обеих сторонах, диспетчер вообще не меняется при загрузке плагинов. Отвергнуто владельцем
продукта. Вариант к тому же не полон: отдать файл потоком и принять входящий вебхук вызовом процедуры
нельзя.

**Только свои маршруты, API ядра остаётся внутренним для нашего фронтенда.** Механизм ровно один, и у
нас свобода менять API ядра. Отвергнуто владельцем продукта: тогда каждое встроенное вью писало бы
заново выдачу данных, которыми ядро уже владеет, и каждое чтение шло бы лишним хопом через воркер.

**Публично только чтение, любое изменение — через воркер плагина.** Выглядит аккуратнее. Отвергнуто
владельцем продукта; и граница эта всё равно держалась бы договорённостью, а не механизмом —
включённый плагин доверен и читает директорию данных сам.

**Публичный маршрут с секретом от платформы: адрес выдаём мы, проверяем сами.** Открыть платформу
наружу по невнимательности было бы нельзя, а секрет можно перевыпустить. Отвергнуто владельцем
продукта: адрес маршрута перестаёт быть свойством плагина — его надо где-то узнать, куда-то
скопировать руками, и он меняется при перевыпуске.

**Публичных маршрутов нет вовсе: кому нужен вебхук, слушает свой порт.** Поверхность платформы не
растёт. Отвергнуто: плагин своего порта не открывает, и сценарий с входящими вебхуками остаётся без
механизма.

**Флаг «без сессии» у обычного маршрута.** Меньше видов вкладов. Отвергнуто: разница между
защищённым и открытым наружу маршрутом слишком велика для булева поля, которое легко скопировать из
чужого примера вместе со значением. Поле `access` в таблице маршрутов ядра — не то же самое: она наша,
целиком видна в одном файле и покрыта тестами, а вклад приходит из чужого кода.

Цена: **API ядра становится публичным контрактом** ([public-contract.md](public-contract.md)) —
ломать его теперь дорого. Ответственность за открытую наружу дыру целиком на авторе плагина, поэтому
документация SDK обязана описывать публичный маршрут не как удобство, а с прямым предупреждением.
Браузерная часть плагина получает двух адресатов — API ядра и свои маршруты, — и в SDK они должны
выглядеть по-разному, иначе автор будет искать сессии в своём неймспейсе.

Открытым остаётся, требовать ли для публичного маршрута отдельного включения человеком: сейчас он
подчиняется общему правилу «вклад включённого плагина включён».
