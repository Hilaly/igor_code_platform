# ADR-0003: pnpm workspaces as the package manager

- **Статус:** Accepted
- **Дата:** 2026-07-26

## Контекст

Монорепозиторий содержит несколько пакетов, и один из них — SDK — публичный: его увидят авторы
плагинов, посторонние по отношению к репозиторию люди.

Ключевой риск монорепы — незадекларированные зависимости. Если менеджер пакетов складывает все
зависимости в общий корневой `node_modules`, пакет может импортировать то, чего нет в его
`package.json`, и локально всё соберётся. Ошибка вскроется только у потребителя пакета — в нашем
случае у автора плагина, которому SDK не заведётся.

Выбор рантайма зафиксирован в [ADR-0002](0002-nodejs-lts-as-runtime.md).

## Решение

**pnpm workspaces.** Внутренние связи между пакетами — через протокол `workspace:*`.
Версия pnpm фиксируется полем `packageManager` в корневом `package.json` и ставится через
corepack, чтобы у всех участников был один и тот же инструмент.

## Альтернативы

- **npm workspaces.** Отвергнут. Есть на любой машине и не требует установки, но хойстит
  зависимости в корень — ровно тот сценарий, из-за которого сломанный SDK обнаруживается не у
  нас, а у автора плагина.
- **bun install при Node-рантайме.** Отвергнут вслед за ADR-0002: второй тулчейн в проекте ради
  одной команды, а `bun.lock` читается только Bun.
- **Yarn с Plug'n'Play.** Отвергнут. Модель ещё строже pnpm, но PnP плохо уживается с
  инструментами, рассчитанными на обычный `node_modules`, — а у плагинов, по решению владельца,
  свои npm-зависимости, и им нужен предсказуемый способ разрешения модулей.

## Последствия

- На машине разработчика нужен pnpm (через corepack). Лок-файл — `pnpm-lock.yaml`.
- Пакет, забывший объявить зависимость, падает сразу у нас, а не у пользователя SDK.
- Решение касается только сборки репозитория. Чем демон устанавливает зависимости плагинов в
  рантайме — отдельный вопрос, и совпадать с pnpm он не обязан.
