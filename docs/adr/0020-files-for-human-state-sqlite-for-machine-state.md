# ADR-0020: Files for human-owned state, SQLite for machine-owned state

- **Статус:** Accepted
- **Дата:** 2026-07-26

## Контекст

[ADR-0008](0008-data-directory-config-and-instance-lock.md) зафиксировал одну директорию данных и
`config.json` внутри неё, но не формат остального состояния. А состояние у платформы разнородное:

- то, что правит человек, — конфигурация. Она обязана открываться редактором и диффиться;
- то, что пишет платформа и что растёт, — дерево записей сессий Pi, журнал. У сессии тысячи
  записей, и по ним нужны выборки: список сессий, путь до корня, записи определённого типа.

Хранилище сессий у Pi — внедряемый интерфейс `SessionStorage`
([agent-runtime-contract.md](../agent-runtime-contract.md)), поэтому формат выбираем мы, а не он.
Референсная реализация в комплекте Pi — JSONL-файлы.

`node:sqlite` входит в стандартную библиотеку Node 24.18.0 и на этой версии уже не печатает
`ExperimentalWarning` — проверено запуском, [runtime-checks.md](../runtime-checks.md), проверка 10.
Там же измерения: 10 000 записей в одной транзакции — 20 мс, выборка по индексированному полю —
1.6 мс.

## Решение

**Форму хранения определяет владелец данных.**

**Файлы — то, что правит человек.** `config.json` и `credentials.json` (учётные данные
LLM-провайдеров: их пишет Pi через `CredentialStore.modify`, но человеку нужен доступ, чтобы
починить сломанный логин руками). Запись атомарна: временный файл в той же директории плюс
`rename`. На файле кредов права `0600`.

**SQLite — то, что пишет платформа и что растёт.** Один файл `state.db`, доступ через встроенный
`node:sqlite`: сессии агентов, журнал, всё последующее состояние такого рода.

**Записи сессии хранятся блобом с вынесенными колонками.** Формат записи — чужой контракт, мы его
не разбираем: в колонки выносятся только поля, по которым нужны выборки (идентификатор, родитель,
тип, время), остальное лежит JSON-текстом в той же строке.

**Миграции — с первого дня.** Версия схемы в `user_version`, миграции только вперёд, применяются
при открытии базы. Первая миграция создаёт схему; отсутствие базы и пустая база — один и тот же
путь кода.

## Альтернативы

**Всё файлами (JSON + JSONL).** Максимально прозрачно, чинится руками, бэкап — копия папки, и у
Pi такая реализация уже есть. Отвергнуто по цене чтения: «список сессий» превращается в обход всех
файлов, выборка записей по типу — в разбор всего дерева, а сериализация конкурентных записей
целиком на нас. Это ровно та работа, которую SQLite уже сделал.

**Всё в SQLite.** Последовательнее, но конфигурация перестаёт правиться редактором, а владелец
продукта зафиксировал именно `config.json`. Хранить настройки в базе, которую нельзя открыть без
инструмента, — потеря возможности починить демона, который не стартует.

**`better-sqlite3` вместо встроенного модуля.** Быстрее и API богаче, но это нативная сборка на
машине пользователя — против ставки на возможности рантайма
([ADR-0002](0002-nodejs-lts-as-runtime.md)) и лишний барьер для установки.

**Внешняя СУБД (PostgreSQL и подобные).** Локальный однопользовательский демон, который «запускается
и больше не глушится», не может требовать поднятого рядом сервера. Против вижна.

## Последствия

- Механизмов записи два, значит правило разделения должно быть явным и повторяемым: правит человек
  → файл; пишет платформа и это растёт → база. Новое состояние сначала проходит через этот вопрос.
- Бэкап перестаёт быть наивным копированием: файл базы на живом демоне копировать нельзя. Для этого
  берётся `backup()` из `node:sqlite` — он есть в экспортах модуля (проверено).
- Миграции нужны с самого начала, в том числе для схемы журнала. Плата за то, что состояние
  перестало быть текстом.
- Поиск по содержимому записей сессии невозможен без разбора блоба. Понадобится — добавим
  отдельный индекс или FTS, не переделывая хранилище: колонки для выборок уже вынесены.
- `node:sqlite` — молодой API. Правило перечитывать [runtime-checks.md](../runtime-checks.md) при
  обновлении Node распространяется и на него; теперь оно защищает не удобство, а хранилище.
