# ADR-0053: Plugin backend access is its own routes, the public core API and the bus

- **Статус:** Accepted
- **Дата:** 2026-07-26

## Контекст

[ADR-0043](0043-plugin-sdk-is-an-importable-module-surface.md) обещал, что стиль API одинаков на
браузерной и серверной стороне, но **чем** браузерная часть плагина разговаривает с бэкендом, не
решал. Без этого не пишется ни одно из пяти встроенных вью
([ADR-0047](0047-plugin-management-in-the-core-other-views-as-built-in-plugins.md)): все они состоят
из чтения состояния ядра и действий над ним.

Что уже зафиксировано и ограничивает выбор:

- слушатель один, маршрутизация — собственный табличный диспетчер, префиксные ветки для маршрутов
  плагинов меняются на живом сервере ([ADR-0026](0026-web-api-on-node-http-with-a-table-dispatcher.md));
- проверка сессии применяется в диспетчере, а не в обработчике (там же);
- шина односторонняя, запрос-ответ поверх неё запрещён, но у каждого состояния обязан быть способ
  спросить «как сейчас» ([ADR-0041](0041-bus-events-are-notifications-state-is-requested-from-its-owner.md));
- обновления доходят до браузера единственным SSE-соединением
  ([ADR-0017](0017-single-sse-connection-with-a-frontend-event-bus.md),
  [ADR-0038](0038-sse-sends-every-event-with-an-index.md)).

## Решение

**Плагин объявляет свои HTTP-маршруты.** Обработчик исполняется в воркере плагина. Своего порта или
сокета плагин не открывает: все запросы приходят на единственный слушатель и проходят через
диспетчер ядра. Ветки маршрутов снимаются при выгрузке и перезагрузке плагина.

**Проверка сессии остаётся в диспетчере, то есть распространяется и на маршруты плагинов.** Маршрут
чужого кода не может случайно оказаться незащищённым, потому что защита не в обработчике.

**API ядра публично.** Браузерная часть любого плагина читает состояние ядра — сессии, проекты,
плагины, провайдеров — тем же API, которым пользуются встроенные вью. Проксировать состояние ядра
через собственный воркер не нужно.

**Обновления идут шиной, чтение — запросом.** Браузер узнаёт об изменениях из SSE-потока и
перечитывает состояние; шина остаётся уведомлением. Публикация в шину из браузера — тоже запрос через
ядро, отдельной лазейки для неё не появляется.

## Альтернативы

**Только вызов процедуры в свой воркер, маршрутов у плагина нет.** Один механизм и одинаковый стиль
на обеих сторонах, диспетчер вообще не меняется при загрузке плагинов. Отвергнуто владельцем
продукта. Независимо от вкуса вариант и не полон: отдать файл потоком и принять входящий вебхук
(сценарий 4 из [vision.md](../vision.md)) вызовом процедуры нельзя.

**Только свои маршруты, API ядра остаётся внутренним для нашего фронтенда.** Механизм ровно один, и
у нас свобода менять API ядра. Отвергнуто владельцем продукта: тогда каждое из пяти встроенных вью
писало бы заново выдачу данных, которыми ядро уже владеет, и каждое чтение шло бы лишним хопом через
воркер.

**Публично только чтение, любое изменение — через воркер плагина.** Выглядит аккуратнее: изменения
проходят через код, где их можно проверить и записать. Отвергнуто владельцем продукта; и граница эта
всё равно держалась бы договорённостью, а не механизмом — включённый плагин доверен и читает
директорию данных сам ([ADR-0016](0016-plugin-enablement-as-the-trust-boundary.md)).

## Последствия

- **API ядра становится публичным контрактом.** Ломать его теперь дорого: это версия платформы
  ([ADR-0044](0044-plugin-manifest-lives-in-package-json.md)), а не внутренняя правка. Значит его
  придётся описать в `docs/` как публичный интерфейс, а не оставить видимым из кода.
- Маршрут плагина — это вклад: выключается отдельно
  ([ADR-0032](0032-every-contribution-is-switchable.md)) и исчезает вместе с плагином. Открытая
  страница, дергающая снятый маршрут, обязана получать внятный ответ, а не общий «не найдено» — по
  тому же правилу, по которому выключенный плагин показывает заглушку вместо пустой страницы
  ([ui-extension-model.md](../ui-extension-model.md)).
- Каждый запрос к маршруту плагина — это сериализация в воркер и обратно. Лимит тела и таймаут ответа
  становятся частью контракта: без них зависший плагин держит соединение, а их у нас всего шесть на
  источник ([runtime-checks.md](../runtime-checks.md), проверка 9).
- Входящие вебхуки получают механизм — это маршрут плагина. Но их аутентификация не является сессией
  пользователя, а диспетчер сейчас проверяет сессию у всего. Как объявляется маршрут, доступный без
  входа, — вопрос, который придётся решить до плагина вебхуков, и решать его надо явно: маршрут без
  проверки сессии, объявленный по невнимательности, открывает платформу наружу.
- Браузерная часть плагина получает два адресата — API ядра и свои маршруты. Это разные вещи по
  смыслу (чужое состояние против своего), поэтому в SDK они и должны выглядеть по-разному, иначе
  автор будет искать сессии в своём неймспейсе.
