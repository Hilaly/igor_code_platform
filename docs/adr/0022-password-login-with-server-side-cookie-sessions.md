# ADR-0022: Password login with server-side cookie sessions

- **Статус:** Accepted
- **Дата:** 2026-07-26

## Контекст

Вижн: один пользователь, один экземпляр платформы, вход по логину и паролю, первый вход создаёт
учётную запись. Механика не выбиралась.

Транспорт накладывает жёсткое ограничение. Всё, что сервер шлёт по своей инициативе, идёт через SSE
([ADR-0013](0013-sse-for-server-initiated-updates.md)), а браузерный `EventSource` не умеет
проставлять заголовки — `Authorization` для основного соединения недоступен. Значит признак
аутентификации обязан ехать в cookie: это единственное, что браузер отправляет с потоком сам.

Демон слушает `http://127.0.0.1` — TLS нет, и в локальной установке не предполагается.

`scryptSync` есть в `node:crypto` и на параметрах `N=2^15, r=8, p=1` считает хеш за 69 мс —
проверено запуском, [runtime-checks.md](../runtime-checks.md), проверка 11.

## Решение

**Пароль хранится как scrypt-хеш.** Соль — 16 байт из `randomBytes`, длина хеша 64 байта,
параметры `N=2^15, r=8, p=1`. Сравнение — `timingSafeEqual`. **Параметры хранятся рядом с хешем**,
чтобы поднять их со временем, не ломая существующий вход: при успешной проверке старым набором хеш
пересчитывается новым.

**Сессия — непрозрачный токен, состояние на сервере.** 32 байта из `randomBytes` в base64url.
В базе ([ADR-0020](0020-files-for-human-state-sqlite-for-machine-state.md)) лежит не токен, а его
SHA-256: копия базы не даёт живых сессий. Рядом — время создания и истечения.

**Cookie:** `HttpOnly`, `SameSite=Strict`, `Path=/`. Флаг `Secure` не ставится — по `http` браузер
такую cookie не отправит вовсе; появится TLS, флаг станет обязательным.

**Проверка на каждом запросе, включая SSE-поток.** Выход удаляет запись сессии, поэтому живой поток
после выхода обрывается, а не доживает до конца процесса.

**Учётная запись создаётся первым входом.** Пока записи об аккаунте нет, API отвечает «требуется
регистрация» и принимает создание; после этого — только вход. Смена пароля удаляет все сессии.

## Альтернативы

**JWT в cookie.** Сервер без состояния — но отзыв требует чёрного списка, то есть состояние
возвращается, только в худшем виде: две структуры вместо одной. При одном пользователе и уже
существующей базе выгоды нет.

**HTTP Basic.** Работает с чем угодно, но пароль летит в каждом запросе, выйти из системы нечем, и
на SSE-поток это тоже распространяется.

**Токен в query-строке для SSE** — обход ограничения `EventSource`. Отвергнуто: секрет попадает в
логи, в историю браузера и в `Referer`.

**argon2id.** Формально сильнее scrypt против атаки на GPU, но в Node это нативная зависимость в
ядре ([ADR-0002](0002-nodejs-lts-as-runtime.md)). Для локального демона с одним паролем
scrypt-хеш за 69 мс — достаточная планка.

## Последствия

- `SameSite=Strict` означает, что переход на интерфейс по ссылке с другого сайта приходит
  неаутентифицированным. Для локального интерфейса это норма и одновременно защита от CSRF без
  отдельного токена.
- Отсутствие `Secure` привязывает решение к локальному доступу. Демон обязан слушать `127.0.0.1`;
  открытие наружу — отдельное решение, и оно тянет за собой TLS, иначе cookie уедет по сети открытой.
- Один пользователь — нет ролей. Плагин, дошедший до API, действует от имени владельца; разграничения
  между плагинами нет и не планируется, границей остаётся включение
  ([ADR-0016](0016-plugin-enablement-as-the-trust-boundary.md)).
- Сессии переживают перезапуск демона, потому что лежат в базе. Это удобно и означает, что истечение
  обязано быть явным — иначе токен живёт вечно.
- 69 мс на проверку пароля — это по построению: вход не может быть быстрым. Значит эндпоинт входа
  нельзя оставлять без ограничения частоты, иначе он же становится способом занять процессор.
  Конкретный механизм (пауза, счётчик неудач) не выбран — открытый вопрос.
