# ADR-0014: The agent runs in-process in the core

- **Статус:** Accepted
- **Дата:** 2026-07-26

## Контекст

[ADR-0010](0010-core-owns-agent-sessions.md) зафиксировал, что сессией владеет ядро и что агент
не исполняется внутри плагина, но оставил открытым, где именно он исполняется: в самом ядре или
в отдельных воркерах ядра.

## Решение

**Агент исполняется в процессе демона, инпроцесс.** Цикл агента и объекты Pi (`Session`,
`AgentHarness`) живут там же, где ядро. Отдельного воркера на сессию нет.

Плагины при этом остаются в своих воркерах — межпоточной остаётся только граница плагина.

## Альтернативы

**Воркер на сессию агента.** Дал бы изоляцию по памяти (`maxOldGenerationSizeMb` работает только
у воркера — [runtime-checks.md](../runtime-checks.md), проверка 5) и параллелизм по CPU.
Отвергнуто владельцем продукта. Технически это ещё и дорого: `Session` и `AgentHarness` —
объекты с богатым API, через границу потока их пришлось бы проксировать целиком, а контекст
диалога сериализовать на каждый шаг.

**Воркер плагина.** Отвергнуто раньше, в [ADR-0010](0010-core-owns-agent-sessions.md).

## Последствия

- Цикл агента не платит за сериализацию. Платят только хуки плагинов — они пересекают границу
  воркера ([agent-runtime-contract.md](../agent-runtime-contract.md)).
- Изоляции по памяти у сессий нет. Утечка в цикле агента или распухший контекст бьют по демону
  целиком, и ограничить сессию по памяти нечем. Это прямая плата за инпроцесс.
- Все сессии делят один event loop с веб-API и SSE. Любая тяжёлая синхронная работа в цикле
  агента задержит и отдачу интерфейса, и потоки событий. Требование к реализации, а не пожелание.
- Основная нагрузка агента — ожидание модели, то есть I/O; CPU уходит на разбор стрима. Тяжёлые
  инструменты приносят плагины, а они в воркерах — туда нагрузка и уйдёт.
- Откат к воркерам остаётся возможным без ломки контракта: API плагинов уже асинхронный
  ([ADR-0011](0011-plugins-run-as-supervised-workers.md)), сигнатуры при переносе не изменятся.
