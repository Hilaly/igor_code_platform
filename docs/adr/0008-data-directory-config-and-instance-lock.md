# ADR-0008: Data directory, configuration file and single-instance lock

- **Статус:** Accepted
- **Дата:** 2026-07-26

## Контекст

Демон запускается из терминала и, по замыслу, больше не глушится. Владелец продукта
зафиксировал: у запуска есть ровно один опциональный аргумент — путь к директории данных, по
умолчанию `~/.sovereign_platform`. Внутри неё лежит `config.json`. Всё остальное состояние
платформы хранится там же: сессии агентов, учётные данные LLM-провайдеров, любые данные, которые
платформа создаёт сама.

Из этого следует ограничение на зависимости. Библиотеки, которые по умолчанию пишут в домашнюю
директорию, использовать «как есть» нельзя: CLI из состава Pi, например, держит своё состояние в
`~/.pi/agent/`. Библиотечная часть Pi этого не навязывает — и хранилище сессий
(`SessionStorage`), и хранилище кредов (`CredentialStore`) там внедряются приложением.

Второй демон на той же директории данных недопустим: два процесса писали бы в одну базу и один
и тот же лог, а «сингл инстанс» заявлен в вижне. Порт для этого не годится — он берётся из
конфигурации, которая читается уже после открытия директории, и не мешает поднять второй демон
на другом порту поверх тех же данных. Делимый ресурс здесь — директория, её и надо защищать.

## Решение

**Аргумент запуска один** — путь к директории данных. Всё, что настраивается, настраивается в
`config.json` внутри неё.

**Никто не пишет за пределы директории данных.** Внешние библиотеки подключаются только через
внедряемые реализации хранилищ; реализация, которая ходит в `$HOME` сама, не используется.

**Единственность экземпляра защищается лок-файлом** `<datadir>/daemon.lock`:

1. Захват — атомарное эксклюзивное создание файла: `fs.open(path, "wx")`. Это единственный
   примитив блокировки, который в Node работает одинаково на всех целевых платформах: за ним
   стоит `O_CREAT|O_EXCL` — операция ядра, гонку двух одновременных стартов она исключает.
2. В файл пишется JSON `{ pid, startedAt, hostname, port }`. Содержимое не участвует в захвате,
   оно нужно для диагностики и для проверки на протухание.
3. Захват не удался (`EEXIST`) — файл читается:
   - `hostname` чужой → отказ. Директория данных лежит на сетевом диске, проверить процесс на
     другой машине нечем, и гадать здесь дороже, чем отказать.
   - `pid` жив (`process.kill(pid, 0)` не бросил `ESRCH`) → отказ. В сообщении — `pid` и порт
     работающего демона, чтобы пользователь понимал, к кому идти.
   - `pid` мёртв → лок протух после `kill -9` или падения машины. Файл удаляется, захват
     повторяется **один раз**. Второй `EEXIST` означает, что параллельный старт нас опередил, —
     отказ.
4. Освобождение — удаление файла при штатном завершении (`SIGINT`, `SIGTERM`). После `kill -9`
   файл остаётся; этот случай закрывает проверка на протухание из пункта 3.

Оба примитива проверены запуском на Node 24.18.0 — [runtime-checks.md](../runtime-checks.md),
проверка 8.

## Альтернативы

**`flock` / блокировка дескриптора.** Правильный способ на POSIX: лок снимается ядром вместе с
процессом, протухших локов не бывает вовсе. Но в Node нет встроенного `flock`, а на Windows его
нет как понятия. Пришлось бы тянуть нативную зависимость ради одной функции — против ставки на
встроенные возможности рантайма ([ADR-0002](0002-nodejs-lts-as-runtime.md)).

**Занять порт и считать это локом.** Не защищает директорию: два демона на разных портах
спокойно откроют одни и те же данные. Плюс порт известен слишком поздно.

**Лок в общесистемном месте (`/var/run`, `%TEMP%`).** Ломает главное правило этого решения —
всё состояние внутри директории данных. К тому же локов должно быть столько, сколько директорий
данных, а не один на машину.

**Несколько аргументов командной строки вместо `config.json`.** Отвергнуто владельцем продукта:
аргумент один, остальное — в конфиге.

## Последствия

- Перенос установки — это копирование одной директории. Ничего не остаётся в `$HOME`.
- Любая новая зависимость, которая хранит состояние, проверяется на возможность указать ей путь.
  Не умеет — не берём или оборачиваем. Это дополнительный критерий выбора библиотек.
- Возможен ложный отказ старта: система переиспользовала `pid` мёртвого демона, и живым окажется
  чужой процесс. Плата принята сознательно — ложный отказ с внятным сообщением дешевле, чем два
  демона на одних данных. Лечится удалением `daemon.lock` руками.
- Демон, зависший без реакции на сигналы, держит лок до `kill`. Это правильно: он всё ещё владеет
  директорией.
- Проверка на протухание удаляет чужой файл. Поэтому она делает ровно одну повторную попытку —
  чтобы два одновременно стартующих демона не могли по очереди сносить лок друг друга.
