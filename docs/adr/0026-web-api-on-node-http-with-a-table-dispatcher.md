# ADR-0026: Web API on node:http with a table dispatcher

- **Статус:** Accepted
- **Дата:** 2026-07-26

## Контекст

Транспорт зафиксирован раньше: одно долгоживущее SSE-соединение плюс разовые HTTP-запросы
([ADR-0013](0013-sse-for-server-initiated-updates.md),
[ADR-0017](0017-single-sse-connection-with-a-frontend-event-bus.md)). Отказ от изолированных
iframe ([ADR-0023](0023-single-renderer-tier-for-plugin-ui.md)) убрал второй origin — слушатель
один. Оставалось выбрать, на чём написан HTTP-слой.

Состав того, что этот слой обслуживает, решает вопрос:

- небольшой фиксированный API ядра — вход, плагины, сессии;
- SSE-поток, то есть сырой `ServerResponse`, живущий часами;
- маршруты плагинов, появляющиеся и исчезающие при каждой перезагрузке любого плагина;
- браузерные ассеты плагинов по URL с ревизией
  ([ADR-0025](0025-plugin-browser-code-is-built-by-the-daemon.md)) — с `Range`, `ETag` и
  бессрочным кешированием;
- отдача файлов плагинов потоком.

Большая часть этого — динамика. Проверено запуском (Fastify 5.10.0, Hono 4.12.32, sirv 3.0.2,
Node 24.18.0):

| Проверка                                    | Результат                                |
| ------------------------------------------- | ---------------------------------------- |
| Fastify: маршрут после `listen()`           | `FST_ERR_INSTANCE_ALREADY_LISTENING`     |
| Fastify: повторная регистрация того же пути | `FST_ERR_DUPLICATED_ROUTE`               |
| Hono: маршрут после старта                  | добавляется, отвечает `200`              |
| Hono: тот же путь второй раз                | отвечает **прежний** обработчик          |
| Hono: API снятия маршрута                   | отсутствует                              |
| sirv: `ETag` и `If-None-Match`              | `200` с etag, затем `304`                |
| sirv: `Range: bytes=0-99`                   | `206`, `content-range: bytes 0-99/10000` |
| sirv: `immutable` вместе с `maxAge`         | `public,max-age=31536000,immutable`      |
| sirv: `GET /../../etc/hosts`                | `404`                                    |

Вывод из этих цифр: маршрутизатор фреймворка нам под динамику не подходит ни в одном варианте.
Fastify её не принимает вовсе, Hono принимает, но не отдаёт обратно — после перезагрузки плагина
отвечала бы его прошлая ревизия. Это не ошибка, а тихо устаревший код, то есть худший исход.

## Решение

**`node:http` плюс собственный табличный диспетчер.** Небольшая фиксированная таблица маршрутов
ядра плюс префиксные ветки для маршрутов и ассетов плагинов; ветки меняются на живом сервере при
загрузке, выгрузке и перезагрузке плагина.

**Скучные и опасные части берём библиотеками, а не пишем сами:**

- `sirv` — раздача файлов: `Range`, `ETag`, условные запросы, бессрочное кеширование, отказ выйти
  за корень;
- `cookie` — разбор и сборка заголовка ([ADR-0022](0022-password-login-with-server-side-cookie-sessions.md));
- `zod` в `packages/protocol` — схемы тел запросов и событий, общие для демона и веба.

**SSE пишется в `ServerResponse` напрямую** — без прослоек, которые могут буферизовать поток.

## Альтернативы

**Fastify.** Схемы на маршрут, `@fastify/static`, `@fastify/cookie`, инкапсуляция — всё это
применимо только к маленькой фиксированной части, потому что динамика всё равно уходит за wildcard
и наш диспетчер. Платить фреймворком за меньшую часть работы смысла нет.

**Hono.** Маленький, стандартные `Request`/`Response`. Отвергнут по результату проверки: снять
маршрут нельзя, повторная регистрация оставляет живым старый обработчик. Плюс адаптер между
Web-потоками и потоками Node ложится ровно на два места, где контроль над потоком нужен больше
всего — SSE и отдача файлов.

**Express 5.** Против Fastify не даёт ничего, типы слабее.

**Писать раздачу файлов самим.** `Range`, `304`, нормализация пути — известный источник дыр,
а проверка показала, что узкая библиотека это уже делает правильно.

## Последствия

- Маршрутизация, отображение ошибок в коды, лимиты тела и таймауты — наши. Гасится тем, что
  таблица маршрутов ядра маленькая и покрыта тестами, а диспетчер табличный, а не набор `if`.
- Диспетчер становится единственным местом, где применяется проверка сессии. Это плюс: новый
  маршрут не может случайно оказаться незащищённым, потому что защита не в обработчике.
- Заголовки мы контролируем точно — а это теперь требование: неизменяемое кеширование ревизий,
  политика содержимого, заголовки SSE.
- Валидацию входа надо звать явно; забытый вызов компилятор не поймает. Частично закрывается тем,
  что типы приходят из `protocol` и расхождение с обработчиком видно по типам.
- Ассеты плагинов идут с того же origin, что и SSE-поток, и делят с ним пул из шести соединений на
  источник ([runtime-checks.md](../runtime-checks.md), проверка 9).
