# ADR-0011: Plugins run as supervised workers with a fully asynchronous API

- **Статус:** Accepted
- **Дата:** 2026-07-26

## Контекст

Изоляция «воркер на плагин» выбрана в вижне и подтверждена запуском: лимит памяти воркера
действительно убивает воркер, а не демона ([runtime-checks.md](../runtime-checks.md), проверка 5).
Остаётся ответить, как ядро с этими воркерами обращается — какой формы у плагина API и что
происходит, когда плагин падает.

Граница воркера асинхронна физически: между потоками ходят сообщения, а не вызовы. Значит форма
API — не вопрос вкуса, а вопрос того, совпадает ли она с реальностью транспорта.

## Решение

**Весь публичный API плагинов асинхронный.** Каждый метод SDK возвращает промис — включая те,
где ядро могло бы ответить немедленно. Синхронных методов в SDK нет.

**Плагины загружаются на старте демона.**

**Ядро — супервизор.** Падение плагина не роняет демона и не задевает соседей. Краш при загрузке
и краш во время работы обрабатываются одинаково: ядро пробует перезапустить плагин с таймаутом.
Задержка растёт от попытки к попытке до потолка, состояние плагина видно снаружи. Конкретные
интервалы — деталь реализации, они меняются дёшево.

## Альтернативы

**Синхронные методы там, где ядро может ответить сразу.** Технически достижимо через
`Atomics.wait` поверх `SharedArrayBuffer`. Отвергнуто: блокирует поток плагина целиком, ломает
его собственный событийный цикл, и любой перенос метода на «медленную» сторону становится
ломающим изменением сигнатуры. Асинхронность по умолчанию делает такие переносы невидимыми.

**Падать целиком, если плагин не загрузился.** Прямо против «демон запускается один раз и больше
не глушится»: один сломанный плагин лишал бы пользователя всей платформы.

**Не перезапускать, ждать ручного вмешательства.** То же самое, только медленнее: демон,
требующий внимания после каждой сетевой икоты в плагине, не соответствует замыслу.

## Последствия

- Любой код, работающий с SDK, асинхронный. Это заражает и сами плагины — плата за то, что
  плагин можно перезапускать и переносить, не трогая сигнатуры.
- Перезапуск теряет всё, что плагин держал в памяти. Плагин обязан восстанавливаться из данных,
  а не из состояния процесса. Агентные сессии это переживают — ими владеет ядро
  ([ADR-0010](0010-core-owns-agent-sessions.md)).
- Вечно ломаный плагин будет перезапускаться вечно. Потолок задержки удерживает это в рамках
  фонового шума, но нужен видимый статус, иначе поломка останется незамеченной.
- Открыто: что происходит с подписками и хуками плагина, пока он отсутствует между попытками.
  Сейчас предполагается, что они сняты, — то есть агент в этот момент работает без вмешательства
  плагина. Это надо либо подтвердить, либо заменить на очередь.
