# ADR-0057: Plugin storage is a key-value store plus a directory

- **Статус:** Accepted
- **Дата:** 2026-07-26

## Контекст

«Своё хранилище в директории данных» упоминалось дважды — в составе SDK
([ADR-0043](0043-plugin-sdk-is-an-importable-module-surface.md)) и как место для доменных данных
плагина ([ui-extension-model.md](../ui-extension-model.md)) — и ни разу не было описано. Формы у него
не было, хотя без хранилища не пишется ни один прикладной плагин: таск-трекер из сценария 2
([vision.md](../vision.md)) состоит из своих данных.

Что уже решено рядом: вся директория данных одна
([ADR-0008](0008-data-directory-config-and-instance-lock.md)), состояние человека лежит файлами, а
машинное состояние — в SQLite ([ADR-0020](0020-files-for-human-state-sqlite-for-machine-state.md)).

## Решение

**Плагин получает две вещи: хранилище ключ-значение и свою папку.**

- **Ключ-значение** даёт SDK. Живёт в SQLite ядра (ADR-0020), поэтому атомарность записи и
  одновременный доступ — забота платформы, а не автора плагина. Это ответ на типичную потребность:
  сохранить настройку, состояние, небольшой список.
- **Папка** выдаётся внутри директории данных для тех случаев, где нужны файлы: вложения, кэш,
  собственная база. Что в ней лежит — дело плагина.

**Пространство ключей и папка принадлежат плагину и адресуются его идентичностью.** Идентичность
приходит из бутстрапа воркера, а не аргументом (ADR-0043), поэтому залезть в чужое пространство через
SDK невозможно.

**Границей безопасности это не является.** Включённый плагин исполняется с правами процесса и читает
директорию данных целиком ([ADR-0016](0016-plugin-enablement-as-the-trust-boundary.md)). Разделение
здесь нужно для порядка и для того, чтобы платформа могла показать и убрать данные плагина, а не для
защиты.

**Выключение плагина данные не удаляет.** Выключение — это не деинсталляция: выключенный вклад
сохраняется в `preferences.json` даже если исчез (ui-extension-model.md), и данные ведут себя так же.

## Альтернативы

**Только папка: плагину выдаётся директория, дальше он сам.** Ничего не изобретаем, полная свобода
автора. Отвергнуто владельцем продукта; и цена варианта видна заранее — каждый второй плагин напишет
свой JSON-файл с гонками при записи, а платформа не сможет ни показать данные плагина, ни осмысленно
их убрать.

**Отдельный файл SQLite на плагин плюс API к нему.** Прикладной плагин масштаба таск-трекера получает
нормальную базу сразу. Отвергнуто владельцем продукта. Отдельно замечу: версии схемы и миграции всё
равно остались бы на авторе, но выглядело бы это так, будто за них отвечает платформа, — а такой файл
ещё и надо открывать, закрывать и переживать перезагрузку плагина.

**Хранить состояние плагинов в `preferences.json`.** Там уже лежат выключенные вклады и выбор темы.
Отвергнуто: файл перечитывается на живом демоне и предназначен для предпочтений пользователя, а не для
данных плагина; смешав их, мы получили бы перезапись пользовательского файла прикладным кодом.

## Последствия

- Данные плагина живут в двух местах, и это придётся объяснять в документации SDK: ключ-значение для
  состояния, папка для файлов. Автор, выбравший неудачно, обнаружит это не сразу.
- У платформы появляется обязанность отвечать на вопрос «сколько занимает этот плагин» и «убери его
  данные». Вью плагинов — естественное место для этого, но удаление данных выключенного плагина
  необратимо, а значит требует подтверждения, а не переключателя.
- Ключ-значение в общей базе означает, что плагин может её раздуть. Квот здесь нет и вводить их нет
  смысла: тот же плагин может писать в папку напрямую. Ограничением остаётся включение (ADR-0016) и
  наблюдаемость размера.
- Идентификатор плагина становится частью схемы данных. Переименование плагина — это потеря его
  данных, если не сделать переноса; значит идентификатор в манифесте
  ([ADR-0044](0044-plugin-manifest-lives-in-package-json.md)) окончателен сильнее, чем казалось при
  его введении.
- Перекрытие по источнику (ADR-0030) ставит вопрос, который придётся решить при первом же перекрытом
  плагине: агент из папки проекта и одноимённый встроенный — это одно пространство ключей или два.
  Здесь он не решается, потому что ответ зависит от того, чем перекрытие является для пользователя —
  заменой плагина или его настройкой.
