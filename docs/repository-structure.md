# Структура репозитория

## Что утверждено

- Монорепозиторий. Один репозиторий на всю платформу.
- Язык — TypeScript.
- В репозитории живут: бэкенд-демон, фронтенд на React + Vite, общие пакеты и SDK-пакет для
  авторов плагинов.
- Система модульная: части отделены друг от друга и не лезут во внутренности соседа.
- Точка входа для разработчика — `make`: и dev-режим, и сборка.
- Рантайм — Node.js 24 LTS ([ADR-0002](adr/0002-nodejs-lts-as-runtime.md)).
- Менеджер пакетов — pnpm workspaces ([ADR-0003](adr/0003-pnpm-workspaces.md)).
- В dev-режиме поднимаются два процесса — Vite-сервер фронтенда и бэкенд, оба с хот-релоадом.
- Продакшн-сборка — единое приложение, запускаемое из терминала.

## Что из этого следует без выбора

Раскладка обязана разделять четыре сущности, потому что у них разные потребители:

| Сущность | Кто потребитель |
| --- | --- |
| Демон (ядро + веб-API) | конечный пользователь, запускает из терминала |
| Веб-интерфейс | браузер пользователя |
| SDK для плагинов | автор плагина, внешний по отношению к репозиторию человек |
| Общий код (типы, контракты API) | демон и веб-интерфейс одновременно |

Отдельно: SDK — публичный контракт. Он единственный пакет, который увидят посторонние, и
ломать его дороже, чем всё остальное.

## Открытые вопросы

Ни один не решён. По каждому нужен выбор владельца продукта.

### 1. Раскладка каталогов

- **`apps/*` + `packages/*`** — приложения (демон, веб) отдельно от библиотек (SDK, общее).
  Общепринято, сразу видно, что запускается, а что импортируется. Два уровня вложенности.
- **Плоский `packages/*`** — всё однородно, короче пути. Граница «приложение или библиотека»
  теряется, для монорепы с публичным SDK это минус.
- **Демон в корне, остальное в подкаталогах** — минимум церемоний на старте. Плохо масштабируется:
  корень быстро зарастает конфигами всех частей сразу.

### 2. Как фронтенд попадает в продакшн-сборку

- **Статика вшивается в бинарь/бандл демона** — одно приложение, ничего не потерять при
  переносе. Пересборка фронта требует пересборки демона.
- **Статика лежит рядом отдельной папкой** — фронт можно обновить отдельно, но «единое
  приложение» перестаёт быть одним файлом.

### 3. Как собираются внутренние пакеты

- **Каждый пакет собирается в `dist` (tsc или бандлер)** — честные границы, пакет публикуемый.
  Появляется шаг сборки между «поправил» и «увидел».
- **Пакеты потребляются исходниками** — сборки нет вообще, правка видна сразу. Возможно не на
  каждом рантайме и требует аккуратности с публикацией SDK наружу.

### 4. Где живут плагины

- **Только в директории данных** (`~/.sovereign_platform`) — репозиторий не знает о плагинах,
  чистая граница ядра и расширений.
- **Плюс каталог примеров в репозитории** — есть на чём проверять хот-релоад и SDK в тестах,
  но нужен договор, как ядро их подхватывает в dev-режиме.

### 5. Скоуп имён пакетов

Например `@sovereign/sdk`, `@sovereign/core`. Влияет на то, под каким именем SDK увидят авторы
плагинов, и меняется потом дорого.

---

Разрешённые вопросы переезжают в раздел «Что утверждено», значимые — оформляются ADR.
