# Структура репозитория

## Что утверждено

- Монорепозиторий. Один репозиторий на всю платформу.
- Язык — TypeScript.
- В репозитории живут: бэкенд-демон, фронтенд на React + Vite, общие пакеты и SDK-пакет для
  авторов плагинов.
- Система модульная: части отделены друг от друга и не лезут во внутренности соседа.
- Точка входа для разработчика — `make`: и dev-режим, и сборка.
- Рантайм — Node.js 24 LTS, менеджер пакетов — pnpm workspaces ([toolchain.md](toolchain.md)).
- В dev-режиме поднимаются два процесса — Vite-сервер фронтенда и бэкенд, оба с хот-релоадом.
- Продакшн-сборка — единое приложение, запускаемое из терминала. В артефакт вшиты статика
  фронтенда и исходники встроенных плагинов ([toolchain.md](toolchain.md)).
- Раскладка — три корневых каталога:

  ```
  apps/                    то, что запускает пользователь
    daemon/                ядро, веб-API, CLI
    web/                   веб-интерфейс, React + Vite
  packages/                то, что импортируют
    sdk/                   публичный контракт для авторов плагинов
    browser-sdk/           публичное взаимодействие браузерного UI плагина с платформой
    ui-kit/                примитивы интерфейса и токены темы, публичный пакет
    protocol/              схемы и типы API, общие для демона и веба
    agent-runtime-pi/      реализация агентного рантайма на Pi
  plugins/                 то, что демон загружает в рантайме
    starter/               стартовый плагин: агент по умолчанию и скилы платформы
      package.json         манифест плагина
      src/worker.ts        lifecycle-точка worker
      agents/generic/AGENT.md файловое определение starter.generic
  ```

  Направление зависимостей: `apps` зависят от `packages`, обратно — никогда. `plugins` зависят от
  `packages`, не зависят от `apps` и друг от друга, и не импортируются никем — их загружает демон.
  Правила проверяются автоматически.

- `browser-sdk` и `ui-kit` — публичные пакеты наравне с `sdk`
  ([public-contract.md](public-contract.md), [ui-kit.md](ui-kit.md)). `browser-sdk` зависит от
  `protocol` только для внутренней host-поверхности, а `apps/web` устанавливает его runtime и
  передаёт реализацию кеша браузерных модулей. Основной entrypoint не отдаёт типы протокола и не
  реэкспортирует UI Kit.

- `ui-kit` отвечает только за вид браузерного интерфейса.
  Он не импортирует `apps/*`, а `apps/web` строит оболочку и встроенные компоненты только из него:
  компонент, сделанный мимо кита, плагину недоступен. Отдельный от `sdk` он потому, что тянет React,
  а `sdk` не должен.

- Импорт `@earendil-works/*` разрешён только внутри `packages/agent-runtime-pi`
  ([architecture.md](architecture.md)) и проверяется линтером — для `apps/`, `packages/` и
  `plugins/`. Исключений сегодня нет; одно предусмотрено на будущее — реэкспорт типов событий в
  `sdk` ([hooks.md](hooks.md)). Интерфейс агентного рантайма объявлен в `sdk`, прикладной сервис
  поверх него — в ядре.

- Внутренние пакеты потребляются исходниками, без шага сборки. `tsc` — только проверка типов.
- Имена пакетов — в скоупе `@sovereign`; не предназначенные к публикации помечены `"private": true`.

## Внутренние области демона

`apps/daemon/src` разделён на восемь предметных областей:

| Область          | Ответственность                                                              |
| ---------------- | ---------------------------------------------------------------------------- |
| `platform`       | аргументы запуска, директория данных, атомарная запись, лок, шина и журнал   |
| `http`           | диспетчер маршрутов, HTTP-сервер, SSE, health и доступ к файловой системе    |
| `authentication` | учётная запись, серверные сессии входа и маршруты аутентификации             |
| `settings`       | снимок настроек, наблюдение за файлами и предпочтения внешнего вида          |
| `projects`       | пути, хранение, доступность, жизненный цикл и маршруты проектов              |
| `providers`      | креды, каталоги моделей, попытки входа и маршруты провайдеров                |
| `sessions`       | служба сессий, очередь работы модели, сборка инструментов и встроенные tools |
| `plugins`        | плагины, общий файловый слой и standalone-ресурсы, вклады и мосты к службам  |

В корне остаются только `main.ts`, который собирает приложение, и
`import-boundary.test.ts`, который проверяет архитектурные правила. Тесты лежат рядом со своими
модулями; фикстуры воркеров — в `plugins/fixtures/`. Там же лежат tracked-источники `placed`,
`rival` и `browserless` для живой проверки browser SDK. `plugins/runbook-fixtures.ts` копирует
именно эти каталоги в свежую директорию данных; игнорируемый `apps/daemon/.sovereign-dev` источником
для seed не служит.

У каждой области есть `public.ts` с явными именованными реэкспортами. Внутри области разрешены
прямые импорты соседних файлов. Между областями разрешён только импорт
`../<area>/public.ts`; глубокий импорт во внутренний файл соседа запрещён. `main.ts` — единственный
composition root: он может использовать все области, но только через `./<area>/public.ts`.
`public.ts` задаёт внутренний фасад приложения, а не совместимый публичный контракт: он не выходит
из пакета `@sovereign/daemon` и может меняться вместе с реализацией.

Общий файловый слой области `plugins` разбирает и обнаруживает `AGENT.md` и `SKILL.md` как внутри
плагинов, так и в standalone-корнях. `file-resource-roots.ts` вычисляет разрешённые нативные и
межклиентские корни, `file-resource-watcher.ts` наблюдает их появление и содержимое, а
`standalone-file-resources.ts` атомарно заменяет их снимки в едином реестре вкладов. Несмотря на
расположение рядом с loader, standalone-сервис не является плагином: он не создаёт worker и не
участвует в lifecycle исполняемого кода.

Разрешённое направление зависимостей:

| Область          | Может импортировать из                                  |
| ---------------- | ------------------------------------------------------- |
| `platform`       | —                                                       |
| `http`           | `platform`                                              |
| `authentication` | `http`, `platform`                                      |
| `settings`       | `http`, `platform`                                      |
| `projects`       | `http`, `platform`                                      |
| `providers`      | `http`, `platform`                                      |
| `sessions`       | `projects`, `http`, `platform`                          |
| `plugins`        | `settings`, `providers`, `sessions`, `http`, `platform` |

Границы защищает корневой ESLint: отдельный блок `no-restricted-imports` для каждой области
проверяет и вход только через `public.ts`, и направление по таблице. Узкие блоки повторяют общие
запреты на импорт приложений и Pi, потому что flat config заменяет опции правила, а не складывает
их. Архитектурный тест запускает настоящий корневой конфиг через `ESLint.lintText`, чтобы изменение
порядка или состава блоков не сняло запрет молча. Динамический относительный импорт между областями
запрещён: его направление нельзя надёжно проверить до исполнения. Единственное точечное исключение
стоит на вызове в `plugin-worker.ts`, который загружает внешнюю точку входа плагина по вычисленному
`file:` URL; остальные вычисляемые и относительные динамические импорты там тоже остаются ошибкой.
TypeScript эти внутренние границы пока не защищает; его компилятор проверяет типы уже разрешённого
графа.

## Что из этого следует без выбора

Раскладка обязана разделять семь сущностей, потому что у них разные потребители:

| Сущность                        | Кто потребитель                                           |
| ------------------------------- | --------------------------------------------------------- |
| Демон (ядро + веб-API)          | конечный пользователь, запускает из терминала             |
| Веб-интерфейс                   | браузер пользователя                                      |
| Серверный SDK для плагинов      | автор плагина, внешний по отношению к репозиторию человек |
| Browser SDK для UI плагина      | браузерный код плагина и хост                             |
| UI Kit                          | браузерный код плагина и веб-интерфейс                    |
| Общий код (типы, контракты API) | демон и веб-интерфейс одновременно                        |
| Встроенный плагин               | демон, загружает его в рантайме на отдельном воркере      |

Отдельно: `sdk`, основной entrypoint `browser-sdk` и `ui-kit` — публичные контракты. Их увидят
посторонние авторы плагинов, и ломать их дороже, чем внутренние пакеты и host-подпути.

## Раскладка внутри каталога плагина

`package.json` с полем `sovereign` задаёт идентификатор, worker и требуемый диапазон версий
платформы. Два необязательных каталога принадлежат тому же плагину: `agents/<name>/AGENT.md` и
`skills/<name>/SKILL.md` ([file-resources.md](file-resources.md)). Loader считает оба корня только от
обнаруженной директории плагина; отдельной встроенной раскладки агентов или скилов нет. Остальные
файлы автор раскладывает свободно и может ссылаться на них из определения относительными путями.

В репозитории встроенный плагин имеет вид `plugins/<plugin>/{package.json,src,agents,skills}`. В
production его каталог целиком распаковывается в
`<директория данных>/builtin/<версия платформы>/<plugin>/`: переносится единица плагина, а не worker
отдельно от файловых ресурсов.

Тестовый внешний плагин имеет ту же раскладку в
`apps/daemon/src/plugins/fixtures/<plugin>/`. Для воспроизводимого runbook seed добавляет в каждую
скопированную фикстуру directory symlink `node_modules/@sovereign/sdk` на workspace-пакет
`packages/sdk`; `@sovereign/browser-sdk` внутрь не копируется, потому что остаётся singleton-модулем
браузерного хоста.

## Почему так

### Папки с проверяемыми фасадами внутри демона

Плоский каталог перестал показывать владельцев кода, но отдельные единицы сборки областям пока не
нужны. Поэтому выбран промежуточный уровень: предметные папки делают структуру видимой, явные
`public.ts` сужают вход, а ESLint превращает глубокую или обратную зависимость в ошибку проверки.
Так существующие границы проверяются на реальном графе изменений до более дорогого выделения
пакетов.

**Только папки без фасадов и правил.** Отвергнуто: навигация стала бы лучше, но любой файл всё ещё
мог бы импортировать внутренности соседа или замкнуть области в цикл. Такая граница держалась бы
только договорённостью.

**Сразу вынести каждую область в workspace-пакет.** Отложено: пакеты репозитория потребляются
исходниками и сейчас не образуют компилируемые TypeScript project references. Одни `package.json`
добавили бы зависимости и церемонию, но не помешали бы обойти их относительным импортом. Настоящая
защита компилятором потребует деклараций, порядка сборки и изменения принятой модели разработки.

Область следует поднимать в пакет, когда у неё появляется независимый потребитель или жизненный
цикл, отдельная публикация либо сборка, или когда ручное сопровождение фасада и ESLint становится
дороже компилируемой границы. До этого пакет — дополнительная единица конфигурации без нового
потребительского контракта.

**Общий `shared` или `internal`.** Отвергнуто: он стал бы неограниченным каналом обхода матрицы.
Низкоуровневый код принадлежит `platform` или `http`, предметный — своей области; повторное
использование само по себе не меняет владельца.

Цена выбранного решения: границу защищает ESLint, а не компилятор; экспорт фасада поддерживается
вручную; правила `no-restricted-imports` приходится повторять из-за семантики flat config. Поэтому
конфигурация проверяется отдельным архитектурным тестом, а ограничение явно считается
промежуточным, не эквивалентным пакетной изоляции.

### Три корневых каталога, а не плоский список пакетов

В репозитории живут сущности с разными потребителями, и главный риск — обратные зависимости:
приложение начинает импортировать из соседнего приложения, и через полгода демон нельзя собрать без
фронтенда.

**Плоский `packages/*`.** Короче пути и меньше церемоний, но все пакеты оказываются равны, различие
«приложение или библиотека» теряется, и запрет на обратные зависимости не на чем основать.

**Демон в корне репозитория.** Самый быстрый старт, но корень зарастает конфигами всех частей сразу,
а демон перестаёт быть равноправным пакетом — вынуть его оттуда потом дороже всего.

Третий корень появился позже: плагин не подходит ни под «запускают», ни под «импортируют» — демон
**загружает** его в рантайме на отдельном воркере, и по vision тут со временем окажется большая часть
кода репозитория.

**Внутри пакета демона, `apps/daemon/plugins/*`.** Ближе всего к тому, что встроенные плагины
поставляются вместе с демоном. Отвергнуто: плагины оказываются в одном пакете с ядром — один
`tsconfig`, один граф импортов, — и правило «демон плагины не импортирует, а загружает» приходится
выражать как запрет пакету импортировать собственный подкаталог. Такое правило воюет с инструментами,
а непроверяемое правило считается отсутствующим. Без запрета встроенный плагин вызовут напрямую, и он
превратится в модуль ядра со странным путём.

**Среди пакетов, `packages/plugin-*`.** Плагины сразу становятся workspace-пакетами, зависимости и
проверка типов работают без настройки. Отвергнуто: всё в `packages/` импортируемо по определению,
поэтому «плагины никто не импортирует» опирается только на правило линтера, без структурной
поддержки. Плюс публичные контракты `sdk` и `ui-kit` теряются в списке из двадцати плагинов.

**Отдельный репозиторий на встроенные плагины.** Отвергнуто: они вшиваются в артефакт, поэтому сборка
перестала бы быть одной командой в одном репозитории, а версии плагинов и платформы синхронизировались
бы руками с первого же дня.

Правило «`plugins/*` не импортирует никто» и есть причина отдельного корня: оно проверяется по пути, а
внутри пакета демона или среди `packages/*` его подпереть нечем. Каждый встроенный плагин — это
workspace-пакет со своим `package.json`, иначе его npm-зависимости некому решить на сборке. Появление
четвёртого корневого каталога требует такого же разбора, как этот.

Следствие: проверка типов покрывает плагины, значит ошибка во встроенном плагине ломает `make check`.
Так и должно быть — встроенный плагин держит ту же планку, что остальной код. И у нашего кода нет
короткой дороги, которой нет у внешнего автора: встроенный плагин, которому нужен другой плагин, не
может его импортировать — только шина событий и точки расширения.

### Внутренние пакеты потребляются исходниками

Рантайм исполняет TypeScript без транспайлера ([toolchain.md](toolchain.md)), поэтому сборка
внутренних пакетов перестала быть обязательной. Цикл правки для нас не второстепенен: хот-релоад
заявлен базовой функциональностью ядра, а сборка каждого пакета означает watch-процесс на каждый
пакет.

**Каждый пакет собирается в `dist`.** Даёт привычные границы и пакет, готовый к публикации в любом
виде, но возвращает шаг сборки в цикл разработки — против той самой скорости правки, ради которой
строится хот-релоад.

**Гибрид: внутри исходники, SDK собирается при публикации.** Отвергнуто: у SDK появилось бы два
режима существования, и стало бы возможным расхождение «у нас работает, у автора плагина нет» — самая
дорогая для отладки категория ошибок, потому что воспроизвести её у себя нельзя.

Цена: проверка типов больше не является побочным эффектом сборки — её нужно звать явно, отдельной
целью в `make` и обязательным шагом в CI. Появление потребителя, не умеющего TypeScript, сделает
решение непригодным.

### Скоуп `@sovereign`

Имя SDK попадает в импорты чужого кода, и менять его после того, как плагины разошлись, дорого. На
2026-07-26 пакетов `@sovereign/sdk`, `@sovereign-platform/sdk`, `sovereign-sdk` и `sovereign-platform`
в npm нет; это не доказывает, что свободен сам скоуп.

**`@sovereign-platform/*`.** Совпадает с именем проекта и реже конфликтует, но длиннее в каждой
строке импорта, а их будут сотни.

**Без скоупа (`sovereign-sdk`).** Ничего не нужно регистрировать, но по имени импорта не видно, свой
пакет или сторонний, и каждое имя должно быть уникально глобально.

Отсюда обязанность: скоуп нужно занять до первой публикации SDK, а не после.
