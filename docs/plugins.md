# Плагины

Контракт между платформой и плагином: как плагин объявляет себя, откуда его берут, когда он работает
и что он может добавить. Почему устроено именно так — в разделе «Почему так» в конце.

## Что такое плагин

Папка с исходниками. Никакой сборки перед установкой не требуется: платформа исполняет TypeScript
как есть ([toolchain.md](toolchain.md)).

```
hello/
  package.json        манифест: поле sovereign
  src/worker.ts       серверная точка входа
  src/browser.tsx     браузерная точка входа, если у плагина есть интерфейс
```

Раскладка внутри папки свободна, важны только объявленные точки входа.

## Манифест

Манифест — поле `sovereign` в `package.json` плагина. Отдельного файла нет: пакетный менеджер и так
требует `package.json`, а два файла-манифеста рядом расходятся.

| Поле                 | Обязательность | Значение                                               |
| -------------------- | -------------- | ------------------------------------------------------ |
| `sovereign.id`       | обязательно    | идентификатор плагина, `^[a-z0-9][a-z0-9-]*$`          |
| `sovereign.worker`   | обязательно    | путь к серверной точке входа внутри папки              |
| `sovereign.browser`  | необязательно  | путь к браузерной точке входа                          |
| `sovereign.platform` | обязательно    | диапазон версий платформы, с которыми плагин совместим |

```json
{
  "name": "@someone/hello",
  "version": "1.0.0",
  "type": "module",
  "sovereign": {
    "id": "hello",
    "worker": "src/worker.ts",
    "platform": "^0.1.0"
  }
}
```

`sovereign.id` — не имя npm-пакета: имя со скоупом содержит слэш, а идентификатор попадает в
маршрут `/p/<id>/...`. `"type": "module"` обязателен по правилам самого Node: без него точка входа
читается как CommonJS и импорты не работают.

Диапазон версий читается в виде `*`, `1.2.3`, `^1.2.3`, `~1.2.3`, `>=1.2.3`; `^` ведёт себя как в
npm — на нулевом мажоре ломающим считается минор. Составные диапазоны и предрелизы не читаются:
непонятная запись — отказ, а не молчаливое «подходит». Что считается ломающим изменением платформы —
в [public-contract.md](public-contract.md).

Манифест читается **без исполнения кода плагина**. Папка без `package.json` или без поля `sovereign`
плагином не считается и просто пропускается.

## Источники

| Источник               | Где                                   | Ранг | По умолчанию |
| ---------------------- | ------------------------------------- | ---- | ------------ |
| `builtin`              | `plugins/` в поставке                 | 0    | включён      |
| `data`                 | `<директория данных>/plugins/`        | 1    | выключен     |
| `project:<id проекта>` | `.sovereign/plugins/` в папке проекта | 2    | выключен     |

`<id проекта>` — идентификатор записи проекта ([sessions-and-projects.md](sessions-and-projects.md)),
а не путь папки. Ключ плагина выходит из трёх частей: `project:b7Kq3xv9pQdT:hello`. Разбирается он
по **последнему** двоеточию, и это однозначно — двоеточий не допускает ни идентификатор плагина, ни
идентификатор проекта.

**Набор корней не постоянен.** Источник даётся проекту, который не в архиве и папка которого
доступна:

- **архивный проект источником не является** — «убран с глаз» обязано значить и «его код не
  работает», иначе архивация прячет проект в интерфейсе, но оставляет его плагины перекрывать чужие
  вклады;
- **проект с недоступной папкой источником не является** — читать оттуда нечего. Возврат папки
  возвращает и источник ([sessions-and-projects.md](sessions-and-projects.md));
- **эфемерный проект источником является:** плагин, положенный в `work`, перекрывает встроенный, и
  это неочевидное следствие того, что папка `work` лежит внутри директории данных.

Решение человека о таком плагине переживает и архивацию, и пропажу папки: запись в
`preferences.json` никуда не девается, а плагин просто перестаёт обнаруживаться.

**Реестр один, но разрешение контекстное.** Обнаруженное во всех источниках хранится в одном реестре
объявлений. Базовый снимок включает built-in, data и пользовательские standalone-объявления. Снимок
проекта добавляет только объявления `project:<id>` этого проекта и его project standalone-корни.
Объявления другого проекта отбрасываются **до** группировки по идентичности, выбора приоритета и
диагностики конфликтов, поэтому одинаковые копии из двух проектов друг другу не мешают.

Ранг — приоритет среди уже применимых объявлений. Плагин из директории данных перекрывает встроенный
в базовом и любом проектном контексте; версия из папки проекта перекрывает обе только в своём
проекте. Все виды вкладов проходят один общий алгоритм по metadata происхождения и идентичности;
добавление нового вида не требует отдельного правила проектной применимости.

Перекрытие не значит «замена версии»: это **два разных плагина**. У каждого своё включение, своё
состояние, свой ключ `<источник>:<id>`. Спорят они не как плагины, а как вклады.

**Каждая папка проекта — свой источник, и ранг у них общий.** Это не создаёт глобального конфликта:
разрешение одного проекта никогда не рассматривает источник другого. Равный ранг конфликтует только
внутри одного уже отфильтрованного контекста; спорный вклад не применяется, а платформа ничего за
человека в `preferences.json` не дописывает.

## Включение

Включение — **граница контроля, а не безопасности** ([vision.md](vision.md)). Пользователь один и
плагины пишет сам или руками своих агентов; выключатель существует не для защиты от чужого кода, а
чтобы немедленно убрать свой — тот, что написан агентом, не прочитан построчно и ведёт себя не так.
Поэтому встроенный работает сразу, а любой другой ждёт явного включения: незнакомый код не
запускается молча.

Решения человека живут в `preferences.json` ([data-directory.md](data-directory.md)):

```json
{
  "plugins": {
    "builtin:tasks": { "enabled": false },
    "data:hello": { "enabled": true, "disabledContributions": ["hello.panel"] }
  }
}
```

Записи нет — решения не было, и действует умолчание источника. Плагин, названный в файле без
`enabled`, считается включённым.

Тот же файл пишет платформа по запросу `PUT /api/plugins/:key/preferences`
([web-api.md](web-api.md)): интерфейсу не нужен свой способ хранить решения человека, а файл
остаётся источником истины.

**Включённый плагин может всё, что может демон:** файловая система, сеть, директория данных, чужие
сессии через шину событий. Воркер — изоляция от сбоя, а не от злого умысла, и второго не будет.

**Переключать плагины и вклады может только человек.** Это операция API ядра, доступная интерфейсу с
сессией пользователя; в SDK переключения нет — ни для чужих вкладов, ни для своих. Иначе выключенное
человеком включалось бы кодом, и выключатель перестал бы быть последним словом. Своё поведение плагин
настраивает своим хранилищем, а не тем механизмом, которым человек его останавливает.

## Жизненный цикл

| Состояние    | Когда                                                                   |
| ------------ | ----------------------------------------------------------------------- |
| `discovered` | манифест прочитан, решение о включении ещё не применено                 |
| `disabled`   | выключен человеком или ещё ни разу не включён                           |
| `refused`    | манифест или версия платформы не годятся — отказ платформы, не человека |
| `installing` | ставятся зависимости                                                    |
| `starting`   | воркер поднят, идёт `activate`                                          |
| `running`    | `activate` завершился, вклады применены                                 |
| `stopping`   | идёт `deactivate` и остановка воркера                                   |
| `stopped`    | выгружен штатно: демон завершается или плагин исчез с диска             |
| `failed`     | воркер упал или `activate` бросил; держится до следующей попытки        |

Каждый переход виден в журнале демона и публикуется событием `core.plugin.lifecycle`. Состояние
целиком отдаёт снимок `GET /api/plugins` — статусы плюс действующий набор вкладов
([web-api.md](web-api.md)).

Различать стоит два «не работает»:

- **`disabled`** — так решил человек, лечится переключателем;
- **`refused`** — так решила платформа: манифест не читается, версия не подходит, точки входа нет.
  Причина всегда названа, и «включить» такой плагин нельзя, его надо починить.

**Отдельного «перезапускается» нет.** Пауза между попытками проводится в `failed`, и у состояния есть
номер попытки и момент следующей: одно и то же — «плагина сейчас нет, потому что он упал» — не должно
иметь двух имён.

**Задержка перезапуска растёт до потолка, попытки не кончаются.** Счётчик попыток сбрасывается не по
факту старта, а когда плагин продержался в `running` достаточно долго: иначе редкая ошибка раз в сутки
навсегда оставила бы плагин на потолке задержки, а плагин, падающий сразу после `activate`, крутился
бы в быстром цикле.

**Провал установки зависимостей не перезапускается.** Это не падение кода: пока внешний реестр или
сеть не починены, повтор раз в минуту не приблизит успех. Повтор происходит по действию — правке
плагина или повторному включению.

**Выгрузка ждёт `deactivate` ограниченное время.** Не ответивший вовремя воркер снимается
принудительно, и это записывается в журнал ([runtime-checks.md](runtime-checks.md), проверка 16).

Правка исходников включённого плагина перезагружает его, не трогая демон.

## Что плагин пишет

Возможности берутся импортом, а не приходят аргументом:

```ts
import { contribute, log, type PluginModule } from "@sovereign/sdk";

export const activate: PluginModule["activate"] = async () => {
  await contribute.custom({ id: "board", title: "Board" });
  await log.info("hello is up");
};

export const deactivate: PluginModule["deactivate"] = async () => {
  await log.info("hello is going down");
};
```

- **`activate` обязателен**, `deactivate` — нет. **Всё асинхронно:** граница воркера асинхронна
  физически, между потоками ходят сообщения, а не вызовы.
- **`deactivate` ждут ограниченное время.** Не ответивший воркер снимают принудительно.
- **Идентичность плагина приходит из воркера, а не из кода.** Бутстрап воркера получает порт к
  демону, инициализирует состояние модуля `sdk` и только после этого импортирует код плагина.
  Объявить себя другим плагином невозможно: идентичность не является аргументом.
- **Источник записи в журнале проставляет ядро** (`plugin:<id>`). Записи уходят в `stdout` демона —
  ни в интерфейс, ни другим плагинам журнал не попадает ([logging.md](logging.md)).
- **Код плагина исполняется в своём воркере** и может пользоваться нестираемым синтаксисом TypeScript
  (`enum`, `namespace`, parameter properties) — платформе он запрещён, плагину нет
  ([toolchain.md](toolchain.md)).
- **Вызов SDK вне воркера плагина** отвечает внятной ошибкой «не инициализирован». В тестах хост
  подменяется швом `@sovereign/sdk/testing`, и плагин импортируется **после** установки шва: импорты
  ESM поднимаются к началу модуля, поэтому статический импорт выполнится раньше подготовки.
- **Плагин, поднявший собственный воркер, получит там неинициализированный SDK.**
- **Перезапуск теряет всё, что плагин держал в памяти.** Плагин обязан восстанавливаться из данных, а
  не из состояния процесса. Агентные сессии это переживают — ими владеет ядро
  ([architecture.md](architecture.md)).

## Провайдеры LLM

Плагин видит провайдеров и их модели, узнаёт статус авторизации и обновляет динамические списки
моделей ([models-and-providers.md](models-and-providers.md)):

```ts
import { providers } from "@sovereign/sdk";

const list = await providers.list();
const models = await providers.models("anthropic");
const status = await providers.status("anthropic");
const report = await providers.refresh();

// Вход целиком, своим диалогом; конец приходит возвращаемым значением.
const conclusion = await providers.login({
  providerId: "anthropic",
  method: "api_key",
  dialogue: { ask: (prompt) => "sk-…" },
});

await providers.logout("anthropic");

// Свой провайдер — только данные: функции границу воркера не переживают.
await providers.register({
  id: "vendor-local",
  name: "Vendor Local",
  baseUrl: "http://127.0.0.1:11434/v1",
  api: "openai-completions",
  apiKey: { label: "Vendor key" },
  models: [{ id: "vendor-large", name: "Vendor Large", contextWindow: 32_000, maxTokens: 4_096 }],
});
```

**Свой провайдер регистрируется в `activate` и живёт, пока жив плагин** — та же механика, что у
подписок на шину: выгрузка, падение и перезагрузка его убирают, вернувшийся плагин регистрирует его
заново. Занятый идентификатор — отказ операции, а не замена. Пределы определения и то, что кред
переживает плагина, — в [models-and-providers.md](models-and-providers.md).

**Значение креда через SDK не читается и не записывается** — ни методом, ни полем. Единственный
писатель кредов платформа, и причина не в защите, а в сериализации записи OAuth-токена: второй
писатель ломает обновление молча и редко.

**Канал плагина стал двусторонним, и пара «запрос-ответ» в нём ровно одна.** Всё остальное —
журнал, вклады, публикация, подписка — по-прежнему уходит без ответа: о проблеме плагин узнаёт
событием жизненного цикла, а не исключением на месте вызова. Исключение сделано для провайдеров,
потому что список, статус и вход бессмысленны без ответа. **Общего RPC из этого не следует:** вид
запроса — закрытое объединение типов SDK, а не произвольное имя метода, и добавление вида — это
версия платформы ([public-contract.md](public-contract.md)).

## Вклады

Вклад — то, что плагин добавляет платформе. У всех видов общая часть: идентификатор — он же ключ
переключения — и метаданные отображения; прикладная часть своя у каждого вида.

**Виды, которые понимает ядро:** агент, инструмент, скил, подписка на хук, команда, место, компонент,
страница, маршрут, публичный маршрут, цветовая схема, каталог локали, событие шины. **Плюс один общий
вид** — для вкладов, потребитель которых другой плагин, а не ядро: у него ядро проверяет
идентификатор и переключаемость, а форму полезной нагрузки понимает потребитель.

Реализованы сейчас только общий вид (`contribute.custom`) и событие (`contribute.event`) — перечень
нереализованного в конце документа.

**Кастомный LLM-провайдер вкладом не стал.** До реализации он числился здесь наравне с остальными
видами; сделан он операцией `providers.register`
([models-and-providers.md](models-and-providers.md)), потому что регистрация обязана уметь отказать
на месте вызова — идентификатор провайдера может быть уже занят, а вклады применяются одним снимком
после `activate` и об отказе сообщают событием жизненного цикла. Цена: **по отдельности этот
провайдер человеком не переключается**, убирается он только вместе с плагином.

- **Неймспейс даёт хост.** Объявленный `board` становится `<id плагина>.board`. Объявить вклад в
  чужом неймспейсе нельзя, неймспейс `core` недоступен.
- **Регистрация во время `activate` применяется одним снимком.** Наблюдатель видит либо прежний
  набор, либо новый целиком — не состояние, где страница уже есть, а её компонент ещё нет.
- **Каждый вклад переключается человеком по отдельности.** Выключенный вклад не участвует ни в чём —
  в том числе не перекрывает одноимённый из менее специфичного источника.
- **Вклад включённого плагина по умолчанию включён.** Доверие уже дано включением плагина; требовать
  включать каждый новый инструмент после обновления плагина значит превращать обновление в квест.
- **Выключенные вклады перечислены в `preferences.json`** и сохраняются, даже если вклад исчез:
  вернулся — остаётся выключенным.
- **Эффект переключения немедленный.** Списки пересобираются; активная цветовая схема падает на схему
  по умолчанию, выключенный каталог локали — на базовую локаль, заменяемое место — на встроенного
  провайдера.
- **Спор при равном ранге источника не применяет ни один вклад** и уходит диагностикой. Из-за
  неймспейса такой спор возможен только внутри одного плагина: два плагина одного источника не могут
  занять один идентификатор — их плагинные идентификаторы уже различны.
- **Выключение плагина снимает всё, что он зарегистрировал.**
- **Плагин не вправе считать, что все его вклады активны.** Отсутствие своего же инструмента —
  нормальное состояние, а не ошибка. Узнать причину, по которой вклад выключен, плагин не может и
  починить её тоже: остаётся только переживать отсутствие.

Выключение вклада — **не мера безопасности:** код плагина продолжает работать в своём воркере.
Границей доверия остаётся включение плагина.

Реестр хранит объявления отдельно от результата разрешения. Plugin loader заменяет одним снимком
программные и файловые объявления плагина, standalone-сервис — снимок конкретного файлового корня.
Повторный неизменившийся scan не двигает ревизию; watcher передаёт `resourceChanged`, когда изменился
entry-файл или соседний ресурс, и тогда одна атомарная замена повышает её ровно один раз, даже если
разобранная регистрация совпала с прежней.

Standalone- и plugin-owned определения имеют разные пространства имён: короткий `review` и
квалифицированный `github.review` сосуществуют. Standalone-корни с одинаковым коротким именем
разрешаются по заданному им числовому приоритету, plugin-owned копии — по лестнице
`project → data → built-in`. Идентичность включает вид вклада, поэтому одинаковые строки id у
агента и скила не спорят. Файловое и программное объявления одного плагина с одинаковыми видом и
declared id создают локальный конфликт: исключается только эта идентичность, остальные объявления
того же снимка применяются.

Файловый диагностический снимок проекта сохраняет не только активные определения, но и
`shadowed`, `switched-off` и `invalid` вместе с путями и diagnostics. Административный снимок
плагинов, напротив, показывает union действующих plugin-owned объявлений по всем проектным
контекстам: управление плагином не должно терять проектную декларацию только потому, что она не
входит в базовый каталог.

### Вклад «агент»

Пять прикладных полей поверх общей части:

- **инструкции** — системный промпт агента;
- **отбор инструментов** — что брать и что не брать, **шаблонами имён**, а не списком: набор
  инструментов динамический, он собирается хуком `tools_collect` из включённых плагинов и меняется
  при перезагрузке любого из них, поэтому перечислить его в определении агента нельзя. Пример
  владельца продукта — `file-*` — и есть шаблон;
- **модель** — значение по умолчанию, а не фиксация;
- **уровень ризонинга** — тоже по умолчанию: и модель, и уровень переопределяются на каждый турн
  ([sessions-and-projects.md](sessions-and-projects.md));
- **скилы, доступные агенту.**

**Скилы отбираются агентом, а инструменты открывает ядро.** `AgentHarness.skill()` наше поле
фронтматтера не читает и `setActiveTools` не зовёт — это делаем мы
([agent-runtime-contract.md](agent-runtime-contract.md)). Поле «скилы» отвечает на вопрос «какие
скилы этому агенту доступны», а расширение набора инструментов происходит в момент загрузки скила.

Проверить отбор инструментов при регистрации нельзя — шаблон может не совпасть ни с чем. Значит
«агент, у которого не осталось ни одного инструмента» — законное состояние, и его надо показывать, а
не считать ошибкой конфигурации.

**Синтаксис отбора инструментов и скилов общий.** Два списка шаблонов; метасимвол один — `*`,
любой отрезок имени. Совпадение
идёт по всему имени целиком, а не по подстроке: `read` не совпадает с `read-file`. Остальные
метасимволы регулярных выражений — обычные буквы: `a.b` совпадает только с `a.b`. Регулярных
выражений здесь нет намеренно — автор плагина пишет `file-*`, а не экранирует точки, и чужое
выражение с возвратами стоило бы платформе времени на каждом сборе набора.

Сначала применяется `include`, из результата вычитается `exclude`; **`exclude` приоритетнее**.
Пустой `include` — это «ничего», а не «всё»: иначе опечатка в наборе молча открыла бы агенту `bash`.

```ts
await contribute.agent({
  id: "agent",
  title: "Base agent",
  instructions: "…системный промпт…",
  tools: { include: ["*"], exclude: ["bash"] },
  skills: { include: ["review-*"], exclude: ["*-unsafe"] },
});
```

И `tools`, и `skills` в SDK необязательны; внутри каждого из них можно опустить `exclude`. Умолчаний SDK не
подставляет — ни модели, ни пустых списков: их нормализует ядро. Отсутствующий селектор и отсутствующий
`exclude` означают пустые списки. Неявного `*` нет: без явного `include` агент не получает ни инструментов, ни
скилов. Вторая точка, где решается «что значит не сказано», означала бы два разных ответа на один вопрос.

## События

Событие — способ рассказать, не зная соседа. Оно объявляется вкладом со схемой нагрузки, а имя
получает неймспейс публикатора ([event-bus.md](event-bus.md)):

```ts
import { contribute, defineEvent, events, z, type PluginModule } from "@sovereign/sdk";

export const taskCreated = defineEvent("task.created", z.object({ id: z.string() }));

export const activate: PluginModule["activate"] = async () => {
  await contribute.event(taskCreated); // объявление: событие видно в реестре и выключается
  await taskCreated.publish({ id: "42" }); // публикация, с проверкой по схеме здесь же

  await events.subscribe("tracker.task.created", (payload, origin) => {
    // payload непрозрачна: чужой контракт мог измениться
  });
};
```

- **Схема пишется на `zod`, и `z` берётся из SDK** — не из своей зависимости: два экземпляра `zod`
  в процессе дают несовместимые типы схемы.
- **Нагрузка проверяется в воркере публикатора.** Не прошедшая проверку публикация отказывается на
  месте вызова и до ядра не доходит; в ядро уезжает описание схемы данными — для реестра.
- **Публиковать можно после того, как `activate` вернул управление.** Объявления применяются одним
  снимком, и до этого события ещё нет: попытка опубликовать раньше отказывается с записью в журнал.
- **Событие — это вклад,** поэтому выключенное человеком объявление означает, что публикации больше
  нет: отказ уходит в журнал, а плагин продолжает работать.
- **Дескриптор события — обычный экспорт модуля.** Подписчик импортирует его у публикатора и
  получает и типы, и возможность проверить нагрузку у себя. Схема между воркерами не ходит.
- **Подписка — по точному полному имени, без масок,** и возвращает отписку. Подписаться на
  необъявленное событие не ошибка: публикатор бывает ещё выключен.
- **События ядра слушаются так же и без исключений.** Записей журнала среди них нет
  ([logging.md](logging.md)).
- **Кольцо автор разрывает сам.** Плагин, подписанный на собственное событие и публикующий его из
  обработчика, зациклится: платформа этого не ловит.

## Хранилище

Плагин получает две вещи: **хранилище ключ-значение** и **свою папку**.

- Ключ-значение даёт SDK; живёт оно в файле, который пишет ядро
  ([data-directory.md](data-directory.md)), поэтому атомарность записи и одновременный доступ
  — забота платформы, а не автора. Это ответ на типичную потребность: сохранить настройку, состояние,
  небольшой список.
- Папка выдаётся внутри директории данных для тех случаев, где нужны файлы: вложения, кэш,
  собственная база. Что в ней лежит — дело плагина.

**Ключ — источник плюс идентификатор, а не только идентификатор.** Перекрытие — это другой плагин, а
не настройка того же: у встроенного и у перекрывающего его пространства ключей и папки разные.
Источник плагина из папки проекта — это конкретная папка, поэтому одноимённые плагины из разных
проектов тоже не делят состояние. **Данные не переезжают вслед за плагином:** автор, перенёсший плагин
из папки проекта в директорию данных, получает пустое состояние.

**Границей безопасности это не является.** Включённый плагин читает директорию данных целиком.
Разделение нужно для порядка и для того, чтобы платформа могла показать и убрать данные плагина.

**Выключение плагина данные не удаляет.** Выключение — не деинсталляция.

## Зависимости

Внешний плагин вправе пользоваться npm-зависимостями:

- есть `node_modules` — платформа не трогает ничего и не сверяет содержимое с манифестом;
- нет — ставит объявленное в `dependencies` через `npm` из `PATH`, и это отдельный этап
  жизненного цикла, а не скрытая пауза;
- поставленное платформой переустанавливается при изменении манифеста; привезённое — никогда;
- нет `npm` — плагин остаётся в `failed` с этим объяснением;
- `postinstall`-скрипты исполняются: отдельного решения это не требует, включённый плагин и так
  исполняет свой код.

У встроенных плагинов этого этапа нет: их зависимости решаются при сборке артефакта
([toolchain.md](toolchain.md)).

**Хот-релоад игнорирует `node_modules` внутри папки плагина.** Наблюдение идёт за директорией, а
установка пишет в неё тысячи файлов: без исключения этого подкаталога установка вызвала бы
перезагрузку плагина, которая вызвала бы проверку зависимостей, и так по кругу.

## Чего ещё нет

Реализовано ядро: манифест, источники, включение, воркеры, вклады общего вида и события,
публикация и подписка на шину, зависимости, перезагрузка, наблюдаемость снаружи. Не реализовано и
потому пока недоступно плагину:

- **типизированные виды вкладов** — из перечисленных выше есть общий вид `contribute.custom`,
  событие `contribute.event` и агент `contribute.agent`;
- **HTTP-маршруты плагина,** а вместе с ними и чтение состояния соседа ([web-api.md](web-api.md));
- **хранилище плагина** (ключ-значение и папка);
- **браузерная часть**: `sovereign.browser` разбирается, но ничего не собирает и не отдаёт;
- **хуки** ([hooks.md](hooks.md)): подписаться на `tools_collect` плагин пока не может, набор
  инструментов собирает одно ядро.

Сессии агента плагину доступны: `sessions.*` в SDK отдаёт тот же набор операций, что и веб-API
([sessions-and-projects.md](sessions-and-projects.md)). Это вторая — и последняя — пара
«запрос-ответ» в канале плагина.

## Почему так

### Воркер на плагин и полностью асинхронный API

**Решает не изоляция, а выгрузка.** Хот-релоад плагинов — требование вижна, а надёжно убрать код из
процесса Node нечем: повторный импорт с обходом кеша оставляет прежний модуль живым, пока на него
держит ссылку таймер, подписка или незавершённый промис, и частая перезагрузка копит утечки.
`terminate()` снимает поток целиком — вместе со всем, что плагин успел завести. Изоляция от сбоя и
лимит памяти достаются тем же решением бесплатно и подтверждены запуском
([runtime-checks.md](runtime-checks.md), проверка 5).

**Плагины в основном потоке, перезагрузка обходом кеша модулей.** Синхронное API и никакой
сериализации. Отвергнуто по причине выше: выгрузка перестаёт быть гарантированной, а зависший
плагин уносит с собой веб-API и все агентские сессии.

**Процесс на плагин.** Дал бы настоящие права ОС и устойчивость к нативному крашу. Отвергнуто по
цене: десятки постоянно живущих процессов против десятков потоков — это память и время старта, а
сериализация на границе точно такая же.

**Общий RPC «плагин зовёт ядро по имени метода».** Одна пара сообщений закрывает и провайдеров, и
всё, что появится потом. Отвергнуто: это не механизм, а разрешение — с ним любой метод ядра
становится вызываемым из плагина без отдельного решения, а публичным контрактом оказывается вся
внутренность демона. Ограничение провайдерами оставляет односторонность каналом по умолчанию:
следующий вид ответа придётся объявлять так же явно, как этот.

Остаточный риск назван честно: воркер спасает от исключения, зависания и превышения памяти, но
**падение нативного аддона уносит весь демон** — плагины ставят npm-зависимости, среди которых
бывают нативные. Отсюда и оговорка вижна про перезапуск демона как аварийный выход.

**Синхронные методы там, где ядро может ответить сразу.** Технически достижимо через `Atomics.wait`
поверх `SharedArrayBuffer`. Отвергнуто: блокирует поток плагина целиком, ломает его собственный
событийный цикл, и любой перенос метода на «медленную» сторону становится ломающим изменением
сигнатуры. Асинхронность по умолчанию делает такие переносы невидимыми.

**Падать целиком, если плагин не загрузился.** Прямо против «демон запускается один раз и больше не
глушится»: один сломанный плагин лишал бы пользователя всей платформы.

**Не перезапускать, ждать ручного вмешательства.** То же самое, только медленнее: демон, требующий
внимания после каждой сетевой икоты в плагине, не соответствует замыслу.

Цена: любой код, работающий с SDK, асинхронный, и это заражает сами плагины. Вечно ломаный плагин
будет перезапускаться вечно — потолок задержки удерживает это в рамках фонового шума, но видимый
статус обязателен, иначе поломка останется незамеченной.

### Включение — граница контроля, а не безопасности

Плагины распространяются исходниками, приносят свои npm-зависимости и исполняются с полными правами
процесса. Владелец продукта security-модели не требует: пользователь один, автор плагинов — он сам
или его агенты, защищаться не от кого. Задача выключателя другая — **немедленно убрать код, который
ведёт себя не так,** не читая его и не останавливая демон. Кода этого владелец построчно не читал:
его писал агент.

**Песочница с правами на плагин.** Правильный ответ в мире, где плагины ставят не глядя. Не наш мир.
Вдобавок воркер границей безопасности не является, а настоящая изоляция потребовала бы отдельных
процессов плюс модели разрешений — по объёму это сопоставимо с самой платформой. Экспериментальная
модель разрешений Node сюда тоже не подходит: она задаётся на процесс, а не на воркер.

**Реестр доверенных авторов, подписи.** Не для системы с одним пользователем и плагинами, которые он
чаще всего пишет сам.

**Всё включено всегда, выключателя нет.** Тогда сломанный плагин нечем убрать, кроме удаления папки
и перезапуска демона, — а это ровно то, чего требование хот-релоада велит избегать.

Отсюда обязанность: выключение обязано быть полным — недостаточно остановить воркер, надо снять всё,
что плагин зарегистрировал. Значит ядру нужен реестр регистраций с привязкой к плагину, а не
разрозненные коллекции.

### Новый плагин выключен, встроенный включён

**Новый плагин включён по умолчанию.** Удобнее: положил папку — заработало. Отвергнуто: недоверенный
код исполнялся бы без единого вопроса, а весь механизм защиты сводился бы к тому, успел ли
пользователь заметить новую папку.

**Встроенные выключены, как и все остальные.** Формально последовательнее, но делает свежую установку
мёртвой: платформа не умеет ничего, пока пользователь не найдёт и не включит поставленное вместе с
ней. Защиты это не добавляет — согласие на встроенный код дано установкой.

Следствие, которое надо держать в голове: за встроенный плагин отвечаем мы, а не пользователь. Во
встроенные попадает только то, что мы готовы включать всем по умолчанию, а список встроенных — часть
release notes, а не деталь реализации. **Переопределённый встроенный плагин наследует не состояние
встроенного, а правило своего источника:** перекрывающая версия — ранее не виданный код, и она
выключена.

### Жизненный цикл наблюдаем событиями

**Состояние плагинов только через запрос к API.** Интерфейс узнавал бы об изменениях с задержкой или
через поллинг, которого в системе нет ([web-api.md](web-api.md)).

Событий при этом недостаточно: вкладка, открытая позже, пропустила всё, что было до неё. Значит нужен
разовый запрос за текущим снимком плюс поток изменений — общий шаблон для всего интерфейса.

**Меньше состояний: `active` / `inactive` / `error`.** Проще для кода и бесполезно для человека:
«неактивен» одинаково значит «я его выключил», «он не совместим» и «он ставит зависимости». Разница
между ними и есть то, ради чего жизненный цикл наблюдаем.

**Отдельное `restarting` между `failed` и `starting`.** Отвергнуто: состояние ничем не отличалось бы
от `failed` с назначенным моментом попытки, а различать их пришлось бы каждому потребителю.

**Отказ от плагина после N неудачных попыток.** Соблазнительно — перестаёт шуметь в журнале. Но тогда
плагин, упавший из-за временной причины, остаётся мёртвым до перезапуска демона, а человек узнаёт об
этом случайно. Растущая задержка даёт то же затихание без потери восстановления.

**Сброс счётчика попыток при удачном `activate`.** Отвергнуто: плагин, падающий через секунду после
активации, никогда бы не дошёл до больших задержек и жёг бы процессор циклом «поднялся — упал».

### Перекрытие по источнику, спор при равном ранге не применяется

**Явный выбор пользователя на каждое место или на каждый вклад.** Гибче. Отвергнуто: это второе
правило перекрытия рядом с первым, плюс интерфейс выбора, хранение предпочтений и семантика
«выбранный провайдер исчез» — механика ради решения, которое пользователь уже принял, когда включил
плагин.

**Порядок регистрации.** Ничего не требует. Отвергнуто: зависит от таймингов загрузки, то есть
невоспроизводимо и необъяснимо пользователю.

**Детерминированный победитель при равном источнике — по id, по времени загрузки, по порядку в
манифесте.** Ошибки не бывает никогда, место всегда занято. Отвергнуто: победитель, выбранный
сравнением строк, случаен по существу, и установка нового плагина молча меняла бы поведение уже
работающего места.

**Взять первый и предупредить.** Дешевле всего. Отвергнуто: предупреждение, за которым всё равно
что-то работает, читают один раз и перестают.

**Отдельный реестр на проект.** В нём фильтрация получается автоматически. Отвергнуто: loader,
standalone-сервис и административный API получили бы несколько копий одного lifecycle-state и
обязательство синхронно обновлять их. Один declaration registry хранит происхождение один раз и
отбирает применимые объявления перед общим разрешением; сессия спрашивает результат по `projectId`.

**Сначала разрешить глобально, потом отфильтровать проекты.** Проще кешировать один результат.
Отвергнуто: две равноприоритетные project-копии создали бы конфликт и исчезли раньше, чем контекст
смог бы оставить правильную. Применимость поэтому проверяется до precedence/conflict.

Цена конфликта внутри одного контекста: функциональность **отсутствует**, а не деградирует — для заменяемого
места есть встроенный провайдер, а для имени инструмента нет, агент просто не увидит инструмент.
Поэтому диагностика обязана быть заметной в интерфейсе, а не строкой в журнале. И два плагина, честно
предлагающих одно и то же, не могут быть включены одновременно: платформа не угадывает, какой из них
имел в виду пользователь.

Обратная сторона правила источников: нельзя «включить плагин, но оставить встроенный компонент» —
единственный способ выключить один вклад или убрать плагин из более частного источника. Выбор не
переживает перемещения плагина, поэтому источник обязан быть виден в интерфейсе управления плагинами.

### Источник проекта называет запись, а не папку

До реализации здесь было записано `project:<путь>`. Владелец продукта выбрал `project:<id записи>`, и
документ переписан.

**`project:<путь папки>`.** Ключ читается глазами, и по нему видно, о какой папке речь. Отвергнуто:
путь длинный, содержит пробелы и юникод, требует кодирования в маршруте
`PUT /api/plugins/:key/preferences`, а на macOS ещё и меняет написание от регистра — ключ в
`preferences.json` разъезжался бы с ключом в памяти на ровном месте. Идентификатор записи короткий,
URL-безопасный и от написания пути не зависит.

**`project:<folderKey>`,** то есть нормализованный путь. Отвергнуто по той же причине плюс одна
своя: на macOS `folderKey` понижен в регистре и раскрыт по симлинкам, то есть в файле настроек
человек видел бы путь, которого он не вводил.

Цена решения: по ключу в `preferences.json` не видно, какому проекту принадлежит плагин, — за этим
надо идти в `projects.json` или в интерфейс. Плюс запись переживает удаление проекта осиротевшей:
идентификатор больше ни на что не указывает. Это не отличается от записи о плагине, папку которого
удалили ([backlog.md](backlog.md)).

### Переключается любой вклад, и переключает только человек

**Переключать только плагин целиком.** Не даёт оставить встроенный компонент и оставляет конфликт
двух плагинов из одного источника без выхода.

**Переключать по типу вклада** (все инструменты плагина сразу). Грубее, чем нужно, и не решает случай
двух плагинов, дающих по навигатору.

**Новый вклад выключен по умолчанию.** Последовательно с правилом для новых плагинов. Отвергнуто:
обновление плагина перестаёт работать до ручного вмешательства, а защиты это не добавляет — код
плагина всё равно исполняется.

**Плагин переключает только свои вклады.** Плагин смог бы сам убрать то, что у него не работает, и
чужого при этом не трогает. Отвергнуто владельцем продукта: выключенный человеком вклад плагин
включает обратно, и решение пользователя перестаёт быть последним.

**Переключать может любой включённый плагин.** Платформа автоматизируема до конца. Отвергнуто
владельцем продукта по той же причине: выключатель — последнее средство человека убрать
взбесившийся плагин, и оно бесполезно, если убранное включается обратно кодом.

Запрет обеспечен только на серверной стороне. Браузерная часть включённого плагина работает в той же
странице и с той же сессией пользователя, что и наши вью, а значит физически может позвать публичное
API ядра — включая переключение. Отдельной границы там нет и не будет: единый ярус рендеринга
означает, что код плагина в браузере равен нашему ([ui-extension-model.md](ui-extension-model.md)).

### Виды вкладов типизированы, плюс один общий

**Только закрытый перечень, общего вида нет.** Вся платформа знает про любой вклад всё: форма
проверяется при регистрации, вью плагинов показывает вклад по-человечески, стиль один. Отвергнуто
владельцем продукта: плагин не смог бы предложить вид вклада другим плагинам, хотя публиковать свои
места в интерфейсе ему уже разрешено — получилось бы, что расширять можно интерфейс, но не логику.

**Одна функция регистрации на всё, вид — строка, нагрузка произвольная.** Максимальная
расширяемость. Отвергнуто владельцем продукта; и задача так не решается: у вклада «агент»
по-прежнему не было бы контракта, а ядро не смогло бы проверить ничего, кроме идентификатора.

Общий вид — лазейка: им можно выразить то, для чего есть типизированный вид, и получить вклад,
который ядро не проверяет. Диагностикой это не ловится, лечится только документацией. Плата за то,
что плагины могут расширять друг друга.

### Состав вклада «агент»

**Ровно четыре поля из vision, без скилов.** Каждое поле обосновано словами владельца. Отвергнуто
владельцем продукта; и по существу поле всё равно появилось бы, потому что скилы в vision открывают
инструменты именно этому агенту, — только позже и ценой версии платформы.

**Всё, что настраивается у harness:** плюс режимы очередей стиринга и догоняющих сообщений, параметры
стрима, политика повторов. Отвергнуто владельцем продукта; эти поля описывают поведение сессии, а не
свойства агента.

**Отбор инструментов списком имён.** Проще проверить при регистрации. Отвергнуто: набор собирается в
рантайме, поэтому «проверить при регистрации» невозможно в принципе, а список пришлось бы править при
появлении каждого нового инструмента.

**Один список шаблонов вместо двух.** Меньше полей. Отвергнуто владельцем продукта: «взять всё, кроме
одного» — самый частый случай, и одним списком он выражается только перечислением всего остального,
то есть тем самым списком имён, от которого отказались выше.

**`include` приоритетнее `exclude`.** Отвергнуто владельцем продукта. Набор инструментов растёт со
временем, и запрет, который перебивается разрешением, перестаёт быть запретом ровно в тот момент,
когда появляется новый инструмент, подходящий под старый разрешающий шаблон.

### SDK берётся импортом, а не аргументом

**`ctx` аргументом функции активации.** Граница видна: всё, что плагин может, он получил в аргументе,
и тест — это `activate(fakeCtx)` без всякой машинерии. Отвергнуто владельцем продукта. Взвешивая
честно: главный аргумент против `ctx` не в эргономике, а в том, что он не устраняет неявное
состояние, а перекладывает его на автора — любой файл плагина, которому нужен журнал или шина, обязан
получить `ctx`, и автор на второй день заводит `let ctx` на уровне модуля, только уже без наших
гарантий. Единственное, что теряется вместе с `ctx`, — бесплатный тестовый шов, поэтому шов
приходится поставлять, и он становится частью публичного контракта.

**Декларативный объект: плагин экспортирует описание себя.** Всё видно без запуска. Отвергнуто по
требованию: скил открывает агенту инструменты полем во фронтматтере, то есть набор инструментов
меняется в рантайме и одним статическим описанием не выражается.

**И импорты, и `ctx` одновременно.** Отвергнуто: два способа сделать одно и то же удваивают типы и
раздваивают документацию.

**Шарить браузерную часть SDK как синглтон страницы.** Экономит несколько килобайт на бандл.
Отвергнуто: общий модуль не может определить, какой из плагинов его вызвал, и идентичность пришлось
бы передавать аргументом — то есть на браузерной стороне вернулся бы `ctx`. Поэтому браузерная часть
SDK вкладывается в бандл каждого плагина; синглтонами страницы остаются `react`, `react-dom` и
фронтовая шина.

Имена импортируемых функций становятся публичным контрактом: переименование — ломающее изменение.

### Манифест в `package.json`

**Отдельный `plugin.json`.** Наши поля не смешиваются с npm-полями. Отвергнуто: имя и версия
оказались бы в двух файлах, и первый же рассинхрон стал бы источником вопроса «какая версия
настоящая».

**Манифест кодом: `plugin.ts` с типизированным экспортом.** Ошибки ловил бы компилятор. Отвергнуто:
чтобы прочитать метаданные, понадобился бы трансформ и исполнение кода — а метаданные нужны именно до
исполнения, для проверки коллизий и для отрисовки вкладов без загрузки бандлов.

**Брать идентификатор из npm-поля `name`.** Одним полем меньше. Отвергнуто из-за слеша в
scoped-именах и из-за того, что npm-имя может быть занято или переименовано по причинам, не связанным
с платформой.

**Не проверять версию платформы.** Ноль работы. Отвергнуто: плагин ломался бы посреди работы, причём
выглядело бы это как баг ядра, а не как несовместимость. Отказ по версии — не то же, что выключенный
плагин: пользователь его не выключал, и в интерфейсе это обязано выглядеть как ошибка с причиной.

### Демон ставит зависимости, привезённые уважает

**Только привезённые модули, демон не ставит ничего.** Офлайн, детерминированно, ноль внешних
инструментов. Отвергнуто как единственный путь: автор обязан собрать нативные аддоны под каждую ОС и
архитектуру пользователя, обновление одной зависимости превращается в переупаковку, а «папка с
исходниками» весит десятки мегабайт. Как **побочный** путь вариант сохранён — он достаётся бесплатно,
потому что Node резолвит существующий `node_modules` сам.

**Общий `node_modules` на все плагины директории данных.** Дубли исчезают. Отвергнуто: два плагина с
несовместимыми версиями одного пакета перестают быть совместимы друг с другом, а причина конфликта не
видна ни одному из авторов.

**Установка в отдельный каталог с дедупликацией по хешу манифеста.** Экономит диск и время, как
pnpm. Отвергнуто: резолв модулей пришлось бы подменять — своя реализация хранилища пакетов ради
экономии диска.

**Свой установщик.** Lock-файлы, проверка целостности, распаковка тарболлов, кеш — отдельный продукт,
а не деталь платформы.

Цена: `npm` в `PATH` становится требованием окружения ([runbook.md](runbook.md)); платформа, которая
«работает локально», в момент включения плагина ходит в интернет; самодостаточный бинарь без Node в
системе лишил бы демона установщика.

### Хранилище: ключ-значение плюс папка

**Только папка: плагину выдаётся директория, дальше он сам.** Полная свобода автора. Отвергнуто
владельцем продукта; цена видна заранее — каждый второй плагин напишет свой JSON-файл с гонками при
записи, а платформа не сможет ни показать данные плагина, ни осмысленно их убрать.

**Отдельный файл SQLite на плагин плюс API к нему.** Прикладной плагин получает нормальную базу
сразу. Отвергнуто владельцем продукта: версии схемы и миграции всё равно остались бы на авторе, но
выглядело бы это так, будто за них отвечает платформа, — а такой файл ещё и надо открывать, закрывать
и переживать перезагрузку плагина. Отдельно от этого довода база отвергнута и в самой платформе
([data-directory.md](data-directory.md)). Плагину, которому нужна своя база, никто не мешает завести
её в выданной папке — но своей зависимостью и под свою ответственность.

**Хранить состояние плагинов в `preferences.json`.** Там уже лежат выключенные вклады и выбор темы.
Отвергнуто: файл перечитывается на живом демоне и предназначен для предпочтений пользователя, а не
для данных плагина.

**Одно пространство ключей на идентификатор: перекрытие — это тот же плагин другой версии.**
Настройки и накопленное состояние переезжают вместе с перекрытием, и для пользователя это выглядит
как обновление. Отвергнуто владельцем продукта. Цена варианта видна на главном сценарии перекрытия из
папки проекта — разработке своей версии плагина: черновик работал бы с боевыми данными и мог бы их
затереть, а откатиться было бы некуда.

**Ключ по идентификатору, но копия при первом перекрытии.** Данные и есть, и не общие. Отвергнуто как
худшее из двух: момент копирования становится скрытым состоянием.

Следствия: идентификатор плагина и его источник становятся частью схемы данных, поэтому переименование
плагина или переезд папки проекта — это потеря состояния, если не сделать переноса; перекрыв плагин,
человек видит пустое состояние, и вью плагинов обязано показывать это как разные записи с разными
источниками; чистка данных плагинов из папки проекта цепляется к удалению проекта, иначе база копит
состояние плагинов из папок, которых больше нет; квот на хранилище нет и вводить их незачем — тот же
плагин может писать в папку напрямую.
