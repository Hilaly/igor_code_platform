# Файловые агенты, Agent Skills и проектная применимость вкладов

## Статус и границы документа

Документ фиксирует только решения, уже согласованные при обсуждении файловых агентов и поддержки
[Agent Skills](https://agentskills.io/client-implementation/adding-skills-support). Это ещё не
полный дизайн и не план реализации: невыбранные части перечислены в разделе «Открытые вопросы» и
не считаются утверждёнными.

## Реестр и применимость вкладов

Реестр объявлений остаётся один на процесс. Плагины из всех источников обнаруживаются и запускаются
глобально, каждый плагин по-прежнему живёт в одном воркере. Проектная область не создаёт отдельный
реестр или экземпляр плагина на проект.

При этом единственный глобальный результат разрешения вкладов заменяется результатом для конкретного
потребителя. У агентной сессии такой контекст есть: идентификатор её проекта.

Для агентной сессии проекта `P` применимы:

- вклады встроенных плагинов;
- вклады плагинов из директории данных;
- вклады плагинов из источника `project:P`;
- не применимы вклады из источников остальных проектов.

Перекрытия и конфликты разрешаются после отбора применимых объявлений. Поэтому проектный вклад
перекрывает пользовательский или встроенный только в сессиях своего проекта, а одноимённые вклады из
двух разных проектов друг с другом там не встречаются.

Проектная применимость распространяется на **все виды вкладов, которые потребляет агентная
сессия**, в том числе на агентов, инструменты, скилы и подписки на хуки. Потребители без проектного
контекста — например, глобальная шина и общие HTTP-маршруты — не получают проектную область только
из-за этого решения; их правила требуют отдельного дизайна, если их понадобится изменить.

Как и сейчас, сессия не замораживает набор вкладов при создании. Действующий для проекта набор
пересчитывается на живой системе, чтобы выключение, перезагрузка или исчезновение плагина меняли
следующий доступный агенту снимок без перезапуска демона.

## Отбор скилов агентом

Поле `skills` в определении агента имеет ту же семантику, что и поле `tools`: два списка glob-шаблонов
`include` и `exclude`.

```ts
skills: {
  include: ["document-*", "code-review"],
  exclude: ["*-unsafe"],
}
```

Правила отбора совпадают с инструментами:

- метасимвол `*` означает любой отрезок имени;
- шаблон совпадает с полным именем, а не с подстрокой;
- сначала выбираются совпавшие с `include`, затем из них удаляются совпавшие с `exclude`;
- `exclude` всегда имеет приоритет над `include`;
- пустой `include` означает «ничего», а не «всё»;
- отсутствие совпадений законно и не делает определение агента ошибочным.

Список скилов динамический, поэтому совпадение шаблонов нельзя проверять при регистрации агента.
Сначала для проекта сессии разрешается текущий набор вкладов-скилов, затем к нему применяется отбор
выбранного агента. В каталог, видимый модели, попадают только прошедшие отбор скилы.

## Корни файловых скилов

Платформа поддерживает нативные каталоги Sovereign и межклиентские каталоги `.agents/skills`.
Таблица перечисляет области от более приоритетной к менее приоритетной:

| Область | Путь                           | Назначение                       |
| ------- | ------------------------------ | -------------------------------- |
| Project | `<project>/.sovereign/skills/` | нативные скилы Sovereign проекта |
| Project | `<project>/.agents/skills/`    | межклиентские скилы проекта      |
| User    | `<data-directory>/skills/`     | нативные пользовательские скилы  |
| User    | `~/.agents/skills/`            | межклиентские пользовательские   |

`<data-directory>/skills/` означает фактически выбранную директорию данных, а не обязательный путь
в домашнем каталоге. При значении по умолчанию это `~/.sovereign_platform/skills/`; при явном
позиционном аргументе запуска пользовательский нативный корень переезжает вместе со всей директорией
данных.

Внутри корня скил соответствует формату Agent Skills: это каталог с файлом, названным ровно
`SKILL.md`; рядом могут лежать `scripts/`, `references/`, `assets/` и другие ресурсы. Полный текст и
ресурсы не должны целиком попадать в начальный контекст: сохраняется progressive disclosure — сначала
модели показываются имя и описание, инструкции загружаются при активации, связанные файлы читаются
по необходимости.

Frontmatter поддерживает обязательные поля Agent Skills `name` и `description`, стандартные
необязательные поля `license`, `compatibility`, `metadata`, `allowed-tools` и расширение Pi
`disable-model-invocation`. Неизвестные поля игнорируются: один клиент вправе хранить в общем скиле
метаданные, которых другой не понимает. Поддержка поля означает, что loader распознаёт и проверяет
его форму. Если `allowed-tools` присутствует, его значение должно быть строкой и сохраняется в
определении как непрозрачная метадата. В этом срезе runtime не разбирает список и не меняет по нему
доступность или подтверждение инструментов — это соответствует фактическому поведению Pi.

Frontmatter разбирается как строгий YAML 1.2. Синтаксическая ошибка или повтор ключа делают
некорректным только текущее определение; остальные файлы продолжают загружаться. Неизвестные поля
ошибкой не считаются и после разбора игнорируются. Диагностика сохраняет путь к файлу и причину
отказа, а хот-релоад возвращает определение в реестр после исправления файла.

Размер каждого entry-файла `AGENT.md` и `SKILL.md` ограничен 1 МиБ (1 048 576 байт). Превышение
лимита делает некорректным только текущее определение и показывается как файловая диагностика.
Соседние ресурсы определения этим сервисом не измеряются и специального платформенного лимита не
получают: они загружаются по необходимости обычными инструментами с их собственными ограничениями.

К имени применяются ограничения Agent Skills, кроме одного намеренного расширения: наряду со
строчными латинскими буквами, цифрами и `-` разрешён символ `_`. Поэтому имя состоит из символов
`[a-z0-9_-]`, а остальные ограничения стандарта на длину и дефисы сохраняются. Скил с `_` загружается
обычно, но получает предупреждение о несовместимости со строгими Agent Skills-клиентами. Это
предупреждение не делает файл некорректным.

Встроенных standalone-скилов нет: всё встроенное поставляется плагинами из существующего корня
`plugins/`. Проектный скил применяется только в контексте своего проекта; скил одного проекта не
перекрывает скил в сессии другого проекта. Идентичность и перекрытие standalone- и plugin-owned
определений описаны ниже.

## Файловые агенты

Определение агента тоже хранится как Markdown с YAML-frontmatter. Каждый агент занимает отдельную
директорию, а точка входа называется ровно `AGENT.md`:

```text
<agents-root>/
└── code-agent/
    ├── AGENT.md
    └── ...            необязательные файлы этого агента
```

Markdown-body `AGENT.md` содержит непустые инструкции агента. Frontmatter имеет следующий контракт:

```yaml
---
name: code-agent
description: Агент для работы с кодом
tools:
  include: ["*"]
  exclude: []
skills:
  include: ["*"]
  exclude: []
model: optional-provider/optional-model
thinking-level: medium
---
```

`name` и `description` обязательны. `tools`, `skills`, `model` и `thinking-level` необязательны;
если они указаны, их значения проверяются по тем же контрактам, что у программного вклада агента.
Значение `name` обязано совпадать с именем директории агента; несовпадение делает определение
некорректным и создаёт диагностику. Если `tools` отсутствует, агент не получает инструментов; если
`skills` отсутствует, агент не получает скилов. То есть оба отсутствующих селектора эквивалентны
`{ include: [], exclude: [] }`, а не `*`. Неизвестные поля frontmatter игнорируются. Относительные
ссылки из определения разрешаются от директории агента. Благодаря отдельной директории определение
может иметь собственные сопутствующие файлы, не смешивая их с файлами соседних агентов.

Агенты — формат Sovereign, а не часть стандарта Agent Skills. Поэтому для них нет межклиентских
корней `.agents`; standalone-агенты поддерживаются только в нативных корнях:

| Область | Путь                           | Назначение                 |
| ------- | ------------------------------ | -------------------------- |
| Project | `<project>/.sovereign/agents/` | агенты конкретного проекта |
| User    | `<data-directory>/agents/`     | пользовательские агенты    |

Встроенных standalone-агентов нет. Базовая поставка приносит агентов только из каталогов встроенных
плагинов. Проектный standalone-агент доступен только сессиям своего проекта. Агент из одного проекта
не виден в другом и не конфликтует с одноимённым агентом другого проекта.

## Агенты и скилы внутри плагинов

Любой плагин может поставлять файловые определения агентов и скилов в необязательных каталогах рядом
со своим `package.json`:

```text
<plugin>/
├── package.json
├── agents/
│   └── <agent-name>/
│       └── AGENT.md
└── skills/
    └── <skill-name>/
        └── SKILL.md
```

Эта раскладка одинакова для всех трёх источников плагинов:

```text
<built-in>/<plugin>/agents/
<built-in>/<plugin>/skills/

<data-directory>/plugins/<plugin>/agents/
<data-directory>/plugins/<plugin>/skills/

<project>/.sovereign/plugins/<plugin>/agents/
<project>/.sovereign/plugins/<plugin>/skills/
```

`<built-in>` здесь означает существующий корень встроенных плагинов `plugins/`. Новые уровни
`built-in/plugins/`, отдельные `<built-in>/agents/` и `<built-in>/skills/` не создаются. Текущая
раскладка встроенных плагинов не меняется.

Plugin loader ищет `agents/` и `skills/` относительно уже обнаруженного каталога конкретного
плагина (`DiscoveredPlugin.directory`). Поэтому в разработке это
`<repository>/plugins/<plugin>/{agents,skills}/`, а в production —
`<data-directory>/builtin/<version>/<plugin>/{agents,skills}/` после существующей штатной распаковки.
Отдельный путь файловых ресурсов не настраивается, а parser не различает built-in, data и project
каталоги.

Файловые определения внутри плагина принадлежат этому плагину и его источнику. Они появляются только
у включённого и успешно запущенного плагина, применяются одним снимком вместе с программными
`contribute.*`, снимаются при выключении, падении, перезагрузке или исчезновении плагина и могут
переключаться человеком по отдельности как обычные вклады. Определения проектного плагина наследуют
применимость только к сессиям проекта этого источника.

Изменение `AGENT.md`, `SKILL.md` или соседних ресурсов является изменением плагина и проходит через
его существующий hot reload. Отдельного жизненного цикла для файловой части плагина нет.

Существующий встроенный `base-agent` мигрирует на этот же путь. Его единственное агентное
определение переезжает в `plugins/base-agent/agents/agent/AGENT.md`; программный
`contribute.agent()` и отдельный TypeScript-файл инструкций удаляются. Worker остаётся обязательной
лёгкой оболочкой текущего plugin contract: он успешно активируется и может записать lifecycle-log,
но больше не дублирует декларативный вклад. Идентификаторы `base-agent` и `base-agent.agent`, а также
возможность выключить плагин или его вклад сохраняются.

## Идентичность и перекрытия

Standalone- и plugin-owned определения остаются в разных пространствах имён:

- standalone-агент или скил получает короткий идентификатор `<name>`;
- файловый ресурс плагина, как и его программный вклад, получает существующий идентификатор
  `<pluginId>.<name>`.

`<name>` берётся из имени директории определения после проверки формата. Точные ограничения имени и
его согласование с полями frontmatter описываются контрактом конкретного формата, но standalone-имя
не является квалифицированным именем плагина. Перемещение одной версии плагина между built-in, data
и project не меняет идентификаторы его ресурсов.

Standalone `code-review` и plugin-owned `github.code-review` — два разных определения. Они могут
одновременно присутствовать в наборе проекта, не конфликтуют и не перекрывают друг друга. Поэтому в
`skills.include/exclude` плагиновый скил адресуется полным именем, например `github.*`, а standalone —
коротким, например `code-review`.

Перекрытие происходит только между определениями с одинаковой идентичностью:

- одноимённые standalone-определения разрешаются по уже заданному порядку их файловых корней;
- одноимённые ресурсы одного plugin id разрешаются по существующему порядку источников плагина
  `project → data → built-in`, но только после отбора применимых к проекту источников;
- совпадение короткого standalone-имени с объявленным именем ресурса плагина не создаёт перекрытия.

Сессия сохраняет окончательный `agentId`: короткий для standalone-агента и квалифицированный для
plugin-owned агента. Отдельные alias, `replaces` и неявная замена плагинового определения standalone-
файлом в первой реализации не поддерживаются.

### Ответственность plugin loader

Файловые каталоги внутри плагина загружает платформенный plugin loader в демоне, а не код самого
плагина. Для каждого обнаруженного плагина loader:

1. читает и проверяет `package.json` как сейчас;
2. обнаруживает и разбирает `agents/*/AGENT.md` и `skills/*/SKILL.md` рядом с манифестом;
3. запускает воркер и собирает программные вклады, объявленные во время `activate()`;
4. только после успешного `activate()` передаёт реестру один снимок файловых и программных вкладов.

Ошибка одного файлового определения не даёт только этому определению попасть в снимок и не блокирует
плагин или остальные его вклады. Диагностика сохраняет путь, источник и причину, чтобы UI показывал
файл среди проблемных ресурсов. При выключении, падении, перезагрузке или исчезновении плагина loader
снимает весь его снимок из реестра.

Файловый и программный вклад одного плагина не могут объявить один вид ресурса с одинаковым именем.
Если это произошло, ни один из двух претендентов на этот идентификатор не применяется, а UI получает
диагностику. Ошибка остаётся локальной для спорного идентификатора и не блокирует остальные вклады
или жизненный цикл плагина.

Standalone-каталоги `<data-directory>/{agents,skills}` и проектные `.sovereign/{agents,skills}` не
принадлежат плагину. За них отвечает отдельный сервис демона рядом с plugin loader. Оба потребителя
используют один общий файловый механизм парсинга, наблюдения и диагностики, но standalone-сервис не
является плагином и не подчиняется жизненному циклу конкретного плагина.

### Standalone file resource service

Standalone file resource service живёт всё время работы демона, наблюдает за всеми применимыми
standalone-корнями и передаёт реестру атомарные снимки найденных агентов, скилов и диагностик. Hot
reload — часть его контракта, а не необязательная оптимизация:

- появление корректного `AGENT.md` или `SKILL.md` добавляет определение;
- изменение entry-файла или соседнего ресурса обновляет снимок;
- удаление снимает определение;
- появление ошибки снимает только проблемное определение и добавляет диагностику;
- исправление ошибки убирает диагностику и возвращает определение без перезапуска демона.

Каждый корень обходится только на один уровень: распознаются ровно `<root>/<name>/AGENT.md` и
`<root>/<name>/SKILL.md`. Вложенные директории не ищутся как дополнительные определения, но остаются
ресурсами уже найденного агента или скила.

Симлинки на директорию определения, entry-файл и соседние ресурсы разрешены. Изменение цели симлинка
считается изменением ресурса; сломанный или недоступный симлинк даёт диагностику вместо молчаливого
пропуска. Поскольку discovery не рекурсивный, симлинк не расширяет глубину поиска новых определений.

Обновление публикуется целым снимком: потребитель видит прежнюю или новую версию набора, но не
промежуточное состояние во время пересканирования.

## Каталог и активация скилов

Runtime следует model-driven механике Pi. Для каждого применимого и разрешённого агенту скила в
системный prompt попадает компактная XML-запись с тремя полями:

- `name` — окончательное короткое или квалифицированное имя;
- `description` — описание из frontmatter;
- `location` — абсолютный путь к `SKILL.md`.

Когда задача соответствует описанию, модель активирует скил обычным доступным ей инструментом
`read`, прочитав полный `SKILL.md` по `location`. Относительные пути разрешаются от директории
`SKILL.md`; связанные scripts, references и assets модель читает отдельно по необходимости.

Скил с `disable-model-invocation: true` остаётся известен платформе и виден в диагностическом UI, но
не попадает в каталог модели. Поскольку явная пользовательская активация в этот срез не входит, такой
скил в текущем срезе активировать нельзя.

Отдельный model-tool `activate_skill` не добавляется. Пользовательские slash-команды, включая
`/skill:name`, и иная явная пользовательская активация не входят в этот срез.

Прочитанный моделью `SKILL.md` остаётся обычным результатом `read`. Runtime не помечает его как
защищённый и не вводит особых правил compaction: инструкции скила сворачиваются и удаляются из
контекста по тем же правилам Pi, что остальные результаты чтения файлов.

### Ответственность session service и runtime

Plugin loader отвечает за появление объявлений в общем реестре, но не решает, что доступно конкретной
сессии. Контекстное разрешение выполняет session service по `projectId`, а runtime получает уже
разрешённый и отфильтрованный набор.

Применимость пересчитывается в каждой точке, где актуальный набор имеет значение:

1. **Список агентов для проекта.** Сначала известен `projectId`, затем интерфейс или API получает
   агентов, применимых к этому проекту. Единого глобального списка выбираемых агентов больше нет.
2. **Создание сессии.** Выбранный `agentId` повторно проверяется в наборе проекта; только после этого
   его определение передаётся runtime для создания сессии.
3. **Ленивое открытие сессии.** Сохранённые `projectId` и `agentId` разрешаются заново. Исчезнувший
   или выключенный агент не уничтожает запись сессии, но не даёт поднять harness до возвращения
   определения.
4. **Каждый турн.** Инструменты, скилы и хуки разрешаются заново для проекта сессии непосредственно
   перед применением к runtime. Так hot reload и переключение вкладов действуют без пересоздания
   сессии.

Сессия сохраняет идентификаторы и историю разговора, но не копию определений и не снимок вкладов.
Сохранённый `agentId` связывает сессию с актуальным объявлением по правилам идентичности выше.

## Web API и интерфейс

Существующий `GET /api/agents` сохраняется. Он возвращает глобальный базовый каталог без проектного
контекста: применимые built-in, data и пользовательские standalone-агенты, но не определения из
какого-либо проекта. Маршрут остаётся полезен для обратной совместимости, общего обзора и
администрирования, но не является полным источником выбора агента для проектной сессии.

Для проектного контекста добавляются подресурсы проекта:

```http
GET /api/projects/:projectId/agents
GET /api/projects/:projectId/file-resources
```

Первый маршрут возвращает окончательный набор агентов, применимый к проекту после отбора источников и
разрешения перекрытий. Второй возвращает файловые агенты, скилы и их состояния, включая источник,
путь и диагностику некорректных, затенённых и выключенных определений. Неизвестный проект отвечает
`404`; пустой применимый набор — успешный ответ с пустым списком.

Только `GET /api/projects/:projectId/agents` используется как источник выбора агента при создании
сессии. `POST /api/sessions` в любом случае повторно разрешает переданные `projectId` и `agentId` на
актуальном снимке, поэтому устаревший ответ клиента не создаёт сессию с уже исчезнувшим агентом.

Экран создания сессии сначала получает проект и только затем загружает его агентов. До выбора проекта
поле агента недоступно. Смена проекта сбрасывает выбранного агента и зависимые от него умолчания
модели и thinking level. При переходе со страницы конкретного проекта проект уже выбран, поэтому
форма сразу запрашивает его каталог.

На странице проекта появляется раздел файловых агентов и скилов: количество доступных определений и
перечень проблемных файлов с путём, источником и причиной. Редактирование файлов и управление ими из
этого раздела в текущий срез не входят.

Если агент сохранённой сессии исчез или стал неприменим, история сессии остаётся доступна. Экран
показывает предупреждение с `agentId`, блокирует composer, а попытка начать турн отвечает `409`.
Возврат определения через hot reload снова делает сессию рабочей без миграции её записи.

Изменение объявлений публикуется событием-инвалидацией `core.contributions.changed` с ревизией, но
без одного глобального разрешённого снимка. Клиент, которому нужен актуальный набор, повторно
запрашивает подресурс выбранного проекта. Существующее `core.plugin.contributions` может продолжать
описывать изменения плагиновых объявлений, но не заменяет контекстную инвалидацию standalone- и
проектных ресурсов.

## Общий файловый механизм

Агенты и скилы обнаруживаются одним механизмом файловых ресурсов. У них общие:

- модель областей `project → user → built-in`;
- разрешение перекрытий в контексте проекта;
- наблюдение за файловыми корнями и применение изменений без перезапуска демона;
- правила диагностики отсутствующих, некорректных и затенённых определений;
- инфраструктура чтения Markdown с YAML-frontmatter.

При этом агент и скил остаются разными типами вклада и разными форматами. `AGENT.md` немедленно даёт
ядру определение, из которого пользователь выбирает при создании сессии. `SKILL.md` даёт доступный
агенту ресурс с progressive disclosure и проходит дополнительный отбор `skills.include/exclude`.
Общая инфраструктура не превращает один формат в частный случай другого.

## Открытые вопросы

До реализации нужно отдельно согласовать:

- точную wire-схему файловой диагностики и пагинацию, если список окажется достаточно большим.

## Почему так

### Один реестр объявлений, разрешение в контексте сессии

Отдельный реестр и отдельные воркеры плагинов на каждый проект не нужны: проект уже известен сессии,
а объявления можно отфильтровать перед разрешением перекрытий. Так сохраняются один жизненный цикл
плагина и хот-релоад, но содержимое одного проекта больше не меняет агента, работающего в другом.

Прежний глобальный результат обслуживал сценарий «обкатать плагин в проекте, затем перенести в
директорию данных». Для агентных вкладов его цена стала неприемлемой: проектный `SKILL.md`, агент,
инструмент или хук влиял бы на чужие проекты, а два проекта с одноимённым скилом создавали бы
глобальный конфликт вместо стандартного проектного перекрытия.

### Строгий YAML и совместимость по полям

Loader не пытается восстанавливать смысл синтаксически некорректного YAML: эвристическое исправление
может незаметно изменить селекторы, модель или инструкции агента. По той же причине при повторе ключа
не выбирается ни первое, ни последнее значение — определение отклоняется целиком.

Строгость относится к синтаксису YAML и форме известных полей, но не к набору всех возможных полей.
Неизвестные поля разрешены ради совместимости между клиентами и будущих расширений формата. Ошибка
остаётся локальной для одного файла, видна в UI с причиной и исчезает после исправления благодаря
хот-релоаду.

### Лимит только для entry-файлов

Entry-файл читается и разбирается целиком при discovery и каждом hot reload, поэтому ограничение в
1 МиБ защищает демон от случайно огромного Markdown и сохраняет предсказуемое время пересборки
снимка. Этого достаточно для frontmatter и инструкций существенно большего обычного размера.

Соседние ресурсы не входят в начальный контекст и читаются только при необходимости. Их полный обход
и измерение нарушили бы progressive disclosure, усложнили бы симлинки и сделали бы стоимость reload
зависимой от всего дерева определения. Поэтому отдельная квота на них в file resource service не
вводится.

### Ресурсы относительно каталога плагина

Discovery уже разрешает источник плагина в конкретный каталог: исходный `plugins/<plugin>/` в
разработке и распакованный `builtin/<version>/<plugin>/` в production. Поиск файловых ресурсов
относительно этого каталога сохраняет один механизм для всех источников и один жизненный цикл кода и
Markdown-определений.

Отдельное встраивание ресурсов или настраиваемый built-in-путь отвергнуты: они создали бы второй
адрес одной версии плагина, который можно рассинхронизировать с манифестом, воркером и hot reload.

### Файловый `base-agent` при неизменном plugin lifecycle

Перенос базового агента в `AGENT.md` проверяет новый путь на настоящем встроенном определении и
убирает два источника истины для инструкций. При этом разрешение плагина без worker расширило бы
манифест, discovery, supervisor и критерий успешной активации, хотя для поддержки файловых ресурсов
этого не требуется.

Поэтому worker пока сохраняется как минимальная оболочка жизненного цикла, а сам агент объявляется
только файлом. Оставить программный `base-agent` тоже отвергнуто: тогда основной встроенный агент не
использовал бы проектируемый формат и постоянно требовал бы отдельного пути сопровождения.

### Отбор скилов совпадает с отбором инструментов

Скилы, как и инструменты, появляются и исчезают на живой системе. Список точных имён устаревал бы
при установке каждого нового скила, а отдельный язык шаблонов создавал бы две разные семантики одной
задачи. Приоритет `exclude` сохраняет явный запрет при росте набора.

### Нативные и межклиентские корни

`.sovereign/skills/` даёт платформе собственное предсказуемое место, а `.agents/skills/` позволяет
использовать один скил в нескольких совместимых клиентах. Пользовательские корни дают общий набор,
проектные — более частную настройку. Встроенные определения не получают отдельного корня: базовая
поставка уже состоит из встроенных плагинов, и второй способ положить рядом тот же ресурс создавал бы
встроенный вклад без владельца и жизненного цикла.

### Отдельная директория на агента

Один файл `<name>.md` был бы достаточен только пока агент состоит из frontmatter и инструкций.
Каталог `<name>/AGENT.md` сразу задаёт стабильную базу для относительных ссылок и сопутствующих
файлов. Та же форма уже знакома по Agent Skills, но имя точки входа намеренно другое: форматы имеют
разные контракты и не должны определяться по содержимому одного универсального Markdown-файла.

Имя директории и `name` во frontmatter обязаны совпадать, чтобы файловый адрес, идентификатор в
реестре и сохранённый `agentId` не расходились. Использовать одно из имён только как отображаемое
отвергнуто: для человекочитаемого названия уже есть `description`, а два технических имени создавали
бы неявный alias.

Отсутствующие `tools` и `skills` означают пустые селекторы. Неявное `*` отвергнуто как небезопасное:
после установки нового плагина агент получил бы новые возможности без изменения своего определения.
Явный `include: ["*"]` остаётся доступен агенту, которому действительно нужен весь динамический
набор.

### Один обход, два формата

Два независимых watcher и два механизма приоритетов расходились бы при первом изменении правил
областей. Общий файловый слой отвечает только за обнаружение, происхождение, перекрытие и
диагностику. Перевод `AGENT.md` во вклад агента и `SKILL.md` во вклад скила остаётся раздельным,
поскольку жизненный цикл их содержимого различается.

### Отдельный сервис рядом с plugin loader

Встроенный системный плагин для standalone-корней отвергнут: эти определения не имеют собственного
плагинового владельца, а их доступность и hot reload являются базовой функцией платформы. Передача
обхода каждому поставляющему плагину тоже отвергнута: standalone-корни существуют без плагина, а
авторы повторяли бы один и тот же watcher и parser.

Отдельный сервис демона сохраняет границу ответственности: plugin loader управляет ресурсами своего
плагина и его жизненным циклом, standalone-сервис — независимыми файловыми корнями, а общий нижний
слой обеспечивает им одинаковые правила чтения, диагностики и наблюдения.

### Плоский discovery с разрешёнными симлинками

Рекурсивный поиск `SKILL.md` и `AGENT.md` отвергнут: утверждённая раскладка уже задаёт отдельную
директорию непосредственно под корнем, а рекурсия делает случайную вложенную копию новым
определением и требует ограничений глубины и общего числа каталогов. Один уровень оставляет
вложенное дерево свободным для ресурсов определения.

Симлинки разрешены, потому что пользователь может хранить общий агент или скил вне директории данных
либо проекта. Цена — watcher обязан учитывать изменение цели и явно диагностировать сломанные ссылки,
а не только следить за самой записью каталога.

### Активация скила обычным read

Отдельный `activate_skill` не нужен: runtime уже даёт модели чтение файлов, а Pi раскрывает ей
`name`, `description` и `location`, после чего модель читает подходящий `SKILL.md`. Второй инструмент
дублировал бы доступный путь и потребовал отдельной синхронизации схемы с динамическим каталогом.
Пользовательские slash-команды Pi относятся к интерактивной оболочке `pi-coding-agent`, которую
платформа не использует, и намеренно оставлены за границей этого среза.

Особая защита результата чтения `SKILL.md` при compaction тоже отвергнута: выбранная цель — повторить
механику Pi без отдельного вида сообщения или результата инструмента. Цена — при долгом разговоре
полные инструкции могут быть пересказаны или удалены на общих основаниях; если это проявится как
практическая проблема, управление контекстом скилов проектируется отдельным срезом.

### `allowed-tools` без runtime-семантики

Agent Skills определяет `allowed-tools` как экспериментальную строку предварительно разрешённых
инструментов, но конкретная семантика зависит от клиента. Pi распознаёт поле в документации, однако
его model-driven загрузка скилов не меняет по нему набор инструментов во время чтения `SKILL.md`.

Платформа поэтому проверяет строковый тип и сохраняет исходное значение для совместимости, но не
выдаёт скилу дополнительных прав и не ограничивает им агента. Динамическое применение потребовало бы
отдельно определить момент активации, пересечение с `agent.tools`, время жизни разрешения и поведение
после compaction; это не скрывается под простым разбором frontmatter.

### Underscore — совместимое расширение имени

Строгий Agent Skills разрешает в `name` только строчные латинские буквы, цифры и дефис. Sovereign
дополнительно принимает `_`, потому что это утверждённый общий алфавит имён файловых агентов и скилов.
Полный отказ от такого скила был бы несовместим с нативным форматом платформы; молчаливое принятие
скрывало бы проблему при переносе в другой клиент. Поэтому определение работает, а диагностика
отмечает отклонение от строгого стандарта.

### Дубликат внутри плагина ломает только свой идентификатор

Приоритет файлового или программного объявления одного плагина отвергнут: оба принадлежат одному
источнику и одному владельцу, поэтому выбирать победителя не по чему, а порядок загрузки сделал бы
результат зависимым от тайминга. Ошибка всего плагина была бы несоразмерна одной коллизии. Реестр
исключает только спорный идентификатор и сохраняет диагностику, продолжая применять остальные вклады.

### Проектные агенты — подресурс проекта

Query-параметр `GET /api/agents?projectId=...` потребовал бы помнить, что глобально выглядящий
маршрут без параметра имеет другую семантику. Подресурс `GET /api/projects/:projectId/agents` выражает
область адресом и не позволяет форме создания сессии случайно запросить неправильный каталог.

При этом удалять `GET /api/agents` не требуется. Он сохраняет обратную совместимость и честно
показывает базовый каталог без ресурсов какого-либо проекта. Цена двух маршрутов — необходимость явно
документировать, что только проектный ответ пригоден для выбора агента проектной сессии.

Один глобальный снимок в событии отвергнут по той же причине, по которой разрешение вкладов стало
контекстным: такого снимка больше нет. Событие несёт только ревизию и заставляет заинтересованного
клиента перечитать данные нужного проекта.

### Файловые определения принадлежат плагину

Плагин мог бы сам обходить свои каталоги и регистрировать каждый файл через SDK. Отвергнуто: каждый
автор повторял бы один parser, watcher и правила диагностики, а одинаковая файловая раскладка имела бы
разное поведение у разных плагинов. Платформа обнаруживает стандартные каталоги сама, но не отрывает
их содержимое от плагина: файловые и программные вклады появляются и исчезают одной атомарной
версией.

### Standalone и плагины не делят пространство имён

Единое плоское пространство коротких имён позволило бы проектному standalone-файлу неявно заменить
встроенного агента или скил. Отвергнуто: оно ломает действующий контракт `<pluginId>.<declaredId>`,
создаёт конфликты между независимыми плагинами и позволяет установке плагина незаметно подменить
инструкции уже известного ресурса. Для сохранённых сессий понадобилась бы миграция `agentId`.

Отдельный внутренний адрес владельца плюс второе логическое имя тоже отвергнуты для первой версии.
Такая модель сохраняет владельца и одновременно позволяет перекрытия по короткому имени, но требует
определить, какой из двух идентификаторов хранит сессия, как выбирается победитель и что происходит
при его исчезновении. Это новая модель реестра ради пока не заявленного сценария.

Короткие standalone-имена и существующие квалифицированные имена плагинов дают нужную файловую
совместимость без миграции реестра. Цена решения: standalone-файл не может неявно заменить
`base-agent.agent`, а в glob-шаблонах плагиновые скилы указываются с неймспейсом. Если явная замена
понадобится, для неё отдельно проектируется `replaces`, а совпадение имён не получает скрытой
семантики.
