# Файловые агенты, Agent Skills и проектная применимость вкладов

## Статус и границы документа

Документ фиксирует только решения, уже согласованные при обсуждении файловых агентов и поддержки
[Agent Skills](https://agentskills.io/client-implementation/adding-skills-support). Это ещё не
полный дизайн и не план реализации: невыбранные части перечислены в разделе «Открытые вопросы» и
не считаются утверждёнными.

## Реестр и применимость вкладов

Реестр объявлений остаётся один на процесс. Плагины из всех источников обнаруживаются и запускаются
глобально, каждый плагин по-прежнему живёт в одном воркере. Проектная область не создаёт отдельный
реестр или экземпляр плагина на проект.

При этом единственный глобальный результат разрешения вкладов заменяется результатом для конкретного
потребителя. У агентной сессии такой контекст есть: идентификатор её проекта.

Для агентной сессии проекта `P` применимы:

- вклады встроенных плагинов;
- вклады плагинов из директории данных;
- вклады плагинов из источника `project:P`;
- не применимы вклады из источников остальных проектов.

Перекрытия и конфликты разрешаются после отбора применимых объявлений. Поэтому проектный вклад
перекрывает пользовательский или встроенный только в сессиях своего проекта, а одноимённые вклады из
двух разных проектов друг с другом там не встречаются.

Проектная применимость распространяется на **все виды вкладов, которые потребляет агентная
сессия**, в том числе на агентов, инструменты, скилы и подписки на хуки. Потребители без проектного
контекста — например, глобальная шина и общие HTTP-маршруты — не получают проектную область только
из-за этого решения; их правила требуют отдельного дизайна, если их понадобится изменить.

Как и сейчас, сессия не замораживает набор вкладов при создании. Действующий для проекта набор
пересчитывается на живой системе, чтобы выключение, перезагрузка или исчезновение плагина меняли
следующий доступный агенту снимок без перезапуска демона.

## Отбор скилов агентом

Поле `skills` в определении агента имеет ту же семантику, что и поле `tools`: два списка glob-шаблонов
`include` и `exclude`.

```ts
skills: {
  include: ["document-*", "code-review"],
  exclude: ["*-unsafe"],
}
```

Правила отбора совпадают с инструментами:

- метасимвол `*` означает любой отрезок имени;
- шаблон совпадает с полным именем, а не с подстрокой;
- сначала выбираются совпавшие с `include`, затем из них удаляются совпавшие с `exclude`;
- `exclude` всегда имеет приоритет над `include`;
- пустой `include` означает «ничего», а не «всё»;
- отсутствие совпадений законно и не делает определение агента ошибочным.

Список скилов динамический, поэтому совпадение шаблонов нельзя проверять при регистрации агента.
Сначала для проекта сессии разрешается текущий набор вкладов-скилов, затем к нему применяется отбор
выбранного агента. В каталог, видимый модели, попадают только прошедшие отбор скилы.

## Корни файловых скилов

Платформа поддерживает нативные каталоги Sovereign и межклиентские каталоги `.agents/skills`.
Таблица перечисляет области от более приоритетной к менее приоритетной:

| Область | Путь                           | Назначение                       |
| ------- | ------------------------------ | -------------------------------- |
| Project | `<project>/.sovereign/skills/` | нативные скилы Sovereign проекта |
| Project | `<project>/.agents/skills/`    | межклиентские скилы проекта      |
| User    | `<data-directory>/skills/`     | нативные пользовательские скилы  |
| User    | `~/.agents/skills/`            | межклиентские пользовательские   |

`<data-directory>/skills/` означает фактически выбранную директорию данных, а не обязательный путь
в домашнем каталоге. При значении по умолчанию это `~/.sovereign_platform/skills/`; при явном
позиционном аргументе запуска пользовательский нативный корень переезжает вместе со всей директорией
данных.

Внутри корня скил соответствует формату Agent Skills: это каталог с файлом, названным ровно
`SKILL.md`; рядом могут лежать `scripts/`, `references/`, `assets/` и другие ресурсы. Полный текст и
ресурсы не должны целиком попадать в начальный контекст: сохраняется progressive disclosure — сначала
модели показываются имя и описание, инструкции загружаются при активации, связанные файлы читаются
по необходимости.

Встроенных standalone-скилов нет: всё встроенное поставляется плагинами из существующего корня
`plugins/`. Полная модель приоритетов, включая плагиновые определения и ещё не решённую идентичность,
уточняется отдельно. Проектный скил применяется только в контексте своего проекта; скил одного
проекта не перекрывает скил в сессии другого проекта.

## Файловые агенты

Определение агента тоже хранится как Markdown с YAML-frontmatter. Каждый агент занимает отдельную
директорию, а точка входа называется ровно `AGENT.md`:

```text
<agents-root>/
└── code-agent/
    ├── AGENT.md
    └── ...            необязательные файлы этого агента
```

Markdown-body `AGENT.md` содержит инструкции агента. Frontmatter содержит его структурированные
свойства; точный набор и правила полей ещё требуют согласования. Относительные ссылки из определения
разрешаются от директории агента. Благодаря отдельной директории определение может иметь собственные
сопутствующие файлы, не смешивая их с файлами соседних агентов.

Агенты — формат Sovereign, а не часть стандарта Agent Skills. Поэтому для них нет межклиентских
корней `.agents`; standalone-агенты поддерживаются только в нативных корнях:

| Область | Путь                           | Назначение                 |
| ------- | ------------------------------ | -------------------------- |
| Project | `<project>/.sovereign/agents/` | агенты конкретного проекта |
| User    | `<data-directory>/agents/`     | пользовательские агенты    |

Встроенных standalone-агентов нет. Базовая поставка приносит агентов только из каталогов встроенных
плагинов. Проектный standalone-агент доступен только сессиям своего проекта. Агент из одного проекта
не виден в другом и не конфликтует с одноимённым агентом другого проекта.

## Агенты и скилы внутри плагинов

Любой плагин может поставлять файловые определения агентов и скилов в необязательных каталогах рядом
со своим `package.json`:

```text
<plugin>/
├── package.json
├── agents/
│   └── <agent-name>/
│       └── AGENT.md
└── skills/
    └── <skill-name>/
        └── SKILL.md
```

Эта раскладка одинакова для всех трёх источников плагинов:

```text
<built-in>/<plugin>/agents/
<built-in>/<plugin>/skills/

<data-directory>/plugins/<plugin>/agents/
<data-directory>/plugins/<plugin>/skills/

<project>/.sovereign/plugins/<plugin>/agents/
<project>/.sovereign/plugins/<plugin>/skills/
```

`<built-in>` здесь означает существующий корень встроенных плагинов `plugins/`. Новые уровни
`built-in/plugins/`, отдельные `<built-in>/agents/` и `<built-in>/skills/` не создаются. Текущая
раскладка встроенных плагинов не меняется.

Файловые определения внутри плагина принадлежат этому плагину и его источнику. Они появляются только
у включённого и успешно запущенного плагина, применяются одним снимком вместе с программными
`contribute.*`, снимаются при выключении, падении, перезагрузке или исчезновении плагина и могут
переключаться человеком по отдельности как обычные вклады. Определения проектного плагина наследуют
применимость только к сессиям проекта этого источника.

Изменение `AGENT.md`, `SKILL.md` или соседних ресурсов является изменением плагина и проходит через
его существующий hot reload. Отдельного жизненного цикла для файловой части плагина нет.

## Общий файловый механизм

Агенты и скилы обнаруживаются одним механизмом файловых ресурсов. У них общие:

- модель областей `project → user → built-in`;
- разрешение перекрытий в контексте проекта;
- наблюдение за файловыми корнями и применение изменений без перезапуска демона;
- правила диагностики отсутствующих, некорректных и затенённых определений;
- инфраструктура чтения Markdown с YAML-frontmatter.

При этом агент и скил остаются разными типами вклада и разными форматами. `AGENT.md` немедленно даёт
ядру определение, из которого пользователь выбирает при создании сессии. `SKILL.md` даёт доступный
агенту ресурс с progressive disclosure и проходит дополнительный отбор `skills.include/exclude`.
Общая инфраструктура не превращает один формат в частный случай другого.

## Открытые вопросы

До реализации нужно отдельно согласовать:

- кто владеет общим файловым механизмом и объявляет найденные агенты и скилы: встроенный плагин, ядро
  или общий helper SDK, вызываемый поставляющими ресурс плагинами;
- как логические имена standalone- и plugin-owned определений соотносятся с неймспейсными
  идентификаторами вкладов и могут ли они претендовать на одно имя;
- как разрешаются коллизии standalone-каталога, межклиентского каталога и каталога плагина внутри
  одной области;
- какие поля входят во frontmatter `AGENT.md`, как из имени директории получается идентификатор и
  какие нарушения приводят к отказу;
- строгий или совместимый разбор frontmatter, включая диагностику некорректного YAML;
- предел глубины и размера обхода, реакцию на симлинки и правила наблюдения за изменениями;
- точный путь встроенного каталога в исходниках и production-артефакте;
- как существующий встроенный `base-agent` переезжает из TypeScript-плагина в файловое определение;
- способ активации моделью и пользователем, форму каталога в контексте и защиту загруженных
  инструкций при компакции;
- расширение скила полем с шаблонами открываемых инструментов и момент применения этих инструментов;
- изменения веб-API и интерфейса: выбор проекта должен предшествовать выдаче применимых агентов и
  остальных проектно-зависимых вкладов;
- диагностику затенённых, выключенных и непригодных скилов.

## Почему так

### Один реестр объявлений, разрешение в контексте сессии

Отдельный реестр и отдельные воркеры плагинов на каждый проект не нужны: проект уже известен сессии,
а объявления можно отфильтровать перед разрешением перекрытий. Так сохраняются один жизненный цикл
плагина и хот-релоад, но содержимое одного проекта больше не меняет агента, работающего в другом.

Прежний глобальный результат обслуживал сценарий «обкатать плагин в проекте, затем перенести в
директорию данных». Для агентных вкладов его цена стала неприемлемой: проектный `SKILL.md`, агент,
инструмент или хук влиял бы на чужие проекты, а два проекта с одноимённым скилом создавали бы
глобальный конфликт вместо стандартного проектного перекрытия.

### Отбор скилов совпадает с отбором инструментов

Скилы, как и инструменты, появляются и исчезают на живой системе. Список точных имён устаревал бы
при установке каждого нового скила, а отдельный язык шаблонов создавал бы две разные семантики одной
задачи. Приоритет `exclude` сохраняет явный запрет при росте набора.

### Нативные и межклиентские корни

`.sovereign/skills/` даёт платформе собственное предсказуемое место, а `.agents/skills/` позволяет
использовать один скил в нескольких совместимых клиентах. Пользовательские корни дают общий набор,
проектные — более частную настройку. Встроенные определения не получают отдельного корня: базовая
поставка уже состоит из встроенных плагинов, и второй способ положить рядом тот же ресурс создавал бы
встроенный вклад без владельца и жизненного цикла.

### Отдельная директория на агента

Один файл `<name>.md` был бы достаточен только пока агент состоит из frontmatter и инструкций.
Каталог `<name>/AGENT.md` сразу задаёт стабильную базу для относительных ссылок и сопутствующих
файлов. Та же форма уже знакома по Agent Skills, но имя точки входа намеренно другое: форматы имеют
разные контракты и не должны определяться по содержимому одного универсального Markdown-файла.

### Один обход, два формата

Два независимых watcher и два механизма приоритетов расходились бы при первом изменении правил
областей. Общий файловый слой отвечает только за обнаружение, происхождение, перекрытие и
диагностику. Перевод `AGENT.md` во вклад агента и `SKILL.md` во вклад скила остаётся раздельным,
поскольку жизненный цикл их содержимого различается.

### Файловые определения принадлежат плагину

Плагин мог бы сам обходить свои каталоги и регистрировать каждый файл через SDK. Отвергнуто: каждый
автор повторял бы один parser, watcher и правила диагностики, а одинаковая файловая раскладка имела бы
разное поведение у разных плагинов. Платформа обнаруживает стандартные каталоги сама, но не отрывает
их содержимое от плагина: файловые и программные вклады появляются и исчезают одной атомарной
версией.
