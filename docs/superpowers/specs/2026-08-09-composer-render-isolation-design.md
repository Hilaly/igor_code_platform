# Изоляция рендера композера агентской сессии

## Проблема

Черновик сообщения сейчас принадлежит `ChatView`. Контролируемый `Textarea` вызывает `setDraft` на
каждый введённый символ, поэтому React повторно рендерит всё поддерево `ChatView`, включая
`SessionMessageList`.

Это не означает безусловную перерисовку каждого пикселя окна: React ещё сравнивает полученное дерево
с DOM. Но до сравнения лента заново:

- фильтрует записи активной ветки;
- строит карты результатов инструментов;
- создаёт действия каждой записи;
- разбирает сохранённый Markdown через `ReactMarkdown`.

Профилирование длинной открытой сессии в dev-режиме показало повторный render
`SessionMessageList` на каждый символ с `actualDuration` от 24 до 43 мс. Это уже больше бюджета
кадра 16,7 мс при 60 Гц без учёта layout и paint.

## Цель

Набор текста, очистка принятого сообщения и локальное состояние отправки должны обновлять только
композер. Неизменившаяся история не должна повторно рендериться из-за состояния ввода.

## Не входит в задачу

- виртуализация или пагинация истории;
- изменение внешнего вида композера;
- изменение правил `Enter`, очередей, модели или reasoning;
- оптимизация обработки новых live-дельт: новая дельта действительно меняет ленту и обязана её
  обновить.

## Состояние черновика

`MessageComposer` становится владельцем строки `draft`. Публичные props `draft` и
`onDraftChange` удаляются; компонент сам:

- обновляет черновик из `Textarea`;
- читает его при submit, steer, follow-up, next-turn и append;
- очищает после принятого действия;
- сбрасывает при смене `sessionId`;
- сохраняет при отказе действия или ошибке.

Так обычное нажатие клавиши обновляет состояние на уровне `MessageComposer` и не вызывает render
родительского `ChatView`.

### Подстановка текста из дерева

Дерево записей остаётся отдельным sibling-компонентом, поэтому прямого setter черновика у него
больше нет. `ChatView` хранит только одноразовый запрос замены:

```ts
export type ComposerDraftReplacement = {
  sessionId: string;
  sequence: number;
  text: string;
};
```

`EntryTreeDrawer.onEditorText` создаёт новый запрос для текущей сессии. `sequence` различает два
последовательных перехода с одинаковым текстом. `MessageComposer` применяет только запрос с
совпадающим `sessionId`; старый запрос другой сессии не может заполнить новый композер.

Это состояние меняется только при явном переходе по дереву, а не при наборе каждого символа.

## Граница истории

`SessionMessageList` экспортируется через `memo`. Для работы границы `ChatView` сохраняет
ссылочную стабильность props, которые не изменились:

- `before` с notices создаётся через `useMemo`;
- `after` с очередями создаётся через `useMemo`;
- `onLabelRefusalChange` создаётся через `useCallback`.

Изменение `open`, busy-состояния, архива, меток, очередей, notices или callback верхнего уровня
по-прежнему обновляет ленту. Мемоизация запрещает только render с тем же набором данных.

Локальное владение draft — основная изоляция. `memo` — вторая граница, чтобы последующие локальные
состояния или безвредные parent-render не вернули дорогое поведение.

Внутри ленты применяются две дополнительные дешёвые границы:

- `Markdown` экспортируется через `memo` и обновляется только при изменении `text`;
- `outcomes`, `shown` и `liveOrder` вычисляются через `useMemo` по своим снимкам данных.

Это не заменяет границу `SessionMessageList`: такая оптимизация нужна для неизбежных обновлений
ленты от live-дельт, ошибок, очередей и действий над записями.

## Асинхронная отправка и ошибки

Текущая защита `operationToken` и `currentSessionId` сохраняется. Поздний результат старой сессии не
очищает новый черновик и не снимает `submitting` у другой сессии.

После успешного принятия `MessageComposer` очищает собственный draft. Отказ с текстовой причиной
или rejected promise оставляет введённый текст для повторной отправки. Ошибка по-прежнему уходит в
`onError`.

## Проверки

Компонентные тесты должны доказать:

1. ввод в композер не вызывает повторный render сохранённого Markdown;
2. submit использует локальный draft и очищает его только после принятия;
3. смена `sessionId` очищает draft;
4. запрос из дерева заменяет draft, включая повторную подстановку одинакового текста;
5. запрос предыдущей сессии игнорируется;
6. реальные изменения `open` продолжают обновлять историю;
7. повторный render `SessionMessageList` с тем же текстом не запускает повторный Markdown parse.

После автоматических тестов повторяется браузерный профиль на той же длинной сессии. При
последовательном вводе в логе профайлера не должно быть update-коммитов `SessionMessageList`.

## Почему так

**Только `memo(SessionMessageList)`.** Убирает измеренный дорогой render, но оставляет высокочастотное
состояние в слишком широком владельце. Любой новый нестабильный prop снова пробивает границу.
Отвергнуто как неполная защита.

**Только перенести draft в `MessageComposer`.** Устраняет текущий parent-render, но не защищает
историю от последующих независимых обновлений `ChatView` с теми же данными. Отвергнуто как
недостаточная защита дорогого поддерева.

**Только `memo(Markdown)`.** Убирает повторный parse, но оставляет обход всей ленты, вычисление
селекторов и создание props для каждой записи на каждую клавишу. Отвергнуто как единственный фикс,
принято как дешёвая вторая граница для live-дельт.

**Мемоизировать только `modelPickerGroups`.** После переноса draft это не влияет на набор текста,
а без `memo(NextTurnPicker)` стабильный массив сам по себе не запрещает render компонента. Оставлено
за пределами этой задачи.

**Императивный ref композера.** Позволил бы дереву напрямую менять поле, но вводит скрытый
командный интерфейс и отдельный жизненный цикл ref. Отвергнуто: одноразовый типизированный запрос
явно привязан к сессии и остаётся обычным React data flow.

**Виртуализация истории.** Снижает цену действительно изменившейся большой ленты, но меняет
прокрутку, измерение элементов и доступность. Она не нужна, чтобы неизменившаяся история вообще не
рендерилась при вводе, поэтому остаётся отдельной будущей задачей только после новых измерений.
