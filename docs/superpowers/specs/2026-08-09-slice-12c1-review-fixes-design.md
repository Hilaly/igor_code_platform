# Исправления среза 12c-1 по ревью

## Цель

Довести ветку `feat/slice-12c1-tabs-and-commands` до состояния, в котором реализация команд и мест
соответствует утверждённому контракту, безопасно переживает смену ревизии плагина и объединяется с
актуальным `main` без потери изменений обеих веток.

Исправление закрыто, когда интерфейс не загружает браузерный бандл ради показа кнопки или палитры,
`invoke` не бросает ни при каком поведении плагинного дескриптора, ожидающий вызов не исполняет
устаревшую ревизию, команда появляется только в месте `action`, а публичная документация совпадает с
кодом.

## Причины дефектов

У найденных ошибок три общих причины:

1. `PluginModuleCache.moduleOf` одновременно читает состояние и начинает загрузку. Пассивный интерфейс
   не может проверить уже известный `available`, не вызвав `import()`.
2. Ожидание команды замыкается на снимок `BrowserRuntime` на момент щелчка. При `building` и смене
   ревизии старый снимок больше не описывает действующий бандл, а удаление записи кеша не будит
   ожидателя.
3. Общий рендерер коллекции получает только идентификатор места. Он не знает, является место
   `collection` или `action`, хотя только второе вправе принимать команды.

Исключение из `available` — отдельный дефект границы доверия: плагинный код вызывается из React-render
без преобразования исключения в управляемый исход.

## Внутренний контракт кеша модулей

`PluginModuleCache` разделяет две операции:

- загрузочная операция возвращает состояние и при необходимости начинает загрузку действующей
  ревизии; её используют `PlaceInstance` и `invoke`;
- пассивная операция возвращает только уже существующее состояние той же ревизии и никогда не
  начинает загрузку; её используют кнопки и палитра.

Кеш публикует стабильную числовую версию состояния для `useSyncExternalStore`. Версия меняется при
завершении загрузки и при удалении либо замене действующей записи. Благодаря этому один host-хук может
наблюдать каталог из произвольного числа команд, не вызывая React hooks в цикле и не создавая новый
snapshot-объект на каждое чтение.

Загрузочная операция остаётся единственным владельцем `import()` и таблицы стилей. Пассивное чтение не
создаёт запись кеша, не вставляет `<link>` и не обращается к сети.

## Вызов и доступность команды

`useCommands` хранит актуальный `BrowserRuntime` в ссылке, доступной уже начатым вызовам. Во время
ожидания каждый сигнал кеша и каждое изменение снимка заново проверяют по `commandId`:

- существует ли команда в текущем контексте;
- существует ли её плагин;
- есть ли у текущего статуса браузерная ревизия;
- завершилась ли загрузка именно этой ревизии.

Промежуточный статус `building` без browser assets означает ожидание. Новая ревизия начинает новую
загрузку; старая после удаления из кеша не запускается повторно. Исчезнувшая команда или плагин
завершают уже начатый вызов исходом `failed`. Размонтирование runtime сохраняет существующую гарантию
`failed` вместо вечного Promise.

Чтение дескриптора, вызов `available` и вызов `run` находятся внутри одной границы обработки ошибок.
Любое синхронное или асинхронное исключение становится `{ kind: "failed", reason }` и попадает в
дедуплицированную диагностику. `invoke` никогда не возвращает rejected Promise из-за плагинного кода.

Host-логика доступности читает только пассивное состояние кеша:

- модуль ещё не загружался или грузится — команда видима и считается доступной;
- модуль загружен, `available` вернул `false` — кнопка и строка палитры выключены;
- `available` бросил — интерфейс остаётся цел, команда выключена, причина уходит в диагностику;
- экспорт отсутствует или имеет неверную форму — команда выключена и диагностируется.

Кнопка и палитра используют одну функцию разбора дескриптора и одинаково трактуют состояние.
Публичные `Command`, `CommandOutcome`, `useCommands` и `useCommandCatalog` не меняются. Обогащённый
каталог доступности остаётся host-only API: плагин не получает новый способ инспектировать чужие
загруженные модули.

## Кардинальность и отображение мест

`CollectionPlace` получает проверенную кардинальность места:

- `collection` рисует только компоненты;
- `action` рисует компоненты и команды в общем детерминированном порядке;
- `single` и `tabs` этим рендерером не обслуживаются.

Для места ядра кардинальность берётся из `corePlaces`, для места плагина — из разрешённого объявления
места. Неизвестный `placeId` продолжает ждать и не считается ошибкой: порядок появления плагинов не
фиксирован.

Plugin Detail получает исход `incompatible` для команды, направленной в известное место не-`action`,
вместо ложного `added`. Такой вклад не рисуется. Компоненты сохраняют прежнюю семантику всех четырёх
кардинальностей.

Ключ смешанного ряда включает вид вклада: `component:<id>` или `command:<id>`. Это соответствует
идентичности реестра и допускает компонент и команду с одинаковым объявленным id.

## Пространство имён ядра

Идентификатор плагина `core` резервируется проверкой манифеста. Отказ происходит до исполнения кода и
содержит явную причину. Идентификатор `core` нельзя использовать ни во встроенном, ни в data-, ни в
project-источнике: источник не меняет принадлежность namespace.

Это предотвращает коллизию `core.<command>` с командами хоста у источника, а не маскирует её разными
React keys. Остальные идентификаторы, соответствующие `pluginIdPattern`, не меняются.

## Документация и интеграция

`public-contract.md` получает четвёртую кардинальность `tabs`. Тематические документы фиксируют
разделение пассивного чтения и загрузки, обработку исключений `available`, ограничение команды местом
`action` и зарезервированный namespace `core`.

Исторический план 12c-1 приводится к факту: выполненные шаги отмечаются, оправданные отмены остаются
записанными как отмены. Наблюдавшееся единожды падение теста session rename записывается в backlog как
подозреваемый flake и не считается блокером этого среза.

Перед исправлениями ветка объединяется с актуальным локальным `main`. Конфликты в тестах и документах
разрешаются сохранением требований обеих веток, после чего выполняется полный TDD-набор уже на
объединённом дереве. История не переписывается, push и PR не выполняются без отдельной просьбы.

## Проверка

Каждый дефект получает тест, который сначала падает на старой реализации:

- исключение из `available` возвращает `failed`, не ломает кнопку и не ломает палитру;
- рендер кнопки и открытие палитры не вызывают загрузочную операцию кеша;
- уже загруженный `available: false` выключает и кнопку, и строку палитры;
- вызов, начатый на старой ревизии, пережидает `building`, исполняет только новую ревизию и завершается;
- исчезновение команды, плагина или runtime завершает ожидание управляемым исходом;
- команда не рисуется в `collection`, `single` или `tabs`, а Plugin Detail сообщает `incompatible`;
- компонент и команда с одинаковым id имеют разные React keys;
- манифест с plugin id `core` отвергается с понятной причиной.

После точечных циклов выполняются `make check`, `make build`, `git diff --check` и повторный просмотр
диффа относительно merge-base с `main`. Для Node с экспериментальным пустым `globalThis.localStorage`
проверки запускаются с `NODE_OPTIONS=--no-experimental-webstorage`; это ограничение окружения, а не
изменение продуктового контракта.

## Почему так

**Оставить один `moduleOf` с флагом `load: false`.** Отвергнуто: булев флаг скрывает важную границу
побочного эффекта, а неверное значение снова незаметно потянет все бандлы. Две именованные операции
делают сетевое действие видимым в месте вызова.

**Хранить доступность отдельно в React state кнопки и палитры.** Отвергнуто: два потребителя неизбежно
разойдутся в обработке loading, missing export и исключений. Один host-слой читает один кеш и отдаёт
одинаковую семантику.

**Исполнять старую ревизию, если её import уже начался.** Отвергнуто: после `retain` эта ревизия больше
не входит в снимок хоста. Запуск её кода после обновления означал бы исполнение вклада, которого
действующий реестр уже не подтверждает.

**Считать неизвестное место несовместимым.** Отвергнуто: плагины обнаруживаются без фиксированного
порядка, и вклад вправе ждать объявления места другим плагином. Несовместимость известна только тогда,
когда само место уже объявлено с не-`action` кардинальностью.

**Разрешить plugin id `core`, различив строки палитры внутренним ключом.** Отвергнуто владельцем:
коллизия останется в адресном `invoke` и в будущих публичных пространствах имён. Namespace ядра
резервируется на входе.
