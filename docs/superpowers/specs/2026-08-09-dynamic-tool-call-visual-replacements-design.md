# Динамическая подмена визуала вызовов инструментов

**Статус:** утверждено владельцем продукта 2026-08-09.

## Задача

Сейчас каждый блок `tool-call` в сохранённой истории и каждый живой вызов инструмента безусловно
рисуется одним компонентом UI-кита — `ToolCall`. Этого недостаточно для инструментов со своим
предметным визуалом. Например, инструмент запуска субагента должен иметь возможность показать
собственную карточку или поток работы агента вместо общей технической карточки.

Любой включённый плагин должен иметь возможность заменить визуал любого инструмента, включая
встроенный или принадлежащий другому плагину. Если replacement отсутствует, конфликтует, не
загрузился или упал, остаётся нынешний встроенный `ToolCall`.

## Граница решения

Этот срез проектирует только выбор браузерного компонента для одного вызова инструмента.

В него не входят:

- новые способы исполнения инструментов;
- поток прогресса инструмента;
- хранение предметного состояния инструмента;
- контракт субагентов и дочерних сессий;
- маски и группы имён инструментов;
- изменение встроенного визуала `ToolCall`.

Специализированный компонент сам решает, откуда брать свои предметные данные. Хост даёт ему
идентичность размещения через существующий `PlaceContext`, но не превращает внутренние пропсы
`ToolCall` в публичный контракт.

## Существующий контракт остаётся достаточным

Нового вида вклада нет. Плагин использует обычный вклад `kind: "component"`, который уже умеет:

- адресоваться в ещё не появившееся место;
- разрешаться по рангу источника;
- конфликтовать с равным по рангу претендентом без случайного победителя;
- лениво загружать browser export;
- возвращаться к встроенному провайдеру при ошибке загрузки или отрисовки;
- применяться только в подходящем проектном контексте.

Не добавляются `tool-renderer`, `target`, matcher или другие поля регистрации. Resolver мест и форма
`ComponentContribution` не меняются.

## Динамическое семейство мест

Каждое имя инструмента задаёт своё одиночное заменяемое место. Это не статическое место в
`corePlaces`, а динамическое семейство, экземпляр которого появляется, когда вызов с таким именем
попадает в ленту:

```ts
toolCallPlaceId(toolName);
```

Каноническая форма идентификатора:

```text
core.session.tool-call.t-<utf8-hex-tool-name>
```

Например:

```text
spawn_agent → core.session.tool-call.t-737061776e5f6167656e74
```

Полное hex-кодирование UTF-8 выбрано потому, что имена инструментов не обязаны соответствовать
шаблону place id. Оно обратимо и не создаёт коллизий между, например, `write_file` и `write-file`.
Читаемое исходное имя всё равно находится в `PlaceContext` и диагностике вызова.

Чистая функция `toolCallPlaceId` живёт рядом с моделью мест в `@sovereign/protocol` и
реэкспортируется из `@sovereign/sdk`, чтобы ядро и автор плагина не повторяли правило адресации.
Добавляется только helper публичного имени; wire-форма вклада не меняется.

## Регистрация replacement

Плагин регистрирует обычный component-вклад по точному имени инструмента:

```ts
await contribute.component({
  id: "subagent-tool-call",
  placeId: toolCallPlaceId("spawn_agent"),
  export: "SubagentToolCall",
});
```

Один browser export может обслуживать несколько имён: плагин регистрирует несколько вкладов с
разными `id` и `placeId`, но одним `export`. Маски не нужны в первом срезе: особый визуал является
осознанным свойством конкретного инструмента, а точное имя сохраняет явность конфликтов.

Право на replacement не связано с владельцем инструмента. Любой плагин может адресовать component
в место любого точного имени. Ранги источников и проектный контекст ограничивают применение так же,
как у остальных мест.

## Размещение в ленте

Обе ветки текущего рендера — сохранённый `SessionContentBlock` и живой `StreamedTool` — используют
один внутренний компонент размещения. Он получает уже собранное ядром состояние вызова и строит:

```tsx
<HostPlace
  id={toolCallPlaceId(toolName)}
  context={{
    project: projectId,
    subject: { sessionId, toolCallId, toolName },
  }}
  builtIn={<ToolCall {...builtInProps} />}
/>
```

`project` — настоящий проектный контекст открытой сессии. Поэтому вклад из папки проекта может
заменить визуал только в этом проекте, вклад из директории данных — во всех проектах, если его не
перекрыл более частный источник.

`subject` содержит только строковые идентификаторы:

- `sessionId` — сессия, внутри которой находится вызов;
- `toolCallId` — конкретный вызов;
- `toolName` — исходное, незакодированное имя инструмента.

`input`, `output`, `status` и внутренние callbacks в `subject` не копируются. Это сохраняет
действующее правило: контекст места описывает предмет размещения, но не замораживает пропсы
встроенного React-вью как публичный API. Специализированный компонент получает `{ context }` по
нынешнему browser contract и использует `toolCallId` для обращения к собственной или публичной
предметной поверхности.

Встроенный `ToolCall` продолжает получать все текущие пропсы напрямую из `apps/web`. Его поведение и
вид не меняются.

## Разрешение и fallback

Для каждого показанного вызова применяется существующий `HostPlace`:

1. Нет component-вклада для вычисленного id — рисуется встроенный `ToolCall`.
2. Есть единственный победитель — загружается его browser export и создаётся отдельный экземпляр.
3. Два вклада одинакового максимального ранга спорят — не применяется ни один, публикуется
   диагностика, рисуется встроенный `ToolCall`.
4. Плагин выключен или исчез из снимка — на следующем рендере возвращается встроенный `ToolCall`.
5. Бандл, экспорт или отрисовка replacement сломаны — `InstanceBoundary` показывает встроенный
   `ToolCall` и публикует диагностику.
6. Replacement сам вернул `null` — это его осознанный результат по действующему контракту; fallback
   не включается.

Каждый tool call является отдельным React-экземпляром, даже когда несколько вызовов одного имени
используют один и тот же вклад и export. Локальное состояние одного визуала не разделяется с другим.

## Публичный контракт

Публичным становится правило динамического семейства `core.session.tool-call.*` и функция
`toolCallPlaceId(toolName)`. Публичными не становятся:

- `ToolCallProps` UI-кита;
- внутренние типы `StreamedTool` и `ToolOutcome` веб-приложения;
- форма состояния конкретного инструмента;
- способ, которым специализированный renderer получает свои предметные данные.

Удаление или изменение алгоритма `toolCallPlaceId` после публикации является ломающим изменением:
старые component-вклады перестанут попадать в места. Поэтому единственным источником правила
остаётся общая функция, а строковые литералы в коде ядра и плагинов не используются.

## Проверки

### Протокол и SDK

- `toolCallPlaceId` выдаёт place id, допустимый действующим `placeIdPattern`.
- Разные имена, включая `_`, `-`, точки, Unicode и имена с одинаковой человекочитаемой
  нормализацией, дают разные id.
- Один и тот же helper доступен ядру через protocol и автору плагина через SDK.
- Форма `ComponentContribution` и зарегистрированного component-вклада не меняется.

### Browser SDK

- Существующий `HostPlace` выбирает component для динамического id.
- Равный конфликт возвращает built-in и диагностику.
- Ошибка browser export или рендера возвращает built-in.
- Два экземпляра одного динамического места получают разные `PlaceContext` и независимое состояние.

Большая часть fallback-проверок уже существует для обычных мест; новые тесты доказывают, что
динамический id не обходит этот путь, а не повторяют весь контракт загрузчика.

### Веб-приложение

- Сохранённый tool call и живой tool call вычисляют одинаковый place id.
- В `subject` передаются `sessionId`, `toolCallId` и исходный `toolName`, а в `project` — проект
  сессии.
- При отсутствии replacement результат и семантика нынешнего `ToolCall` не меняются.
- Replacement одного имени не затрагивает вызовы другого имени.

Визуальная регрессия не требуется: встроенный вид не меняется, а произвольный вид принадлежит
плагину. Проверяется выбор компонента и сохранение fallback.

## Почему так

### Динамическое место вместо нового вида вклада

`tool-renderer` отвергнут: он повторил бы регистрацию browser export, разрешение источников,
конфликты, ленивую загрузку, границу ошибок и fallback — всё, что уже делает `component`.

### Семейство мест вместо одного статического места с matcher

Один `core.session.tool-call` с `target.toolName` отвергнут. Он потребовал бы нового поля вклада и
особого отбора до resolver, хотя действующая модель уже разрешает произвольное количество мест и
вклады в места, которые появятся позже. Имя инструмента естественно является частью адреса места.

### Точный tool name вместо масок

Маски отвергнуты для первого среза: они добавляют приоритет «точное имя против шаблона», пересечения
шаблонов и новые виды конфликтов. Плагин может явно зарегистрировать один export для нескольких
точных имён несколькими обычными вкладами.

### Идентичность вместо публичных пропсов встроенного вью

Передача `input`, `output` и `status` replacement-компоненту отвергнута: это превратило бы текущую
форму внутреннего `ToolCall` в публичный контракт и расходилось бы с общей моделью мест, где контекст
называет предмет, а данные читаются публичными сервисами. Для предметного визуала достаточно
стабильных `sessionId` и `toolCallId`; его собственный поток и состояние проектируются вместе с самим
инструментом, а не универсальным renderer seam.
