# Рендеринг live-сессии и Markdown

## Цель

Синхронизировать геометрию live-вызовов инструмента с сохранёнными репликами и показывать reasoning
и текст ответа агента через существующий UI-kit `Markdown` уже во время стриминга.

## Область

В срез входят три изменения:

1. Live `ToolCall` получает тот же визуальный контейнер `Message role="agent"`, что и сохранённые
   блоки, поэтому ограничивается `--sovereign-reading-width` и не становится отдельной записью
   сессии.
2. Сохранённый и live reasoning рендерятся компонентом `Markdown`.
3. Live текст ответа рендерится компонентом `Markdown` на каждой пришедшей дельте без debounce и
   без выделения стабильных блоков.

JSON-viewer для аргументов инструментов в этот срез не входит: `ToolCall` сохраняет текущий
`CodeBlock` и строковый `argumentsText`.

## Поведение и границы

Live-обёртка нужна только для DOM-раскладки. Протокол и состояние сессии не меняются: tool call
остаётся элементом live turn, а в сохранённой истории — блоком того же сообщения агента.

`Markdown` уже применяет GFM и санитайзинг, поэтому новые парсеры и зависимости не добавляются.
Незакрытые Markdown-конструкции во время стриминга могут временно перестраивать DOM; это принято
как экспериментальное поведение. Если на реальных ответах проявятся скачки или нагрузка, debounce
или рендеринг стабильных блоков оформляются отдельным срезом.

## Почему так

Ранее `StreamingText` был выбран как плоский поток из-за повторного разбора всего текста на каждой
дельте и скачков на незакрытых fenced code blocks. Владелец продукта явно выбрал прямой Markdown
во время стриминга для проверки реального поведения; сохранение текущего варианта после теста
не считается ограничением архитектуры.
