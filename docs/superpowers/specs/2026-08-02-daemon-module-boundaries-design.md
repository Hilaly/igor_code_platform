# Внутренние границы демона

## Цель

Разделить плоский `apps/daemon/src` на предметные области и сделать нарушения их границ ошибкой
`make lint`, не превращая области во workspace-пакеты и не меняя поведение демона.

Эта итерация проверяет предполагаемые пакетные границы на существующем коде. Отдельный пакет
появится только тогда, когда области понадобится независимый потребитель, свой жизненный цикл или
компилируемая TypeScript-граница.

крупных модулей, в том числе `sessions.ts`, в этой итерации не дробится.

## Публичный вход области

У каждой области есть `public.ts` с явными именованными реэкспортами того, чем пользуются другие
области и `main.ts`. `export *` не используется: расширение внутреннего модуля не должно молча
расширять фасад области.

`public.ts` — внутренний фасад приложения, а не публичный контракт платформы. Он не экспортируется
из `@sovereign/daemon`, не доступен плагинам и не получает гарантий совместимости между версиями.

Внутри одной области модули импортируют соседние файлы напрямую. Между областями допустим только
импорт `../<area>/public.ts`. Прямой импорт `../<area>/<module>.ts` считается нарушением независимо
от того, экспортирует ли модуль нужное имя.

`main.ts` остаётся composition root и импортирует только фасады областей. Исключения для глубоких
импортов ему не нужны.

## Направление зависимостей

Разрешённые зависимости областей:

| Область          | Может импортировать из                                  |
| ---------------- | ------------------------------------------------------- |
| `platform`       | —                                                       |
| `http`           | `platform`                                              |
| `authentication` | `http`, `platform`                                      |
| `settings`       | `http`, `platform`                                      |
| `projects`       | `http`, `platform`                                      |
| `providers`      | `http`, `platform`                                      |
| `sessions`       | `projects`, `http`, `platform`                          |
| `plugins`        | `settings`, `providers`, `sessions`, `http`, `platform` |

`main.ts` может импортировать все области. Направление повторяет существующий ациклический граф;
рефакторинг не добавляет новые связи и не вводит общий предметный пакет для обхода матрицы.

Импорты workspace-пакетов (`@sovereign/protocol`, `@sovereign/sdk`,
`@sovereign/agent-runtime-pi`) остаются под действующими правилами репозитория. Новые внутренние
алиасы путей не вводятся: относительный путь показывает пересечение границы прямо в исходнике.

## Проверка ESLint

Корневой `eslint.config.js` получает отдельные блоки `no-restricted-imports` для каждой области.
Каждый блок одновременно проверяет:

- импорт из чужой области только через её `public.ts`;
- импорт только из областей, разрешённых матрицей;
- сохранение действующих запретов на `apps` и `@earendil-works/*`, поскольку в flat config опции
  более узкого блока заменяют, а не дополняют прежние.

`apps/daemon/src/import-boundary.test.ts` запускает настоящий корневой ESLint через `lintText` и
проверяет минимум четыре случая:

1. разрешённую зависимость через `public.ts`;
2. отказ глубокому импорту при разрешённом направлении;
3. отказ обратной зависимости через `public.ts`;
4. доступ `main.ts` ко всем фасадам и сохранение прежнего запрета на Pi вне
   `packages/agent-runtime-pi`.

Тест проверяет конфигурацию, которая реально исполняется в `make lint`, а не копию матрицы в
тестовом коде.

## Сохранение поведения и проверка

Рефакторинг меняет только пути модулей, фасады и правила импортов. HTTP-маршруты, протокол,
состояние, порядок запуска, обработка сигналов, формат файлов и API SDK не меняются.

Проверка включает:

- новый тест архитектурной границы;
- существующие тесты демона после переноса;
- `make typecheck`;
- `make lint`;
- `make test`;
- `make build`;
- `make fmt-check`, кроме заранее существующего и принятого владельцем нарушения форматирования в
  `docs/superpowers/plans/2026-08-02-compact-menu-trigger.md`, которое этот рефакторинг не меняет.

## Документация

Тем же рефакторингом обновляются:

- `docs/repository-structure.md`: раскладка областей, матрица зависимостей, роль `public.ts` и
  проверка ESLint;
- актуальные тематические документы, которые прямо ссылаются на перемещённые файлы демона;
- `docs/README.md`, если в ходе реализации появится новый тематический документ.

Выполненные планы и спецификации из `docs/superpowers/` остаются историческими снимками и не
переписываются под новые пути.

## Почему так

**Предметные папки с проверяемыми фасадами.** Выбрано как наименьший шаг, который делает
архитектурную ошибку автоматическим отказом CI и одновременно показывает, выдерживают ли границы
реальный граф изменений. Плоский каталог уже скрывает области, но код пока не требует семи новых
единиц сборки.

**Сразу вынести области в `packages/*`.** Отложено: текущие пакеты потребляются исходниками и не
являются изолированными TypeScript project references. Простое добавление `package.json` дало бы
церемонию пакетов, но всё ещё позволило бы относительный обход к исходникам. Настоящая
компиляторная изоляция потребовала бы изменить утверждённую модель сборки, выпускать декларации и
задать порядок компиляции.

**Только папки без фасадов и правил ESLint.** Отвергнуто: такая раскладка улучшает навигацию, но
любой модуль по-прежнему может импортировать внутренности соседа, поэтому заявленной границы не
существует.

**Один общий `internal` или `shared` для зависимостей областей.** Отвергнуто: каталог быстро стал бы
неограниченным каналом обхода матрицы. Низкоуровневые механизмы имеют конкретные области `platform`
и `http`; предметный код остаётся у своего владельца и выходит через его фасад.

**Проверять только глубокие импорты.** Отвергнуто: фасад без направления зависимостей разрешил бы
циклы между областями. Матрица фиксирует и способ импорта, и допустимое направление.

Цена выбранного варианта: ESLint, а не TypeScript, остаётся механизмом защиты; фасады нужно
поддерживать вручную; опции `no-restricted-imports` в flat config приходится повторять и страховать
тестом. Если эти накладные расходы или независимость области вырастут, это станет фактическим
основанием поднять её в компилируемый пакет.
