# Встроенный плагин Mission и bridge событий браузерного SDK

## Статус

Утверждённый дизайн, реализованный своим срезом.

**Контракт инструмента с тех пор расширен.** Действующее описание — [mission.md](../../mission.md):
там пять состояний шага вместо трёх, исход миссии, `expectedRevision`, возврат снимка писателю и
инструмент `mission-read`. Ниже — дизайн исходного среза; маршрут, событие и browser bridge в нём
описаны актуально.

## Цель и границы

`mission` — встроенный плагин Sovereign, который повторяет поведение текущего инструмента
планирования агента: хранит один полный снимок миссии на одну сессию, принимает обновление от модели
и показывает снимок в правой панели. Это не проектный task manager и не общий список задач.

Поставка состоит из backend-воркера и browser-бандла плагина. Для доставки уже существующих SSE-событий
в plugin-owned browser components добавляется небольшой публичный bridge в `@sovereign/browser-sdk` и
web host-приложении. Ядро, его маршруты и транспорт не меняются; используется единственный общий
`GET /api/events`.

## Backend-контракт

Плагин объявляет инструмент `mission-update`. Модель передаёт полный снимок:

```ts
{
  mission: string;
  explanation?: string;
  plan: Array<{
    step: string;
    status: "pending" | "in_progress" | "completed";
  }>;
}
```

`sessionId` берётся из `PluginToolInvocation` и не входит в аргументы инструмента. `mission` и
`step` после trim непустые; план содержит минимум один шаг; одновременно допускается не более одного
`in_progress`; неизвестные поля и статусы отклоняются. Каждый успешный вызов заменяет весь снимок.

Снимок хранится через SDK storage под ключом `mission.<sessionId>`:

```ts
{
  mission: string;
  explanation?: string;
  plan: MissionStep[];
  revision: number;
  updatedAt: string;
}
```

Запись и увеличение `revision` происходят последовательно; событие публикуется только после успешной
записи. Ошибка storage возвращается модели как управляемая ошибка и не публикует событие.

## Route и event

Плагин объявляет авторизованный маршрут `GET /api/p/mission/:sessionId`. Он возвращает полный снимок
и `revision`; отсутствие миссии возвращает `404`, а отказ авторизации и недоступность чужой сессии
обрабатываются общим диспетчером маршрутов.

Плагин объявляет событие `changed` с payload `{ sessionId: string; revision: number }`. Хост добавляет
неймспейс плагина, поэтому полное имя — `mission.changed`. Это инвалидация, а не источник истины:
полный snapshot всегда читается через route. Пропуск события, перезапуск воркера или SSE gap не
ломают состояние.

## Browser bridge

Web-приложение уже поддерживает одно SSE-соединение и frontend bus. `BrowserRuntimeProvider` получает
readonly bridge подписки, а `@sovereign/browser-sdk` экспортирует публичный hook вроде
`useSovereignEvents()`. Hook не создаёт сеть и не знает о `EventSource`; он только подписывает и
отписывает plugin-owned компонент от host-provided bus.

`MissionPanel` объявляется вкладом `core.panel.tabs`, получает `PlaceContext.subject.sessionId` и:

- загружает snapshot при монтировании и смене сессии;
- подписывается на `mission.changed`, фильтрует по текущему `sessionId`;
- после события перечитывает route и отбрасывает ответ с более старым `revision`;
- при reconnect/gap повторяет обычный snapshot fetch;
- показывает empty, loading, error и success states, миссию, пояснение, прогресс, шаги, текущий
  `in_progress` и время обновления;
- не редактирует и не создаёт состояние.

Последовательность доставки:

```text
mission-update → storage.set → mission.changed → daemon SSE → frontend bus
→ MissionPanel route fetch → revision check → render
```

## Проверки

- unit-тесты валидации, revision, изоляции ключей и отказа storage;
- тесты tool и route, включая отсутствие подмены `sessionId` и авторизацию;
- тест публикации события только после записи;
- browser SDK тесты подписки/отписки без создания `EventSource`;
- Mission UI тесты для всех состояний, фильтрации сессии, revision race и reconnect/gap;
- существующие `make check` и `make build`.

## Почему так

### Per-session snapshot, а не проектная доска

Модель должна видеть цель текущей работы и её шаги, не смешивая их с пользовательским управлением
проектом. Поэтому состояние адресуется контекстом вызова и не имеет project-wide API.

### Полная замена снимка

Инструмент повторяет семантику `update_plan`: один вызов описывает актуальный план целиком. Частичные
операции породили бы неявное слияние и гонки между параллельными турнами.

### Событие как инвалидация

Шина не гарантирует буфер или повторную доставку. Snapshot route нужен для восстановления после
пропуска, а `revision` защищает от ответа старого чтения. Передача всей миссии в событии отвергнута:
она дублировала бы источник истины и усложняла recovery.

### Bridge вместо второго SSE

Отдельный `EventSource` внутри панели нарушил бы правило одного SSE на приложение и дал бы разные
жизненные циклы reconnect. Bridge раскрывает уже существующий frontend bus через публичный SDK без
изменения ядра и без третьего плагина.

### Не добавлять UI-редактирование

Mission — наблюдаемое состояние плана модели. Редактирование человеком стало бы вторым писателем и
потребовало бы разрешения конфликтов, которого текущий контракт не обещает.
