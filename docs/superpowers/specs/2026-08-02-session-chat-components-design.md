# Компоненты ленты и композера сессии

## Цель

Разделить перегруженный `ChatView` на самостоятельные feature-компоненты ленты сообщений и
композера без изменения поведения экрана сессий, его маршрутов или серверного контракта.

## Границы

Экран сессий остаётся master–detail-вью: `SessionsView` показывает список сессий и открытую
сессию, а `ChatView` координирует правую панель. Внутри `ChatView` появляются две явные границы:

- `SessionMessageList` собирает видимую ленту из сохранённых записей активной ветки, ожидающих
  турнов и live-буфера. Здесь же остаётся предметное отображение реплик, служебных записей,
  вызовов инструментов, меток и действий fork;
- `MessageComposer` показывает поле ввода, выбор режима сообщения занятой сессии, отправку,
  дописывание без запуска и прерывание.

Оба компонента живут в `apps/web/src/sessions/`. В `@sovereign/ui-kit` они не переносятся:
`SessionEntry`, очереди сообщений, fork и метки принадлежат предметной области сессий, тогда как
универсальные `MessageFeed`, `Message`, `Textarea` и `ToolCall` уже предоставляет UI-кит.

## Поток состояния

`ChatView` остаётся владельцем черновика сообщения:

```ts
const [draft, setDraft] = useState("");
```

`MessageComposer` получает `draft` и `onDraftChange` как контролируемые свойства. Это сохраняет
единую точку связи с `EntryTreeDrawer`: после перехода к прежней пользовательской реплике дерево
возвращает `editorText`, а `ChatView` кладёт его в тот же черновик через `setDraft`. В результате
текст появляется в поле композера и может быть изменён перед отправкой новой ветки.

Локальный выбор `steer`, `follow-up` или `next-turn` принадлежит `MessageComposer`, потому что он
нужен только его контролам. Состояния дерева и компакции остаются в `ChatView`. Данные сессии и
сетевые действия продолжают приходить сверху пропами; новые компоненты не выполняют собственных
HTTP-запросов.

## Сохранение поведения

Рефакторинг обязан сохранить:

- порядок ленты: сохранённые записи, принятые и ожидающие турны, затем live-буфер;
- подавление только первого live-prompt, который уже появился среди сохранённых записей, без
  подавления последующего steering с тем же текстом;
- отсутствие композера у архивной сессии;
- обычный запуск турна в простое и отправку в выбранную очередь во время работы;
- `append` только в простое и `interrupt` только во время работы;
- очистку черновика после каждой принятой отправки;
- подстановку `editorText` из дерева в контролируемый композер;
- текущие правила доступности меток и fork.

## Проверка

Выделение каждого компонента выполняется отдельным TDD-циклом: сначала прямой компонентный тест
описывает его интерфейс и падает из-за отсутствующего модуля, затем переносится минимальная
реализация. Существующие интеграционные тесты `SessionsView` остаются страховкой совместной работы,
включая переход из дерева в черновик. В конце запускаются тесты веб-пакета и полный `make check`.

## Почему так

**Контролируемый композер и черновик в `ChatView`.** Выбрано, потому что черновик меняют два
соседних компонента: сам композер при вводе и дерево после навигации. Локальный черновик внутри
`MessageComposer` потребовал бы императивного ref-интерфейса или синхронизации двух состояний.

**Feature-компоненты вместо новых примитивов UI-кита.** Выбрано, потому что компоненты знают
контракт сессий и не являются универсальными элементами интерфейса. Перенос в UI-кит связал бы
общий пакет с предметной моделью сессий.

**Один новый универсальный контейнер чата.** Отвергнуто: `ChatView` уже выполняет эту роль, а новый
слой только переложил бы те же пропы без самостоятельной ответственности.

**Перенос всего состояния в каждый дочерний компонент.** Отвергнуто: он разрывает связь дерева с
черновиком и скрывает координацию между частями экрана за императивными вызовами.
