# Срез 13: системный prompt агента и его собственная папка

## Цель

Файловый агент знает абсолютную папку, в которой лежит его `AGENT.md`, а встроенный `base-agent`
самостоятельно читает проектные инструкции через обычный инструмент `read`. Ядро не читает
`AGENTS.md`, не копирует его содержимое в prompt и не вводит отдельного хранилища файлов агента.

Срез закрыт, когда:

- файловый путь `AGENT.md` сохраняется от parser до живой runtime-сессии;
- system prompt стабильно состоит из инструкций агента, `<agent_data>` и `<available_skills>`;
- изменение файлового определения применяется к следующей операции модели без пересоздания сессии;
- у программного агента без `AGENT.md` блока `<agent_data>` нет;
- `base-agent` прямо требует прочитать применимый проектный `AGENTS.md` через `read`.

## Проектные инструкции читает модель

Текст встроенного `plugins/base-agent/agents/agent/AGENT.md` получает правило:

1. перед работой над проектом проверить `AGENTS.md` в корне открытого проекта обычным `read`;
2. если файл существует, следовать ему;
3. перед изменением файлов в подкаталоге прочитать более близкий `AGENTS.md`, если он там есть;
4. отсутствие такого файла не считать отказом задачи.

Это инструкция модели, а не новый loader. Демон не ищет `AGENTS.md`, не следит за ним отдельно и не
сохраняет его текст в сессии. Обычное чтение оставляет поведение прозрачным: модель видит тот же файл,
который доступен её инструментам в рабочей папке.

## Путь файлового определения

`AgentFileDefinition` получает обязательное поле `location` с путём входного `AGENT.md`, по тому же
правилу, которое уже действует для `SkillFileDefinition.location`. Discovery передаёт абсолютный путь,
а parser сохраняет его без нормализации.

Принятый вклад агента получает необязательное `location?: string`:

- файловые определения плагина и standalone-корня передают абсолютный путь;
- программный `contribute.agent` поля не получает;
- публичный `AgentSummary` путь не раскрывает: он нужен runtime, а не каталогу клиента.

Перед передачей в `@sovereign/agent-runtime-pi` демон вычисляет `dirname(location)` и записывает его как
`AgentDefinition.directory?: string`. Рантайм не должен знать устройство plugin roots и не вычисляет
папку по идентификатору агента.

## Блок `<agent_data>`

Рантайм рендерит только один поддержанный сейчас факт:

```xml
<agent_data>
  <directory>/absolute/path/to/agent</directory>
</agent_data>
```

Путь экранируется как XML-текст: `&`, `<`, `>`, `"`, `'` превращаются в сущности. Для отсутствующего
`directory` renderer возвращает пустую строку, поэтому программный агент не получает пустой wrapper.

XML-экранирование становится общей маленькой функцией runtime-пакета и используется также каталогом
скилов. Это не публичный контракт пакета.

## Сборка system prompt

Prompt собирается каждый раз, когда Pi запрашивает `systemPrompt`, из непустых секций через два
перевода строки:

1. `instructions`;
2. `<agent_data>`;
3. `<available_skills>`.

Инструкции по-прежнему обязательны и не могут стать пустыми. Отсутствие данных агента или скилов не
оставляет лишних пустых wrappers и не меняет текст соседних секций.

Живая сессия получает отдельный mutator `setAgentDirectory(directory?: string)`. Демон вызывает его
рядом с `setInstructions` и `setSkills` при каждом `prepareForModel`, поэтому одинаковое правило
работает для:

- обычного турна;
- автоматической и ручной компакции;
- summary при навигации по ветке;
- операции, которая успела постоять в общей очереди.

При первом создании или повторном открытии сессии актуальная папка также передаётся в
`AgentDefinition`, чтобы первая операция не зависела от промежуточного состояния.

Если hot reload заменил файлового агента программным агентом с тем же идентификатором, следующий
`prepareForModel` передаёт `undefined`, и старый `<agent_data>` исчезает. Если путь файлового
определения изменился, следующий prompt содержит новую папку.

## Публичные и внутренние границы

- `AgentContributionRegistration.location` входит во внутренний протокольный контракт реестра
  вкладов, потому что реестр переносит принятый файловый ресурс между подсистемами демона.
- SDK-форма программного `contribute.agent` не меняется.
- HTTP-формы `AgentSummary`, сессий и file-resources не получают новый путь.
- Формат JSONL-сессии не меняется: папка агента разрешается живьём, а не сохраняется рядом с
  историей.
- Специальных API для памяти или произвольных файлов в папке агента в этом срезе нет.

## Проверка

Тесты доказывают:

- parser сохраняет точный путь `AGENT.md`;
- plugin и standalone registrations переносят его только файловым агентам;
- renderer экранирует XML и ничего не выводит без directory;
- runtime соблюдает порядок трёх секций и меняет/убирает папку на следующей операции;
- sessions service передаёт `dirname(location)` при create/open и повторно разрешает его после hot
  reload;
- интеграционный тест файловых ресурсов видит `<agent_data>` в реальном запросе scripted model;
- встроенный prompt содержит явную инструкцию читать `AGENTS.md` через `read`.

После адресных тестов запускается полный `make check`.

## Почему так

**Автоматически читать и подмешивать `AGENTS.md`.** Отвергнуто владельцем продукта: это скрывает от
модели обычную файловую операцию, вводит отдельные правила поиска и слежения и смешивает проектные
инструкции с механизмом собственных данных агента.

**Записать абсолютную папку прямо в `AGENT.md`.** Отвергнуто: встроенные и переносимые плагины не
знают место установки заранее. Путь является runtime-данными и должен добавляться ядром.

**Передавать в runtime полный путь `AGENT.md`.** Отвергнуто: будущие память и другие файлы принадлежат
папке агента, а не одному definition-файлу. Граница runtime сразу выражает устойчивое понятие
`directory`.

**Сохранить папку агента в JSONL сессии.** Отвергнуто: hot reload обязан менять следующую операцию, а
сохранённое значение немедленно стало бы устаревшим. Источником истины остаётся живой реестр вкладов.
