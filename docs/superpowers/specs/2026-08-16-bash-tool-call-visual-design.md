# Визуал вызовов bash-семейства инструментов

**Статус:** дизайн, утверждён владельцем продукта 2026-08-16 по секциям; семейство расширено на
`job-output` и `job-kill` решением владельца тем же днём.

## Задача

Сейчас каждый вызов инструмента рисуется общей карточкой `ToolCall` UI-кита: имя, подпись-резюме,
бейдж статуса, а при разворачивании — JSON-аргументы и сырой вывод. Для инструментов bash-семейства
это работает плохо: вывод пестрит служебными маркерами (`[stderr]`, `[exit code: N]`,
`[timed out after N seconds]`, `[output truncated; full output: …]`, `[status: …]`, `(no output)`),
которые читаются как текст, а команда и её исход визуально не разделены.

Задача — дать вызовам инструментов `bash`, `job-output` и `job-kill` собственную карточку в языке
платформы (вариант A мокапа, выбранный владельцем): команда с промптом `$`, вывод, stderr-секция с
тоном опасности, бейджи исхода. Три инструмента — одно семейство: их объявляет один плагин
`starter`, и контракт результата у них общий (docs/bash-tool.md).

## Граница

- Меняется **только визуал вызовов инструментов `bash`, `job-output`, `job-kill`** в ленте сессии.
  Механика исполнения, лимиты и контракт результата не трогаются (docs/bash-tool.md).
- Ядро не меняется: встроенный `ToolCall` остаётся как был и как fallback для всех остальных
  инструментов.
- Локализация делается существующим паттерном плагинов (см. «Локализация»); развилка «где живёт
  локаль окна» остаётся в docs/backlog.md и этим срезом не решается.

## Механизм

Плагин `starter` получает браузерную часть: в манифесте появляется `"browser": "src/browser.tsx"`,
демон сам собирает бандл (docs/ui-extension-model.md). Воркер регистрирует три component-вклада в
динамические места вызовов инструментов (спека
2026-08-09-dynamic-tool-call-visual-replacements-design.md) — **один browser export на все три имени**,
как предписывает та спека:

```ts
await contribute.component({
  id: "starter-bash-tool-call",
  placeId: toolCallPlaceId("bash"),
  export: "BashToolCall",
});
await contribute.component({
  id: "starter-job-output-tool-call",
  placeId: toolCallPlaceId("job-output"),
  export: "BashToolCall",
});
await contribute.component({
  id: "starter-job-kill-tool-call",
  placeId: toolCallPlaceId("job-kill"),
  export: "BashToolCall",
});
```

Имя инструмента компонент узнаёт из `context.subject.toolName`. Вклады — заменяемые по обычным
правилам: вклад из папки проекта или директории данных может перекрыть любой из них, конфликт и
отказ возвращают встроенный `ToolCall`.

## Данные

Замена места получает только идентичность — `PlaceContext.subject: { sessionId, toolCallId,
toolName }` (строки). Данные компонент берёт сам из публичного маршрута
`GET /api/sessions/:sessionId/entries`, как панель Mission берёт свой снимок.

Записи появляются **во время турна**: рантайм (pi) пишет `message_end` каждого сообщения в файл
сессии прогрессивно, а не в конце турна. Поэтому:

- `tool-call` с `input` (команда и timeout для bash, `jobId` для job-инструментов) доступен, как
  только модель вызвала инструмент — заголовок виден на карточке всё время исполнения, включая
  фоновые задания на минуты;
- `tool-result` с выводом и признаком отказа появляется, когда инструмент завершился;
- статус карточки перечитывается по `core.sessions.changed` (турн закончился → вывод и финальный
  статус), по `subscribeRecovery` (переподъём стрима) и ограниченным retry в состоянии
  «записей ещё нет» (доли секунды между вызовом модели и записью).

Задержка «вывод появляется в конце турна» — не регрессия: текущий UI тоже показывает статусы по
записям, а не по потоку.

## Компонент

`BashToolCall` (plugins/starter/src/bash-tool-call.tsx) — карточка на токенах UI-кита, стили — свой
CSS-файл плагина (как `mission-panel.css`), компоненты переиспользуются из `@sovereign/ui-kit`
(`Badge`, `Code`, `CodeBlock`, `Disclosure`, `Notice`).

Заголовок зависит от инструмента: для `bash` — `$ команда`; для `job-output` и `job-kill` — имя
тула и `jobId` из input (моно-шрифт). Справа — бейдж статуса.

Состояния:

| Состояние | Условие | Вид |
|---|---|---|
| `running` | есть input, результата нет | заголовок + бейдж «Выполняется» (accent) |
| `done` | результат есть, `failed: false` | + вывод и бейджи исхода (success) |
| `failed` | результат с `failed: true` | то же в danger-оформлении |
| `no-data` | записей ещё не нашли | компактная строка `bash · Выполняется` |

Для `job-output` бейдж статуса отражает **статус задания из текста результата**, а не факт ответа
инструмента: `[status: running]` → «Выполняется» (accent), `[status: completed]` → «Готово»
(success), `[status: killed]` → «Остановлено» (danger). Текст — единственный источник правды о
задании: фаза сессии занята турном целиком и отдельные задания не различает.

Структура:

- карточка: тонкая рамка, акцентная левая граница по статусу (accent / success / danger), моно-шрифт;
- тело — `Disclosure`, **свёрнут по умолчанию всегда** (как все тулколы): stdout — блок кода;
  stderr — отдельная секция с подписью `stderr` и тоном danger; подвал — бейджи исхода;
- `(no output)` и `(no new output)` — приглушённая строка;
- упавший результат без маркеров (например `unknown job <id>`) — весь текст в stderr-секцию.

Подвал: `exit 0` (зелёный) / `exit N` (красный), `timed out after Ns`, `killed by signal: SIG`,
`output truncated` с путём к полному логу, `timeout clamped`, метка `background` при
`run_in_background: true`. JSON-аргументы не показываются — команда уже в заголовке, а остальные
поля превратились в бейджи.

## Парсинг результата

Чистая функция `parseBashResult(text)` в отдельном модуле (plugins/starter/src/parse-bash-result.ts),
контракт маркеров — ровно тот, что строит `tools.ts` (docs/bash-tool.md):

- финальные маркеры после тела: `[exit code: N]`, `[timed out after N seconds]`,
  `[killed by signal: SIG]`, `[timeout clamped to N seconds by the platform]`;
- статус задания у `job-output`: `[status: running|completed|killed]` → `jobStatus`;
- разделитель секций — строка `[stderr]` (первое вхождение);
- пометки усечения внутри своих секций: `[output truncated; full output: <path>]` и job-вариант
  `[some output was dropped from memory; full output: <path>]`;
- `(no output)` и `(no new output)` → флаг `noOutput`.

Выход: `{ stdout, stderr, exitCode?, timedOut?, killedBy?, truncatedPath?, clampedSeconds?,
jobStatus?, noOutput }`. Устойчивость: текст без маркеров показывается целиком stdout-блоком (а у
упавшего результата — целиком в stderr-секции), парсер карточку не роняет.

## Локализация

Хардкод строк запрещён. Паттерн тот же, что локализует панель Mission и subagents (соседний
ворктри `claude/right-panel-visual-issues-65ea5c`):

- `plugins/starter/src/messages.ts` — namespace + каталоги en/ru, один модуль на обе половины
  плагина;
- воркер объявляет `contribute.localeCatalog` для en и ru;
- браузерная часть — хук `useTranslator` (fetch `/api/preferences` → `createTranslator` из
  `@sovereign/ui-kit`), дословная копия миссийного: общего модуля в SDK нет, развилка записана в
  docs/backlog.md.

## Тесты и проверка

1. Парсер — unit-тесты `node --test` (рядом с `bash.test.ts`): каждый маркер и комбинации, включая
   статусы заданий (`running`/`completed`/`killed`), `(no new output)` и «незнакомый текст».
2. Компонент — vitest + jsdom + @testing-library/react (образец `mission-panel.test.tsx`): состояния
   running / done / failed / no-data, заголовки всех трёх инструментов, stderr-секция, бейджи
   исхода, статусы заданий, метка `background`, свёрнутость.
3. Регистрация — в `worker.test.ts`: три component-вклада в `toolCallPlaceId` каждого имени и оба
   `localeCatalog` появляются в активации.
4. Скрипт теста плагина — `node --test "src/**/*.test.ts" && vitest run` (паттерн subagents).
5. Typecheck, lint, fmt, полный прогон тестов всех пакетов.
6. Живая проверка в dev: bash в состояниях running/done/failed, фоновое задание с опросом
   `job-output` в трёх статусах, `job-kill`, обе локали, свёрнутость.

Новые devDependencies (`vitest`, `jsdom`, `@testing-library/react`, `react`, `@sovereign/browser-sdk`,
`@sovereign/ui-kit`) — версии уже разрешены в lockfile (их тянет mission/subagents), lockfile не
меняется. Установка — `env -u WATCH_REPORT_DEPENDENCIES pnpm install` (CLAUDE.md): переменная из
окружения dev-демона ломает воркер-протокол pnpm.

## Почему так

- **Плагин, а не ядро.** Визуал bash-семейства — предметная собственность инструментов, и механизм
  подмены уже построен (динамические места тулов, спека 2026-08-09). Ядро остаётся минимальным,
  встроенный `ToolCall` — общим fallback'ом. Вклады заменяемы как любые другие.
- **Один компонент на три инструмента.** Паттерн «один export, несколько вкладов» прямо описан в
  спеке 2026-08-09; контракт результата у трёх инструментов общий, и парсер один. Отдельные
  компоненты на каждый инструмент означали бы три копии карточки без новой информации.
- **Статус задания — из текста результата, а не из сессии.** `job-output` отвечает успешно, даже
  когда задание ещё бежит; фаза сессии различает только турн целиком. `[status: …]` в тексте —
  единственный источник правды о задании, и карточка отражает именно его.
- **Данные из записей сессии, а не из контекста места.** Спека 2026-08-09 явно решила: хост даёт
  замене только идентичность, предметные данные компонент добывает сам. Расширение `subject`
  данными вызова отменяло бы это решение, вдобавок `subject` строковый, а вывод бывает 64 КБ —
  контекст места раздулся бы данными, которые там не проектировали держать.
- **Собственный бэкенд плагина не нужен.** Воркер не видит результат вызова: `invoke` возвращает
  строку рантайму, и дальше она живёт в записях. Свой маршрут плагина с реестром инвокаций дал бы
  ровно то, что уже даёт `entries` (input во время турна), а output — всё равно только из записей.
  Отвергнуто: новая механика без новой информации.
- **Свёрнуто всегда.** Авторазворот упавших вызовов рассматривался и отвергнут владельцем:
  поведение по умолчанию должно быть как у всех тулколов.
- **Косплей терминала (вариант B мокапа) отвергнут.** Тёмная «консоль» спорит с визуальным
  языком платформы, в тёмной схеме даёт «окно в окне», а настоящих ANSI-цветов в выводе всё равно
  нет (`NO_COLOR=1`) — выразительность покупалась бы конфликтом с дизайн-системой.
- **Хардкод строк отвергнут.** Локализация плагинов уже делается соседней веткой по паттерну
  «каталоги вкладом + переводчик кита»; повторять зашитые строки значило бы плодить третий
  способ.
