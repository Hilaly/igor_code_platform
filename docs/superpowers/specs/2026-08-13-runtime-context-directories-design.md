# Контекст директорий агентской сессии

## Цель

Агент однозначно различает три файловые области: текущий проект, собственную долговременную папку
и общую директорию данных Sovereign. Папка определения агента больше не выглядит как рабочая
директория сессии.

Изменение закрыто, когда каждая операция модели получает актуальный структурированный контекст,
который прямо говорит, где выполнять проектную работу и для чего предназначены две остальные
директории.

## Model-visible контракт

Существующий блок `<agent_data>` заменяется одним блоком `<runtime_context>`:

```xml
<runtime_context>
  <cwd>/absolute/path/to/project</cwd>
  <agent_personal_directory>/absolute/path/to/agent</agent_personal_directory>
  <sovereign_data_directory>/absolute/path/to/sovereign-data</sovereign_data_directory>

  <directory_guidance>
    Work on the current project in cwd. Use it as the default location for project files and project-relative operations.
    The agent personal directory contains this agent's definition and private persistent files, such as its own notes. Do not treat it as the project workspace.
    The Sovereign data directory contains platform-managed shared data. Use it only when the task requires Sovereign resources or state; do not treat it as the current project.
  </directory_guidance>
</runtime_context>
```

`cwd` — абсолютная папка проекта, к которому относится сессия. Это рабочая директория инструментов
и место по умолчанию для чтения, изменения и создания файлов задачи. Имя поля намеренно совпадает с
общеупотребимым понятием current working directory.

`agent_personal_directory` — абсолютная папка, содержащая выбранный `AGENT.md` и соседние файлы
конкретного файлового агента. Агент может хранить там собственные долговременные заметки и служебные
файлы, но не должен переносить туда проектную работу. Слово `private` в guidance означает личную
область этого агента по назначению, а не изоляцию прав доступа: инструменты исполняются в обычной
файловой системе процесса.

`sovereign_data_directory` — абсолютный корень общих данных запущенного экземпляра Sovereign. В нём
живут платформенные настройки, сессии, пользовательские агенты, скилы, команды и плагины. Это адрес
для задач, которым явно нужны ресурсы или состояние Sovereign, а не запасной workspace.

Порядок полей и guidance фиксирован, чтобы prompt был детерминированным. Все значения экранируются
как XML-текст.

## Наличие значений

`cwd` и `sovereign_data_directory` обязательны для любой сессии: проект является обязательной
частью session summary, а директория данных задаётся при старте демона.

`agent_personal_directory` присутствует только у файлового агента с известным `AGENT.md`.
Программный агент без собственного каталога получает тот же `<runtime_context>`, но без этого
элемента. Guidance остаётся единым: отсутствие пути означает, что платформа не предоставила
агенту личную папку и записывать заметки по выдуманному адресу нельзя.

Пустого `<runtime_context>` не бывает, поскольку два обязательных пути существуют всегда.

## Передача данных и обновление

Runtime рендерит блок из трёх независимых значений:

- `cwd` берётся из `AgentSessionSummary.folder`, то есть из той же величины, с которой создаётся
  `NodeExecutionEnv`;
- personal directory продолжает вычисляться демоном как `dirname(agent.location)` и обновляться
  перед каждой операцией модели после повторного разрешения живого определения;
- Sovereign data directory передаётся явно из точки композиции демона в session service, затем в
  agent session store. Runtime не выводит её из родителя `sessions/`: раскладка хранения не должна
  становиться скрытым контрактом.

`cwd` сессии и корень данных экземпляра неизменны в течение жизни harness. Personal directory
остаётся живым значением: hot reload может изменить путь или убрать его перед следующей операцией.
System prompt, как и сейчас, строится заново на каждой model operation.

Итоговый порядок непустых секций системного prompt:

1. инструкции агента;
2. `<runtime_context>`;
3. `<available_skills>`.

HTTP-формы и JSONL-сессии не расширяются: пути нужны только при сборке runtime-контекста.

## Проверка

Тесты доказывают:

- renderer выдаёт утверждённый XML, экранирует метасимволы и опускает только отсутствующую personal
  directory;
- runtime всегда передаёт настоящий `cwd`, а не папку агента, и сохраняет порядок секций prompt;
- смена или исчезновение файлового определения меняет personal directory на следующей операции;
- session service и точка композиции передают точный корень данных Sovereign без вычисления из
  `sessions/`;
- интеграционный scripted model видит все три пути для файлового агента.

После адресных тестов выполняется полный `make check`.

## Почему так

**Оставить имя `<agent_data>` и добавить в него два пути.** Отвергнуто: имя по-прежнему ставит
личность агента в центр блока и не выражает, что это контекст исполнения всей сессии.

**Передать только три подписанных пути.** Отвергнуто: названия уменьшают неоднозначность, но не
задают приоритет. Короткий guidance прямо называет `cwd` местом работы и запрещает трактовать две
остальные директории как workspace.

**Сделать personal directory рабочей папкой или местом всех результатов.** Отвергнуто: она
принадлежит определению агента и его долговременным заметкам, тогда как результаты пользовательской
задачи принадлежат текущему проекту.

**Создавать personal directory программному агенту.** Отвергнуто: это вводит новое хранилище,
правила идентичности и жизненный цикл. В этом изменении платформа только точно описывает реально
существующие пути.

**Вычислять Sovereign data directory как родителя `sessions/`.** Отвергнуто: это связывает runtime с
внутренней раскладкой данных и ломается при независимом размещении session store. Корень передаётся
явной зависимостью.
