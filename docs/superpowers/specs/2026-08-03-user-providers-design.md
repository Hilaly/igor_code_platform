# Пользовательские LLM-провайдеры

## Задача

Человек должен уметь добавить LLM-провайдера из интерфейса, выбрать один из поддерживаемых
протоколов запросов, войти по API-ключу и пользоваться его моделями в обычных сессиях. Такой
провайдер принадлежит пользователю, переживает перезапуск демона и исчезает только после явного
удаления.

Платформа уже умеет собирать провайдера из данных для плагина и исполнять четыре протокола через Pi.
Новая возможность не вводит второй каталог и не даёт браузеру доступ к секрету: пользовательские,
встроенные и плагинные провайдеры сходятся в существующей коллекции моделей, а ключ по-прежнему
пишет только credential store.

## Пользовательский сценарий

На странице настроек провайдеров появляется действие «Новый провайдер». Оно открывает отдельное
вью `/settings/providers/new`, а не диалог. Форма содержит:

- неизменяемый после создания идентификатор и отображаемое имя;
- базовый URL запросов к моделям;
- формат запросов: OpenAI Chat Completions, OpenAI Responses, Anthropic Messages или Google
  Generative AI;
- режим каталога моделей и вычисленный URL каталога;
- общие значения для автоматически найденных моделей;
- редактируемый список ручных моделей.

Провайдер сохраняется без API-ключа. После создания интерфейс открывает его обычную страницу, где
человек входит существующим диалогом API-ключа. Успешный вход автоматически запускает загрузку
моделей. Ошибка загрузки не отменяет вход и не удаляет провайдера: она показывается отдельно, а
модели можно добавить вручную.

У пользовательского провайдера на странице деталей есть «Редактировать», «Обновить модели» и
«Удалить». Редактирование открывает `/settings/providers/:providerId/edit`; идентификатор там виден,
но недоступен для изменения. Удаление требует подтверждения и одновременно удаляет определение,
сохранённый ключ и кэш моделей.

Встроенные и плагинные провайдеры не получают действий редактирования и удаления. Старые адреса
`/providers` и `/providers/:providerId` продолжают заменяться каноническими адресами настроек.
Короткие `/providers/new` и `/providers/:providerId/edit` также разбираются только как совместимые
ссылки и заменяются на `/settings/providers/new` и `/settings/providers/:providerId/edit`.

## Определение и происхождение

На проводе появляется отдельный `UserProviderDefinition`. Он не расширяет плагинный
`CustomProviderDefinition`: одинаковые сегодня поля не должны связывать постоянную сущность UI с
жизненным циклом воркера. Обе формы переводятся в один внутренний вход сборщика runtime-провайдера.

Определение пользователя содержит:

- `id`, `name`, `baseUrl`, `api`;
- режим endpoint каталога: `default`, `custom` с абсолютным URL либо `disabled`;
- `modelDefaults`: окно контекста, максимум ответа, reasoning, виды входа и цены;
- `manualModels`: полные определения моделей, всегда сохраняемые независимо от сети;
- `modelOverrides`: частичные поправки автоматически найденных моделей по идентификатору;
- `disabledModelIds`: автоматически найденные модели, которые человек явно скрыл.

Секрета, сетевого кэша и результата последней попытки обновления в определении нет. API-ключ живёт
в `credentials.json`, последний успешный сетевой список — в `model-catalogs.json`, а последний
результат обновления — только в памяти демона для обратной связи текущему UI.

`ProviderSummary` получает `origin: "builtin" | "plugin" | "user"`. Существующее поле `custom`
сохраняет прежний узкий смысл «зарегистрирован плагином» и равно `origin === "plugin"`; проверка
права на изменение опирается только на точное происхождение `user`. Каталог принимает происхождение
при регистрации, но не знает про HTTP, файлы UI или владельца плагина.

## Проверка определения

Контракт проверяется в `@sovereign/protocol` до записи:

- идентификатор состоит из строчных латинских букв, цифр, `.`, `_` и `-`, начинается с буквы или
  цифры и не содержит `/`;
- идентификатор уникален среди встроенных, плагинных и пользовательских провайдеров;
- имя и идентификаторы моделей после обрезки пробелов не пусты;
- `baseUrl` и пользовательский URL каталога — абсолютные `http:` или `https:` URL;
- URL не содержат встроенных логина, пароля или fragment; ключ передаётся только через auth;
- окно контекста и максимум ответа — положительные целые, цены — конечные неотрицательные числа;
- виды входа ограничены `text` и `image`, повторяющиеся идентификаторы ручных моделей запрещены;
- формат API принадлежит закрытому перечню четырёх реализаций, уже имеющихся в Pi.

HTTP разрешён намеренно: основной потребитель кастомного провайдера — локальный сервер. Демон уже
исполняет модельные запросы к указанному человеком адресу; запрос каталога имеет ту же границу
доверия и не вводит отдельной SSRF-возможности относительно самого провайдера.

## Постоянное хранилище

`apps/daemon/src/providers/user-provider-store.ts` — единственный писатель нового
`user-providers.json` в директории данных. Файл содержит массив определений, записывается атомарно с
правами `0600` и читается один раз при старте. Отсутствующий файл означает пустой список.

Негодный файл не превращается в пустой: стор сохраняет причину, не перезаписывает исходное
содержимое и отказывает создающим, изменяющим и удаляющим операциям. Встроенный каталог при этом
остаётся рабочим, а UI провайдеров показывает проблему пользовательского реестра отдельно от
проблемы `credentials.json`.

При старте определения регистрируются до подъёма HTTP-сервера. Если сохранённый идентификатор после
обновления платформы занял встроенный провайдер, демон не подменяет ни одну сторону и продолжает
работать: запись остаётся в пользовательском сторе с диагностикой конфликта, видна в UI и может быть
удалена. Поскольку идентификатор неизменяем, разрешение такого конфликта — удалить запись и создать
провайдера под новым именем.

Стор отвечает только за один файл и не знает о runtime-каталоге, ключах, кэше или сессиях. Их
связывает `UserProviderService` в области `providers`; зависимости передаются узкими портами.

## Каталог и жизненный цикл

При создании сервис сначала синхронно резервирует идентификатор в общем runtime-каталоге, затем
атомарно пишет определение. Если запись не удалась, регистрация откатывается. Поэтому провайдер не
может попасть на диск поверх встроенного или плагинного и не остаётся только в памяти после отказа
файловой системы. До завершения записи резервная регистрация не публикуется наружу: мутация
сериализована, а событие уходит только после commit стора.

При редактировании стор сначала сохраняет целиком новое определение с прежним `id`, затем каталог
заменяет runtime-провайдера. Открытый сетевой запрос держит уже выбранный объект и доигрывает; со
следующего обращения сессия видит новое определение. Если выбранная модель была удалена, действует
существующая деградация сессии «model is not available», а история остаётся читаемой.

Перед заменой runtime-провайдера runtime-граница переписывает сохранённый динамический кэш через
новые defaults, overrides и disabled ids. Поэтому простое изменение окна контекста или reasoning
применяется сразу к уже известным идентификаторам, без обязательного сетевого обновления. Форма
кэша остаётся непрозрачной для демона.

Удаление запрещено, пока хотя бы одна сессия с моделью этого провайдера имеет фазу, отличную от
`idle`. Проверка приходит в сервис функцией из composition root, поэтому область `providers` не
импортирует `sessions`. Простаивающие и архивные сессии удалению не мешают: после него их история
читается, но новый турн требует выбрать доступную модель.

После проверки занятости сервис синхронно снимает runtime-провайдера: уже начатый запрос держит
свой объект и доигрывает, а новый больше не может стартовать. Затем сервис:

1. отменяет идущую попытку входа;
2. удаляет credential;
3. удаляет кэш моделей;
4. удаляет постоянное определение;
5. публикует `core.providers.changed`.

Ключ удаляется до определения. Если промежуточная файловая операция падает, определение остаётся и
runtime-провайдер регистрируется обратно из него; повтор операции безопасен. Худший частичный исход
— существующий провайдер просит заново войти или загрузить каталог. Обратный порядок оставлял бы
секрет провайдера, которого UI уже не показывает.

Создание, изменение и удаление сериализуются сервисом. Плагинная регистрация остаётся в том же
каталоге и получает прежний немедленный отказ по занятому идентификатору.

## Автоматический каталог моделей

Режим `default` вычисляет URL функцией `defaultModelsUrl(api, baseUrl)`. Для OpenAI Completions,
OpenAI Responses и Google Generative AI функция добавляет сегмент `/models` к уже версионированному
API root. Для Anthropic Messages стандартный endpoint — `/v1/models`: функция добавляет `v1/models`
к корню и не дублирует `v1`, если совместимый base URL уже заканчивается этим сегментом. Во всех
случаях сохраняются origin и пользовательский префикс пути. Таблица остаётся ключованной форматом:
будущий протокол сможет получить другой путь без условий в форме.

Форма хранит именно режим, а не признак «поле когда-то трогали». Пока выбран `default`, изменение
base URL или протокола сразу пересчитывает показанный URL. `custom` хранит введённый абсолютный URL,
`disabled` полностью выключает сетевое обнаружение. Человек может в любой момент вернуть режим по
умолчанию.

Сетевой загрузчик живёт в `packages/agent-runtime-pi`, рядом со сборкой кастомного провайдера:
только этот пакет импортирует Pi, знает форму credential и превращает внешний ответ в runtime
`Model`. Демон передаёт только сохранённое определение и существующий непрозрачный models store.
Секрет не возвращается из пакета и не попадает в HTTP-ответ, определение или журнал.

Запросы используют `GET`, общий abort signal обновления и ограниченный таймаут. Авторизация зависит
от протокола:

- OpenAI Completions и Responses — `Authorization: Bearer <key>`;
- Anthropic Messages — `x-api-key` и обязательный версионный заголовок;
- Google Generative AI — `x-goog-api-key`, чтобы ключ не оказался в query string и журналах.

Адаптеры принимают официальные оболочки каталогов: `data[]` у OpenAI и Anthropic, `models[]` у
Google. Они следуют объявленному протоколом курсору пагинации, отбрасывают записи без строкового
идентификатора, нормализуют Google `models/<id>` до `<id>` и удаляют дубликаты с сохранением первого
порядка. Неожиданная форма всего ответа считается ошибкой, а отдельная негодная запись пропускается.

Список собирается так:

1. к каждому найденному `id` применяются общие значения и затем его персональное переопределение;
2. отключённые автоматические идентификаторы отбрасываются;
3. ручные модели добавляются отдельно и выигрывают при совпадении идентификатора;
4. результат переводится в runtime-модели выбранного API.

Значения по умолчанию: контекст `128000`, максимум ответа `8192`, только текст, reasoning выключен,
цены входа и выхода `0`. Имя неизвестной модели равно её идентификатору. UI явно показывает эти
значения как предположения, а не как сведения провайдера.

Последний успешный динамический список сохраняется существующим `model-catalogs.json`. При старте
пользовательский провайдер сначала восстанавливает его общим `refresh({ allowNetwork: false })`, до
того как сессии начинают обслуживать запросы. Неудачное обновление не заменяет список и не стирает
ручные модели. Повторное успешное обновление добавляет новые и убирает исчезнувшие автоматические
модели; ручные записи и сохранённые overrides остаются.

Общий `POST /api/providers/refresh` продолжает обновлять все динамические каталоги. Для страницы
пользовательского провайдера добавляется адресная операция, которая обновляет только его. Небольшая
provider-scoped оркестрация остаётся внутри runtime-границы и использует те же credential и cache
порты; демон не воспроизводит разрешение ключа и не читает секрет.

После успешного входа адресное обновление запускается автоматически. Вход считается успешным даже
при отказе каталога. Результат обновления хранится сервисом в памяти, публикуется обычное
`core.providers.changed`, и заново прочитанная детальная страница показывает число моделей либо
причину последней ошибки.

## HTTP API

Существующие маршруты списка, входа и моделей остаются общими. CRUD пользовательских определений
получает отдельный namespace, чтобы `user` или `new` не могли быть приняты за идентификатор обычного
провайдера:

- `GET /api/user-providers` — определения, конфликты запуска и последний результат обновления без
  секретов;
- `POST /api/user-providers` — создать и вернуть сохранённое определение;
- `GET /api/user-providers/:providerId` — получить одну запись для формы;
- `PUT /api/user-providers/:providerId` — заменить определение с тем же `id`;
- `DELETE /api/user-providers/:providerId` — удалить определение, ключ и кэш;
- `POST /api/user-providers/:providerId/models/refresh` — адресно перечитать каталог.

Неверное тело отвечает `400`, неизвестная запись — `404`, занятый идентификатор, активная сессия и
нечитаемый файл — `409`. Сетевой отказ обновления отвечает `200` типизированным исходом с полем
`error`: прежний список остаётся действующим, поэтому сама операция завершилась наблюдаемым
результатом, а не потеряла состояние.

Каждое успешное создание, изменение, удаление и обновление моделей публикует
`core.providers.changed`. Отдельного события пользовательского реестра нет: потребителей интересует
изменившийся общий каталог, а владелец подробностей перечитывает свой ресурс.

SDK плагинов не получает CRUD пользовательских определений. Он продолжает видеть такой провайдер в
общем списке и использовать его модели, но регистрировать и снимать может только собственные
эфемерные провайдеры.

## UI и состояние

`ProvidersView` остаётся чистой композицией без `fetch`. Контроллер провайдеров получает отдельные
операции пользовательского реестра и передаёт вью данные и обработчики. Большая форма выделяется в
`UserProviderFormView`, а редактор одной модели — в небольшой предметный компонент; сетевой state и
маршрутизация в них не проникают.

Экран списка показывает действие создания и различает происхождение провайдеров. Конфликтная
сохранённая запись, которой нет в runtime-каталоге, показывается отдельной предупреждающей строкой с
действием удаления. Страница деталей пользовательского провайдера показывает:

- формат API, base URL и фактический models URL;
- состояние ключа и существующий диалог входа;
- время и результат последнего обновления;
- ручной и автоматически обнаруженный источник каждой модели;
- действия обновления, редактирования и удаления.

В форме модели можно добавлять и удалять ручные записи, менять общие значения, переопределять
характеристики найденной модели и отключать её. Поля цен находятся в расширенной части и не мешают
основному сценарию. Сохранение отключено при локальной ошибке; серверная ошибка остаётся на форме и
не теряет введённые данные.

## Ошибки и конкуренция

- Повторное нажатие сохранения, удаления и обновления блокируется локальным pending-состоянием.
- Сервер всё равно сериализует мутации, поэтому две вкладки не теряют запись; поздняя полная замена
  определения выигрывает, как у остальных store-backed сущностей проекта.
- Закрывшаяся вкладка отменяет свой fetch, но уже принятая сервером атомарная запись не откатывается.
- Удаление во время активной сессии возвращает названный конфликт и ничего не очищает.
- Удаление во время входа отменяет диалог перед очисткой ключа.
- Редактирование с негодным `user-providers.json` и вход с негодным `credentials.json` показывают
  разные причины: один файл не маскирует другой.
- Сетевые тела каталога имеют ограничение размера; не-JSON, превышение лимита, timeout и HTTP-отказ
  превращаются в безопасное сообщение без содержимого ответа и без ключа.

## Проверка

Тесты протокола доказывают пути, парсинг всех четырёх форматов определения и отказы по URL, числам,
идентификаторам и дубликатам. Тесты стора доказывают restart, атомарность, `0600`, отказ поверх
негодного файла и отсутствие секрета.

Тесты runtime-границы через локальный HTTP-сервер доказывают заголовки четырёх протоколов,
пагинацию, abort/timeout/лимит тела, нормализацию ответов, значения по умолчанию, overrides, ручной
приоритет, восстановление кэша и сохранение прежнего списка после отказа. Значение тестового ключа
не должно встречаться ни в снимке, ни в определении, ни в записях logger-double.

Тесты сервиса и маршрутов доказывают создание, restart-регистрацию, конфликт со встроенным и
плагинным идентификатором, живую замену, адресное обновление, автоматическое обновление после входа,
блокировку удаления активной сессией и порядок полной очистки.

Тесты веб-приложения доказывают канонические адреса, отдельные create/edit вью, неизменяемый `id`,
автопересчёт models URL, переключение default/custom/disabled, ручные модели, локальные ошибки,
сохранение ввода после серверного отказа, действия только у `origin: user` и подтверждение удаления.

Полная проверка: `make check` и `make build` под Node 24.

## Границы изменения

В эту итерацию не входят произвольные функции запросов, OAuth пользовательского провайдера,
пользовательские заголовки, автоматическое определение протокола, загрузка цен и возможностей из
неофициальных источников, расписание фонового обновления и импорт/экспорт определений. Новые форматы
API добавляются кодом платформы в закрытую таблицу.

## Почему так

**Отдельный постоянный реестр и общий runtime-каталог.** Определение пользователя имеет собственный
жизненный цикл, но модельная сессия должна видеть ровно ту же коллекцию, что UI и плагины. Второй
каталог дал бы разные ответы на один вопрос; генерация управляемого плагина связала бы простую запись
настроек с установкой, активацией и падениями воркера.

**Не хранить реестр в общих preferences.** Провайдер — именованная сущность с моделями, секретом,
кэшем, конфликтами и отдельным CRUD, а не переключатель интерфейса. Запись preferences при каждом
редактировании создала бы лишнюю связь между независимыми настройками.

**Определение отдельно от ключа и кэша.** Форму можно сохранить до авторизации, секрет остаётся у
единственного сериализованного писателя, а автоматически восстановимый список не делает основной
файл негодным. Один общий документ либо раскрыл бы ключ через CRUD, либо заставил бы форму
перезаписывать секрет, которого она не читает.

**Отдельный тип от определения плагина.** Переиспользовать структурно похожий тип короче сегодня,
но тогда изменение постоянного редактора становилось бы ломающим изменением SDK плагинов. Общим
остаётся внутренний перевод в Pi, а не публичный жизненный цикл.

**Закрытый список четырёх протоколов.** Формат — исполняемая реализация, а не подпись. Произвольная
строка потребовала бы принести код запроса, то есть вернуть секрет и каждый модельный вызов в воркер
или браузер. Уже имеющиеся lazy-адаптеры Pi дают нужные варианты без новой внешней зависимости.

**Гибридный каталог вместо только ручного или только автоматического.** Стандартные endpoints часто
отдают лишь идентификатор и не знают цены, окна контекста или reasoning. Только автоматика создала бы
ложно точные данные и не работала бы с совместимыми серверами без каталога; только ручной ввод
превратил бы десятки доступных моделей в рутину. Явные defaults и overrides делают неполноту
наблюдаемой.

**Редактируемый endpoint с режимом default.** Простое текстовое поле теряет различие между
автоматически вычисленным и намеренно введённым URL, поэтому неясно, обновлять ли его после смены
base URL. Явный режим решает это без скрытого dirty-флага формы.

**Адресное обновление внутри runtime-границы.** Имеющийся Pi `refresh()` обходит всех динамических
провайдеров. Запускать его после входа в один локальный сервер значит неожиданно ходить во все
остальные сети. Нужная provider-scoped оркестрация должна видеть credential только внутри пакета,
который уже владеет Pi; вынос её в демон нарушил бы границу и размножил работу с секретом.

**Не блокировать редактирование простаивающими сессиями.** Сессия хранит ссылку на модель и уже умеет
переживать её исчезновение. Запрет любой правки, пока существует хоть одна старая история, сделал бы
конфигурацию практически неизменяемой. Блокируется только удаление во время реально идущей работы,
чтобы не оборвать запрос из-под неё.

**Очистка ключа раньше определения.** Несколько файлов нельзя заменить одной атомарной операцией.
Выбранный порядок оставляет после сбоя видимую, повторно удаляемую сущность без части восстановимых
данных, но не невидимый секрет. База данных или журнал транзакций ради трёх идемпотентных удалений
противоречили бы файловой модели платформы и цене отказа.
