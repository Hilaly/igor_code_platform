# Источники плагинов: Sovereign и межклиентские корни

## Цель

Платформа ищет пользовательские и проектные плагины в нативных каталогах Sovereign и в каталогах
`.agents`, общих с другими клиентами. Старые каталоги `plugins/` в директории данных и в корне
проекта перестают быть источниками сразу, без обратной совместимости и без миграции.

## Вне границ

- Не переносить и не изменять существующие файлы плагинов, включая dev-данные.
- Не добавлять запускную миграцию, fallback, предупреждение о старом пути или чтение старого пути.
- Не менять форму манифеста, SDK, жизненный цикл воркера, включение плагина или правила вкладов.
- Не менять целевую распаковку встроенных плагинов; меняется только набор внешних user/project roots.

## Корни и порядок перекрытия

Платформа формирует список корней в порядке возрастания специфичности:

| Ранг | Source                           | Путь                            | Назначение                                  |
| ---: | -------------------------------- | ------------------------------- | ------------------------------------------- |
|    0 | `builtin`                        | встроенные плагины поставки     | Базовая поставка платформы                  |
|    1 | `user:agents`                    | `~/.agents/plugins/`            | Межклиентские пользовательские плагины      |
|    2 | `user:sovereign`                 | `~/.sovereign/plugins/`         | Нативные пользовательские плагины Sovereign |
|    3 | `project:<project-id>:agents`    | `<project>/.agents/plugins/`    | Межклиентские плагины проекта               |
|    4 | `project:<project-id>:sovereign` | `<project>/.sovereign/plugins/` | Нативные плагины проекта Sovereign          |

Более высокий ранг перекрывает вклад с тем же полным идентификатором от менее специфичного
источника. Два вклада на одинаковом ранге конфликтуют и не применяются; порядок обхода каталогов
не выбирает победителя.

Project roots создаются только для доступных неархивных проектов. Как и сейчас, реестр остаётся
плоским: плагин, найденный в одном доступном проекте, активен для всей платформы, а не только для
сессий этого проекта. Два проекта имеют одинаковый ранг, поэтому их одинаковые вклады конфликтуют.

## Форма источника и ключа

Source различает scope и namespace клиента. Один плагин, лежащий в `.agents` и `.sovereign`, — это
две независимые установки с разными включением, хранилищем и диагностикой.

Ключ плагина строится как `<source>:<plugin-id>`:

```text
builtin:base-agent
user:agents:hello
user:sovereign:hello
project:b7Kq3xv9pQdT:agents:hello
project:b7Kq3xv9pQdT:sovereign:hello
```

Идентификатор проекта остаётся идентификатором записи проекта, не путём. Он не содержит двоеточия;
идентификатор плагина тоже не содержит двоеточия. Поэтому ключ по-прежнему разбирается по последнему
двоеточию, а source — без неоднозначности.

`builtin` включён по умолчанию. Все четыре внешних source выключены по умолчанию; человек включает
каждую установку отдельно через существующий механизм preferences.

## Обнаружение и наблюдение

Каждый root обрабатывается одинаково: загрузчик просматривает только непосредственные дочерние
папки, читает в них `package.json`, проверяет поле `sovereign` и существование worker entry. Полный
рекурсивный обход проекта не вводится: `.agents/plugins` и `.sovereign/plugins` — уже точные,
явные точки обнаружения.

Watcher ставится на каждый вычисленный root. При появлении, удалении или правке плагина действуют
нынешние правила debounce, повторного обнаружения и hot reload. При архивировании проекта,
недоступности его папки или удалении записи проекта обе его root-папки исчезают из watcher и из
набора обнаружения.

## Удаляемые пути и отсутствие миграции

После реализации следующие пути не входят в список roots и никогда не читаются загрузчиком или
watcher:

```text
<data-directory>/plugins/
<project>/plugins/
```

Также удаляются старые source-строки `data` и `project:<project-id>`. Значит старые keys наподобие
`data:hello` и `project:<project-id>:hello` больше не являются ключами известных плагинов. Платформа
не переносит файлы, не переписывает `preferences.json`, не пробует старые пути и не пытается угадать
соответствие между старой и новой установками.

## Изменяемые границы реализации

- `packages/protocol/src/plugin.ts`: новые допустимые source-строки, построители project source,
  определение project id, ранги и default enablement.
- `apps/daemon/src/plugin-sources.ts`: user roots и по две project root-папки на проект; удаление
  корней `data` и `<project>/plugins`.
- `apps/daemon/src/main.ts`: без новой механики; существующее пересчитывание roots и переустановка
  watcher получают расширенный список.
- Тесты protocol, discovery, watcher, enablement, contribution registry, snapshot и supervisor:
  ожидаемые source/key обновляются; добавляются проверки пяти рангов, конфликта равных project roots
  и исключения старых путей.
- Документация о плагинах, директории данных, запуске и production-артефакте: описывает только
  новые внешние roots и их приоритет.

## Критерии готовности

- Плагин из каждого из пяти roots обнаруживается с корректным source и key.
- Вклад из `.sovereign` побеждает одноимённый вклад из `.agents` на том же scope.
- Проектный `.agents` побеждает user `.sovereign`; проектный `.sovereign` побеждает все остальные.
- Одинаковые вклады из двух project roots с равным рангом не применяются.
- Плагины в `<data-directory>/plugins` и `<project>/plugins` не обнаруживаются и не наблюдаются.
- Архивирование или недоступность проекта снимают обе его project roots.
- `make check` проходит после изменения.

## Почему так

### Два namespace на scope, а не один объединённый каталог

`.agents` нужен как межклиентский формат расположения, `.sovereign` — как нативный формат
платформы. Их нельзя объединить в один source: тогда потеряются отдельные keys включения, состояние
и объяснимая диагностика того, какая из двух установок дала вклад. Явный ранг делает нативный
Sovereign-слой осознанным override поверх совместимого слоя.

### Явные roots, а не рекурсивный поиск по проекту

Полный обход проекта захватывает чужие зависимости и `package.json`, плохо масштабируется и делает
источник плагина неочевидным. Две стандартные подпапки дают совместимость без неограниченного поиска.

### Немедленное удаление старых путей

Fallback и миграция создают два действующих соглашения о расположении плагинов, усложняют
приоритеты и сохраняют код, который надо будет когда-то удалять. Новая раскладка применяется сразу;
существующие файлы остаются на диске, но платформа их больше не читает.
