# Срез 12c-2: страницы плагина

## Цель

Плагин занимает целую страницу на своём адресе `/p/<pluginId>/<pageId>/*` и строит внутри неё свою
навигацию. Срез закрыт, когда на собранном демоне страница плагина открылась по адресу, показала
заголовок из снимка до загрузки бандла, увела вглубь себя вложенным путём с параметром, пережила
перезагрузку и кнопку «назад», ушла на маршрут ядра фасадом и вернулась заглушкой с возвратом после
выключения плагина — на том же URL, без перезагрузки страницы.

Этим срез 12c закрывается целиком: первая часть, вкладки правой панели и команды, пройдена.

## Статус и границы документа

Нормативные документы по теме — [ui-extension-model.md](../../ui-extension-model.md) (места, вклады,
страницы и маршруты), [plugins.md](../../plugins.md) (виды вкладов и их формы),
[ui-kit.md](../../ui-kit.md) (оболочка и маршрутизатор),
[public-contract.md](../../public-contract.md) (что публично). Срез добавляет к ним один вид вклада,
один хук браузерного SDK и один публичный тип адреса; всё остальное — реализация уже записанного
обещания модели расширения.

Пошагового плана работ здесь нет — он в [плане среза](../plans/2026-08-09-slice-12c2-plugin-pages.md).

## Решения владельца продукта

Приняты 2026-08-09 до написания кода:

1. **маршрутизатор дорабатывается свой**, внешняя библиотека не берётся;
2. **вид вклада «страница»** — четырнадцатый, а не место с компонентом;
3. **фасад навигации — хук**, и он умеет выход на маршруты ядра;
4. **автоматической записи в левой панели у страницы нет**, но страницы перечислены ссылками во вью
   плагина.

## Уточнения после финального ревью

Приняты владельцем продукта 2026-08-09 после проверки готовой ветки.

### Переход из страницы остаётся явным

`navigate(path)` владеет только хвостом текущей страницы. Обычные и percent-кодированные сегменты
`.` и `..` нормализуются до того, как адрес передаётся браузеру. Сырая обратная косая черта следует
семантике URL браузера: становится разделителем до свёртки dot-сегментов; percent-кодированная `%5C`
остаётся данными. Подъём выше базы упирается в корень страницы. То же правило действует для
необязательного `path` назначения `plugin-page` в `navigateCore`: оно выбирает другую страницу, но
не даёт её хвостом захватить адрес ядра или третьей страницы.

`pluginId` и `pageId` назначения `plugin-page` — opaque-сегменты URL. Web-маршрутизатор кодирует их
существующим преобразованием opaque-сегмента и декодирует обратным: `.`, `..`, `/`, обратная косая
черта и текст, похожий на percent-кодировку, остаются значениями, а не структурой маршрута. Допустимые
зарегистрированные идентификаторы сохраняют прежнее написание URL.

Это не граница доверия: включённый browser-код плагина исполняется в realm хоста и технически может
позвать History API сам. Это граница публичной модели навигации и владения URL. Переход внутри своей
страницы выражается строкой, а выход — отдельным типизированным действием `navigateCore`. Благодаря
этому смена внутренних путей ядра не ломает плагин молча, а будущие проверки, телеметрия и политика
переходов получают одну явную границу.

### Навигационные типы принадлежат browser SDK

Автор browser-части плагина импортирует `CoreDestination`, `SettingsSection` и
`settingsSections` из `@sovereign/browser-sdk`. Их объявление живёт там же: простой реэкспорт из
`@sovereign/protocol` сохранил бы в публичной декларации зависимость от внутреннего пакета.

Web-хост использует тот же тип из browser SDK. Протокол больше не публикует навигационные типы;
совпадение `settingsSections` с заменяемыми местами `core.settings.*` проверяется интеграционным
тестом web-хоста, где сходятся публичная browser-поверхность и внутренний реестр мест.

### Статус относится к победившей регистрации

После `resolvePluginPage` состояние открытой страницы ищется по `registration.pluginKey`, а не по
первому плагину с тем же `pluginId`. Поэтому при встроенной копии и перекрывающей её копии из
директории данных заголовок, browser-ревизия, ожидание и ошибка всегда принадлежат одному владельцу.

Когда активной регистрации нет, поиск состояния по оконному `pluginId` остаётся отдельным правилом:
он нужен, чтобы различить выключенный, ещё запускающийся и отсутствующий плагин. Ревью не меняет эти
состояния и их пользовательский смысл.

### Документация сверяется целиком

Исправление обновляет не только документы, названные ревью. Весь `docs/` сверяется с текущим кодом и
историей ветки: статусы срезов, стабильность UI kit, число и состав вкладов, публичные импорты,
навигационный контракт и описание жизненного цикла. Исторические планы остаются историческими, но
их утверждения о конечном состоянии не должны противоречить нормативным документам.

### Проверка

Каждый поведенческий дефект получает красный тест до изменения production-кода:

- literal, percent-кодированные и смешанные dot-сегменты не выводят `navigate` из базы страницы;
- тот же набор не позволяет `navigateCore({ kind: "plugin-page" })` открыть маршрут вне выбранной
  страницы;
- публичный consumer импортирует все навигационные типы только из browser SDK, а web-хост принимает
  этот же `CoreDestination`;
- при двух оконных копиях одного плагина состояние берётся по ключу регистрации-победителя.

После локальных циклов выполняются полный `make check`, `make build`, `git diff --check` и повторная
проверка чистоты ветки. Живой прогон повторяется для изменённой навигации страницы.

## Исходная предпосылка: маршрутизатор работал только с путём

До реализации обещание модели — «плагин получает от хоста базовый путь, относительный путь,
**параметры** и фасад навигации» — исполнить было нечем, и это было не догадкой, а двумя строками:

```ts
// apps/web/src/router.ts
const page = matchPage(target.location.pathname);          // query не читается вовсе
if (canonicalPath !== target.location.pathname) {
  target.history.replaceState(undefined, "", canonicalPath); // query и hash стираются
}
navigate: (page) => {
  if (path === target.location.pathname) { return; }        // переход по параметрам молчит
```

Отсюда три правки, и все три — предпосылка страницы, а не её украшение.

**Адрес перестаёт быть путём.** Рядом с `Page` появляется место:

```ts
export type Location = { page: Page; query: Readonly<Record<string, string>> };
export function matchLocation(url: string): Location;
export function urlOf(location: Location): string;
```

`Page` и `matchPage`/`pathOf` остаются как есть и продолжают отвечать за путь: параметры — вторая ось
адреса, и вписывать их в одиннадцать вариантов `Page` значило бы поселить `query?` в каждом. У ядра
параметров нет ни на одном маршруте; они заводятся ради страниц плагина, и место для них ровно одно.

`Navigation.navigate` принимает `Location | Page`, где голый `Page` значит пустые параметры. Тридцать
существующих вызовов в `App.tsx` от этого не меняются ни одним символом — и это проверяемый признак
того, что параметры не протекли в маршруты ядра.

**Сравнение при переходе — по полному адресу.** `pathname + search` вместо `pathname`: переход,
меняющий только параметр, перестаёт быть молчаливым. Это ровно тот случай, ради которого страница
кладёт фильтр в адрес.

**Канонизация перестаёт стирать.** `readCurrent` переписывает адрес только когда разошёлся **путь**, и
переносит `search` и `hash` в новый адрес. Сегодня `/providers/anthropic?tab=models#log` доезжает до
`/settings/providers/anthropic` без обоих хвостов, и это молча.

Первоначальный план заодно предлагал чинить утечку слушателя: `addEventListener("popstate", announce)`
не снимался, а `useMemo` под `StrictMode` создавал два экземпляра навигации. План вводил `dispose()`
из эффекта `App.tsx`, но живая проверка показала обратную регрессию: первый cleanup StrictMode снимал
единственный слушатель. Итоговый контракт подписочный — слушатель появляется с первым подписчиком и
снимается с последним; `dispose` у самой навигации не нужен.

Ограничение записывается прямо: `query` — `Record<string, string>`, повторяющийся ключ теряет все
значения, кроме последнего. Цена принята сознательно, пункт уходит в [backlog.md](../../backlog.md).

## Вид вклада «страница»

```ts
export type PageContributionRegistration = RegistrationCommon & {
  kind: "page";
  /** Обязателен, как у команды: ссылка и шапка рисуются до загрузки бандла. */
  title: string;
  /** Имя экспорта в браузерном бандле плагина. */
  export: string;
};
```

Сторона плагина — одна строка в `activate`, и плагин не учит ничего нового:

```ts
await contribute.page({ id: "log", title: "Log", export: "LogPage" });
```

Полей `path` и `route` у объявления нет намеренно. Адрес страницы задаёт хост, а не автор: неймспейс
`/p/<pluginId>/<pageId>/` целиком выведен из идентификаторов, которые уже есть. Дай автору сказать
путь — и появится второй способ занять чужой адрес, который придётся проверять и разрешать спором.

**Адресом служит `declaredId`, а не идентификатор с неймспейсом.** Неймспейс — это `<pluginId>.<id>`, и
в адресе, где `pluginId` уже стоит отдельным сегментом, он дал бы `/p/placed/placed.log`. Реестр при
этом продолжает namespace-ить как всем: спор об идентификаторе и перекрытие копии по рангу источника
считаются по namespace-ному `id`, а адрес читается по паре «`pluginId` + `declaredId`».

Проверок при регистрации три, и все по образцу команды: нужен браузерный вход (`sovereign.browser` в
манифесте), непустой `title`, непустой `export`. Четвёртой — на URL-безопасность идентификатора — не
появляется: навигационные `pluginId` и `pageId` остаются публичными строками, а web-маршрутизатор
всегда сериализует их существующим codec opaque-сегмента. Дублировать в браузере daemon-регекс
объявления значило бы завести вторую грамматику, которая неизбежно разойдётся с первой.

### Разрешение страницы

```ts
// packages/protocol/src/places.ts
export function resolvePluginPage(
  pluginId: string,
  pageId: string,
  contributions: readonly ContributionRegistration[],
  context: PlaceContext,
): PageContributionRegistration | undefined;
```

Живёт рядом с `resolveCommand` и по той же причине: правила контекста и ранга источника одни, и второй
их набор разошёлся бы с первым при первой же правке. Внутри — существующий
`registrationsForContext`: он снимает спор равного ранга и даёт перекрытие копии из директории данных
над встроенной.

**Контекст страницы — оконный, без `project`.** Значит вклад плагина из папки проекта страницу не
занимает: адрес `/p/<pluginId>/<pageId>` один на всё окно, и открыть его можно, не открыв ни одного
проекта. Тот же довод, по которому проектный вклад не заменяет оконное вью (решение 4 среза 12b-2).

## Фасад навигации

```ts
// @sovereign/browser-sdk
export type PageNavigation = {
  /** База страницы: `/p/<pluginId>/<pageId>`. */
  basePath: string;
  /** Относительный путь внутри страницы, всегда с ведущим слэшем; на корне — `/`. */
  path: string;
  query: Readonly<Record<string, string>>;
  navigate(
    path: string,
    options?: { query?: Readonly<Record<string, string>>; replace?: boolean },
  ): void;
  /** Выход на адреса, которыми владеет ядро. */
  navigateCore(destination: CoreDestination): void;
};

export function usePageNavigation(): PageNavigation;
```

**Хук, а не пропсы корневого компонента.** Навигация нужна на любой глубине — кнопке в третьем
вложенном компоненте страницы, — и пропсами её пришлось бы протаскивать вниз руками через код, который
пишет автор плагина. Хук ещё и не замораживает форму пропсов страницы: `PlaceProps` останутся тем, что
они есть, а поверхность навигации растёт минорами.

Вне страницы плагина хук бросает: это ошибка автора, а не состояние, о котором надо рассказывать
данными. Падение ловит существующий `InstanceBoundary` — оболочка остаётся живой, отказ виден в
диагностике вью плагинов.

**`path` передаётся так, как стоит в адресе, — percent-кодированным.** Декодирование сегментов —
дело страницы: только она знает, где у неё сегмент, а где разделитель внутри сегмента. Симметрия при
этом сохраняется: то, что пришло в `path`, годится обратно в `navigate` без потерь.

**`navigate` не выпускает из поддерева через публичный API.** Путь всегда разрешается относительно
`basePath`; literal и percent-кодированные сегменты `.` и `..` нормализуются, сырая обратная косая
черта считается разделителем до этой свёртки, а `%5C` остаётся данными. Подъём выше базы упирается в
неё, как в корень файловой системы. Это граница владения URL в API, не security sandbox: включённый
browser-код плагина исполняется в realm хоста и может вызвать History API напрямую.

`replace: true` нужен именно параметрам: страница, кладущая фильтр в адрес, не обязана наполнять
историю браузера по нажатию на каждый чекбокс.

### Адреса ядра публикуются данными

```ts
// packages/browser-sdk/src/navigation.ts
export const settingsSections = [
  "projects",
  "appearance",
  "usage",
  "providers",
  "plugins",
  "daemon",
  "diagnostics",
] as const;
export type SettingsSection = (typeof settingsSections)[number];

export type CoreDestination =
  | { kind: "home" }
  | { kind: "session"; sessionId: string }
  | { kind: "new-session" }
  | { kind: "session-archive" }
  | { kind: "settings"; section: SettingsSection }
  | {
      kind: "plugin-page";
      pluginId: string;
      pageId: string;
      path?: string;
      query?: Readonly<Record<string, string>>;
    };
```

Набор нарочно узкий: расширить его можно минором, сузить — только мажором. `CoreDestination`,
`SettingsSection` и `settingsSections` принадлежат корню `@sovereign/browser-sdk`: список разделов
настроек и так публичен именами мест `core.settings.<section>`, а browser-плагин не должен зависеть
от внутреннего transport-пакета `@sovereign/protocol` ради навигации.

Страница чужого плагина стоит в этом же перечне не по недосмотру: форму адреса `/p/…` задаёт модель
расширения, то есть ядро. Плагин, который хочет увести на соседа, называет соседа — а не строит его
адрес строкой.

Перевод из публичного адреса в наш `Page` живёт в одном месте — `apps/web/src/navigation/core-destination.ts`.

## Открытая страница

Маршрут остаётся у ядра: `PageView` на `page.kind === "plugin"` рисует вью страницы вместо нынешней
заглушки. Состояний у неё четыре, и три из них — не отказ:

| Что в снимке                                         | Что человек видит                         |
| ---------------------------------------------------- | ----------------------------------------- |
| вклад найден, бандл готов                            | страница плагина                          |
| плагин или вклад выключен                            | заглушка «страница выключена» с возвратом |
| плагин собирается (`building`, браузерной части нет) | ожидание                                  |
| такого плагина или такой страницы нет                | заглушка «страницы нет» с возвратом       |
| сборка упала                                         | отказ с причиной сборки и возвратом       |

Общий «не найдено» здесь запрещён моделью прямо: «Плагин выключен, а его страница открыта —
показывается заглушка с возвратом… Включили обратно — страница восстанавливается на том же URL».
Значит адрес переживает выключение, а возврат ведёт на главную — не в историю: страницу открывают и
прямой ссылкой, и тогда назад возвращаться некуда.

Отдельно про `building`: отсутствие браузерной части — **ожидание, а не отказ**. Это ловушка,
пойманная живой проверкой среза 12b-2, и здесь она повторяется дословно.

Для найденной активной страницы lifecycle и browser-состояние относятся к точной копии с
`key === registration.pluginKey`. Искать первую оконную копию по одному `pluginId` можно только
когда активной регистрации нет и надо различить выключенный, запускающийся и отсутствующий плагин.

Заголовок в шапке берётся из снимка, до загрузки бандла, — как подпись вкладки и заголовок команды.

**Ленивость достаётся даром.** Модель обещает «код активируется лениво: при открытии страницы»: бандл
грузит тот, кто отрисовался, а страница не отрисована, пока на её адрес не пришли.

## Как человек попадает на страницу

Автоматической записи в левой панели нет. Страница попадает в интерфейс тем, что плагин **сам** кладёт
рядом: секцией сайдбара, командой, кнопкой в полосе действий — всем тем, что у него уже есть с 12b-2 и
12c-1. Левая панель остаётся тем, чем человек управляет, а не списком, который дописывают плагины.

Чтобы объявленная страница не оказалась недостижимой, её адрес перечислен ссылкой на странице плагина в
настройках, рядом с остальными его вкладами. Это ещё и единственное место, где видно все страницы
плагина сразу.

## Что киту достаётся

Ничего нового. Заглушка собрана из существующих `EmptyState` и `Button`, шапку даёт `ViewHeader`.
Строка в таблице роадмапа так и записывается.

## Не входит в работу

- **заменяемость страницы плагина** чужим плагином: страница остаётся plugin-owned, как записано в
  публичном контракте. Добавляется минором, когда появится потребитель;
- **разбиение бандла по страницам** — открытая страница тянет весь браузерный бандл плагина;
  существующий пункт бэклога;
- **повторяющиеся ключи query** (`?tag=a&tag=b`) — ограничение записывается, а не снимается;
- **внешняя библиотека маршрутизации** — решением владельца вопрос закрыт в пользу своего роутера;
- горячие клавиши страниц, декларативное условие видимости, сохранение состояния экземпляра — пункты
  бэклога, оставшиеся от 12c-1;
- перевод заголовка страницы каталогом локали плагина.

## Проверка

Живой сценарий на собранном демоне из чистой временной директории данных, тем же способом, что
«Вкладки и команды плагина живьём»:

- `/p/placed/log` открывает страницу плагина; заголовок в шапке пришёл из снимка;
- переход внутрь даёт `/p/placed/log/entry/3?filter=warn`, а страница видит `/entry/3` и `filter`;
- перезагрузка на этом адресе возвращает то же состояние;
- кнопка «назад» браузера возвращает на предыдущий **вложенный** адрес, а не на маршрут ядра;
- переход, меняющий только параметр, происходит; до среза он молчал;
- `navigateCore` уводит на раздел настроек, и адрес ядра остаётся каноническим;
- выключение плагина оставляет адрес живым и показывает заглушку с возвратом; включение возвращает
  страницу на том же URL без перезагрузки;
- правка исходников плагина меняет ревизию и переставляет страницу, не гася оболочку;
- страница перечислена ссылкой на `/settings/plugins/data%3Aplaced`.

Перед каждым коммитом — `make check`. Перед переписыванием истории и после него — `make check`,
`make build`, `git diff --check` и повторный живой прогон.

## Почему так

### Маршрутизатор дорабатывается свой

**Взять `react-router`.** Готовые вложенные маршруты, параметры, блокировки переходов — ровно то, что
понадобится странице. Отвергнуто владельцем продукта: вложенные маршруты внутри `/p/…` строит сам
плагин своим кодом, и хосту знать их не нужно вовсе — ему нужен один сегмент базы и хвост строкой.
Цена альтернативы при этом полная: библиотека становится singleton-зависимостью хоста, её приходится
класть в реестр модулей, переписывать тридцать вызовов навигации и переносить в чужую модель наши
непубличные правила разбора — opaque-сегменты `.` и `..`, легаси-адреса с переписыванием, проверку
`isSessionId` до превращения мусора в запрос.

Записанное в бэклоге «внешняя библиотека станет вопросом вместе со страницами плагинов» этим и
закрывается: вопрос задан, ответ — свой роутер.

### Страница — вид вклада, а не место с компонентом

**Плагин объявляет своё место `<pluginId>.page.<pageId>` кардинальности `single` и кладёт туда
компонент.** Нового вида вклада не появляется вовсе, а заменяемость страницы достаётся даром.
Отвергнуто: хост не отличил бы такое место от любого другого места плагина, то есть не смог бы ни
перечислить страницы, ни взять для ссылки заголовок, ни отказать в регистрации странице без экспорта.
«Страница» — это утверждение об адресе, а место утверждает только о композиции.

Цена принятого варианта названа прямо: заменить страницу чужого плагина сегодня нельзя. Это минор,
который добавляется при появлении потребителя, а не мажор, который придётся отыгрывать.

### Фасад умеет выход на маршруты ядра

**Замкнуть страницу в её поддереве.** Меньше публичной поверхности: адреса ядра остаются нашим
внутренним делом. Отвергнуто владельцем продукта: страница, из которой нельзя открыть сессию или
раздел настроек, вынуждает автора рисовать свои тупики вместо ссылок в интерфейс, в который его
пригласили.

**Дать `navigate("/settings/plugins")` строкой пути.** Ноль новых типов. Отвергнуто: публичным
контрактом становится сам формат пути, и любая канонизация маршрутов ядра — та самая, которую мы уже
делали в 12a, уводя маршруты плагина на `/api/p/` — ломала бы плагины молча. Закрытый перечень
`CoreDestination` ломает их компилятором, а не в браузере пользователя.

### Автоматической записи в левой панели нет

**Каждая объявленная страница сама появляется секцией сайдбара.** Плагин не пишет ничего, страница
достижима сразу. Отвергнуто: пять плагинов по три страницы дают пятнадцать строк, которые человеку
нечем убрать, — левая панель перестаёт ему принадлежать. Средства положить себя в панель у плагина уже
есть, и они добровольные.

Цена: объявленная и никуда не положенная страница достижима только прямым адресом. Отсюда список
страниц во вью плагина — он не навигация, а гарантия, что объявленное видно.

### Параметры — `Record<string, string>`

**Отдавать `URLSearchParams`.** Умеет повторяющиеся ключи, встроен в браузер, ничего не теряет.
Отвергнуто: объект изменяемый, и мутация его копии страницей выглядела бы как навигация, ничего не
меняя, — ровно та ловушка, которую мы чиним в этом же срезе. Простая запись без сюрпризов дороже
поддержки `?tag=a&tag=b`, а цена записана в бэклог.
