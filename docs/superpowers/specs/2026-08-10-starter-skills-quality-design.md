# Качество встроенных starter-скилов

## Цель

Четыре скила плагина `starter` должны не только перечислять формат и API Sovereign, но и вести
агента по воспроизводимому процессу создания агента, скила или плагина. Примеры обязаны соответствовать
действующим runtime-контрактам, а подробная справочная информация должна загружаться только по
необходимости.

## Границы

Изменяются только:

- `plugins/starter/skills/creating-skills`;
- `plugins/starter/skills/creating-agents`;
- `plugins/starter/skills/plugin-backend`;
- `plugins/starter/skills/plugin-frontend`;
- тесты плагина `starter`;
- документация об этих изменениях.

Идентификаторы скилов, parser файловых ресурсов, runtime-контракты и публичный SDK не меняются.

## Структура скила

Каждый `SKILL.md` становится короткой рабочей инструкцией:

1. frontmatter с description, сформулированным через условия применения;
2. основной принцип;
3. последовательность действий;
4. минимальный корректный пример;
5. проверка результата;
6. частые ошибки;
7. ссылка на подробный файл в `references/`.

Технические таблицы, полный список полей, диагностика, перечень core places и объёмные справки по
SDK переезжают в `references/`. Ссылка всегда относительна директории конкретного скила, чтобы
встроенный ресурс оставался самодостаточным вне исходного монорепозитория.

## Создание скилов

`creating-skills` различает:

- reference-скил с точными сведениями о формате или API;
- workflow-скил с последовательностью действий;
- discipline-скил, меняющий поведение агента под давлением.

Автор начинает с повторяемой задачи и наблюдаемого результата, пишет description как условие
активации, выбирает степень свободы инструкций и выносит тяжёлые материалы в соседние ресурсы.
Parser допускает пустое тело, но инструкция прямо объясняет, что полезный model-invocable скил
должен содержать руководство или ссылки на ресурсы.

## Создание агентов

`creating-agents` отделяет файловый формат от проектирования роли. Перед записью `AGENT.md` автор
задаёт:

- одну миссию;
- границы и нецели;
- минимальный набор инструментов и скилов;
- порядок работы;
- условия остановки и обращения к пользователю;
- контракт итогового ответа;
- обязательную проверку результата.

Wildcard `include: ["*"]` описывается как осознанный выбор для общего агента: он автоматически
разрешает и будущие совпавшие вклады. Для специализированных агентов рекомендуется allowlist.

## Плагины

`plugin-backend` остаётся обязательной основой любого исполняемого плагина. Он показывает минимальный
manifest, lifecycle и последовательность регистрации вкладов. Пример события не публикует его
внутри `activate`, потому что снимок вкладов действует только после успешного завершения активации.

`plugin-frontend` применяется дополнительно, когда есть `sovereign.browser`. Команда экспортируется
как объект `Command` с методом `run`, а не как React-компонент. Подробный перечень places и
browser-контрактов хранится в reference-файле.

## Автоматическая проверка

Тест плагина `starter` проверяет сами артефакты документации:

- каждый starter-скил успешно проходит действующий `parseSkillFile`;
- descriptions начинаются с `Use when`;
- все локальные Markdown-ссылки из скилов разрешаются в существующие файлы;
- TypeScript и TSX code fences синтаксически разбираются TypeScript;
- канонический пример имени скила не содержит `_`;
- frontend-пример экспортирует команду формой `Command`;
- backend-пример не публикует только что объявленное событие внутри `activate`;
- `creating-agents` перечисляет `invalid-model`.

Это не заменяет поведенческие eval-сценарии с отдельными агентами, но ловит обнаруженные регрессии
без зависимости от модели.

## Почему так

**Оставить четыре больших справочника без перестройки.** Отвергнуто: parser принимает их, но
агенту приходится самому выводить процесс работы, а два канонических примера уже расходятся с
runtime.

**Создать отдельные новые скилы для workflow и сохранить старые reference-скилы.** Отвергнуто:
каталог стал бы неоднозначным — по одному запросу одновременно срабатывали бы формат и workflow.
Текущие четыре идентификатора уже известны модели и должны стать полноценными точками входа.

**Скопировать корневые документы целиком внутрь плагина.** Отвергнуто: появились бы две
редактируемые копии источника истины. Reference-файлы содержат только необходимый автору плагина
публичный контракт, а тесты связывают примеры с действующим parser и TypeScript.

**Проверять качество только ручным review.** Отвергнуто после найденных ошибок команды и события.
Статические тесты не доказывают эффективность prompt-инструкции, но надёжно закрывают механические
ошибки и освобождают review для смысловой проверки.
