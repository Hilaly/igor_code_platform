# Заменяемые страницы ядра

## Статус

Правило утверждено владельцем продукта 9 августа 2026 года.

## Контракт

Каждая страница ядра, которая является route-level рабочим содержимым внутри авторизованной
оболочки, поставляется как одиночное заменяемое место (`single`, `replaceable: true`) с обязательным
built-in провайдером. Это относится в том числе ко всем разделам Settings и к новым страницам того
же класса. Маршрут остаётся маршрутом ядра: плагин заменяет провайдер места, а не перерегистрирует
адрес.

Shell chrome, login/bootstrap до загрузки плагинов, страницы ошибок маршрутизатора и страницы,
целиком принадлежащие самому плагину, этим правилом не охватываются.

## Реализация Usage Analytics

Usage Analytics публикуется как `core.settings.usage`, получает оконный `PlaceContext` и рендерит
текущий `UsageView` через `HostPlace` как built-in. При отсутствии, выключении, конфликте или
ошибке плагинского replacement хост возвращается к этому же built-in вью.

Все Settings-разделы используют одну схему: предметная логика остаётся в `App.tsx`, а граница
подмены — в `HostPlace`. Публичные пропсы встроенных вью наружу не выносятся; замена получает только
контекст места и публичные SDK-сервисы.

## Почему так

**Один контракт для всех рабочих страниц.** Отдельные прямые `ReactNode`-вставки позволяли бы новой
странице случайно обойти plugin runtime и делали бы заменяемость свойством конкретного разработчика.

**Маршрут не меняется при замене.** Стабильный URL сохраняет навигацию, deep link и fallback, а
выбор провайдера остаётся единым для всех мест.

**Login и shell исключены.** До авторизации браузерный снимок плагинов и его доверенный код ещё не
доступны; shell владеет геометрией и жизненным циклом всей оболочки.
