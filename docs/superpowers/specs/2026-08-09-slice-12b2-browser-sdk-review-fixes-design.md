# Исправления среза 12b-2 и браузерный SDK

## Цель

Закрыть замечания ревью ветки `claude/roadmap-next-slice-a86799`, не сужая утверждённое требование
среза 12b-2: плагин обязан уметь опубликовать место в своём интерфейсе, а другой плагин — расширить
или заменить его. Одновременно исправляются найденные гонки загрузчика, потеря проектного контекста,
неверные объяснения во вью плагина и противоречия публичной документации.

Срез остаётся закрытым только после того, как plugin-owned place проверено настоящими браузерными
компонентами двух плагинов. Простого объявления `contribute.place()` в реестре недостаточно.

## Публичные пакеты

### `@sovereign/browser-sdk`

Появляется пакет `packages/browser-sdk` с именем `@sovereign/browser-sdk`. Это публичная
React-зависимая поверхность, через которую браузерный код плагина взаимодействует с хостом.
Отдельный пакет выбран потому, что ближайший срез 12c добавит сюда страницы, навигацию, вкладки и
команды, тогда как `@sovereign/ui-kit` отвечает только за визуальные примитивы и токены.

Основной entrypoint экспортирует только плагиновый контракт текущего среза:

```ts
export type PlaceContext = {
  project?: string;
  subject?: Readonly<Record<string, string>>;
};

export type PlaceProps = {
  id: string;
  context: PlaceContext;
};

export function Place(props: PlaceProps): ReactNode;
export function PlaceCollection(props: PlaceProps): ReactNode;
```

Публичные типы объявляются самим browser SDK. Они структурно сверяются с внутренними типами
`@sovereign/protocol`, но не объявляют протокол публичной зависимостью автора плагина.

Browser bundle получает `@sovereign/browser-sdk` из того же глобального реестра host modules, что
React и UI Kit. Поэтому компонент плагина видит тот же React context, который установил
`apps/web`, а в бандле не возникает второй экземпляр runtime.

### Host-only entrypoint

`@sovereign/browser-sdk/host` предназначен только для `apps/web` и явно не входит в публичный
контракт плагинов. Он экспортирует:

- `BrowserRuntimeProvider`;
- host-варианты одиночного и коллекционного места для core places;
- интерфейс синхронного снимка загрузчика browser module;
- внутренние props, через которые хост передаёт снимок вкладов, статусы плагинов и диагностику.

Сам динамический `import()`, DOM-листы стилей и их кеш остаются в `apps/web`: browser SDK не владеет
сетевой политикой приложения и не получает зависимость от его внутренних модулей.

### `@sovereign/ui-kit`

UI Kit остаётся отдельным пакетом визуальных деталей. Вся текущая поверхность его `src/index.ts`
объявляется стабильной: браузерные плагины уже импортируют оттуда компоненты, поэтому одновременные
формулировки «публично» и «ломается свободно» больше недопустимы. Browser SDK не реэкспортирует UI
Kit и не превращает навигацию или команды в визуальные примитивы.

## Отрисовка места плагина

Плагин рисует объявленное место без повторного указания встроенного компонента:

```tsx
import { Place } from "@sovereign/browser-sdk";

export function BoardPage({ context }: { context: PlaceContext }) {
  return <Place id="placed.board" context={context} />;
}
```

`Place` выполняет следующий поток:

1. Находит действующее объявление `kind: "place"` с этим id в текущем проектном контексте.
2. Проверяет кардинальность `single`.
3. Загружает экспорт `builtIn` из browser bundle владельца объявления.
4. Если место `replaceable`, разрешает вклады `kind: "component"` и пытается отрисовать победителя.
5. При отсутствии победителя, споре равного ранга, отказе загрузки или падении replacement
   возвращается к `builtIn` владельца места.

У одиночного `replaceable: false` component claims место не заменяют. У отсутствующего объявления
компоненты продолжают ждать: публичный `Place` рисует пусто, не превращая порядок запуска плагинов в
ошибку. Если у незаменяемого одиночного места не указан необязательный `builtIn`, оно тоже рисует
пусто; форма регистрации в этом исправлении не ужесточается.

`PlaceCollection` принимает объявления с кардинальностью `collection` или `action`, сортирует
компоненты по группе, `order` и id и изолирует падение каждого экземпляра. У коллекции нет
встроенного provider и нет спора за единственного победителя; необязательный `builtIn` такого
объявления в текущем контракте не используется.

Core places используют тот же внутренний resolver и границы экземпляров. Разница только в
источнике встроенного provider: `apps/web` передаёт готовый React node через host-only API, потому
что вью ядра не является экспортом browser bundle.

## Контекст и приоритет источников

Browser snapshot является объединением базового и всех проектных контекстов. Чтобы браузер
воспроизводил утверждённый общий алгоритм реестра, разрешение идёт в таком порядке:

1. отбрасываются объявления чужих проектов;
2. оставшиеся группируются по identity `kind + id`;
3. в каждой identity побеждает `project -> data -> built-in`, а спор равного ранга не применяется;
4. только затем выбираются объявления конкретного place и разрешается его кардинальность.

Следствие фиксируется тестом: если project-копия contribution с тем же id перенесла компонент в
другое место, data-копия не остаётся действующей в старом месте этого проекта. Для другого проекта
она по-прежнему доступна. Специальная последовательность из старой версии
`ui-extension-model.md`, где place фильтровался до identity, переписывается как противоречащая
общему правилу вкладов из `plugins.md`.

## Жизненный цикл browser module

### Ревизии CSS

Лист стилей активируется только если `(pluginKey, revision)` всё ещё является текущей записью кеша.
Поздний `load` старой ревизии может удалить только собственный link и не может снять текущую
ревизию. Оба порядка завершения `r1/r2` проверяются отдельными тестами.

Если stylesheet не загрузился или последующий JS import завершился отказом, link этой неуспешной
ревизии удаляется. Прежний успешно активированный stylesheet не удаляется устаревшим callback.

### Владение кешем

Кеш, созданный `BrowserRuntimeProvider`, принадлежит этому provider. При unmount он очищает записи
и все принадлежащие им stylesheet links; поздние callbacks после dispose не могут активировать
стили. Это закрывает logout и истечение сессии: plugin CSS не остаётся на странице входа.

Внедрённый через props кеш считается переданным тому же единственному provider. Совместное владение
одним кешем несколькими provider в текущий контракт не входит; если появится потребитель, ему
понадобится отдельный reference-counted API.

### Граница экземпляра

Ключ error boundary включает plugin key, contribution id, export и browser revision. Смена
победителя или экспортируемого компонента поэтому даёт новую попытку даже при одинаковом content
hash двух browser bundles.

## Проект новой сессии

Выбранный для `core.session.new` проект является живым состоянием маршрута, а не одноразовым
аргументом mount. `App` хранит его, пока открыт экран новой сессии, и передаёт одновременно:

- в `PlaceContext.project`, чтобы project plugin мог занять место;
- в `NewSessionView`, чтобы встроенная форма показывала тот же выбор;
- в контроллер сессий, чтобы загрузить агентов проекта.

Ручная смена проекта обновляет все три потребителя. Состояние очищается при уходе с маршрута или
при открытии глобальной формы без project preselection, но не сразу после входа на маршрут.

## Объяснение выключенных вкладов

`PluginDetailView` сохраняет признак `off` до вычисления результата place claim. Выключенный
component всегда описывается как выключенный, а не как добавленный, overridden или действующий
только в проекте. Объявления выключенных places могут использоваться для объяснения их
кардинальности, но не участвуют в фактическом выборе provider или построении коллекции.

## Состояние экземпляра

Текущий browser host сохраняет React state только пока жив конкретный mount. Reload browser bundle,
выключение contribution или unmount provider создают новый экземпляр и теряют это состояние.

Документация больше не обещает host-сериализацию выделения, раскрытых секций и позиции прокрутки.
Такой API остаётся в backlog до вкладок правой панели или другого настоящего потребителя, который
задаст форму JSON, ключ экземпляра, версионирование, лимит размера и обработку несовместимого
состояния. Доменные данные продуктового плагина по-прежнему сохраняются его worker storage и к этой
оговорке не относятся.

## Воспроизводимые fixtures

`placed`, `rival` и `browserless` переносятся из игнорируемой dev-директории в tracked fixtures
демона. Явная seed-команда принимает путь новой временной директории данных, копирует туда fixtures,
включает нужные вклады и отказывается перезаписывать уже существующие цели.

`placed` объявляет `placed.board`, экспортирует его `builtIn` и внутри своего UI вызывает публичный
`Place`. `rival` приносит replacement или элемент коллекции этого места. Сценарий проверяет именно
plugin-to-plugin extension, а не только core places. `browserless` сохраняет проверку понятной
диагностики для component без `sovereign.browser`.

Runbook содержит все команды от пустой временной директории до входа, включения, hot reload,
конфликта и очистки. Утверждения, что browser UI или places ещё отсутствуют, удаляются.

## Документация и публичный контракт

Тем же коммитом, что соответствующий код, обновляются:

- `ui-extension-model.md` — browser SDK, plugin-owned rendering, порядок resolution и фактическое
  время жизни instance state;
- `plugins.md` — применение union snapshot в browser context;
- `public-contract.md` — стабильные `@sovereign/browser-sdk` и текущий UI Kit;
- `repository-structure.md` — новый пакет и настоящий путь fixtures;
- `ui-kit.md` — удаление статуса свободно ломающихся primitives;
- `runbook.md`, `roadmap.md`, `backlog.md`, `master-spec.md` и `README.md` — согласованный статус
  среза и воспроизводимая проверка.

Новых тематических документов, кроме этой утверждённой design spec и последующего implementation
plan, не появляется.

## История ветки

Перед переписыванием создаётся локальная резервная Git-ссылка на исходный HEAD `227a1b3`. Push и PR
не выполняются. После реализации локальная непубликованная история пересобирается так, чтобы каждый
коммит был логически атомарным, проходил проверки и содержал вызванную им документацию. Общий
docs-коммит `227a1b3` как склад документации исчезает, а его строки распределяются по тематическим
коммитам.

Рабочая ветка переименовывается в разрешённый правилами префикс `fix/`; путь worktree не меняется.
Резервная ссылка сохраняется до полной проверки переписанной истории и удаляется только после
сравнения итогового дерева с проверенной реализацией.

## Не входит в работу

- страницы, вкладки, команды и navigation facade среза 12c;
- browser API доменных продуктов из `product-plugins.md`;
- host-сериализация instance state;
- автоматическая публикация пакетов, push или PR;
- декларативный язык видимости вкладов;
- отдельная sandbox/permission boundary для доверенного browser code.

## Проверка

Каждый дефект сначала получает падающий regression test, затем минимальное исправление. Проверяются:

- оба порядка завершения CSS revisions, stylesheet error, JS import error и provider unmount;
- смена упавшего provider на исправный с той же revision;
- identity shadowing до place filtering и изоляция разных project contexts;
- сохранение project context и preselection на всём маршруте новой сессии;
- выключенные core и plugin-owned place claims;
- owner `builtIn`, replacement, equal-rank dispute, collection и падение одного экземпляра
  plugin-owned place;
- полнота host-module registry и исполнение собранного browser bundle с новым SDK;
- seed fixtures и живая проверка без файлов из игнорируемой `.sovereign-dev`.

Перед каждым коммитом запускаются тематические тесты. Перед переписыванием истории и после него
запускаются свежие `make check`, `make build`, `git diff --check` и живая browser-проверка. После
переписывания каждый новый коммит отдельно проверяется `make check`, чтобы зелёным оставалось не
только итоговое дерево.

## Почему так

### Browser SDK отдельно от UI Kit

**Положить `Place` в UI Kit.** Меньше пакетов и уже готовый host module. Отвергнуто после сверки с
`product-plugins.md`: следующий срез добавляет страницы, навигацию, вкладки и команды, которые не
являются визуальными примитивами. Смешанный пакет быстро превратил бы UI Kit одновременно в дизайн-
систему и API оболочки.

**Подмешать web-компоненты только в runtime-объект UI Kit.** Минимальный перенос файлов.
Отвергнуто: TypeScript-поверхность пакета расходилась бы с объектом, который реально отдаёт хост, а
проверка зависела бы от способа загрузки.

Отдельный browser SDK платит одним пакетом и одним host-module specifier, но даёт устойчивую границу:
UI Kit отвечает, как выглядит интерфейс; browser SDK — как плагиновый UI взаимодействует с
платформой.

### Built-in provider разрешает хост

**Плагин повторяет `<Board />` дочерним узлом `Place`.** Проще runtime. Отвергнуто: `builtIn` в
worker declaration и browser render стали бы двумя источниками истины и могли назвать разные
экспорты. Хост уже получает объявление и обязан применить его сам.

### Instance storage не проектируется без потребителя

Публичное хранилище UI-state потребовало бы заранее выбрать ключ экземпляра, JSON-схему,
версионирование, лимит и миграцию. Ни один текущий place этого не использует. Поэтому действующий
контракт честно ограничивается временем mount, а устойчивое состояние появится вместе с первым
вкладочным или иным сохраняемым экземпляром.
