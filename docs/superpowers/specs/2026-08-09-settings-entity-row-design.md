# Кликабельная строка сущности в Settings

## Цель

Унифицировать строки проектов, плагинов и провайдеров в настройках. Вся строка открывает detail, а
интерактивные элементы справа (меню проекта, переключатель плагина и будущие контролы) выполняют
своё действие и не открывают detail.

## Решение

В UI kit добавляется `SettingsEntityRow` как композиционный компонент поверх `SettingsRow`, а не
как предметный компонент Projects или Plugins. Он сохраняет базовую геометрию SettingsRow и
предоставляет слоты для повторяющегося паттерна сущности:

```ts
type SettingsEntityRowProps = {
  label: ReactNode;
  description?: ReactNode;
  meta?: ReactNode;
  actions?: ReactNode;
  onSelect: () => void;
  selectLabel: string;
  describedBy?: string;
};
```

`label` и `description` передаются в левую часть базовой строки. `meta` и `actions` собираются в
правой части; оба слота необязательны. Строка всегда выбираема: `onSelect` и `selectLabel` обязательны.
`describedBy` нужен строкам, у которых дополнительное полное описание живёт вне видимого текста;
Projects связывает им цель строки с tooltip полного пути.

Компонент не знает о проектах, плагинах, маршрутах, переводах или протокольных типах. Он отвечает
только за визуальную композицию и доступное разделение навигации и действий.

## Интеракция и доступность

- Вся поверхность строки имеет один полноразмерный select-target, предоставленный `SettingsRow`.
- Правый control rail находится поверх select-target и сохраняет pointer events для вложенных
  `button`, `input`, `select`, `textarea`, `label`, ссылок и элементов с `role="button"`.
- Нажатие по свободной области строки вызывает только `onSelect`.
- Нажатие по `actions` или `meta`, если там есть интерактивный элемент, не вызывает `onSelect`.
- `selectLabel` используется как доступное имя полноразмерной кнопки выбора.
- Визуальный focus принадлежит строке при клавиатурной навигации; вложенные controls сохраняют
  собственные focus-состояния.

## Визуальный стандарт

`SettingsEntityRow` не добавляет локальных цветов, шрифтов, рамок, скруглений или теней. Внешний
вид наследуется от `SettingsRow` и его UI-kit токенов:

- типографика label/description — роли `SettingsRow`, без переопределения font family/weight;
- `Badge` остаётся единственным компонентом смысловых состояний и использует только его `tone`;
- `Toggle`, `Menu`, `Button` и другие controls остаются компонентами UI kit, включая их размеры,
  focus rings и контраст;
- разделители, hover, active, focus и адаптивное складывание колонок принадлежат
  `settings-frame.module.css`;
- прикладной CSS Projects/Plugins ограничивается только внутренней раскладкой содержимого слотов
  (например, группировкой нескольких badge), без копирования геометрии строки.

На широкой области слева остаётся label/description, справа — meta/actions. На узкой области
`SettingsRow` складывает содержимое в одну колонку согласно существующему container query; правый
блок выравнивается в начало без отдельного экранного исключения.

## Миграция экранов

### Plugins

`PluginRow` переходит на `SettingsEntityRow`. Название и технический key остаются в
`label`/`description`, состояние и число вкладов — в `meta`, переключатель — в `actions`.
Toggle не меняет поведение и остаётся независимым от открытия detail.

### Projects

`ProjectRow` переходит с `ListRow` на `SettingsEntityRow`. Имя проекта и сокращённый путь остаются
слева, badges доступности/эфемерности/конфликта и меню — справа. Tooltip полного пути сохраняется,
но его позиционирование и доступность не должны требовать собственной геометрии строки.

Существующие действия rename/archive/restore/remove, подтверждающие диалоги, поиск, архив и
переход в detail не меняются.

### Providers

Обычный `ProviderRow` переходит с `ListRow` на `SettingsEntityRow`: имя и технический id с доступными
способами входа остаются слева, состояние авторизации, источник credentials, число моделей и badges
происхождения каталога — справа. Вся строка открывает detail провайдера.

Конфликтующий пользовательский провайдер не имеет detail и поэтому использует обычный
`SettingsRow`, а не кликабельный `SettingsEntityRow`; кнопка удаления остаётся независимым control
справа. Строки моделей внутри detail не входят в этот срез: они не являются переходами к сущности и
сохраняют семантику обычного списка.

## Проверка

UI kit:

- render-тесты проверяют DOM-структуру `SettingsEntityRow`, label/description и слоты;
- интеракционный тест проверяет, что клик по select-target вызывает `onSelect`, а клик по вложенному
  control — нет;
- CSS-контракт проверяет отсутствие собственного визуального каркаса у нового компонента и
  сохранение токенов SettingsRow.

Web:

- тесты Projects, Plugins и Providers проверяют новый общий компонент и сохранение действий;
- тесты проверяют, что toggle/menu не открывают detail;
- стили проверяют отсутствие старой геометрии `.projects-row`/`.plugins-row-controls` там, где она
  дублирует SettingsRow;
- выполняются typecheck, ESLint, Prettier и production-сборки UI kit и web.

## Почему так

**Композиция вместо наследования.** React-компоненты в этом проекте являются функциями; наследование
не даёт полезного переиспользования и усложняет публичный API. `SettingsEntityRow` повторно использует
проверенную механику `SettingsRow`, добавляя только предметно-нейтральные слоты.

**Не расширять `ListRow`.** `ListRow` задаёт семантику и геометрию обычного списка. Его использование
в Settings уже признано причиной визуального расхождения; изменение его глобальных стилей затронуло
бы файл-пикер, навигацию и другие списки вне настроек.

**Не добавлять отдельные entity-компоненты для Projects и Plugins.** Они снова разошлись бы по
геометрии и нарушили бы контракт UI kit. Различия между сущностями должны оставаться только в
данных и содержимом слотов.
