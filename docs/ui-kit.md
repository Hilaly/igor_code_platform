# UI-кит и оболочка

Что лежит в `packages/ui-kit` и как из него собрана оболочка `apps/web`. Модель расширения — кто куда
вкладывается — описана отдельно, в [ui-extension-model.md](ui-extension-model.md); здесь про сам кит.

Кит — публичный контракт наравне с SDK ([public-contract.md](public-contract.md)). Наш интерфейс
строится только из него: компонент, сделанный «на месте» в `apps/web`, немедленно становится тем, что
плагин воспроизвести не может.

## Цвета: палитра и роли

Два слоя: палитра и роли.

**Палитра** — пятнадцать базовых значений на вариант, `src/tokens/palette.ts`. Это замороженная часть
контракта: добавление ключа ломает все существующие схемы.

| Ключ            | Что это                                                               |
| --------------- | --------------------------------------------------------------------- |
| `surface`       | фон страницы                                                          |
| `surfaceRaised` | поднятая поверхность: панели, карточки, всплывающие слои              |
| `surfaceSunken` | утопленная поверхность: полосы списков, поля ввода                    |
| `border`        | линии: границы панелей, разделители                                   |
| `ink`           | основной текст                                                        |
| `inkMuted`      | второстепенный текст: подписи, единицы, пояснения                     |
| `accent`        | акцент: выделенное действие, фокус, выбранная строка                  |
| `accentInk`     | текст поверх акцента                                                  |
| `secondary`     | второй акцент: градиенты, волосяные линии, надзаголовки — не действие |
| `danger`        | опасность: удаление, отказ, упавший плагин                            |
| `dangerInk`     | текст поверх опасности                                                |
| `warning`       | предупреждение: работает, но не так, как задумано                     |
| `success`       | успех: доехало, поднялось, применилось                                |
| `overlay`       | затемнение под модальным слоем; значение с прозрачностью              |
| `shadow`        | цвет тени; значение с прозрачностью                                   |

**Роли** — сорок один семантический токен, `src/tokens/roles.ts`; их читают компоненты. Кит выводит
роли из палитры, поэтому роль добавляется без правки схем. Роль становится CSS-переменной на корне
документа: `accentHover` → `--sovereign-accent-hover`.

Группы: поверхности (`pageSurface`, `panelSurface`, `sunkenSurface`, `fillSurface`,
`fillSurfaceStrong`), линии (`border`, `borderStrong`, `borderSubtle`), текст (`text`, `textMuted`,
`textSubtle`, `textOnAccent`, `textOnDanger`), акцент (`accent`, `accentHover`, `accentStrong`,
`accentSurface`, `accentBorder`, `accentText`, `focusRing`), контролы (`controlSurface`,
`controlSurfaceHover`), второй акцент (`secondary`), состояния и слои (см. ниже).

Оттенки состояний палитрой не задаются, а считаются от неё через `color-mix` одним правилом:
**состояние двигает цвет к тексту.** В светлом варианте это темнее, в тёмном — светлее, и автору схемы
не приходится объявлять по три оттенка на каждое действие. Правило живёт в четырёх помощниках:

- `towardsInk(цвет, доля)` — то самое движение к тексту: 8% на наведение, 18% на нажатое состояние и
  дальний конец акцентного градиента, 6% и 12% на нейтральные заливки внутри панели;
- `softSurface(цвет)` — заливка состояния: 14% цвета в поднятой поверхности, чтобы на ней читался
  текст;
- `softBorder(цвет)` — граница заливки: тот же цвет прозрачностью, поэтому ложится на любую
  поверхность под ней;
- `readableText(цвет)` — цветная надпись, уведённая к основному тексту на 22%: чистый `warning` на
  светлой поверхности не читается.

Каждое состояние выведено по одному шаблону — `<состояние>`, `<состояние>Surface`,
`<состояние>Border`, `<состояние>Text` — и состояний четыре: `danger`, `warning`, `success`, `info`.
У «к сведению» своего значения в палитре нет вовсе: это акцент, сведённый к второстепенному тексту
(55/45). Отдельно стоят `overlay` и `shadow` — они приходят из палитры как есть.

Все восемнадцать имён ролей, существовавших до переноса визуала, сохранены: механизма псевдонимов в
коде нет, значит переименовывать нечем.

### Как объявляется схема

```ts
export const midnight: ColorScheme = {
  id: "midnight",
  tokenContract: 2, // мажор контракта токенов; несовпадение — внятный отказ, а не чужие цвета
  variants: { light: { surface: "#f7f8fa" /* … */ }, dark: {/* … */} },
  // Точечное переопределение роли объявляется явно: схема после этого хрупка — переименование роли
  // в ките до неё дойдёт, а вывод из палитры уже нет.
  roleOverrides: { accentHover: "#123456" },
};
```

`tokenContractMajor` сейчас **2**: он поднялся с единицы одной правкой за оба новых ключа палитры —
`secondary` и `shadow` (см. «Почему так»).

`resolveScheme(scheme, variant)` возвращает роли и диагностику: переопределение названо в диагностике
каждый раз, незнакомая роль игнорируется с диагностикой (схему могли написать для более новой версии
кита), чужой мажор — отказ целиком. `applyRoles(roles, target)` пишет переменные; цель приходит
параметром, поэтому применение проверяется без DOM.

Светлая и тёмная — варианты внутри схемы, а не две схемы; «системный» выбор — это выбор одного из двух
по `prefers-color-scheme`.

### Схемы в поставке

Девять, `src/tokens/schemes/`. Список объявлен китом — `shippedSchemes` — а не приложением: тот же
список нужен тесту контраста, каталогу компонентов и вью внешнего вида, и три копии перечисления
разошлись бы на первой добавке. Порядок в массиве — порядок в выпадающем списке.

- **`base`** — встроенная. Она есть всегда: заменить её нечем, и на неё же откатывается интерфейс,
  если названная схема исчезла вместе с выключенным плагином.
- **`imperium`** — пурпур и золото на тёплой бумаге; единственная тема, где второй акцент в деле.
- **`neutral`** — ахроматические поверхности, единственный цвет — акцент.
- **`nord`** — приглушённая арктическая гамма, низкая насыщенность во всех ролях.
- **`obsidian`** — почти монохром: акцент это тёплый графит, цвет остаётся только у состояний.
- **`terminal`** — Tokyo Night: холодный синий на графите, самая тёмная из перенесённых.
- **`oled`** — супертёмный чистый чёрный `#000000` для OLED-экранов с неоновым цианом и маджентой.
- **`sage`** — природные шалфейно-зелёные и терракотовые тона.
- **`check`** — проверочная, с нарочно дикими значениями палитры. На ней участок, покрашенный мимо
  токена, виден с первого взгляда. Дикая по цветам, но читаемая: контраст текста к поверхности в ней
  такой же обязательный, иначе ей не пользуются, и смысл проверки теряется.

Пять средних перенесены из кита предыдущего захода на проект ([roadmap.md](roadmap.md), срез 5) и при
переносе **конвертированы в данные**: у источника схема была CSS-файлом на тему, у нас схема —
объявление, иначе её не сможет принести плагин.

### Чем держится дисциплина цвета

- **Линтер** запрещает цветовые литералы в `packages/ui-kit/**` и `apps/web/**`, кроме
  `src/tokens/**` ([eslint.config.js](../eslint.config.js)).
- **Тест кита** `src/styles/styles.test.ts` обходит дерево пакета и проверяет каждый найденный `.css`:
  нет цветовых литералов (включая именованные цвета: `transparent` и `currentColor` — не цвета, а
  указания); каждая использованная переменная — либо роль, которую выводит кит, либо токен, который
  кит объявляет сам; нет объявленного токена без потребителя, а потребитель за пределами кита
  назван поимённо в списке `usedOutsideTheKit`; у каждого поставляемого примитива есть свой
  `*.module.css`. За CSS линтер не следит, а цвет там завести проще всего.
- **Тест оболочки** `apps/web/src/shell/styles.test.ts` требует того же от `shell.css` — цвет ролью,
  размер шкалой кита — и вдобавок запрещает оболочке селекторы `.sv-`: в имена классов кита снаружи
  не лезут.
- **Проверочная схема** ловит остальное — то, что попало в интерфейс не строкой в коде.
- **Тест контраста** проверяет текстовые пары на **каждой** поставляемой схеме в оба варианта, порог
  4.5 к 1: вывод ролей — наша ответственность, значит читаемость обязана сохраняться при любой
  палитре. Отдельная проверка следит, что между парами и списком «не текст» покрыта вся палитра, —
  новый ключ не проскочит мимо контраста молча.

### Переименование роли

Прежнее имя остаётся псевдонимом нового и даёт диагностику, псевдоним выбывает через один мажор кита.
Механизма псевдонимов в коде пока нет: он появится вместе с первым переименованием —
заводить его на пустом наборе значило бы написать его вслепую.

## Нецветовые токены и масштаб интерфейса

Цветовая схема — данные, приезжающие переменными на корень документа; шкалы одни на всю платформу и
от схемы не зависят. Поэтому они объявлены CSS-файлами в `src/styles/`, а не выводятся из палитры.

Точка входа одна — `src/styles/index.css`, приложение подключает её один раз
(`import "@sovereign/ui-kit/styles.css"`). Стили примитивов сюда не входят: они лежат рядом с
компонентами и приезжают вместе с импортом самого компонента. Порядок импортов внутри значим:

- **`scale.css`** — ось масштаба интерфейса. Три исходных токена: `--sovereign-font-size-base`,
  `--sovereign-space-unit`, `--sovereign-control-height-md`. Больше в файле нет ничего, и это главное
  свойство оси — всё остальное считается от них. Значения переключает атрибут `data-scale` со
  значениями `smaller`, `default` и `larger`; ставит его `applyScale(scale, root)`. Обычный масштаб
  пишется тем же атрибутом со значением `default` — CSS на него не реагирует, а снимать атрибут
  значило бы иметь два способа сказать «обычный». Отсутствие атрибута тоже даёт обычный масштаб,
  поэтому интерфейс не зависит от того, успело ли приложение прочитать предпочтения.
- **`tokens.css`** — типографика (три семейства, шесть кеглей, четыре начертания переменного шрифта,
  межстрочные и межбуквенные шкалы), скругления от `2xs` до `full`, шкала отступов
  `--sovereign-space-*` от `--sovereign-space-unit`, высоты контролов от средней, толщины линий,
  длительности и кривые, порядок слоёв (`z-overlay`, `z-modal`). Просьба обойтись без движения
  выполняется здесь один раз обнулением длительностей: иначе про неё обязан помнить каждый компонент,
  и первый забывший ломает обещание.
- **`effects.css`** — нецветовые по форме, цветные по содержанию: три уровня возвышения
  (приподнятый контрол, всплывающий слой, модальный), градиенты (акцентный, поверхностный, фоновая
  заливка страницы), свечение акцента, волосяная линия вторым акцентом и общий blur со стеклянной
  поверхностью для приподнятых слоёв. Собраны из ролей, поэтому переключаются вместе со схемой,
  ничего о ней не зная.
- **`reset.css`** — сброс и базовая типографика документа, кольцо фокуса на `:focus-visible`,
  выделение, полосы прокрутки. Живёт в ките, а не в оболочке: кегль, семейство и цвет текста — часть
  визуального слоя, и браузерный код плагина, рисующий свой DOM, обязан получить их же.

Шрифты подключены как зависимости и импортируются из `index.css`: **IBM Plex Sans** (текст),
**JetBrains Mono** (моно) и **Unbounded** (заголовки и акцентные надписи), все три —
`@fontsource-variable/`. Локальный демон не ходит на CDN, поэтому шрифт — файл в зависимостях, а не
ссылка.

## Локализация

Каталог адресуется парой «неймспейс и локаль», `src/i18n/`. Ядро владеет неймспейсом `core`, плагин —
своим, и плагин может поставить каталог **для нашего** неймспейса: так на платформе появляется новый
язык интерфейса.

```ts
const translator = createTranslator({
  locale: "ru",
  namespace: coreNamespace,
  catalogs: [coreEnglish, coreRussian, ...fromPlugins],
  onDiagnostic: (text) => diagnostics.record(text),
});

translator.t("appearance.variant.dark"); // «Тёмная»
translator.scope("tracker").t("title"); // строка плагина, в его неймспейсе
```

- Каталоги применяются по порядку и побеждают **по каждому сообщению отдельно**: каталог плагина
  заменяет одну нашу строку, а не весь набор.
- Отсутствующий перевод показывает английскую строку **и** порождает диагностику; повторы одного и
  того же сообщения подавляются — иначе одна дырка на каждом рендере превращает диагностику в поток.
- Ключа нет ни в одной локали — возвращается сам ключ и диагностика: интерфейс от этого не ломается.
- Множественная форма — отдельный ключ на категорию (`plugins.count.one`, `.few`, `.many`); какие
  категории есть в языке, знает `Intl.PluralRules`, а не мы.
- Числа и даты — `formatNumber` и `formatDate` через `Intl`, без внешних зависимостей.

Диагностика уходит колбэком, а не в журнал: журнал живёт в демоне и в браузер не отдаётся
([logging.md](logging.md)).

## Примитивы

`src/components/`, тридцать штук, и это **нестабильная часть контракта**: набор ломается свободно,
пока прикладной код не показал, какие примитивы нужны на самом деле.

Одиннадцать были до переноса визуала: текст и заголовок, кнопка, переключатель, выбор, значок
состояния, панель, список со строками, врезка для диагностики, раскрывающиеся подробности,
моноширинный блок со строчным кодом, пустое состояние с индикатором загрузки.

Подробности раскрывает браузер — `<details>`/`<summary>`, а не состояние React: развёрнутое находится
поиском по странице и работает без нашего кода. Моноширинный блок прокручивается и переносит строки
внутри себя: длинная причина отказа не имеет права растягивать страницу.

Девятнадцать добавлено в процессе полировки визуала и расширения платформы. Их публичная
поверхность переписана под наши соглашения: явные пропсы, `onChange` со значением вместо события,
строки только пропсами и уже переведёнными.

- **`Button`** — `tone`, `onClick`, `disabled`, `pressed`, `busy`, `title` и стандартные для
  интерактивного элемента `id`, `aria-label`, `aria-describedby`, `aria-expanded`,
  `aria-controls`, `aria-haspopup`, `onFocus`, `onBlur`, `onKeyDown`; `describedBy` сохранён как
  совместимое имя связи с описанием.
- **`Input` и `Textarea`** — `value`, `onChange(value)`, `placeholder`, `invalid`, `disabled`, `id`,
  `describedBy`; у поля ещё `type` (`text` | `password` | `search`), `role`, `ref`, обработчики
  клавиатуры и фокуса и атрибуты ARIA для составного контрола (`aria-expanded`, `aria-controls`,
  `aria-label`, `aria-autocomplete`, `aria-activedescendant`, `aria-haspopup`), у области — `rows`.
  Метки, подсказки и текста ошибки здесь нет: их даёт `Field`.
- **`Field`** — обвязка контрола: `label`, `hint`, `error`, `layout` (`stack` | `row`),
  `describedBy`. Контрол приходит рендер-пропом `children(control)` и получает готовые `id`,
  `describedBy`, `invalid`.
- **`Dialog`** — `open`, `onClose`, `title`, `description`, `variant` (`modal` | `drawer`),
  `dismissible`, `footer`, `children`. Рисуется порталом в `body`, фокус держит внутренний
  `useFocusTrap`. **`ConfirmDialog`** поверх него.
- **`Select`** — управляемый кастомный одиночный выбор: `value`, `options`, `onChange(value)`,
  `label`, `disabled`. Триггер — `role="combobox"`, открытый набор — `role="listbox"`; активный
  пункт связан через `aria-activedescendant`, выбранный — через `aria-selected`. Щелчок, `ArrowDown`,
  `Enter` или пробел открывают список; в открытом списке стрелки, `Home` и `End` двигают активный
  пункт, `Enter` или пробел выбирают его, `Escape` закрывает. Недоступные пункты остаются видимыми с
  `aria-disabled`, но пропускаются навигацией и не выбираются; отключённый контрол не принимает
  фокус, щелчок и клавиатуру. Недоступное текущее значение не считается выбранным и вместо него
  показано приглашение.
- **`Combobox`** — управляемый одиночный выбор с текстовым `Input`: `options`, `value`,
  `onChange(value)`, `placeholder`, `disabled`, `invalid`, `label`, `emptyText`. При вводе он
  открывается и фильтрует пункты регистронезависимым совпадением по `label`; закрытие сбрасывает
  запрос, а закрытое поле показывает подпись выбранного доступного пункта. Поле объявлено как
  `role="combobox"` с `aria-autocomplete="list"`, `aria-controls`, `aria-haspopup="listbox"` и
  `aria-activedescendant`; список — `role="listbox"`. `ArrowDown` открывает и двигает активный
  пункт, `ArrowUp`, `Home` и `End` работают в открытом списке, `Enter` выбирает активный доступный
  пункт, `Escape` закрывает. Недоступные пункты показываются с `aria-disabled`, фильтруются как
  обычные, но не активируются и не выбираются; отключённый нативный `Input` не принимает ввод,
  мышь и клавиатуру, а недоступное значение не показывается выбранным.
- **`MultiSelect`** — управляемый множественный выбор: `options`, `value`, `onChange(value[])`,
  `placeholder`, `disabled`, `invalid`, `label`. Это `role="combobox"` с теми же связями с
  `listbox`, а список дополнительно имеет `aria-multiselectable="true"`. `ArrowDown` открывает
  список, стрелки, `Home` и `End` перемещают активный доступный пункт, `Enter` и пробел добавляют
  или снимают его без закрытия, `Escape` закрывает. Выбранные доступные пункты показаны тегами;
  у каждой кнопки удаления есть имя `Удалить <подпись>`. Недоступные пункты видимы, но не выбираются,
  не попадают в теги и пропускаются клавиатурой; отключённый триггер имеет `aria-disabled` и не
  отвечает на ввод.
- **`SegmentedControl` и `RadioGroup`** — управляемые `radiogroup`: первый строит кнопки с
  `role="radio"` и `aria-checked`, второй — нативные `input[type="radio"]`; оба принимают
  `options`, `value`, `onChange(value)`, `label`, `disabled`, а `RadioGroup` ещё `name`. Недоступные
  варианты отключены нативно.
- **`Tabs`** — `tabs` (`id`, `label`, `disabled`, `content`), `value`, `onChange`, `label`.
- **`Tooltip`** — `content`, `side`, `children`. Целиком на CSS; клонирует единственный элемент-
  триггер, добавляя ему `aria-describedby` с идентификатором пузыря `role="tooltip"`.
- **`Menu`** — `label`, `trigger`, `items`. Пункты приходят данными; открытое меню забирает фокус на
  первый доступный пункт, стрелки пропускают недоступные, `Escape` и выбор пункта закрывают меню и
  возвращают фокус на триггер.
- **`Popover`** — `trigger`, `children`, `side`, `ariaLabel`; кнопка-триггер связывается с открытым
  слоем через `aria-expanded` и `aria-controls`, слой имеет `role="dialog"`. Закрывается повторным
  нажатием, `Escape` или щелчком вне него.
- **`Slider`** — управляемый нативный `input[type="range"]`: `value`, `onChange(value)`, `min`,
  `max`, `step`, `disabled`, `showValue`, `label`, `id`; передаёт `aria-label` и границы диапазона.
- **`Breadcrumbs`** — `nav` с подписанным `aria-label`, упорядоченными пунктами и
  `aria-current="page"` на последнем; предыдущие пункты — ссылки или кнопки.
- **`Accordion`** — `items`, `multiple`, `defaultExpandedIds`: кнопка каждого заголовка отражает
  состояние через `aria-expanded`; при `multiple=false` раскрытие следующего пункта закрывает
  предыдущий.
- **`Tree`** — `role="tree"` с `treeitem`, вложенными `group`, `aria-level`, `aria-expanded` и
  `aria-selected`; roving `tabIndex` переносит DOM-фокус. Стрелки ходят по видимым пунктам, вправо
  раскрывает узел или идёт к первому ребёнку, влево закрывает узел или идёт к родителю, `Enter` и
  пробел вызывают `onSelect(node)`.
- **`ToastContainer` / `ToastProvider` / `useToast`** — всплывающие системные уведомления.
  `ToastContainer` остаётся управляемым: получает `toasts` и `onDismiss(id)`. Обёртка
  `ToastProvider` рисует собственный стек, а `useToast()` возвращает `{ toast, dismiss }`:
  `toast({ title, tone, durationMs })` добавляет уведомление и возвращает его идентификатор,
  `dismiss(id)` убирает его раньше срока. По умолчанию уведомление закрывается через 4 секунды;
  `durationMs <= 0` отключает автоматическое закрытие. Хук вне `ToastProvider` бросает ошибку.
  Стек имеет `role="region"` и имя «Уведомления», каждое уведомление — `role="status"`, а его
  кнопка закрытия имеет доступное имя «Закрыть».
- **`Icon`** — унифицированный контейнер иконок с типовой размерной сеткой кита.
- **`Progress`** — `value` (0..1), `tone`, `label`.
- **`Skeleton`** — `variant` (`text` | `rect` | `circle`), `width`, `height`.

**`Modal` из чужого кита не переносился.** `Dialog` с вариантом `drawer` закрывает обе его роли, и
отдельный примитив был бы вторым способом делать то же самое.

Стили — **CSS Modules**: у каждого примитива свой `*.module.css` рядом с ним, тип импорта объявляет
`vite/client` в `types` пакета, отдельного `.d.ts` для этого не нужно. Следствие, которое надо
держать в голове: имена классов хешируются, поэтому селекторы извне в кит перестали работать —
договорённость «не цепляться за наши классы» стала механизмом. То же следствие обязательно и для
браузерных ассетов плагинов ([ui-extension-model.md](ui-extension-model.md)).

Строки приходят компонентам **уже переведёнными**: кит не знает, в каком неймспейсе лежит эта строка,
и переводить её за вызывающего не должен.

## Каталог компонентов

`packages/ui-kit/.ladle/`, запуск — `make catalog` (`ladle serve`). Каталог существует по одной
причине: примитив, перенесённый вперёд своего среза, до появления настоящего потребителя виден только
здесь.

Схему каталог применяет **тем же** способом, что и приложение: `resolveScheme` плюс `applyRoles` в
корень документа и `applyScale` там же. Второго пути применения темы у нас нет и быть не должно —
иначе каталог показывал бы не то, что покажет продукт. Переключатели схемы и масштаба стоят в
`Provider` (`.ladle/components.tsx`) и помнят выбор в `localStorage`: переход между историями — полная
перезагрузка страницы. Светлый и тёмный вариант берутся из собственного переключателя темы Ladle.

Истории — `src/components/primitives.stories.tsx` (примитивы с настоящим потребителем) и
`ported.stories.tsx` (примитивы, которые каталог пока демонстрирует вместо прикладного экрана).
В последних есть управляемые сценарии для `Combobox`, `MultiSelect`, `SegmentedControl`, `RadioGroup`,
`Popover`, `Slider`, `Breadcrumbs`, `Accordion`, `Tree` и `ToastProvider`/`useToast`: они показывают
выбор, недоступные варианты, клавиатурные модели, слои, и автоматическое либо ручное закрытие
уведомления. Строки в историях — литералы, и это единственное место в ките, где так можно: каталог
не поставляется пользователю.

## Оболочка

`apps/web/src/shell/`. Три области: левая панель (основная часть и низ), центральная страница, правая
панель с вкладками. Заменить оболочку плагин не может
([ui-extension-model.md](ui-extension-model.md)) — хост владеет границами, размерами и полосой
вкладок.

- **Низ левой панели** — связь с демоном: состояние потока и время работы. Видно всегда, потому что
  без демона интерфейс не делает ничего.
- **Правая панель** — вкладки «внешний вид» и «диагностика». Вкладка закрывается повторным нажатием,
  панель тогда сжимается до полосы.
- **Раскладка** — ширины панелей и открытая вкладка — живёт в `localStorage`: это уровень «раскладка
  хоста», делить его между машинами незачем. Испорченная запись не роняет оболочку, ширина вне
  пределов подтягивается обратно.
- **Границы панелей** тянутся мышью и стрелками с клавиатуры. Слушают они окно, а не сами себя: при
  протаскивании курсор с границы уходит.
- **Маршрутизатор** свой, `src/router.ts`: маршрутов ядра единицы, а неймспейс страниц плагина —
  `/p/<pluginId>/<pageId>/*` — задан моделью расширения. Внешняя библиотека станет вопросом вместе со
  вложенными маршрутами страниц плагинов.

Единственный CSS вне кита — `shell/shell.css`, геометрия хоста. Цвет в нём приезжает ролью, размер —
шкалой кита, иначе масштаб интерфейса двигал бы примитивы, а раскладку вокруг них нет.

Центральная страница разводится по адресам: `/` — заглушка, `/plugins` — вью управления плагинами,
`/p/<pluginId>/<pageId>/*` — страницы плагинов, которых пока нет.

## Вью управления плагинами

`apps/web/src/plugins/`, адрес `/plugins`. Живёт в ядре, как и остальные вью базовой поставки
([architecture.md](architecture.md)): выключить его нельзя, можно только переопределить плагином — и
тогда выключение этого плагина возвращает встроенное вью.

Панель на плагин: состояние значком, ключ, папка, причина отказа или падения, номер попытки
перезапуска, переключатель плагина и список вкладов с переключателем на каждом ([plugins.md](plugins.md)).
У вклада вида `event` схема нагрузки раскрывается по требованию. Отказанный до чтения манифеста
плагин — только чтение: писать предпочтения по ключу-папке некуда.

Что показывается отдельно, потому что иначе исчезло бы:

- **выключенный вклад** — помеченным в списке, а не отсутствующим;
- **запись о выключенном, но больше не объявленном вкладе** — она сохраняется, даже если вклад ушёл
  вместе с версией плагина;
- **спор равного ранга** и **отвергнутый вклад** — врезками: журнал живёт в терминале и в браузер не
  отдаётся ([logging.md](logging.md)).

Обновляется вью так: снимок `GET /api/plugins` спрашивается на каждом подъёме соединения, кадр
`core.plugin.lifecycle` заменяет строку плагина на месте (в нём и есть полный статус), а смена набора
вкладов и пропуск в потоке ведут к новому запросу снимка — в нём лежит то, чего в событии нет.
Запрос в полёте один: следующий отменяет предыдущий, поэтому ответы разойтись не могут. Записанное
решение показывается сразу, не дожидаясь событий, а отказ записи (`409`) — врезкой с причиной.

Правило применения кадров живёт отдельно от хука (`plugins/state.ts`), потому что проверяется тестом,
а не глазами: DOM-стека для компонентов по-прежнему нет ([backlog.md](backlog.md)).

Ре-рендер на кадр измерен: React сводит пачку кадров сам, и своего батчинга здесь нет
([runtime-checks.md](runtime-checks.md), проверка 25).

## Выбор темы, масштаба и языка

Источник истины — `preferences.json` ([data-directory.md](data-directory.md)), интерфейс читает и
пишет его через `/api/preferences` ([web-api.md](web-api.md)). Выбранное
дополнительно кешируется в браузере: ответ демона приходит позже первой отрисовки, и без кеша страница
мигала бы чужой темой.

`applyAppearance` (`apps/web/src/appearance.ts`) применяет всё сразу: масштаб — атрибутом, схему —
переменными. Масштаб ставится первым и независимо от схемы: отказ схемы не повод оставить кегль
чужим. Названной схемы может не оказаться — её приносил плагин, которого выключили, — и тогда
работает встроенная, с диагностикой. Масштаба может не оказаться в кеше, записанном платформой,
которая про него не знала: подставляется значение по умолчанию, а не выбрасывается весь кеш.

Правка файла руками доезжает до открытого браузера событием `core.preferences.changed` — тем же
путём, что и запись из интерфейса. Отказ записи (`409`, файл на диске правил кто-то ещё) показывается
врезкой: разобраться с этим может только человек.

Смена схемы стоит миллисекунды и не требует ре-рендера: меняются значения CSS-переменных, дерево React
не перестраивается ([runtime-checks.md](runtime-checks.md), проверка 24).

## Почему так

### Кит — отдельный публичный пакет, а не часть SDK

Браузерный UI плагина исполняется компонентом в realm хоста и стоит рядом с нашими элементами —
иногда вместо них ([ui-extension-model.md](ui-extension-model.md)). Значит плагину нужны те же
примитивы, из которых сделан наш интерфейс. Иначе каждый плагин приносит свой набор кнопок и полей, и
интерфейс расползается на глазах, хотя формально всё работает.

**Примитивы внутри `sdk`.** Один пакет вместо двух. Отвергнуто: любой плагин, даже без интерфейса,
получал бы React в зависимостях.

**Плагины используют что угодно.** Максимум свободы автору. Отвергнуто: интерфейс перестаёт быть
одним продуктом, а темы не работают вовсе — компонент со своим цветом не переключится вместе с
цветовой схемой.

**Взять внешнюю библиотеку компонентов и объявить контрактом её.** Меньше работы сейчас. Отвергнуто:
наш публичный контракт оказался бы привязан к чужому релизному циклу, и его ломающие изменения
становились бы нашими. Использовать внешнюю библиотеку **внутри** кита это не запрещает.

Владелец продукта сознательно принял и то, что первые недели работы дают не функциональность, а
фундамент: кит, дописываемый после прикладного кода, всегда отстаёт от него и превращается в свалку
вынесенных постфактум компонентов.

### Темы и локализация — данные, а не код

Перекрасить чужой компонент извне платформа не может: браузерный код плагина рисует свой DOM. Значит
переключение темы обязано работать через то, что компонент читает сам.

**Плагин поставляет свой CSS-файл как тему.** Проще всего. Отвергнуто: у платформы нет общего
словаря, плагин перекрашивает чужие элементы, а конфликт двух тем не разрешается никак.

**Только светлая и тёмная, без схем.** Не выполняет требование, и добавить схемы потом — это менять
контракт токенов, когда плагины на него уже опираются.

**Библиотека интернационализации с компиляцией сообщений.** Богаче `Intl`. Отвергнуто: зависимость
попадает в публичный контракт кита, а её возможности сверх `Intl` нам сейчас не нужны.

**Ключи на русском.** Расходится с правилом «код и идентификаторы на английском» и закрывает
платформу для внешних авторов.

Следствия: плагин может заменить язык интерфейса целиком, включая наши строки, — качество перевода
платформы может зависеть от плагина; переводы правятся без пересборки плагина, потому что каталоги —
данные; непереведённый ключ не ломает интерфейс, но обязан быть виден в диагностике, иначе
расхождение локалей копится молча.

### Два слоя токенов и политика устаревания

Кит пишется **до** прикладного кода, значит часть имён мы угадаем неправильно и захотим переименовать
именно тогда, когда контракт уже публичен.

**Один слой: схема задаёт значения всех ролевых токенов.** Проще на первый взгляд. Отвергнуто по
арифметике: ролей будут десятки и они будут появляться постоянно, а базовых значений единицы. При
одном слое каждое добавление роли ломает все существующие схемы. Перенос визуала это подтвердил:
ролей стало 41 против 18, а палитра выросла на два ключа.

**Только палитра, без точечных переопределений.** Контракт был бы совсем узким. Отвергнуто: автор
схемы не может поправить один неудачный оттенок, не переопределяя вывод целиком. Поэтому
переопределение разрешено, но объявляется в манифесте схемы явно — её хрупкость должна быть видна и
нам, и автору.

**Удалять устаревшие имена сразу.** Кит остаётся чистым. Отвергнуто: ломает чужие схемы без пути
миграции, а выигрыш только косметический.

**Полагаться на дисциплину вместо линтера.** Отвергнуто: цвет мимо токена не виден в ревью, потому
что на нашей схеме он выглядит правильно. Обнаруживает его пользователь чужой схемы.

Цена: замороженная поверхность — палитра; вывод ролей становится нашей ответственностью, поэтому
нужны проверки контраста, а не только совпадения имён; псевдонимы копятся, и срок в один мажор надо
соблюдать; нестабильная зона требует честности с двух сторон — если мы начнём относиться к ней как к
стабильной, плагины сломаются на первом переименовании, и виноваты будем мы.

### Палитра выросла на два ключа за один мажор

`secondary` назван владельцем продукта: на втором акценте держатся градиенты, волосяные линии и
надзаголовки, а вывести его из основного акцента нельзя — это другой цвет, а не другой его оттенок.

`shadow` владелец не называл, и он всё равно добавлен ключом, а не выведен из `overlay`. Причина:
светлой теме нужна **почти незаметная тень при вполне заметном затемнении**, и одним значением это
не выражается — любой множитель, дающий пригодную тень, испортит затемнение под модальным слоем.

**Второй мажор позже, отдельной правкой на каждый ключ.** Отвергнуто: пока все схемы наши, добавка
ключа стоит ноль; после среза 12 схему приносит плагин, и такая же добавка становится ломающим
изменением публичного контракта. Дешевле сделать оба ключа сразу и поднять мажор один раз.

### Перенесённые схемы конвертированы, а не скопированы

**Схема — данные, а не CSS-файл** (решение владельца продукта). У источника палитра была CSS-файлом
на тему; у нас это объявление в коде, потому что схему должен уметь принести плагин, а плагин
браузерного кода для схемы не пишет вовсе. Заодно значения из `oklch` переведены в hex: иначе их не
читает тест контраста.

**Верный перенос значений автора не проходил наш порог контраста почти нигде** — чужой кит контраст
не проверял вообще. Самый показательный случай: `nord`, светлый вариант, `warning` на `surface` —
1.35 к 1, жёлтый на белом не читается в принципе. Правка — корректор светлоты в OKLch с запасом к
порогу (целевые 4.6 при требуемых 4.5), оттенок и цветность сохранены; самое большое движение —
`nord` light `warning`: `#ebcb8b` → `#856525`.

**Снизить порог контраста.** Отвергнуто: порог существует ровно для того, чтобы схемы, которые нам
нравятся, не побеждали читаемость.

**Перенести схемы как есть и мириться с нечитаемым текстом.** Отвергнуто: тогда пять схем поставки
из семи заведомо непригодны для работы, а тест контраста пришлось бы ослабить или отключить — и он
перестал бы что-либо гарантировать и для наших собственных схем.

### CSS Modules вместо одного файла стилей

Решение владельца продукта. До переноса стили кита лежали одним растущим `src/styles.css`, и файл был
общим на всё: сломать чужой компонент правкой своего селектора можно было незаметно.

Что это даёт сверх соседства файла с компонентом: **имена классов хешируются**, и селектор снаружи по
внутренностям кита не работает вовсе. Раньше «не цепляйтесь за наши классы» было договорённостью, и
её нарушал сам `shell.css` (селекторы `.sv-`); теперь это механизм, а тест оболочки следит, чтобы
попытка не вернулась.

Цена: сборщик браузерных ассетов плагина обязан уметь CSS Modules, иначе у автора плагина нет дороги,
которая есть у нас ([ui-extension-model.md](ui-extension-model.md)).

### `Modal` не перенесён

В списке среза он был. В чужом ките это легаси-дубликат `Dialog`: без портала, без фокус-трапа, со
сырым `z-index` и ссылкой на несуществующий токен тени. Наш `Dialog` с вариантом `drawer` закрывает
обе его роли — вопрос по центру и длинный список у края.

**Перенести `Modal` рядом с `Dialog`.** Отвергнуто: это второй способ делать то же самое, причём
строго худший, и выбор между ними пришлось бы объяснять каждому, кто откроет кит.

### Каталог компонентов на Ladle

Восемь примитивов перенесены вперёд своих срезов: настоящий потребитель у них появится в срезах 6–10.
До тех пор проверить их нечем, кроме чтения кода, — а вид, клавиатура и поведение на семи схемах и
трёх масштабах чтением кода не проверяются.

**Обойтись без каталога и ждать потребителя.** Отвергнуто: примитив, ни разу не открытый в браузере,
приезжает в свой срез с дефектами, которые там будут выглядеть как дефекты среза. Каталог окупился на
первой же истории: `Field` понимал пустую строку в `error` как безымянный отказ, то есть красил пустую
форму в красное и вешал `aria-describedby` на пустой элемент. Ни тест разметки, ни линтер этого не
видели — вызывающий писал ровно то, что написал бы любой другой.

**Storybook.** Отвергнуто: тяжелее и со своей сборкой; Ladle работает на Vite, который у нас уже
есть. Цена в любом случае одна — dev-зависимость в ките, ещё один режим запуска и цель в `make`.

### Переход на шрифтовую гарнитуру Unbounded для заголовков

Для акцентных надписей и заголовков выведена variable-гарнитура **Unbounded** вместо Space Grotesk.

**Оставить Space Grotesk.** Отвергнуто: у заголовочных надписей не хватало премиальной выразительности и вариативности начертаний в футуристичной стилистике 2026 года. Unbounded даёт современную широкую геометрию букв и гладкий варьируемый диапазон плотности.

### Новые цветовые схемы `oled` и `sage`

Добавлены две флагманские схемы 2026 года: ультратёмная `oled` (`#000000` с цианово-маджентовым неоном) и органическая природная `sage` (шалфей и глиняная терракота).

**Ограничиться имеющимися 7 темами.** Отвергнуто: для энергоэффективных OLED-дисплеев у платформ 2026 года необходим чисто чёрный фон `#000000`, а в палитре не хватало успокаивающей экоестественной гаммы.

### Кастомные `Select`, `Combobox` и `MultiSelect` вместо нативного `<select>`

**Оставить нативный `<select>`.** Отвергнуто: нативный выпадающий элемент вызывает стандартное белое системное окно ОС, роняющее погружение в тёмных и эффектах стилей (стекломорфизм, блюр, градиенты). Кастомные выпадающие списки полностью адаптируются под токены активной схемы и поддерживают поиск, клавиатуру и выбор тегов.

Они сохраняют различия своих нативных моделей: `Select` выбирает один пункт из списка, `Combobox`
фильтрует доступный для выбора набор текстом, а `MultiSelect` меняет выбор без закрытия списка и
показывает выбранное отдельными тегами. Поэтому у всех трёх один паттерн `combobox`/`listbox`, но
только у множества есть `aria-multiselectable`, а только у поискового поля — `aria-autocomplete`.

**Один универсальный компонент с режимами.** Отвергнуто: режимы смешали бы несовместимые поверхности
и клавиатурные контракты, а вызывающий мог бы получить поиск или удаляемые теги там, где они не
уместны. Три небольших явно названных компонента проще проверить и описать.

### Уведомления через провайдер и хук

Состояние уведомлений принадлежит ближайшему `ToastProvider`: он выводит свой `ToastContainer`, а
потребитель вызывает `useToast().toast` или `dismiss`. Такому вызову не надо вручную передавать
стек через дерево приложения, а управляемый `ToastContainer` остаётся для случая, когда состоянием
владеет вызывающий. Автоматическое закрытие по умолчанию ограничивает шум; `durationMs <= 0` оставлен
для статуса, который требует явного подтверждения человеком.

**Глобальный singleton вне React.** Отвергнуто: он смешал бы независимые деревья React и сделал бы
невозможным локальный жизненный цикл провайдера в тесте или встроенном интерфейсе плагина.

### DOM-тесты сложных интерактивных компонентов

`@testing-library/react` и `jsdom` добавлены только в devDependencies `ui-kit`. Они исполняют реальный
React-рендер и события клавиатуры в изолированном `// @vitest-environment jsdom` тесте: так проверяются
`aria-activedescendant`, пропуск недоступных пунктов и фактическое перемещение DOM-фокуса в `Tree`.

**Оставить только серверный рендер и тесты чистой логики.** Отвергнуто: серверная разметка не меняет
состояние и не имеет фокуса, поэтому не ловит ошибку, при которой roving tabindex меняется, а фокус
остаётся на прежнем `treeitem`.

**Сделать jsdom глобальной средой Vitest.** Отвергнуто: большинство тестов кита проверяет чистые
данные и не нуждается в DOM; окружение выбрано на уровне одного тестового файла, чтобы не менять их
исполнение и стоимость запуска.
