# UI-кит и оболочка

Что лежит в `packages/ui-kit` и как из него собрана оболочка `apps/web`. Модель расширения — кто куда
вкладывается — описана отдельно, в [ui-extension-model.md](ui-extension-model.md); здесь про сам кит.

Кит — стабильный публичный контракт наравне с SDK ([public-contract.md](public-contract.md)). Он
отвечает за вид браузерного интерфейса: примитивы, токены, темы и локализацию. За взаимодействие UI
плагина с платформой отвечает отдельный `@sovereign/browser-sdk`; он не реэкспортирует кит и не
подменяет его визуальные примитивы. Наш интерфейс строится только из кита: компонент, сделанный «на
месте» в `apps/web`, немедленно становится тем, что плагин воспроизвести не может.

## Статус визуального языка

Внедрение [визуального языка Sovereign](superpowers/specs/2026-08-03-sovereign-visual-language-design.md)
завершено всеми четырьмя срезами: основание UI kit, оболочка и системные вью, агентская сессия,
выравнивание остальных страниц и общих состояний приложения. Это действующий контракт, а не
направление будущей полировки. После финального ревью исправлены контраст производных ролей,
служебные `select` каталога, типографика метаданных и семантика заголовка новой сессии; нестабильный
queue-тест и lint с существующим каталоговым build тоже приведены к воспроизводимому состоянию.

Автоматическая проверка после исправлений включает `pnpm -r test`, `pnpm -r typecheck`, неизменённый
`pnpm eslint .` при существующем `packages/ui-kit/build`, `pnpm prettier --check .`, production-build
Ladle, build web-приложения и `git diff --check`. Контраст вычисленных ролей проверяется отдельно на
всех четырёх схемах в светлом и тёмном вариантах и на фактических сочетаниях текста с поверхностью.

Предыдущий browser QA прошёл репрезентативную матрицу схем, масштабов и экранов и нашёл нечитаемые
тёмные `select` каталога. После исправления targeted browser QA повторён в реальном Ladle dark mode:
оба нативных контрола (`scheme` и `scale`) проверены в Imperium, Nord, OLED и Sage. Вычисленные цвет
текста, фон и граница приходят из семантических ролей и визуально читаемы; на каждом контроле отдельно
подтверждён двухпиксельный outline цвета `focusRing`. Дефект белого native background закрыт, новых
дефектов в этом проверенном каталожном срезе не обнаружено. Этот результат не расширяет исходный
coverage приложения: реальная LLM-сессия без настроенного провайдера по-прежнему не проверялась.

## Настройки плагинов

Раздел `/settings/plugins` показывает компактный список: ключ и имя плагина, состояние жизненного
цикла и число вкладов в первой строке справа, уменьшенный общий переключатель — во второй. Отдельного
действия «Открыть» нет: вся строка открывает detail, а переключатель остаётся независимым действием.
Сами вклады не раскрываются в списке, поэтому несколько плагинов не превращают страницу в длинный
повторяющийся реестр.

Деталь живёт по адресу `/settings/plugins/:pluginKey`. В ней доступны общий переключатель плагина,
lifecycle, источник, путь, номер попытки и ошибки регистрации, а ниже — отдельный переключатель каждого
вклада. Для вклада рядом с типом и техническим идентификатором есть раскрываемые технические данные
(схема нагрузки события, метаданные skill, параметры agent или payload custom). Сохранённое решение
для исчезнувшего вклада остаётся видимым отдельным уведомлением.

Ключ плагина кодируется как непрозрачный сегмент маршрута: двоеточия и точки переживают перезагрузку,
а список всегда остаётся каноническим `/settings/plugins`. Экран детали использует ту же левую
навигацию настроек и не открывает правую панель оболочки.

## Цвета: палитра и роли

Два слоя: палитра и роли.

**Палитра** — пятнадцать базовых значений на вариант, `src/tokens/palette.ts`. Это замороженная часть
контракта: добавление ключа ломает все существующие схемы.

| Ключ            | Что это                                                                   |
| --------------- | ------------------------------------------------------------------------- |
| `surface`       | фон страницы                                                              |
| `surfaceRaised` | поднятая поверхность: панели, карточки, всплывающие слои                  |
| `surfaceSunken` | утопленная поверхность: полосы списков, поля ввода                        |
| `border`        | линии: границы панелей, разделители                                       |
| `ink`           | основной текст                                                            |
| `inkMuted`      | второстепенный текст: подписи, единицы, пояснения                         |
| `accent`        | акцент: выделенное действие, фокус, выбранная строка                      |
| `accentInk`     | текст поверх акцента                                                      |
| `secondary`     | второй акцент: редкие ключевые действия, смысловые пометки и надзаголовки |
| `danger`        | опасность: удаление, отказ, упавший плагин                                |
| `dangerInk`     | текст поверх опасности                                                    |
| `warning`       | предупреждение: работает, но не так, как задумано                         |
| `success`       | успех: доехало, поднялось, применилось                                    |
| `overlay`       | затемнение под модальным слоем; значение с прозрачностью                  |
| `shadow`        | цвет тени; значение с прозрачностью                                       |

**Роли** — семантические токены `src/tokens/roles.ts`; их читают компоненты. Кит выводит
роли из палитры, поэтому роль добавляется без правки схем. Роль становится CSS-переменной на корне
документа: `accentHover` → `--sovereign-accent-hover`.

Группы: поверхности (`pageSurface`, `panelSurface`, `sunkenSurface`, `fillSurface`,
`fillSurfaceStrong`), линии (`border`, `borderStrong`, `borderSubtle`), текст (`text`, `textMuted`,
`textSubtle`, `textOnAccent`, `textOnSecondary`, `textOnDanger`), акцент (`accent`, `accentHover`, `accentStrong`,
`accentSurface`, `accentBorder`, `accentText`, `focusRing`), контролы (`controlSurface`,
`controlSurfaceHover`), второй акцент (`secondary`, `secondaryHover`, `secondaryStrong`,
`secondarySurface`, `secondaryBorder`, `secondaryText`), состояния и слои (см. ниже).

`textOnSecondary` выбирается из нейтральных foreground палитры по лучшему **худшему** контрасту на
`secondary`, `secondaryHover` и `secondaryStrong`. Перед измерением прозрачные цвета композятся в
том же порядке, что и кнопка: `pageSurface` → `panelSurface` → состояние → foreground. Если ни один
кандидат — либо явно переопределённый `textOnSecondary` — не держит 4.5 к 1 во всех трёх
состояниях, `resolveScheme` отвергает вариант целиком с диагностикой. `accentInk` напрямую не
переиспользуется: самостоятельный второй акцент может находиться на другой стороне шкалы яркости.

`focusRing` — один ink-biased цвет: 35% `accent` и 65% `ink`. Отдельная матрица нетекстового
контраста требует от него не меньше 3 к 1 на всех реальных соседних поверхностях: page, panel,
sunken, обеих fill, control/hover и мягких accent/secondary/danger/warning/success/info. Геометрия
контрола задаёт наружный offset там, где кольцо окружает сплошную заливку, поэтому второго цвета
кольца не требуется.

Оттенки состояний палитрой не задаются, а считаются от неё через `color-mix` одним правилом:
**состояние двигает цвет к тексту.** В светлом варианте это темнее, в тёмном — светлее, и автору схемы
не приходится объявлять по три оттенка на каждое действие. Правило живёт в четырёх помощниках:

- `towardsInk(цвет, доля)` — то самое движение к тексту: 8% на наведение, 18% на нажатое состояние,
  6% и 12% на нейтральные заливки внутри панели;
- `softSurface(цвет)` — заливка состояния: 14% цвета в поднятой поверхности, чтобы на ней читался
  текст;
- `softBorder(цвет)` — граница заливки: тот же цвет прозрачностью, поэтому ложится на любую
  поверхность под ней;
- `readableMuted` — второстепенный текст, сдвинутый к основному на 4%: этого достаточно, чтобы он
  сохранял порог и на утопленной поверхности поля; `textSubtle` использует тот же цвет, а третью
  ступень создают меньший кегль и контекст компонента, не потеря контраста;
- `readableText(цвет)` — цветная надпись, оставляющая 25% семантического цвета и берущая 75%
  основного текста: так она сохраняет характер состояния и читается даже внутри мягкой заливки.

Каждое состояние выведено по одному шаблону — `<состояние>`, `<состояние>Surface`,
`<состояние>Border`, `<состояние>Text` — и состояний четыре: `danger`, `warning`, `success`, `info`.
У «к сведению» своего значения в палитре нет вовсе: это акцент, сведённый к второстепенному тексту
(55/45). Отдельно стоят `overlay` и `shadow` — они приходят из палитры как есть.

Все восемнадцать имён ролей, существовавших до переноса визуала, сохранены: механизма псевдонимов в
коде нет, значит переименовывать нечем.

### Как объявляется схема

```ts
export const midnight: ColorScheme = {
  id: "midnight",
  tokenContract: 2, // мажор контракта токенов; несовпадение — внятный отказ, а не чужие цвета
  variants: { light: { surface: "#f7f8fa" /* … */ }, dark: {/* … */} },
  // Точечное переопределение роли объявляется явно: схема после этого хрупка — переименование роли
  // в ките до неё дойдёт, а вывод из палитры уже нет.
  roleOverrides: { accentHover: "#123456" },
};
```

`tokenContractMajor` сейчас **2**: он поднялся с единицы одной правкой за оба новых ключа палитры —
`secondary` и `shadow` (см. «Почему так»).

`resolveScheme(scheme, variant)` возвращает роли и диагностику: переопределение названо в диагностике
каждый раз, незнакомая роль игнорируется с диагностикой (схему могли написать для более новой версии
кита), чужой мажор — отказ целиком. Перед выводом ролей функция повторно проверяет выбранную палитру
и известные переопределения, а неожиданный отказ CSS-resolver превращает в `rejected`, не выпускает
исключение в React. `applyRoles(roles, target)` пишет переменные; цель приходит параметром, поэтому
применение проверяется без DOM.

Светлая и тёмная — варианты внутри схемы, а не две схемы; «системный» выбор — это выбор одного из двух
по `prefers-color-scheme`.

### Схемы в поставке

Четыре, `src/tokens/schemes/`. Список объявлен китом — `shippedSchemes` — а не приложением: тот же
список нужен тесту контраста, каталогу компонентов и вью внешнего вида, и три копии перечисления
разошлись бы на первой добавке. Порядок в массиве — порядок в выпадающем списке.

- **`imperium`** — встроенная и схема по умолчанию: пурпур и золото на тёплой бумаге; единственная
  тема, где второй акцент в деле. Тёмный вариант задаёт страницу `#100b09`, утопленную поверхность
  `#130e0c`, поднятую `#1f1814`, поверхность контрола `#261c18`, разделители `#2a221e` и `#362c27`,
  выбранные состояния `#3b2256` и `#482b68`, пурпур `#8e44ad` и золото `#c5a059`. Светлый вариант
  сохраняет поверхности `#e7dcc5`, `#f3ead8`, `#fffaf0` и границу `#d1bea0`. На Imperium
  откатывается интерфейс, если названная схема недоступна.
- **`nord`** — приглушённая арктическая гамма, низкая насыщенность во всех ролях.
- **`oled`** — супертёмный чистый чёрный `#000000` для OLED-экранов с неоновым цианом и маджентой.
- **`sage`** — природные шалфейно-зелёные и терракотовые тона.

Схемы объявлены данными, а не CSS-файлом на тему: благодаря этому тот же контракт доступен плагинам.

### Схема, приехавшая от плагина

Плагин объявляет **тот же документ** вкладом `contribute.colorScheme` ([plugins.md](plugins.md)).
Своего `id` у документа при этом нет: схему называет идентификатор вклада с неймспейсом плагина —
`themed.midnight`.

Проверка разделена надвое: **демон проверяет форму, кит проверяет контракт.** Демон принимает объект
с целым `tokenContract` и палитрами из строк — про палитру он не знает ничего, потому что `paletteKeys`
и `tokenContractMajor` принадлежат киту, а кит зависит от протокола, и обратная зависимость была бы
циклом. Значит схема с верной формой, но чужим мажором или неполной палитрой доезжает до браузера и
отвергается там, диагностикой, — не молча.

Разбирает документ `parseColorScheme(id, document)`: он и знает `paletteKeys`. Результат — либо
готовая `ColorScheme`, либо отказ с причиной. Обе палитры должны быть полными, а каждое обязательное
значение — разрешимым CSS-цветом; то же правило действует на переопределение известной роли.
Поддерживаются стандартные формы, которые понимает CSS-resolver: hex, современные и прежние
`rgb`/`hsl`, `oklch`, alpha и разрешимый `color-mix`. **Неполная или неразрешимая палитра
отвергается целиком**, а не достраивается умолчаниями. `deriveRoles` на плохом ключе собрал бы
сломанный `color-mix`, то есть интерфейс выглядел бы работающим и разбирался бы глазами. Мажор
контракта `parseColorScheme` не проверяет — это работа `resolveScheme`, и она одна на схемы поставки
и на чужие.

В список выбора попадает схема, прошедшая **обе** проверки: `pluginColorSchemes` разбирает документ
и затем разрешает **светлый и тёмный** варианты. Схема с чужим мажором, плохим контрастом или только
одной пригодной палитрой остаётся в диагностике, но не становится выбираемой. Иначе валидный светлый
вариант скрывал бы отказ тёмного до момента переключения темы и мог бы оборвать первый React-render.

Незнакомое имя роли в `roleOverrides` не отсеивается при разборе: `resolveScheme` игнорирует его с
диагностикой, потому что схему могли написать для более новой версии кита.

### Чем держится дисциплина цвета

- **Линтер** запрещает цветовые литералы в `packages/ui-kit/**` и `apps/web/**`, кроме
  `src/tokens/**` ([eslint.config.js](../eslint.config.js)).
- **Тест кита** `src/styles/styles.test.ts` обходит дерево пакета и проверяет каждый найденный `.css`:
  нет цветовых литералов (включая именованные цвета: `transparent` и `currentColor` — не цвета, а
  указания); каждая использованная переменная — либо роль, которую выводит кит, либо токен, который
  кит объявляет сам; нет объявленного токена без потребителя, а потребитель за пределами кита
  назван поимённо в списке `usedOutsideTheKit`; у каждого поставляемого примитива есть свой
  `*.module.css`. За CSS линтер не следит, а цвет там завести проще всего.
- **Тест оболочки** `apps/web/src/shell/styles.test.ts` требует того же от каждого `.css` в
  `apps/web/src` — цвет ролью, размер шкалой кита — и вдобавок запрещает приложению селекторы `.sv-`:
  в имена классов кита снаружи не лезут. Обходится дерево, а не названный файл: второй файл стилей
  появился вместе со вью входа, а дисциплина, которую надо распространять руками, — не дисциплина.
- **Тесты контраста** проверяют пары на **каждой** поставляемой схеме в оба варианта. Для текста
  порог 4.5 к 1: матрица включает вычисленные роли на фактически используемых page, panel, sunken,
  control, hover, fill, selected и state-поверхностях, включая `accentText` выбранной вкладки на
  `accentSurface`; прозрачная на 18% подпись `Notice` сначала композится с реальной заливкой.
  Заполненное secondary-действие отдельно проверяется после alpha-композиции во всех трёх
  состояниях. Для общего `focusRing` действует нетекстовый порог 3 к 1 на матрице соседних
  поверхностей. Ещё одна проверка следит, что между парами и списком «не текст» покрыта вся палитра,
  — новый ключ не проскочит мимо контраста молча.

### Переименование роли

Прежнее имя остаётся псевдонимом нового и даёт диагностику, псевдоним выбывает через один мажор кита.
Механизма псевдонимов в коде пока нет: он появится вместе с первым переименованием —
заводить его на пустом наборе значило бы написать его вслепую.

## Нецветовые токены и масштаб интерфейса

Цветовая схема — данные, приезжающие переменными на корень документа; шкалы одни на всю платформу и
от схемы не зависят. Поэтому они объявлены CSS-файлами в `src/styles/`, а не выводятся из палитры.

Точка входа одна — `src/styles/index.css`, приложение подключает её один раз
(`import "@sovereign/ui-kit/styles.css"`). Стили примитивов сюда не входят: они лежат рядом с
компонентами и приезжают вместе с импортом самого компонента. Порядок импортов внутри значим:

- **`scale.css`** — ось масштаба интерфейса. Три исходных токена: `--sovereign-font-size-base`,
  `--sovereign-space-unit`, `--sovereign-control-height-md`. Больше в файле нет ничего, и это главное
  свойство оси — всё остальное считается от них. Значения переключает атрибут `data-scale` со
  значениями `smaller`, `default` и `larger`; ставит его `applyScale(scale, root)`. Обычный масштаб
  пишется тем же атрибутом со значением `default` — CSS на него не реагирует, а снимать атрибут
  значило бы иметь два способа сказать «обычный». Отсутствие атрибута тоже даёт обычный масштаб,
  поэтому интерфейс не зависит от того, успело ли приложение прочитать предпочтения.
- **`tokens.css`** — типографика (три семейства, шесть кеглей, четыре начертания переменного шрифта,
  межстрочные и межбуквенные шкалы), скругления от `2xs` до `full`, шкала отступов
  `--sovereign-space-*` от `--sovereign-space-unit`, высоты контролов от средней, толщины линий,
  длительности и кривые, порядок слоёв (`z-overlay`, `z-modal`). Контекстная плотность выражена
  `--sovereign-row-height-compact` для навигационных строк, `--sovereign-reading-width` для
  связного текста и `--sovereign-line-height-reading` для его ритма; масштаб меняет композицию
  равномерно, но не стирает эту разницу. Просьба обойтись без движения выполняется здесь один раз
  обнулением длительностей: иначе про неё обязан помнить каждый компонент, и первый забывший ломает
  обещание.
- **`effects.css`** — три сдержанных уровня возвышения: приподнятый контрол, всплывающий слой и
  модальный. Это только нейтральная тень из роли `shadow`; фон остаётся семантической поверхностью.
  Градиентов, свечения, стекла, `backdrop-filter` и декоративных волосяных линий в системе нет.
  Тени собраны из ролей, поэтому переключаются вместе со схемой, ничего о ней не зная.
- **`reset.css`** — сброс и базовая типографика документа, кольцо фокуса на `:focus-visible`,
  выделение, полосы прокрутки. Живёт в ките, а не в оболочке: кегль, семейство и цвет текста — часть
  визуального слоя, и браузерный код плагина, рисующий свой DOM, обязан получить их же.

Шрифты подключены как зависимости и импортируются из `index.css`: **Source Serif 4** — голос и
смысловой слой (`display`), **Onest** — язык управления (`body`), **IBM Plex Mono** — технический
регистр (`mono`). Source Serif 4 и Onest приезжают variable-пакетами Fontsource; для IBM Plex Mono
у Fontsource нет variable-пакета, поэтому кит поставляет статические начертания 400 и 500. Локальный
демон не ходит на CDN, поэтому шрифт — файл в зависимостях, а не ссылка.

### Способ ввода

Приложение один раз вызывает публичный `trackInputModality(document)` до первого React-render. Кит
слушает `pointerdown` и `keydown` в capture-фазе и пишет на корень документа
`data-sovereign-input-modality="pointer" | "keyboard"`; функция возвращает снятие слушателей для HMR
и тестов. Hover-reveal элементы используют два независимых условия: обычный `:hover` для указателя и
`:focus-within` или `:focus` только под корневым атрибутом `keyboard`. Это правило относится и к
прикладным reveal-переопределениям поверх примитивов кита, например к полному пути в строке проекта.
Поэтому нативный focus, который кнопка сохраняет после мышиного click, не удерживает tooltip или
action-rail после hover-out, а переход по `Tab` по-прежнему раскрывает тот же интерфейс без мыши.

### Единый контракт tooltip

Все hover/focus-подсказки в приложении и встроенных вкладах используют публичный `Tooltip` из
`@sovereign/ui-kit`. Прикладной код не создаёт собственные tooltip-обёртки, portal-позиционирование,
React-состояние для показа или ручные `onMouseEnter`/`onFocus`-обработчики. Общий примитив остаётся
источником истины для idle-скрытия, hover и keyboard-focus с учётом `input-modality`,
`aria-describedby`, `role="tooltip"`, неперехвата указателя и сжатия trigger-обёртки в узких flex-
контейнерах.

`Tooltip.content` принимает строку или структурированный `ReactNode`, если подсказке нужны несколько
статических секций или разделитель. Структура передаётся внутрь существующего пузыря и не меняет его
триггер, позиционирование или правила показа. Интерактивные действия и самостоятельные меню в tooltip
не помещаются: для них используется `Menu`, `Popover` или другой соответствующий примитив UI-кита.

## Локализация

Каталог адресуется парой «неймспейс и локаль», `src/i18n/`. Ядро владеет неймспейсом `core`, плагин —
своим, и плагин может поставить каталог **для нашего** неймспейса: так на платформе появляется новый
язык интерфейса.

```ts
const translator = createTranslator({
  locale: "ru",
  namespace: coreNamespace,
  catalogs: [coreEnglish, coreRussian, ...fromPlugins],
  onDiagnostic: (text) => diagnostics.record(text),
});

translator.t("appearance.variant.dark"); // «Тёмная»
translator.scope("tracker").t("title"); // строка плагина, в его неймспейсе
```

- Каталоги применяются по порядку и побеждают **по каждому сообщению отдельно**: каталог плагина
  заменяет одну нашу строку, а не весь набор.
- Отсутствующий перевод показывает английскую строку **и** порождает диагностику; повторы одного и
  того же сообщения подавляются — иначе одна дырка на каждом рендере превращает диагностику в поток.
- Ключа нет ни в одной локали — возвращается сам ключ и диагностика: интерфейс от этого не ломается.
- `scope(namespace).optional(key)` — перевод, которого может законно не быть: у плагина есть право не
  переводить название своего вклада, и `t` на таком ключе вернул бы сам ключ и записал ложную
  диагностику о дырке в переводе. Дырку в **одной** локали `optional` при этом видит по-прежнему:
  есть базовая строка, нет перевода — диагностика будет, иначе молчание скрыло бы настоящее
  расхождение каталогов.
- Множественная форма — отдельный ключ на категорию (`plugins.count.one`, `.few`, `.many`); какие
  категории есть в языке, знает `Intl.PluralRules`, а не мы.
- Числа и даты — `formatNumber` и `formatDate` через `Intl`, без внешних зависимостей.

Диагностика уходит колбэком, а не в журнал: журнал живёт в демоне и в браузер не отдаётся
([logging.md](logging.md)).

### Каталог, приехавший от плагина

Плагин объявляет **ту же пару** вкладом `contribute.localeCatalog` ([plugins.md](plugins.md)):
неймспейс, тег локали и сообщения. Как и схема, каталог — данные, и браузерного кода плагину для него
не нужно.

Неймспейс — `core` либо идентификатор самого плагина; чужой демон не принимает. Тег локали
канонизируется при регистрации (`pt-br` → `pt-BR`), чтобы один язык не дал в выборе две
неразличимые строки, а пустой каталог отвергается: для `core` он добавил бы язык без единой
переведённой строки.

`coreNamespace` объявлен в протоколе (`coreCatalogNamespace`) и лишь реэкспортируется китом: решение о
неймспейсе принимает демон, а два объявления одной строки разошлись бы на первой правке.

**Выбор языка считается только по каталогам неймспейса `core`** (`availableLocales` в
`apps/web/src/catalogs.ts`). Каталог плагина в своём неймспейсе переводит строки самого плагина и
языка платформе не добавляет: выбрав его, человек получил бы английский интерфейс с парой
переведённых строк в одной карточке.

**Каталог выключили — что видит человек.** Строки откатываются на английские, каждая с диагностикой;
`preferences.locale` при этом продолжает называть исчезнувший язык и **не переписывается** — по той же
причине, что и выбранная схема пропавшего плагина. Побочное следствие: `Intl` на этот тег работает
по-прежнему, поэтому даты, числа и множественные формы остаются локализованными, а сами строки —
английскими. Это допустимо и сказано здесь намеренно: найденное потом, такое поведение выглядит багом.

## Примитивы

Текущая поверхность `src/components/`, экспортированная из `src/index.ts`, стабильна и меняется по
общему правилу публичного контракта. Актуальный перечень задают экспорты, а не продублированный здесь
счётчик.

Одиннадцать были до переноса визуала: текст и заголовок, кнопка, переключатель, выбор, значок
состояния, панель, список со строками, врезка для диагностики, раскрывающиеся подробности,
моноширинный блок со строчным кодом, пустое состояние с индикатором загрузки.

Подробности раскрывает браузер — `<details>`/`<summary>`, а не состояние React: развёрнутое находится
поиском по странице и работает без нашего кода. Моноширинный блок прокручивается и переносит строки
внутри себя: длинная причина отказа не имеет права растягивать страницу.

Остальные добавлены в процессе полировки визуала и расширения платформы. Их публичная
поверхность переписана под наши соглашения: явные пропсы, `onChange` со значением вместо события,
строки только пропсами и уже переведёнными.

- **`RaisedSurface`** — `children`. Общая компактная поднятая поверхность: один сильный контур,
  умеренный радиус, фон `panelSurface`, первый уровень возвышения и внутренний отступ. Предметной
  семантики и раскладки у неё нет: вызывающий решает, что это композер, панель действий или другая
  самостоятельная область, и размещает поверхность снаружи. Так приложение не повторяет
  визуальные свойства кита в прикладном CSS.
- **`DurationTimer`** — `totalSeconds`, `labels` (`days`, `hours`, `minutes`, `seconds`) и
  `accessibleLabel`. Плоский цифровой таймер раскладывает длительность на дни и часы `HH : MM : SS`,
  скрывает нулевую группу дней, дополняет разряды часов нулями и сохраняет полное локализованное
  значение доступным именем статической группы без `aria-live`. Короткие подписи единиц приходят из
  каталога (`duration.*.short`), чтобы компактная геометрия не зависела от языка. Доступное имя
  цифрового таймера строит `formatFullUptime`: в отличие от компактного текстового `formatUptime`,
  оно сохраняет секунды и после часа, поэтому имя меняется вместе с видимым значением.
- **`ViewHeader`** — `title`, необязательные `context`, `level` (`1` | `2` | `3`, по умолчанию `1`)
  и `actions`. Контекст показывается рядом с заголовком, а при нехватке места визуально усекается;
  полный текст доступен через атрибут `title`. Контейнерная, а не page-only шапка: даёт семантический
  `header` с заголовком и местом для действий вызывающего, переносит их на узкой ширине и не знает,
  какой именно view она венчает.
- **`AppearancePreview`** — публичный role-based preview выбранного внешнего вида. Принимает
  `title`, полное доступное `label`, видимые `scheme`, `variant`, `scale` и массив `swatches`, чья
  роль закрыта набором `surface` | `accent` | `secondary` | `text`. Компонент отдаёт именованный
  `region` с `aria-live="polite"`, поэтому управляемое изменение настроек объявляется без отдельной
  логики приложения. Цвета свотчей берутся только из семантических ролей; литералы схемы и
  дублирование палитры в CSS приложения запрещены.
- **`Button`** — `type` (`button` | `submit`, по умолчанию `button`), `tone`, `size` (`md` | `sm`),
  `iconOnly`, `onClick`, `disabled`, `pressed`, `busy`,
  `title` и стандартные для интерактивного элемента `id`, `aria-label`, `aria-describedby`,
  `aria-expanded`, `aria-controls`, `aria-haspopup`, `onFocus`, `onBlur`, `onKeyDown`; `describedBy`
  сохранён как совместимое имя связи с описанием. `size="sm"` — для тесных мест (шапка панели); `iconOnly`
  делает кнопку квадратной без боковых отступов, а контент отцентрованным — это кнопка-значок, и
  видимого текста у неё нет, поэтому имя обязан дать `aria-label`, а подсказку — `title`.
- **`List` и `ListRow`** — семантический список и его строка. `ListRow` принимает `selected`,
  `disabled`, `onSelect`, `onDoubleClick`, `actions` и `describedBy`: при наличии `onSelect` строка
  становится кнопкой и получает `aria-describedby`, а `disabled` сохраняет эту кнопку видимой, но
  недоступной для фокуса и выбора. Действия остаются рядом, не вкладывая кнопку в кнопку.
- **`SettingsEntityRow`** — кликабельная строка сущности поверх `SettingsRow`: `label` и
  `description` образуют левую часть, `meta` и `actions` — общий правый rail. `onSelect` и
  `selectLabel` обязательны, `describedBy` связывает полноразмерную цель с дополнительным
  описанием. Вложенные controls остаются поверх цели строки и выполняют собственные действия, не
  запуская переход. Геометрия, типографика, разделители, hover/focus и узкая раскладка полностью
  принадлежат UI kit; Projects, Plugins и Providers передают только предметное содержимое слотов.
- **`Tooltip`** — `content` (`string | ReactNode`), `side`, необязательный явный `id`, `hoverOnly` и `children`. Явный `id` связывает
  подсказку с фокусируемым предком триггера; без него компонент создаёт идентификатор сам. Пузырь
  показывается по hover и по фокусу только при корневой keyboard-modality: обычный фокус после
  указательного клика не удерживает его после hover-out.
- **`Input` и `Textarea`** — `value`, `onChange(value)`, `placeholder`, `invalid`, `disabled`, `id`,
  `describedBy`; у поля ещё `type` (`text` | `password` | `search`), `autoComplete`
  (`off` | `username` | `current-password` | `new-password`), `role`, `ref`, `readOnly`, обработчики
  клавиатуры и фокуса и атрибуты ARIA для составного контрола (`aria-expanded`, `aria-controls`,
  `aria-label`, `aria-autocomplete`, `aria-activedescendant`, `aria-haspopup`), у области — `rows`,
  `ref`, `aria-label`, `onKeyDown`, `autoGrow`, `maxRows` и `onSubmit`. Последние три сделали из
  области ввод чата: поле тянется под содержимое до `maxRows` строк и дальше прокручивается внутри
  себя, `Enter` отправляет, `Shift+Enter` переводит строку. Пустое сообщение и `Enter` посреди
  набора символа методом ввода (`isComposing`) отправкой не считаются: первое потратило бы
  обращение к модели впустую, второе подтверждает вариант иероглифа. Предел роста задаётся строками
  через `--textarea-max-rows` и считается в CSS в единицах `lh` — межстрочный интервал объявлен там
  же и едет вместе с масштабом интерфейса, а повторённое в JS число разошлось бы с ним.
  Метки, подсказки и текста ошибки здесь нет: их даёт `Field`. Список значений `autoComplete` закрыт,
  а не свободная строка: значений в стандарте десятки, и опечатка в строке видна только в чужом
  браузере. По умолчанию атрибут не ставится — браузер угадывает сам, а назвать роль поля должен тот,
  кто знает форму целиком, иначе менеджер паролей предложит текущий пароль там, где просят новый.
- **`Field`** — обвязка контрола: `label`, `hint`, `error`, `layout` (`stack` | `row`),
  `describedBy`. Контрол приходит рендер-пропом `children(control)` и получает готовые `id`,
  `describedBy`, `invalid`.
- **`FilePicker`** — проводник файловой системы в модальном слое: `open`, `cwd`, `value`,
  `entries` (`{name, kind: "file" | "directory"}`), `error`, `onNavigate`, `onValueChange`,
  `onSelect`, `onClose` и строки-пропы (`title`, `upLabel`, `emptyLabel`, `confirmLabel`,
  `cancelLabel`). Собран из `Dialog` + `List`/`ListRow` + `Button`. **Не знает про файловую
  систему**: листинг приходит пропом, пикер только рисует его и сообщает клики — так плагин соберёт
  такой же, а тест кита не требует диска. Три жеста не сводятся в один: одинарный клик выбирает
  кандидата (`onValueChange`), двойной клик по папке переходит в неё (`onNavigate`), «Выбрать»
  подтверждает кандидата (`onSelect`) и закрывает пикер.
- **`Form`** — `onSubmit`, `children`, необязательные `label`, `disabled`. Перехватывает сабмит и
  зовёт `onSubmit`, не перезагружая страницу; `disabled` не даёт вызвать колбэк. `label` попадает в
  `aria-label` нативной формы: вызывающий знает её назначение и может отличить несколько
  самостоятельных действий для скринридера. Нужна там, где Enter в поле подтверждает действие, а
  писать `onKeyDown` в каждый `Input` — то же самое по-другому. Геометрии своей нет (`display:
contents`): раскладку задаёт внутренний контейнер вызывающего. Класс не принимается: как у всех
  примитивов, имя модуля хешируется.
- **`Dialog`** — `open`, `onClose`, `title`, `description`, `variant` (`modal` | `drawer`),
  `dismissible`, `footer`, `children`. Рисуется порталом в `body`, фокус держит внутренний
  `useFocusTrap`. **`ConfirmDialog`** поверх него.
- **Портальный всплывающий слой** — внутренняя общая геометрия `Select`, `Combobox`, `MultiSelect`,
  `Popover`/`ModelPicker`, `Menu` и контекстной карточки `Tree`. Открытая поверхность рендерится в
  `ownerDocument.body` через portal, позиционируется относительно trigger через `position: fixed`,
  переворачивается на противоположную сторону при нехватке места и зажимается внутри viewport с
  отступом 8 px. Слой не владеет ролями, выбором, клавиатурой или фокусом: эти контракты остаются у
  предметных компонентов. Outside click проверяет раздельные DOM-деревья trigger и popup.
- **`Select`** — управляемый кастомный одиночный выбор: `value`, `options`, `onChange(value)`,
  `label`, `placeholder`, `disabled`. `placeholder` обязателен и значения по умолчанию не имеет —
  как и `placeholder` с `emptyText` у `Combobox`, `placeholder` у `MultiSelect` и `label` с
  `toggleLabel` у `Tree`: строка, зашитая в кит, приезжает на чужом языке, и первым же местом, где
  это стало видно, оказался английский интерфейс с русским «Выберите...» в трёх полях подряд.
  Обязательный проп делает забывчивость отказом сборки, а не находкой на скриншоте. Триггер — `role="combobox"`, открытый набор — `role="listbox"`; активный
  пункт связан через `aria-activedescendant`, выбранный — через `aria-selected`. Щелчок, `ArrowDown`,
  `Enter` или пробел открывают список; в открытом списке стрелки, `Home` и `End` двигают активный
  пункт, `Enter` или пробел выбирают его, `Escape` закрывает. Недоступные пункты остаются видимыми с
  `aria-disabled`, но пропускаются навигацией и не выбираются; отключённый контрол не принимает
  фокус, щелчок и клавиатуру. Недоступное текущее значение не считается выбранным и вместо него
  показано приглашение.
- **`Combobox`** — управляемый одиночный выбор с текстовым `Input`: `options`, `value`,
  `onChange(value)`, `placeholder`, `disabled`, `invalid`, `label`, `emptyText`. При вводе он
  открывается и фильтрует пункты регистронезависимым совпадением по `label`; закрытие сбрасывает
  запрос, а закрытое поле показывает подпись выбранного доступного пункта. Поле объявлено как
  `role="combobox"` с `aria-autocomplete="list"`, `aria-controls`, `aria-haspopup="listbox"` и
  `aria-activedescendant`; список — `role="listbox"`. `ArrowDown` открывает и двигает активный
  пункт, `ArrowUp`, `Home` и `End` работают в открытом списке, `Enter` выбирает активный доступный
  пункт, `Escape` закрывает. Недоступные пункты показываются с `aria-disabled`, фильтруются как
  обычные, но не активируются и не выбираются; отключённый нативный `Input` не принимает ввод,
  мышь и клавиатуру, а недоступное значение не показывается выбранным.
- **`MultiSelect`** — управляемый множественный выбор: `options`, `value`, `onChange(value[])`,
  `placeholder`, `disabled`, `invalid`, `label`. Это `role="combobox"` с теми же связями с
  `listbox`, а список дополнительно имеет `aria-multiselectable="true"`. `ArrowDown` открывает
  список, стрелки, `Home` и `End` перемещают активный доступный пункт, `Enter` и пробел добавляют
  или снимают его без закрытия, `Escape` закрывает. Выбранные доступные пункты показаны тегами;
  у каждой кнопки удаления есть имя `Удалить <подпись>`. Недоступные пункты видимы, но не выбираются,
  не попадают в теги и пропускаются клавиатурой; отключённый триггер имеет `aria-disabled` и не
  отвечает на ввод.
- **`ModelPicker`** — управляемый двойной выбор «группа → опция»: `groups`, `value`, `onChange(value)`,
  `onExpandGroup(groupId)`, `label`, `placeholder`, `emptyText`, `disabled` и необязательная сторона
  слоя `side` (`top` | `bottom`, по умолчанию `bottom`). Группа
  (`ModelPickerGroup`) несёт `id`, `label`, `options` (`ModelPickerOption`: `value`, `label`,
  необязательные `description` и `disabled`) и необязательные `loading`, `failureReason`, `disabled`.
  Как и `Select`/`Combobox`, доменно нейтрален: назван в честь первого потребителя, но ни провайдеров,
  ни моделей не знает — их собирает вызывающий. Триггер — `role="combobox"` с `aria-haspopup="tree"`
  и `aria-activedescendant`; открытый слой — `role="tree"`, провайдеры и модели — `treeitem` первого
  и второго уровня, раскрываемые провайдеры имеют `aria-expanded`, модели — `aria-selected`.
  `ArrowDown` открывает список, стрелки,
  `Home` и `End` перемещают активную строку (шапку или опцию), `Enter` и пробел раскрывают группу либо
  выбирают опцию, `ArrowRight`/`ArrowLeft` раскрывают и сворачивают группу под курсором, `Escape`
  закрывает. Раскрытие группы — событие `onExpandGroup`: опций может быть больше тысячи, и спрашиваются
  они по одной группе, а не все сразу; пока опции едут, группа рисует `Spinner` с именем группы, при
  отказе — `Notice` с причиной. Контейнер и закрытие снаружи даёт управляемый режим `Popover`; поверх
  `Accordion` не построен: у того состояние uncontrolled и нет колбэка раскрытия, а здесь без контроля
  над раскрытием `onExpandGroup` не позвать.
- **`NextTurnPicker`** — компактный публичный контрол следующего турна: одна кнопка объединяет
  выбранную модель и уровень reasoning, а открытый слой образует каскад «провайдер → модель» над
  нижней зоной композера. Группы используют роли `tree`/`treeitem` из `ModelPickerMenu`, а модели
  загружаются лениво через `onExpandModelGroup`. Второй пункт каскада выбирает `off`, `minimal`,
  `low`, `medium` или `high`; для модели без поддержки reasoning контрол принудительно показывает
  `off` и оставляет остальные варианты недоступными. Сторона `top` не даёт меню уйти за край
  поднятой поверхности, после закрытия фокус возвращается на объединённый триггер. Все подписи,
  placeholder и доступные имена приходят пропсами и переводчиком вызывающего.
- **`SegmentedControl` и `RadioGroup`** — управляемые `radiogroup`: первый строит кнопки с
  `role="radio"` и `aria-checked`, второй — нативные `input[type="radio"]`; оба принимают
  `options`, `value`, `onChange(value)`, `label`, `disabled`, а `RadioGroup` ещё `name`. Недоступные
  варианты отключены нативно.
- **`Tabs`** — `tabs` (`id`, `label`, `disabled`, `content`), `value`, `onChange`, `label`.
- **`Tooltip`** — `content` (`string | ReactNode`), `side`, необязательный явный `id`, `hoverOnly`, `children`. CSS размещает
  пузырь и показывает его по hover или по `:focus-within`, ограниченному корневой keyboard-modality,
  без React-состояния: обычный фокус после указательного клика не удерживает его после hover-out.
  Компонент клонирует единственный элемент-триггер, добавляя ему `aria-describedby` с идентификатором
  пузыря `role="tooltip"`. Без явного `id` создаёт его сам; явный нужен, когда описание связывается не
  с клонируемым элементом, а с фокусируемым предком.
- **`Menu`** — `label`, `trigger`, `triggerLabel`, `placement`, `block`, `compact`, `items`. Пункты приходят
  данными; открытое меню забирает фокус на первый доступный пункт, стрелки пропускают недоступные,
  `Escape` и выбор пункта закрывают меню и возвращают фокус на триггер. `triggerLabel` нужен, когда
  подпись кнопки — значок вроде `…`: видимого текста для имени тогда не хватает, и скринридер
  называет кнопку многоточием. Без значка не задаётся — дублировать видимую подпись в `aria-label`
  значит разойтись с ней при первой же правке. `trigger` принимает не только строку, а любой узел —
  кнопке в самом низу панели нужен значок рядом с подписью. `placement="above"` раскрывает список
  вверх вместо вниз — для той же кнопки внизу панели, которой вниз раскрываться некуда, там край
  окна. `block` растягивает кнопку и список на всю ширину контейнера вместо ширины по содержимому.
  `compact` предназначен для контекстных меню с триггером `…`: убирает рамку и фон в обычном
  состоянии, оставляя мягкую подсветку при наведении и отдельный фокус. Любое открытое меню
  рисуется общим портальным слоем поверх карточек и панелей, поэтому stacking context или
  `overflow: hidden` у поверхности не прячет список. Его ширина определяется содержимым,
  ограничивается viewport, а позиция зажимается
  с безопасным отступом от краёв окна — контекстное меню не превращается в полоску через всю страницу.
  Клавиатурное и ARIA-поведение остаётся тем же. `disabled` оставляет trigger в раскладке, но запрещает
  открыть меню и выбрать действие.
- **`SplitButton`** — `action`, `actionLabel`, `onAction`, `menuLabel`, `menuTriggerLabel`, `items`,
  `placement`, `tone`, `disabled`. Две части остаются отдельными фокусируемыми кнопками: основная
  запускает частое действие, соседняя открывает общее `Menu` с редкими альтернативами. Отключение
  передаётся обеим частям, а отдельные подписи обязательны для доступного имени.
- **`Popover`** — `trigger`, `children`, `side`, `ariaLabel`; кнопка-триггер связывается с открытым
  портальным слоем через `aria-expanded` и `aria-controls`, слой имеет `role="dialog"`. Закрывается
  повторным нажатием, `Escape` или щелчком вне trigger и портального содержимого.
- **`Slider`** — управляемый нативный `input[type="range"]`: `value`, `onChange(value)`, `min`,
  `max`, `step`, `disabled`, `showValue`, `label`, `id`; передаёт `aria-label` и границы диапазона.
- **`Breadcrumbs`** — `nav` с подписанным `aria-label`, упорядоченными пунктами и
  `aria-current="page"` на последнем; предыдущие пункты — ссылки или кнопки.
- **`Accordion`** — `items`, `multiple`, `defaultExpandedIds`: кнопка каждого заголовка отражает
  состояние через `aria-expanded`; при `multiple=false` раскрытие следующего пункта закрывает
  предыдущий. Раскрытие у него всегда своё: `defaultExpandedIds` — начальный набор, дальше состояние
  принадлежит компоненту, и управляемого режима, как у `Tree`, здесь нет. Разница не в аккуратности,
  а в задаче: у аккордеона раскрытие — прихоть читающего, у дерева оно бывает состоянием данных.
- **`Tree`** — `nodes`, `selectedId`, `onSelect(node)`, `label`, `toggleLabel(node, expanded)`,
  `expandedIds`, `onExpandedChange(expandedIds)`, необязательные `actionsVisibility`,
  `disclosureAlignment` и контекстный
  `TreeNode.context`. Разметка — `role="tree"` с `treeitem`, вложенными
  `group`, `aria-level`, `aria-expanded` и `aria-selected`. Узел (`TreeNode`) несёт `id`, `label`,
  необязательные `title`, `icon`, `badge` (`text` и `tone`, рисуется `Badge`), `actions`, `context` и
  `children`. `context` открывается наведением и фокусом в портальном слое, оставаясь доступным без
  указателя. `actionsVisibility="interaction"` скрывает action-rail в покое и показывает его при
  наведении или при фокусе внутри строки под keyboard-modality; обычный фокус после указательного
  клика rail не удерживает. `always` сохраняет прежнюю геометрию.
  `title` становится нативной подсказкой всей строки: компактное дерево может обрезать видимую
  подпись, но полное имя остаётся доступно без раскрытия и без знания прикладной геометрии самим
  китом. `actions` располагает независимые контролы в отдельном правом rail той же строки: его
  жест не выбирает и не раскрывает узел, а уровень вложенности сдвигает только содержимое, не rail.
  `TreeNode.disclosureIcon` заменяет chevron в кнопке раскрытия, сохраняя её ARIA-состояние и
  клавиатурное управление; функция получает `expanded` и может вернуть разные иконки закрытого и
  открытого состояния. Это позволяет folder-led спискам показывать закрытую/открытую папку в том же
  месте без дублирующей галочки.
  `disclosureAlignment="label"` убирает визуальный слот раскрытия и сдвигает дочерние подписи на
  ширину этого слота, поэтому имя сессии начинается ровно под именем проекта.
  Имя узла
  для скринридера собрано из подписи и метки, а не из содержимого: иначе в
  него уезжают действия, подписи раскрытых детей и имя кнопки раскрытия. Значок декоративный и в имя
  не попадает. `label` (имя дерева) и `toggleLabel` (имя кнопки раскрытия, зависящее от узла и
  состояния) обязательны и умолчаний не имеют — по тому же правилу, что и `placeholder` у `Select`.
  **Мышь и клавиатура означают одно и то же.** Щелчок по строке выбирает узел и только его; щелчок
  по раскрывашке раскрывает узел и только его — это настоящая `<button>` с именем из `toggleLabel`,
  исключённая из обхода `Tab`. С клавиатуры выбирают `Enter` и пробел, раскрывают
  `ArrowRight`/`ArrowLeft`; стрелки вверх и вниз ходят по видимым пунктам, вправо на раскрытом узле
  идёт к первому ребёнку, влево на свёрнутом — к родителю.
  **Раскрытие бывает своё и чужое.** Без пропа `expandedIds` его помнит само дерево; с пропом
  владеет вызывающий, и своего дерево не применяет вовсе — до нового `expandedIds` узел так и
  останется свёрнутым. `onExpandedChange` отдаёт **новый набор целиком** и зовётся в обоих режимах.
  Третьего, смешанного, режима нет (см. «Почему так»).
  Право на `Tab` (roving `tabIndex`) не хранится, а выводится из набора видимых узлов: узел под
  фокусом, иначе выбранный, иначе первый видимый. `.focus()` зовётся только в ответ на действие
  человека — эффекта, переносящего фокус на перерисовке, в дереве нет.
- **`ToastContainer` / `ToastProvider` / `useToast`** — всплывающие системные уведомления.
  `ToastContainer` остаётся управляемым: получает `toasts` и `onDismiss(id)`. Обёртка
  `ToastProvider` рисует собственный стек, а `useToast()` возвращает `{ toast, dismiss }`:
  `toast({ title, tone, durationMs })` добавляет уведомление и возвращает его идентификатор,
  `dismiss(id)` убирает его раньше срока. По умолчанию уведомление закрывается через 4 секунды;
  `durationMs <= 0` отключает автоматическое закрытие. Хук вне `ToastProvider` бросает ошибку.
  Стек имеет `role="region"` и имя «Уведомления», каждое уведомление — `role="status"`, а его
  кнопка закрытия имеет доступное имя «Закрыть».
- **`Icon`** — унифицированный контейнер иконок с типовой размерной сеткой кита. Именованные
  пиктограммы действий (`CopyIcon`, `ForkBeforeIcon`, `ForkThroughIcon`, `SetLabelIcon`,
  `ClearLabelIcon`, `AddIcon`, `MoreIcon`, `ChevronRightIcon`, `PanelLeftCloseIcon`,
  `PanelLeftOpenIcon`, `PanelRightCloseIcon`, `PanelRightOpenIcon`) приходят из Lucide через обёртки
  кита: прикладной код не импортирует библиотеку напрямую и не выбирает собственную толщину линий.
  Текстовые символы `+`, `…`, `▶` и стрелки оболочки не используются как видимые кнопочные знаки;
  доступное имя остаётся на самой кнопке.
- **`BrandMark`** — монограмма продукта на размерной сетке `Icon`: `size` и необязательный `label`.
  Без `label` знак декоративен; с подписью получает роль изображения и доступное имя.
- **`BrandLockup`** — знак и название продукта одной строкой: `name`. Монограмма внутри декоративна,
  а видимое название остаётся доступным текстом. Цвет берётся из контрастной роли `accent-text`.
- **`Progress`** — `value` (0..1), `tone`, `label`.
- **`Skeleton`** — `variant` (`text` | `rect` | `circle`), `width`, `height`.

Тридцать первый добавлен вместе с интерактивным входом в провайдера
([models-and-providers.md](models-and-providers.md)) — до него интерфейс ядра никуда не уводил:

- **`Link`** — `href`, `external`, `children`. Внешняя ссылка открывается новой вкладкой и не отдаёт
  реферер (`rel="noreferrer"`, `noopener` он включает по определению). Новая вкладка здесь не
  украшение: на нашей продолжается диалог входа, и уход со страницы обрывает его. Подчёркивание
  стоит всегда — цвет остался бы единственным отличием ссылки от текста. Куда ведёт адрес, знает
  вызывающий: маршрутизатор живёт в приложении, и разбирать адрес в ките значило бы гадать о чужой
  навигации.

Вью чата ([sessions-and-projects.md](sessions-and-projects.md)) добавляет примитивы, у которых один
общий признак: они показывают текст, написанный не нами.

- **`Markdown`** — `text`. Размётка ответа модели: `react-markdown` с `remark-gfm` (таблицы, списки
  задач, зачёркивание) и `rehype-sanitize`. Сырой HTML не рендерится вовсе — `rehype-raw` не
  подключён, поэтому html-узлы отбрасываются ещё при переводе в hast, а санитайзер стоит вторым
  замком и режет схемы URL: у ссылки остаются `http`, `https` и `mailto`. Заголовок сдвинут на
  уровень вниз (`#` даёт `h2`), потому что `h1` страницы принадлежит оболочке; глубже третьего
  уровня заголовки сходятся в один — у кита их три. Ссылка, код и заголовок рисуются примитивами
  кита (`Link`, `Code`/`CodeBlock`, `Heading`), абзацы, списки, цитата и таблица остаются своими
  тегами и одеваются из `markdown.module.css`: `Text` — строчный `span`, абзац им не собрать.
  Подсветки синтаксиса, математики и сносок нет.
- **`StreamingText`** — `text`, `streaming`, `label`. Идущий ответ разбирается тем же `Markdown`,
  что и законченный; каретка и `aria-busy` остаются, пока `streaming`. `role` не ставит — область
  объявляет лента сообщений, и второе живое объявление внутри неё заставило бы скринридер читать
  ответ дважды. Каретка помечена `aria-hidden`: это курсор, а не текст. Мигание снимается при
  `prefers-reduced-motion`, но сама каретка остаётся — иначе пропадает единственный признак того,
  что ответ ещё идёт.
- **`MessageFeed` и `Message`** — лента переписки и реплика в ней; два экспорта в одном файле, как
  `List` и `ListRow`. Лента принимает `label`, `busy`, `children`, необязательные `className`,
  `before` и `after`; оба слота входят внутрь того же `role="log"` до и после реплик. Лента
  объявляет себя `role="log"` с
  `aria-live="polite"` и **одна на всю переписку** отвечает за озвучивание: живых областей внутри
  реплик больше нет. Она же прилипает к низу — но только если читающий уже был внизу, иначе каждая
  дельта срывала бы чтение истории. Решение вынесено чистой функцией `shouldStickToBottom(metrics)`
  с допуском `stickToBottomSlack`: в `jsdom` раскладки нет, и проверить его на настоящей прокрутке
  нечем. Реплика принимает `role` (`human` | `agent` | `service`), `header` и `children`; роль
  уезжает в `data-role`, а не в имя класса — имена CSS Modules хешируются, цепляться за них нечем.
  Время в шапке форматирует вызывающий: часового пояса и локали кит не знает. Аватаров и
  виртуализации нет.
- **`ToolCall`** — обязательные `toolName`, `status` (`running` | `done` | `failed`), `statusLabel`,
  `argumentsText`; необязательные `summary`, `duration`, `icon`, `output`, `outputLabel`. Композиция
  `Disclosure`, `Badge`, `Code` и `CodeBlock`. Свёрнутая строка всегда показывает техническое имя,
  переведённое состояние и декоративный знак исхода: `●` для `running`, `✓` для `done`, `×` для
  `failed`; если вызывающий их знает, рядом остаются знак типа, краткая цель и уже отформатированная
  длительность. Знак исхода имеет `aria-hidden`: доступное имя задаёт локализованный текст, а не
  глиф. Длинная краткая цель остаётся одной строкой и сокращается многоточием; полное значение
  сохраняется в доступном имени и нативной подсказке `title`, а техническое имя при крайней тесноте
  не обрезается вместе со статусом. Состояния различаются текстом, знаком и семантическим цветом,
  поэтому цвет не остаётся единственным признаком исхода. Блок свёрнут по умолчанию и
  **неуправляемый**: раскрытием по-прежнему заведует браузер, а не состояние React.
  `argumentsText` приходит уже
  сериализованным: в контракте вход инструмента — `unknown`, и решать, как показать чужую
  структуру, обязано вью. `output` появляется не сразу: в потоке вывода инструмента нет вовсе,
  `tool-end` несёт только идентификатор и признак отказа, и вывод приезжает дочитыванием записей
  ([sessions-and-projects.md](sessions-and-projects.md)). UI kit не вычисляет ни `summary`, ни
  `duration`: они описывают прикладные данные, которых у примитива может не быть.

**`Modal` из чужого кита не переносился.** `Dialog` с вариантом `drawer` закрывает обе его роли, и
отдельный примитив был бы вторым способом делать то же самое.

Стили — **CSS Modules**: у каждого примитива свой `*.module.css` рядом с ним, тип импорта объявляет
`vite/client` в `types` пакета, отдельного `.d.ts` для этого не нужно. Следствие, которое надо
держать в голове: имена классов хешируются, поэтому селекторы извне в кит перестали работать —
договорённость «не цепляться за наши классы» стала механизмом. То же следствие обязательно и для
браузерных ассетов плагинов ([ui-extension-model.md](ui-extension-model.md)).

**У плагина форма имени класса другая:** его стили собирает esbuild, и имя выглядит как
`<ключ плагина>_<файл>_<локальное имя>`, без хеша. Опираться на форму имени нельзя ни с той, ни с
другой стороны — общим объявлено только подмножество синтаксиса
([ui-extension-model.md](ui-extension-model.md)). Половину контракта со стороны Vite сторожит
`src/css-modules-contract.test.ts`: он собирает фикстуру настоящим Vite и падает, если обновление
поменяет умолчания.

Строки приходят компонентам **уже переведёнными**: кит не знает, в каком неймспейсе лежит эта строка,
и переводить её за вызывающего не должен.

## Каталог компонентов

`packages/ui-kit/.ladle/`, запуск — `make catalog` (`ladle serve`). Каталог существует по одной
причине: примитив, перенесённый вперёд своего среза, до появления настоящего потребителя виден только
здесь.

Схему каталог применяет **тем же** способом, что и приложение: `resolveScheme` плюс `applyRoles` в
корень документа и `applyScale` там же. Второго пути применения темы у нас нет и быть не должно —
иначе каталог показывал бы не то, что покажет продукт. Переключатели схемы и масштаба стоят в
`Provider` (`.ladle/components.tsx`) и помнят выбор в `localStorage`: переход между историями — полная
перезагрузка страницы. Их нативные `select` — служебные контролы каталога — явно используют роли
`controlSurface`, `controlSurfaceHover`, `border`, `text` и `focusRing`, поэтому системный белый фон
не возвращается в тёмных схемах. Светлый и тёмный вариант берутся из собственного переключателя
темы Ladle.

Истории — `src/components/primitives.stories.tsx` (примитивы с настоящим потребителем) и
`ported.stories.tsx` (примитивы, которые каталог пока демонстрирует вместо прикладного экрана).
В последних есть управляемые сценарии для `Combobox`, `MultiSelect`, `SegmentedControl`, `RadioGroup`,
`Popover`, `Slider`, `Breadcrumbs`, `Accordion`, `Tree` и `ToastProvider`/`useToast`: они показывают
выбор, недоступные варианты, клавиатурные модели, слои, и автоматическое либо ручное закрытие
уведомления. У дерева сценария два, и это те самые два режима раскрытия: `TreeSelection` держит
раскрытие внутри дерева и проверяет, что выбор и раскрытие — разные жесты, `TreeCurrentBranch`
владеет набором снаружи и двигает его кнопками рядом с деревом. `Tree` остался здесь и после того,
как в срезе 10b у него появился потребитель: панель записей сессии пользуется только управляемым
режимом, и без второй истории неуправляемый снова стало бы видно только в коде. Строки в историях — литералы, и это единственное место в ките, где так можно: каталог
не поставляется пользователю.

История `AppearancePreviews` показывает публичный preview в обычном и узком контейнере: четыре
семантических свотча складываются из одной строки в сетку 2×2 без прикладных цветовых значений.

## Оболочка

`apps/web/src/shell/`. Три области: левая панель (основная часть и низ), центральная страница, правая
панель с вкладками. Заменить оболочку плагин не может
([ui-extension-model.md](ui-extension-model.md)) — хост владеет границами, размерами и полосой
вкладок. Области соседствуют без общей поднятой карточки и различаются ролями поверхности: левая
панель — `panelSurface`, центральная страница — `pageSurface`, правая панель — вторичный
`sunkenSurface`. Так граница читается уровнем хоста, а не декоративной рамкой каждого вью.

- **Левая панель** — компактная шапка с кнопкой «скрыть», действие создания сессии и дерево активных
  проектов с сессиями прижаты к верху, а внизу стоят один индикатор связи с демоном и одна кнопка
  меню учётной записи. Верх, список проектов и низ — отдельные секции с небольшим визуальным
  промежутком и разделителем. Список прокручивается только вертикально: панель и секция проектов
  имеют `min-width: 0`, `overflow-x: hidden`, а строки дерева используют `border-box`, поэтому
  action-rail не создаёт горизонтальный скролл. Строки дерева используют компактную высоту; проект
  и сессия отдают полное имя через `TreeNode.title`, поэтому сокращение длинной подписи остаётся
  только визуальным. Действия проекта и сессии не выбирают и не раскрывают узел, появляются при
  hover/focus и остаются доступны с клавиатуры. У строк есть портальные контекстные карточки с
  предметными фактами, а компактные меню открываются также наведением. Карточка всегда привязана к
  правому краю видимой строки и при нехватке места сжимается до безопасного края viewport, не
  перекрывая навигацию. Путь в ней строго сокращается посередине до 20 символов, а полный остаётся в
  `title`. Статус виден всегда, потому что без демона интерфейс не делает ничего; меню раскрывается вверх
  (`placement="above"`, см. `Menu`) и прячет в себе архив, выход и дорогу к настройкам. Отдельного
  пункта «настройки» в навигации нет — владелец решил, что маршруту место в меню, а не в списке вью.
- **Правая панель** — место хоста под вкладки, которые приносят плагины: `core.panel.tabs`,
  кардинальность «вкладки» ([ui-extension-model.md](ui-extension-model.md)). Вкладок ядра у неё нет:
  внешний вид и диагностика переехали в страницу настроек. Полоса вкладок, контейнер и проп `tabs`
  принадлежат оболочке — это опубликованный контракт размещения, а набор для него собирает
  `useHostPlaceTabs`. Вкладов нет или ни один не открыт — панель показывает заглушку. Полоса **не**
  объявляет себя `role="tablist"`: у вкладок ARIA выбрана ровно одна, а здесь повторный щелчок по
  открытой вкладке её закрывает, и `aria-pressed` у кнопок описывает это честно.
- **Палитра команд** — часть оболочки, а не заменяемое место: оболочка принадлежит ядру. Собрана в
  `apps/web` из готовых примитивов кита (`Dialog`, `Input`, `List`), потому что плагину, которому
  захочется своя палитра, нужны части, а не наша компоновка. Показывает команды ядра и команды
  плагинов одним списком; открывается кнопкой в шапке и аккордом Cmd/Ctrl+K. Кнопка обязательна, а не
  декоративна: узкий экран — требование вижна, а на телефоне аккорда нет вовсе.
- **Раскладка** — ширины панелей, их видимость и открытая вкладка — живёт в `localStorage`: это
  уровень «раскладка хоста», делить его между машинами незачем. Испорченная запись не роняет
  оболочку. Минимальная ширина панели — `160 px`; фиксированного максимума нет. Фактический максимум
  зависит от ширины окна, второй видимой панели и двух границ по `5 px`: центральной странице всегда
  резервируется `320 px`. При двух слишком больших сохранённых ширинах сначала поджимается вторичная
  правая панель. Временное сужение окна ограничивает только отображение и не уничтожает сохранённое
  предпочтение для большого монитора. `openTab` — `string | undefined`, а не закрытый тип: вкладки
  приносят плагины, и ядру их идентификаторы заранее не известны. Проверку «такая вкладка есть» делает
  сама оболочка (`tabs.find(...)`), и **забытый идентификатор она не чистит**: плагин исчезает из
  снимка на каждой пересборке, и уборка закрывала бы вкладку человека при каждой правке его исходников.
- **Скрытие панелей** — кнопка «скрыть» в самой панели (слева в шапке, справа в полосе вкладок);
  вернуть скрытую панель — кнопка поверх угла страницы. Скрытая панель не рисуется вовсе, вместе с
  ней — и её граница-ресайзер. По умолчанию правая панель скрыта: на чистой установке вкладок в ней
  нет, пока их не принесёт плагин.
  Обе кнопки — это китовая `Button` (`size="sm" iconOnly`), а не самописная кнопка оболочки: свой
  CSS у оболочки остался только для позиционирования возврата, вид рисует кит. Стрелка скрытия
  смотрит наружу — туда, куда панель свернётся (левую прячем влево `«`, правую вправо `»`); стрелка
  возврата смотрит **к панели** (левая спрятана → её возврат из левого угла смотрит вправо `»`, правая
  → влево `«`), чтобы направление значка совпадало с тем, откуда панель вернётся.
- **Границы панелей** тянутся мышью и стрелками с клавиатуры. Слушают они окно, а не сами себя: при
  протаскивании курсор с границы уходит. Ширина при протаскивании считается от точки начала жеста, а
  не приращением между кадрами: замыкание внутри `onPointerDown` живёт весь жест и не видит новых
  пропов, и шаг от предыдущей точки складывался бы поверх состояния, которое уже устарело в момент
  нажатия. У `role="separator"` есть `aria-label`, `aria-valuenow/min/max` — без имени скринридер
  говорит только число.
- **Маршрутизатор** свой, `src/router.ts`: маршрутов ядра единицы, а неймспейс страниц плагина —
  `/p/<pluginId>/<pageId>/*` — задан моделью расширения. Вопрос внешней библиотеки задан вместе со
  страницами плагина и закрыт решением владельца в пользу своего роутера: вложенные маршруты внутри
  `/p/…` строит сам плагин, и хосту нужен от них один сегмент базы и хвост строкой. Адрес при этом
  перестал быть путём — `Location` это страница плюс параметры: переход, меняющий только параметр,
  происходит, а канонизация старого системного адреса больше не стирает query и якорь. Вложенные
  адреса ядра — `/settings/:section`,
  `/settings/projects/:projectId`, `/settings/providers/:providerId` и `/sessions/:sessionId`:
  выбранный раздел настроек переживает перезагрузку и делится ссылкой. Список разделов закрыт, и
  раздел, которого ядро не знает, становится неизвестной страницей, а не запросом, который вернёт 404.

CSS оболочки — `shell/shell.css`, геометрия хоста. Цвет в нём приезжает ролью, размер — шкалой кита,
иначе масштаб интерфейса двигал бы примитивы, а раскладку вокруг них нет. Тем же ограничены и прочие
файлы стилей приложения — `login/login.css`, `sessions/sessions.css`, `settings/settings.css`,
`projects/projects.css`, `providers/providers.css`: раскладка каждого вью лежит отдельно от оболочки,
потому что с её раскладкой ничего общего не имеет.

Центральная страница разводится по адресам: `/` — заглушка, `/sessions/:sessionId` — чат,
`/sessions/new` — создание, `/sessions/archive` — архив, `/settings/:section` — системные разделы,
`/p/<pluginId>/<pageId>/*` — страница плагина: маршрут ядра, содержимое чужое
([ui-extension-model.md](ui-extension-model.md)).

## Вью управления плагинами

`apps/web/src/plugins/`, раздел `/settings/plugins`. Живёт в ядре, как и остальные вью базовой поставки
([architecture.md](architecture.md)): выключить его нельзя, можно только переопределить плагином — и
тогда выключение этого плагина возвращает встроенное вью.

Одна панель ограничивает один самостоятельный плагин: в её шапке стоят имя и переключатель, а внутри
плоско идут состояние, ключ, папка, причина отказа или падения, номер попытки перезапуска и вклады
([plugins.md](plugins.md)). Сведения о плагине не получают внутренней панели. Вклады — компактные
строки общего `List`/`ListRow`, разделённые с фактами тонкой линией; у каждого свой переключатель.
У вклада вида `event` схема нагрузки раскрывается по требованию. Отказанный до чтения манифеста
плагин — только чтение: писать предпочтения по ключу-папке некуда.

`PluginsView.headingLevel` — внутренний проп композиции `apps/web`, а не экспорт UI kit и не
публичный SemVer-контракт для плагинов. Он принимает `1 | 2`, по умолчанию `1`: самостоятельное вью
владеет заголовком страницы, а внутри `SettingsView` получает `2`, потому что единственный `h1` уже
называет активный раздел. Уровень применяется одинаково в состояниях загрузки, отказа и готового
снимка.

Что показывается отдельно, потому что иначе исчезло бы:

- **выключенный вклад** — помеченным в списке, а не отсутствующим;
- **выключенная заявка на место** — отдельным исходом до объяснения ранга и кардинальности: она не
  считается свободной, не участвует в споре и не добавляется в ряд;
- **запись о выключенном, но больше не объявленном вкладе** — она сохраняется, даже если вклад ушёл
  вместе с версией плагина;
- **спор равного ранга** и **отвергнутый вклад** — врезками: журнал живёт в терминале и в браузер не
  отдаётся ([logging.md](logging.md)).

Обновляется вью так: снимок `GET /api/plugins` спрашивается на каждом подъёме соединения, кадр
`core.plugin.lifecycle` заменяет строку плагина на месте (в нём и есть полный статус), а смена набора
вкладов и пропуск в потоке ведут к новому запросу снимка — в нём лежит то, чего в событии нет.
Запрос в полёте один: следующий отменяет предыдущий, поэтому ответы разойтись не могут. Записанное
решение показывается сразу, не дожидаясь событий, а отказ записи (`409`) — врезкой с причиной.

Правило применения кадров живёт отдельно от хука (`plugins/state.ts`), потому что проверяется тестом,
а не глазами.

Ре-рендер на кадр измерен: React сводит пачку кадров сам, и своего батчинга здесь нет
([runtime-checks.md](runtime-checks.md), проверка 25).

## Вью проектов

`apps/web/src/projects/`, адреса `/settings/projects` и `/settings/projects/:projectId`. Это раздел
единого SettingsView и одновременно сущность первого класса
([sessions-and-projects.md](sessions-and-projects.md)), и создать его должно быть можно на пустой
платформе, без единого плагина.

Форма создания сверху — папка и имя, — дальше список работающих проектов, а архивные под
`Disclosure`: они нужны редко, и лезть за ними в фильтр было бы дороже, чем раскрыть.

Что показывается у строки:

- **«папка недоступна»** — значком. Это состояние проекта, а не ошибка: том отмонтировали, и он
  может вернуться сам;
- **эфемерный проект** — своим значком и локализованным именем: записи на диске у него нет, а
  действий нет ни одного — не выключенных, а отсутствующих. Выключенная кнопка обещает, что
  когда-нибудь она сработает, а переименовать `work` нельзя никогда;
- **проект, занявший запрошенную папку** — значком на своей строке. Отказ создания приносит целую
  запись занявшего ([web-api.md](web-api.md)) именно ради этого: строкой текста нужную строку
  списка не подсветить.

Переименование и безвозвратное удаление идут через `ConfirmDialog` — первый его потребитель в
поставке. У переименования диалог несёт поле ввода (`children`), у удаления — число пропадающих
сессий: подтверждение обязано называть цену, а не спрашивать «вы уверены»
([sessions-and-projects.md](sessions-and-projects.md)). Счётчик `sessionCount` приходит из снимка
проектов, а текст использует отдельные ключи для нуля и множественного числа: категории `zero` нет
ни в русском, ни в английском, и «пропадёт 0 сессий» вышло бы кривым.

Обновляется вью так же, как вью плагинов: снимок `GET /api/projects` на каждом подъёме соединения,
`core.projects.changed` ведёт к новому запросу — нагрузки у события нет вовсе
([event-bus.md](event-bus.md)). Переименование и архивация применяются оптимистично, создание и
удаление ждут ответа: их результат — идентификатор записи, и выдумывать его на клиенте значит
выдумывать состояние сервера.

## Вью провайдеров

`apps/web/src/providers/`, адрес `/settings/providers`. Тоже в ядре: выбрать модель нужно на пустой платформе,
без единого плагина. Что показывает список и почему статусов авторизации три —
[models-and-providers.md](models-and-providers.md) и [web-api.md](web-api.md).

Два режима по адресу: голый `/settings/providers` — плоский список компактных строк;
`/settings/providers/<id>` — страница одного провайдера. Строка разрешённого провайдера в общем
`List`/`ListRow` кликабельна целиком и уводит на страницу; факты и пометки находятся внутри неё, а
действия — только на странице деталей. Исключение — конфликтующее пользовательское определение,
которое не попало в снимок разрешённых провайдеров: его строка никуда не ведёт и несёт отдельное
действие удаления, чтобы конфликт можно было устранить. На странице разрешённого провайдера вход и
модели — разделы одного объекта с заголовками и тонкими разделителями, а не вложенные панели. Адрес —
источник истины: поле «раскрыт» в состоянии не хранится, провайдер страницы ищется в снимке по
`providerId` из маршрута, а адрес переживает перезагрузку и копируется как ссылка.
Идентификатор кодируется одним URL-сегментом. Отдельные `.` и `..` получают служебное представление
с `~`: браузер нормализует dot-сегменты ещё до маршрутизатора, даже если точка percent-кодирована.

Кнопка входа стоит на каждый объявленный способ (`logins`) и подписана словами самого провайдера;
выход показан только там, где есть что убирать. Кнопки живут на странице провайдера, а не в строке
разрешённого провайдера: строка целиком — кнопка перехода, и кнопке внутри кнопки в разметке места
нет. Удаление конфликтующего пользовательского определения находится в ненавигационной строке и
поэтому не создаёт вложенных интерактивных элементов.

`ProvidersView.headingLevel` — такой же внутренний проп композиции `apps/web`, а не экспорт UI kit и
не публичный SemVer-контракт для плагинов. Он принимает `1 | 2` с умолчанием `1`; при встраивании в
настройки `App` передаёт `2`. Это сохраняет смысловой заголовок списка, деталей, загрузки и состояния
«нет такого провайдера», не создавая второй `h1` под заголовком раздела.

**Диалог входа — панель вью, а не модальный слой.** Вход может вести плагин, и на его вопросы
отвечает он (`answerable: false`); модальный слой в этом случае перекрыл бы человеку интерфейс ради
диалога, в котором от него ничего не требуется. Панель показывается выше содержимого и не зависит
от того, открыта ли страница провайдера и приехал ли вообще список.

Что в диалоге: всё сказанное в порядке появления (сообщение со ссылками, адрес входа, код устройства
с адресом и сроком, прогресс), текущий вопрос формой (текст, секрет, выбор, код руками) и исход.
Секрет вводится полем без показа значения, а само значение живёт только в состоянии формы: уезжает
оно единственным путём — телом `POST` (docs/models-and-providers.md).

Что показывается отдельно, потому что иначе исчезло бы:

- **вход, который уже идёт** — вместе с занявшей попыткой: по ней видно, ведёт её плагин или другая
  вкладка той же сессии. Вкладке той же сессии отвечать можно — владелец попытки один;
- **шаг, который больше не ждёт ответа** (`409`) — врезкой, а форма снимается: отвечать ей нечем;
- **вход, кончившийся в разрыв связи** — «сказать нечем»: реестр держит только идущие попытки, и
  выдумывать исход вместо «не знаю» значит врать про вход;
- **выход, который ничего не изменил** — с именем переменной окружения: кред оттуда платформе не
  принадлежит, и убрать его нечем.

Обновляется вью так: снимок `GET /api/providers` и снимок идущих попыток `GET /api/provider-logins`
на каждом подъёме соединения, `core.provider.login`, `core.provider.logout` и
`core.providers.changed` ведут к новому запросу провайдеров, пропуск в потоке — к обоим сразу.
Шаги входа приезжают кадром того же соединения и попадают во вью не шиной, а вызовом: шаг адресован
одному инициатору и ждёт ответа ([event-bus.md](event-bus.md)). Кадр про попытку, о которой вкладка
не знает, ведёт к перечитыванию снимка, а не к сборке попытки из одного шага.

## Вью сессий

`apps/web/src/sessions/`, адреса `/sessions/:sessionId`, `/sessions/new` и `/sessions/archive`.
Постоянное дерево активных проектов и сессий находится в левой панели, а центральная область
показывает только чат или отдельный архив. Открытая сессия живёт в адресе, а не в состоянии вью:
её ссылкой делятся, и перезагрузка
страницы обязана вернуть тот же чат. Что такое сессия и что с ней можно делать —
[sessions-and-projects.md](sessions-and-projects.md).

**Дерево в левой панели** показывает проекты и вложенные активные сессии с меню действий. Имени у сессии может не быть — его даёт
человек, а не создание, — поэтому строка без имени это норма, а не пустое место. Фаза стоит значком и
выделена акцентом у всякой не простаивающей: в списке из десятка это единственный способ найти живую.
Битые файлы сессий не отменяют список: они показаны врезкой над ним.

**Меню строки** — переименовать, в архив или из архива, удалить безвозвратно. Архивация и удаление у
занятой сессии **выключены прямо в меню**, а не только отказом демона: показать невозможное действие
и объяснить отказ постфактум — худший из двух способов сказать одно и то же. Переименование остаётся
доступным всегда: это запись в дерево, а не перенос файла. Удаление спрашивает подтверждение и
говорит, что станет с форками этой сессии — они останутся, потеряв связь с родителем.

**Архив — отдельный экран**, сгруппированный по проектам. Он открывается из меню аккаунта и даёт
восстановить сессию либо удалить её безвозвратно, не засоряя постоянное дерево.

**Лента чата** склеена из трёх слоёв в одном порядке: дочитанные записи, турны, **вставшие в
очередь**, буфер идущего. Порядок именно такой, потому что буфер живёт ровно до конца турна, а потом
то же самое приезжает записями. В очередь смотрит `phase` из ответа на запуск турна: у начатого
турна запись реплики пишется сразу, и показать её ещё и своим слоем значит удвоить её в ленте до
конца работы.

Визуально лента открыта на центральной поверхности без общей карточки: самостоятельными границами
остаются компактная реплика человека, машинный блок и композер, а связный ответ агента читается
непосредственно на странице в колонке `reading-width`. Роли текста следуют автору и назначению, а
не формату записи:

- ответ агента, включая законченный `Markdown` и идущий `StreamingText`, использует Source Serif 4
  и ритм чтения — это спокойный редакционный голос главного результата;
- реплика человека, шапки реплик, подписи рассуждений и служебные строки остаются в Onest — это
  язык интерфейса и управления, который не притворяется вторым ответом агента;
- IBM Plex Mono используется только для машинного регистра: имён инструментов, путей, команд,
  аргументов, вывода, логов, диффов и результатов сборки. Само переведённое состояние инструмента
  остаётся в Onest; `Badge` и подпись вывода `ToolCall` закрепляют тот же интерфейсный регистр и не
  наследуют serif от ответа агента. Поэтому технический блок не превращает весь разговор в терминал.

- Ответ агента и **идущий**, и законченный рисуется разметкой: `StreamingText` использует
  `Markdown` и добавляет только каретку состояния.
- Размышления модели свёрнуты: они бывают длиннее самого ответа, но внутри также рисуются
  `Markdown`.
- Вызов инструмента — свёрнутый блок с аргументами и видимой строкой исхода. Вью выводит краткую
  цель только из уже имеющегося непустого строкового `path`, `file` или `command`; незнакомая форма
  входа безопасно остаётся без краткого описания. Нейтральный знак машинной работы стабилен, а
  длительность не выдумывается: текущие записи и события её не предоставляют. Результат приезжает
  **отдельной записью**, и связывает их только `toolCallId`. Пока результата нет, вызов показан
  идущим.
- Смена модели и уровня размышлений — служебная строка по центру, а не реплика.

У каждой сохранённой обычной реплики под содержимым есть одна строка метаданных и действий. Она
сохраняет место в раскладке, но видна только при наведении на реплику или при фокусе внутри самой
строки под keyboard-modality. Обычный фокус после указательного клика не удерживает действия после
hover-out; переход по `Tab` сохраняет их доступными без мыши, а фокус на раскрытом рассуждении или
вызове инструмента не удерживает чужую панель. В строке стоят локальные дата и время записи в компактном формате
`DD.MM.YYYY, HH:MM`, а также единые icon-only действия с tooltip. Два вида
форка остаются разными кнопками; поставить и снять метку больше не спрятаны в отдельное меню `…`.
Занятая сессия оставляет временно невозможные действия видимыми, но выключенными; архивная не
показывает изменяющие метку действия вовсе. Если все кнопки строки выключены, сама группа действий
становится клавиатурной точкой раскрытия, поэтому время и ограничения остаются доступны без мыши.
Крайние tooltip раскрываются внутрь scroll-контейнера и не обрезаются узкой лентой.

Копирование берёт только непустые текстовые блоки выбранной сохранённой реплики в исходном
порядке, соединяя разорванные техническими блоками части пустой строкой. Размышления, вызовы и
результаты инструментов в clipboard не попадают. После успеха подпись кнопки и tooltip на две
секунды говорят «Скопировано»; отказ Clipboard API показан врезкой рядом с лентой.
Параллельные clipboard-запросы используют правило latest-wins: завершение старого запроса не может
перезаписать подтверждение или отказ более нового.

- Записи `tools-change` и `other` в ленту не попадают вовсе: показывать в переписке нечего.

**Форк** предлагает всю поверхность рантайма: целую сессию, `before` у реплики человека для
«переспросить иначе» и `at` у каждой видимой записи. После форка интерфейс сразу открывает новую
сессию: оставаться на источнике, пока рядом появилась неотличимая строка, значит скрыть исход
действия.

**Панель дерева записей** (`sessions/entry-tree.tsx`) — первый настоящий потребитель `Tree`. Лента
показывает только активную ветку: `GET .../branch` отдаёт её путь, а вью хранит его идентификаторы
рядом с общим списком дерева; брошенные попытки в ней не видны вовсе. Панель кладётся
выдвижным слоем (`Dialog` в варианте `drawer`), а не постоянной колонкой. Своих запросов у неё нет — дерево строится из уже прочитанных записей, вложенность появляется
только в точках ветвления (иначе разговор из ста реплик стал бы лестницей из ста отступов). Метка
записи и признак листа приезжают в узел `badge`. Раскрытием владеет вью: набор — это путь от корня
до листа сессии, пока человек не тронул раскрытие сам, — поэтому панель открывается на работающей
ветке сразу, а не эффектом после первого кадра. Из выбранной записи делаются переход по дереву (с
суммаризацией ветки или без) и правка метки — формой прямо в панели, а не вторым модальным слоем
поверх выдвижного.

**Ввод** — выросшая `Textarea` внутри публичной `RaisedSurface`: поднятая поверхность отделяет
главное действие от открытой ленты, а внешний контейнер приложения задаёт только положение и
боковые поля. `Enter` отправляет, `Shift+Enter` переводит строку, поле тянется до двенадцати строк.
Решает, что делает отправка, **фаза сессии**, а не дельты: у турна, стоящего в очереди, дельт нет
вовсе, и кнопка, повешенная на них, осталась бы «отправить» посреди работы.

- **Сессия простаивает** — основная кнопка запускает турн, соседняя дописывает сообщение в дерево,
  никого не запуская (`append`).
- **Сессия занята** — турна не запустить, и над вводом появляется выбор момента: «прямо сейчас»
  (стиринг), «после турна» (догоняющее), «к следующему турну». Подпись кнопки меняется вместе с
  выбором: три очереди различаются не содержимым, а моментом доставки, и назвать это должна кнопка.
  Рядом остаётся «остановить».
- **Сессия в архиве** — история, статистика и форк доступны, а ввод скрыт: сервер всё равно
  отклоняет в ней и турн, и сообщение, поэтому активный контрол обещал бы невозможное.

**Что ждёт в очередях, видно значками** между лентой и вводом: написавший стиринг обязан видеть, что
тот принят и ждёт, а не пропал. Приезжает это дельтой, поэтому переподъём соединения очереди
обнуляет — верное значение приедет со следующей.

**Строка цифр** под лентой — токены и стоимость по всему файлу сессии, включая брошенные ветки:
вопрос, на который она отвечает, — «сколько я за эту сессию заплатил». Спрашивается отдельным
запросом, а не полем списка.

**Утраты показаны врезками** и копятся, а не заменяют друг друга: за одну пересборку набора пропасть
может несколько инструментов. Приезжают они событием шины `core.sessions.degraded`
([event-bus.md](event-bus.md)) — состояния «инструмент был и пропал» перечитать неоткуда.

**Диалог создания** спрашивает все четыре поля черновика — проект, агент, модель, уровень
размышлений, — а не только обязательные два. Модель и уровень у агента бывают не заданы, и отказ «у
агента нет модели по умолчанию» вылезал бы после нажатия, а не до. Модель выбирается каскадом
провайдер → модель: моделей на все провайдеры больше тысячи, и список спрашивается по одному
провайдеру. Модель без размышлений выключает уровень принудительно. Пусто — значит объяснение, а не
пустой список: нет проекта, нет включённого агента, нет настроенного провайдера — каждое своей
врезкой со ссылкой туда, где это чинится. Отказ `409` оставляет диалог открытым: переведённое
сообщение во врезке, английская причина от демона — в панели диагностики.

Обновляется вью так: снимок `GET /api/sessions`, `GET /api/agents`, снимок открытой сессии и её
записи — на каждом подъёме соединения; `core.sessions.changed` ведёт к перезапросу списка и снимка
открытой. Дельты приезжают кадром того же соединения и попадают во вью не шиной, а вызовом.
Снимок открытой сессии спрашивается **отдельно от списка**: сессия архивного проекта из списка
пропадает, оставаясь читаемой по своему адресу. Вместе со снимком спрашивается статистика — она
меняется тогда же, когда фаза.

## Выбор темы, масштаба и языка

Источник истины — `preferences.json` ([data-directory.md](data-directory.md)), интерфейс читает и
пишет его через `/api/preferences` ([web-api.md](web-api.md)). Выбранное
дополнительно кешируется в браузере: ответ демона приходит позже первой отрисовки, и без кеша страница
мигала бы чужой темой.

`applyAppearance` (`apps/web/src/appearance.ts`) применяет всё сразу: масштаб — атрибутом, схему —
переменными. Масштаб ставится первым и независимо от схемы: отказ схемы не повод оставить кегль
чужим. Названной схемы может не оказаться — её приносил плагин, которого выключили, — и тогда
работает встроенная, с диагностикой. Масштаба может не оказаться в кеше, записанном платформой,
которая про него не знала: подставляется значение по умолчанию, а не выбрасывается весь кеш.

**Окно берёт не весь снимок.** `/api/plugins` — каталог объявлений всех контекстов сразу
([plugins.md](plugins.md)), поэтому копия плагина в папке проекта приезжает в браузер рядом с копией
из директории данных. И схема, и каталог сообщений применяются **ко всему окну**, а не к открытому
проекту, — значит берутся только вклады узла: `windowWideContributions` отбрасывает всё, у чего есть
проект, и один и тот же результат кормит и схемы, и каталоги, и подписи. Без этого отбора один и тот
же `themed.midnight` стоял бы в списке дважды, а `core`-каталог из папки проекта подменял бы строки
платформы у человека, который в этот проект даже не заходил.

Список схем для выбора — `shippedSchemes` плюс `pluginColorSchemes(contributions)`: схемы из снимка
`/api/plugins`, разобранные китом. Отвергнутая схема просто не попадает в список — выбрать её нельзя,
потому что применить её нечем, — а причина отказа **возвращается** рядом со схемами, а не пишется
колбэком. Разбор идёт на каждый снимок плагинов, то есть на любое изменение любого плагина; запись
диагностики прямо из него была бы побочным действием в вычислении, и одна и та же жалоба повторялась
бы с каждым снимком (в режиме разработки — сразу дважды). Кто и когда её покажет, решает вызывающий:
`App.tsx` называет каждую причину **один раз**, помня уже названные.

**Подпись схемы плагина** берётся `describeSchemes` в три ступени: перевод из каталога плагина в его
неймспейсе (`translator.scope(pluginId).optional('appearance.scheme.' + declaredId)`) → `title`
вклада → его идентификатор. Отдельного поля подписи у вклада схемы для этого не заводилось: `title`
есть у каждого вклада. Идентификатор в списке хуже названия, но лучше пустой строки, а каталога у
плагина может не быть вовсе — потому здесь `optional`, а не `t`. Схема поставки этой лестницы не
проходит: её подпись всегда наша, из `core`.

**Выключенный плагин активной схемы** возвращает `imperium` с диагностикой, но `preferences.json`
**не переписывает**: включённый обратно плагин обязан вернуть свои цвета, а перезапись настройки
сделала бы выключение плагина необратимым для выбора. Разобранная схема плагина по той же причине не
кешируется в браузере рядом с настройками — цвета удалённого плагина остались бы навсегда.

**Гонка первого кадра.** Пока снимок плагинов не приехал, схемы плагина нет ни в одном списке, и
жалоба на её отсутствие была бы ложной — на каждой загрузке страницы, у каждого, кто её выбрал.
Поэтому до первого снимка диагностика применения подавляется, а не пишется.

Правка файла руками доезжает до открытого браузера событием `core.preferences.changed` — тем же
путём, что и запись из интерфейса. Отказ записи (`409`, файл на диске правил кто-то ещё) показывается
врезкой: разобраться с этим может только человек.

Смена схемы стоит миллисекунды и не требует ре-рендера: меняются значения CSS-переменных, дерево React
не перестраивается ([runtime-checks.md](runtime-checks.md), проверка 24).

## Вью настроек

`apps/web/src/settings/`, адрес `/settings`. Четвёртое вью базовой поставки появилось раньше среза 12
по прямому требованию владельца: раздел «Внешний вид» прежде был вкладкой правой панели, а
«Диагностика» — другой её вкладкой; оба переехали на страницу целиком, правая панель пустеет.

Форма — master–detail на одной поверхности центрального вью: локальная навигация семи разделов слева,
граница и содержимое выбранного раздела справа. Общую геометрию задаёт публичный `SettingsView` из
UI kit: компактная контекстная строка с полной цепочкой
`◆ Sovereign · Settings · <раздел или объект>`, видимый
надзаголовок навигации `SETTINGS`, плотная выбранная строка и рабочая область. В оболочке единственный
документный `h1` принадлежит route-level header и называет выбранный раздел или объект;
`SettingsPage` получает `headingLevel="none"`, сохраняет именованную `section`, но не рисует второй
крупный заголовок. При самостоятельном рендере вне оболочки тот же компонент по умолчанию создаёт
`h1`. `SettingsRow` задаёт строки «подпись и пояснение слева / контрол справа». Для каталогов
проектов и плагинов `SettingsEntityRow` собирает поверх него единый паттерн `label + description /
meta + actions`: вся строка открывает detail, а вложенные контролы остаются самостоятельными и не
запускают переход. `describedBy` сохраняет связь строки проекта с полным путём в tooltip. `Toggle` — округлый трек с
круглым бегунком: при смене состояния он перемещается и меняет поверхность с границей по токенам
длительности и easing UI Kit; при `prefers-reduced-motion: reduce` переходы отключены. `label` всегда
даёт checkbox доступное имя. `labelDisplay="visible"` по умолчанию показывает подпись рядом с
переключателем; `labelDisplay="tooltip"` скрывает её только визуально и показывает в стандартном
`Tooltip` в режиме `hoverOnly` только при наведении. Все `Toggle` внутри `SettingsRow` используют `tooltip`,
поскольку их назначение уже подписано слева; самостоятельные контролы, например действия дерева
сессий, сохраняют видимую подпись. `Toggle` по умолчанию использует размер `sm`, а `size="xs"` даёт
компактную подпись для плотных строк объектов. `SettingsView` только подставляет семь
самостоятельных section views. Под-навигация собрана из `SettingsNavigationItem`: это кнопки
локальных маршрутов с `aria-current="page"` у выбранной, а не строки общего `List`. Группы полей
внешнего вида и демона отделены тонкими линиями вместо карточек на каждую настройку; вложенных
`Panel` вокруг навигации и содержимого нет. Адрес раздела —
`/settings/<section>`, список разделов закрыт: раздел, которого ядро не знает, становится неизвестной
страницей, а не запросом. Голый `/settings` канонизируется через `history.replaceState` в
`/settings/appearance`: адрес — единственный источник выбранного состояния, но лишняя запись в
истории не появляется.

Каркас лежит в `packages/ui-kit/src/components/settings-frame.tsx`, а предметная раскладка разделов —
в `settings/settings.css`. `SettingsView` зависит от ширины самого вью, потому что ширину центральной
области меняет глобальная панель. В широкой области локальная навигация и содержимое прокручиваются
независимо. Ниже порога навигация встаёт горизонтальной прокручиваемой строкой над содержимым, а не
сжимает его второй узкой колонкой.

На странице настроек правая панель оболочки, её ресайзер и кнопка восстановления временно не
рисуются: три колонки оставили бы слишком мало места формам и каталогам. Это только представительное
условие `Shell`, а не запись в `ShellLayout`: ширина, скрытое состояние и открытая вкладка сохраняются
и возвращаются после ухода со страницы. Глобальная левая навигация остаётся видимой и не меняет
состояние.

Разделы:

- **Проекты** — список папок проектов, создание и управление; деталь адресуется как
  `/settings/projects/:projectId` и сохраняет ту же локальную навигацию.
- **Внешний вид** — выбор схемы и языка, а также сегментированные `SegmentedControl` для темы и
  масштаба. Под строками находится живой `AppearancePreview` из UI Kit: он показывает текущие
  названия схемы, варианта и масштаба и четыре role-based свотча. Содержимое переехало из
  `appearance-panel.tsx` без правки записи: тот же `applyAppearance`, тот же `/api/preferences`, та
  же врезка отказа.
- **Использование** — `/settings/usage`: точные суммы сообщений, кешированных и некешированных
  токенов и стоимости, горизонтальное распределение токенов и таблица по сессиям. Клиент читает
  действующий и архивный `GET /api/sessions`, дедуплицирует идентификаторы и для каждого вызывает
  существующий `GET /api/sessions/:id/stats`. Итоги считают только успешно прочитанные точные
  статистики; если файл битый, сессия исчезла между запросами или отдельная статистика отказала,
  экран явно показывает число прочитанных сессий и все причины неполноты. Если один из двух
  каталогов не прочитан или каталог вернул глобальные `problems`, числового знаменателя нет: экран
  говорит только, что часть точной статистики недоступна. Дневных бакетов, числа запросов и процента
  покрытия нет: текущий протокол их не определяет.
  Сессии архивированных проектов в эти каталоги не входят и аналитика их не заявляет.
- **Провайдеры** — каталог входов и моделей; деталь адресуется как `/settings/providers/:providerId`.
- **Плагины** — состояние и включение плагинов и их вкладов.
- **Демон** — состояние потока, время работы, момент старта и причина, если демон недоступен. Внизу
  левой панели остаётся только цветная точка состояния; раздел разворачивает факты. Время работы
  считает `useUptimeSeconds` раз в секунду, а справа показывает его через `DurationTimer`; при
  загрузке или недоступности на его месте остаётся компактный текст состояния. Здесь же форма
  `config.json` (`config-form.tsx`) — она правит тот же демон, о котором раздел рассказывает, и
  отдельного раздела ради десяти полей заводить не за чем.
- **Диагностика** — то, что в демоне ушло бы в журнал. Содержимое перееехало из `diagnostics-panel.tsx`.

Сетевыми контроллерами владеет `App.tsx`: он держит предпочтения, поток, `health`, диагностику,
`useConfig` и включаемый только на разделе аналитики `useUsage`. Сами section views получают снимки
и обработчики пропами. Каждый из семи разделов проходит через своё заменяемое
`core.settings.<section>` место с текущим section view как built-in; Settings frame и маршрут при
замене остаются у ядра.

### Форма конфига демона

`settings/use-config.ts` держит снимок `GET /api/config`, перезапрашивает его на открытии потока, на
`core.config.changed` и на разрыве потока; `settings/config-draft.ts` содержит только преобразование
снимка в локальный текст и проверку конечного числа; `settings/config-form.tsx` рисует строку
`SettingsRow` на каждый ключ конфига.

У формы нет общего черновика, коллизии и кнопки Save. `Select` уровня журнала отправляет одно значение
сразу после выбора. Числовой `Input` хранит текст своего контрола, чтобы разрешить промежуточные
состояния набора; он отправляет одно конечное число только по `Enter` или потере фокуса. Пустая строка
и нечисловое либо бесконечное значение остаются в поле с `aria-invalid` и не уходят к демону. Проверка
предметных ограничений не дублируется в браузере: она живёт в `parseConfigUpdate`
([data-directory.md](data-directory.md)). Уровни журнала не переводятся: это те же слова, что человек
пишет в файле и видит в выводе демона.

Каждое действие вызывает `PUT /api/config` с объектом из одного ключа; демон сливает его с актуальным
файлом и возвращает полный применённый снимок. Контроллер принимает только ответ последней отправленной
записи и не принимает начатый до неё reload, поэтому поздний ответ не заменяет более новый результат.
Отказ демона (`400`, `409` или `500`) показывается дословно, а затем контроллер перечитывает
авторитетный снимок: файл мог измениться вручную или другим клиентом. Набранный текст при этом остаётся
видимым рядом с причиной отказа. Внешний snapshot обновляет только контролы без локального незавершённого
текста; набранное число остаётся до commit по `Enter` или blur.

## Почему так

### Настройки остаются внутри оболочки, но без третьей панели

Глобальная левая панель содержит ежедневный путь к проектам и сессиям. Настройки сохраняют её и
строят собственный master–detail только в центральной области: человек не теряет рабочий контекст и
возвращается к разговору тем же способом, которым ушёл из него.

**Отдельная полноэкранная оболочка настроек.** Ближе к внешнему референсу и даёт максимум ширины.
Отвергнуто: это второй вариант оболочки ради одной страницы, а путь обратно к основной работе
исчезает вместе с глобальной навигацией.

**Две вложенные карточки `Panel`.** Такой вариант работал раньше и формально уже был master–detail.
Отвергнуто: рамки, радиусы и зазор делали навигацию и содержимое двумя самостоятельными карточками
внутри центральной поверхности, расходовали ширину и хуже показывали их связь. Теперь области
разделены одной линией и используют существующие примитивы только для интерактивного содержимого.

**Скрывать правую панель записью в `ShellLayout`.** Упростило бы условие рендера. Отвергнуто: переход
в настройки незаметно закрывал бы выбранную вкладку и перезаписывал пользовательское состояние.
Признак временной недоступности влияет только на представление; тот же объект layout возвращает
панель в прежнем виде на другой странице.

**Оставить `/settings` неявным с первым разделом.** Не добавляло бы канонический адрес. Отвергнуто:
выбранное состояние одновременно зависело бы от URL и внутреннего fallback вью. Замена адреса без
добавления записи в историю оставляет один источник истины и не делает вид, будто человек отдельно
открывал «Внешний вид».

### Карточка ограничивает самостоятельный объект, а не каждую часть вью

Поднятая карточка остаётся там, где граница выражает самостоятельность объекта: например, одна
панель соответствует одному плагину, которым управляют целиком. Навигация и содержимое настроек,
факты и вклады плагина, а также вход и модели одного провайдера — части уже названного объекта или
маршрута. Они образуют строки и разделы на общей поверхности, поэтому иерархию задают заголовки,
компактные строки и тонкие разделители.

**Карточка на каждую секцию, строку или группу контролов.** Отвергнуто: повторённые рамки, радиусы и
зазоры придают одинаковый вес объекту и его внутренним свойствам, расходуют ширину настроек и
разрывают связный список на набор декоративных островов.

**Своя геометрия, типографика и цвета в каждом системном вью.** Отвергнуто: приложение перестало бы
быть воспроизводимым через публичный UI kit, а темы и масштаб разошлись бы по отдельным реализациям.
Оболочка и прикладные CSS-файлы задают только размещение через роли и шкалу кита; состояние, вид
контролов, строки списка, заголовки, панели и уведомления остаются ответственностью примитивов.

### Каждый контрол конфига применяет своё завершённое действие

Внешний вид меняется одним выбором; уровень журнала устроен так же. Число, напротив, набирается по
символам, поэтому завершённое действие — `Enter` либо blur, а не каждое нажатие и не общая кнопка.
Частичный `PUT` сохраняет независимость соседних настроек: одному контролу не нужно посылать устаревшие
значения остальных.

**Запись на каждое нажатие клавиши.** Отвергнуто: `120000`, набранное с нуля, уехало бы демону шестью
запросами, из которых промежуточные могли быть непреднамеренными или негодными значениями живого
лимита.

**Общая кнопка Save и полный документ.** Отвергнуто: она возвращает общую незафиксированную форму,
соединяет независимые параметры и позволяет устаревшему снимку вкладки перезаписать соседние изменения.

**Повторить правила значений в браузере.** Отвергнуто: второй экземпляр предметных правил расходится с
`parseConfigUpdate` молча. Браузер отсеивает только пустой и нечисловой текст, который невозможно
передать как число; точную доменную причину называет демон.

**Затирать текст отказавшего контрола перезагрузкой.** Отвергнуто: человек лишался бы введённого
значения одновременно с точной причиной отказа. Текст сохраняется до следующего успешного снимка,
тогда как контроллер всё равно перечитывает авторитетный файл.

### Кит — отдельный публичный пакет, а не часть SDK

Браузерный UI плагина исполняется компонентом в realm хоста и стоит рядом с нашими элементами —
иногда вместо них ([ui-extension-model.md](ui-extension-model.md)). Значит плагину нужны те же
примитивы, из которых сделан наш интерфейс. Иначе каждый плагин приносит свой набор кнопок и полей, и
интерфейс расползается на глазах, хотя формально всё работает.

**Примитивы внутри `sdk`.** Один пакет вместо двух. Отвергнуто: любой плагин, даже без интерфейса,
получал бы React в зависимостях.

**Плагины используют что угодно.** Максимум свободы автору. Отвергнуто: интерфейс перестаёт быть
одним продуктом, а темы не работают вовсе — компонент со своим цветом не переключится вместе с
цветовой схемой.

**Взять внешнюю библиотеку компонентов и объявить контрактом её.** Меньше работы сейчас. Отвергнуто:
наш публичный контракт оказался бы привязан к чужому релизному циклу, и его ломающие изменения
становились бы нашими. Использовать внешнюю библиотеку **внутри** кита это не запрещает.

Владелец продукта сознательно принял и то, что первые недели работы дают не функциональность, а
фундамент: кит, дописываемый после прикладного кода, всегда отстаёт от него и превращается в свалку
вынесенных постфактум компонентов.

### Темы и локализация — данные, а не код

Перекрасить чужой компонент извне платформа не может: браузерный код плагина рисует свой DOM. Значит
переключение темы обязано работать через то, что компонент читает сам.

**Плагин поставляет свой CSS-файл как тему.** Проще всего. Отвергнуто: у платформы нет общего
словаря, плагин перекрашивает чужие элементы, а конфликт двух тем не разрешается никак.

**Только светлая и тёмная, без схем.** Не выполняет требование, и добавить схемы потом — это менять
контракт токенов, когда плагины на него уже опираются.

**Библиотека интернационализации с компиляцией сообщений.** Богаче `Intl`. Отвергнуто: зависимость
попадает в публичный контракт кита, а её возможности сверх `Intl` нам сейчас не нужны.

**Ключи на русском.** Расходится с правилом «код и идентификаторы на английском» и закрывает
платформу для внешних авторов.

Следствия: плагин может заменить язык интерфейса целиком, включая наши строки, — качество перевода
платформы может зависеть от плагина; переводы правятся без пересборки плагина, потому что каталоги —
данные; непереведённый ключ не ломает интерфейс, но обязан быть виден в диагностике, иначе
расхождение локалей копится молча.

### Вклад, принадлежащий проекту, окно не применяет

Схему и каталог сообщений интерфейс применяет ко всему окну: цвета стоят на корне документа, язык
общий, а открытого проекта на экране может не быть вовсе. Снимок `/api/plugins` при этом несёт
объявления всех контекстов сразу — иначе проектный плагин нечем было бы показать и включить. Живая
проверка среза 12a это и показала: копия плагина в папке проекта дала второй `themed.midnight` в
списке схем и подменила строку платформы `core`-каталогом из папки проекта.

**Разрешать спор по рангу прямо в браузере** (папка проекта перекрывает директорию данных, как в
демоне). Отвергнуто: ранг проекта действует **внутри** проекта, а не поверх окна. Тогда открытый в
одном проекте плагин перекрашивал бы весь узел, и выключить это было бы нечем, кроме как выключив
плагин.

**Применять проектную схему, когда открыт её проект.** Осмысленно и, возможно, вернётся отдельным
решением. Отвергнуто сейчас: цвет и язык живут на корне документа, а не в панели проекта, поэтому
переключение проекта перекрашивало бы всё окно и меняло язык на ходу. Это отдельная функциональность,
а не побочный эффект отбора вкладов.

**Оставить как есть и написать в документации, что так бывает.** Отвергнуто: дубль в списке выбора —
не особенность, а сломанный выбор: два пункта с одинаковым идентификатором, и что записано в
`preferences.json`, перестаёт определять применённое.

### Два слоя токенов и политика устаревания

Кит пишется **до** прикладного кода, значит часть имён мы угадаем неправильно и захотим переименовать
именно тогда, когда контракт уже публичен.

**Один слой: схема задаёт значения всех ролевых токенов.** Проще на первый взгляд. Отвергнуто по
арифметике: ролей будут десятки и они будут появляться постоянно, а базовых значений единицы. При
одном слое каждое добавление роли ломает все существующие схемы. Перенос визуала это подтвердил:
ролей стало заметно больше прежнего набора, а палитра выросла только на два ключа.

**Только палитра, без точечных переопределений.** Контракт был бы совсем узким. Отвергнуто: автор
схемы не может поправить один неудачный оттенок, не переопределяя вывод целиком. Поэтому
переопределение разрешено, но объявляется в манифесте схемы явно — её хрупкость должна быть видна и
нам, и автору.

**Удалять устаревшие имена сразу.** Кит остаётся чистым. Отвергнуто: ломает чужие схемы без пути
миграции, а выигрыш только косметический.

**Полагаться на дисциплину вместо линтера.** Отвергнуто: цвет мимо токена не виден в ревью, потому
что на нашей схеме он выглядит правильно. Обнаруживает его пользователь чужой схемы.

Цена двухслойной модели: палитра и вся остальная поверхность, экспортированная из
`src/index.ts`, входят в стабильный публичный контракт. Вывод ролей становится нашей
ответственностью, поэтому нужны проверки контраста, а не только совпадения имён; псевдонимы
экспортированных токенов копятся, и срок в один мажор надо соблюдать. Свободно меняться могут только
неэкспортируемые детали вывода ролей и реализации примитивов. Переименование публичного экспорта
допускается только с совместимым переходом либо в новой мажорной версии, иначе оно ломает плагины.

### Палитра выросла на два ключа за один мажор

`secondary` назван владельцем продукта: это редкий второй акцент для ключевого действия композера,
смысловых пометок и надзаголовков, а вывести его из основного акцента нельзя — это другой цвет, а не
другой его оттенок.

Точные тёмные ступени Imperium, которым нет места в замороженной палитре (`controlSurface`,
`accentSurface`, `accentStrong`, `borderStrong`), объявлены variant-specific переопределениями
встроенной схемы. Этот механизм намеренно не читается из документа плагина: чужая схема остаётся
строго 15-ключевыми данными контракта 2, а first-party схема может буквально воспроизвести
утверждённую иерархию без нового мажора. Обычные публичные `roleOverrides` по-прежнему работают
одинаково для обоих вариантов и диагностируются как хрупкие.

`shadow` владелец не называл, и он всё равно добавлен ключом, а не выведен из `overlay`. Причина:
светлой теме нужна **почти незаметная тень при вполне заметном затемнении**, и одним значением это
не выражается — любой множитель, дающий пригодную тень, испортит затемнение под модальным слоем.

**Второй мажор позже, отдельной правкой на каждый ключ.** Отвергнуто: пока все схемы наши, добавка
ключа стоит ноль; после среза 12 схему приносит плагин, и такая же добавка становится ломающим
изменением публичного контракта. Дешевле сделать оба ключа сразу и поднять мажор один раз.

### Перенесённые схемы конвертированы, а не скопированы

**Схема — данные, а не CSS-файл** (решение владельца продукта). У источника палитра была CSS-файлом
на тему; у нас это объявление в коде, потому что схему должен уметь принести плагин, а плагин
браузерного кода для схемы не пишет вовсе. Заодно значения из `oklch` переведены в hex: иначе их не
читает тест контраста.

**Верный перенос значений автора не проходил наш порог контраста почти нигде** — чужой кит контраст
не проверял вообще. Самый показательный случай: `nord`, светлый вариант, `warning` на `surface` —
1.35 к 1, жёлтый на белом не читается в принципе. Правка — корректор светлоты в OKLch с запасом к
порогу (целевые 4.6 при требуемых 4.5), оттенок и цветность сохранены; самое большое движение —
`nord` light `warning`: `#ebcb8b` → `#856525`.

**Снизить порог контраста.** Отвергнуто: порог существует ровно для того, чтобы схемы, которые нам
нравятся, не побеждали читаемость.

**Перенести схемы как есть и мириться с нечитаемым текстом.** Отвергнуто: тогда часть схем поставки
заведомо непригодна для работы, а тест контраста пришлось бы ослабить или отключить — и он перестал
бы что-либо гарантировать и для наших собственных схем.

### Вычисленные CSS-цвета разбирает одна стандарто-совместимая библиотека

`@asamuzakjp/css-color` версии `6.0.5` подключён к UI kit точной production-зависимостью. И
production-вывод `textOnSecondary`, и тестовый oracle вызывают его публичные `resolve` и
`convert.colorToRgb`: первый вычисляет стандартные CSS colors (`rgb`, `hsl`, `oklch` и
`color-mix`), второй переводит результат в sRGB для яркости WCAG. Это необходимо на применении
схемы, а не в каждом render: плагинный `ColorSchemeDocument` публично принимает CSS-color строкой,
и выбор контрастного foreground должен одинаково понимать встроенный hex и внешний функциональный
синтаксис. Vite включает браузерный ESM в UI Kit chunk; Node API библиотека не использует.

**Самописный перевод sRGB ↔ Oklab и разбор `color-mix`.** Отвергнуто владельцем продукта: такая
реализация дублировала бы меняющийся CSS Color, потребовала бы отдельно доказывать обработку alpha,
процентов и gamut mapping и могла бы одинаково ошибиться в вычислении и в проверке. Зрелый парсер
оставляет формулы production-роли простыми CSS-строками, а сложность стандарта изолирует в тестах.

**Оставить парсер только в тестах, а production понимать один `#RRGGBB`.** Отвергнуто после
регрессионной проверки плагинных `rgb()`, `hsl()` и `oklch()`: документ схемы принимает строку CSS,
поэтому такой вывод выбирал нечитаемый `textOnSecondary` для верной внешней схемы.

**Написать локальный компактный парсер.** Отвергнуто: он либо повторяет меняющийся CSS Color и
ошибается независимо от тестового oracle, либо поддерживает подмножество синтаксиса, которого
публичный контракт не объявлял.

**Запретить функциональные цвета при `parseColorScheme`.** Отвергнуто: это новое ограничение
публичного контракта плагинов и ломающая смена уже принятой формы `string`.

Цена production-зависимости — больший UI Kit chunk и необходимость осознанно обновлять точную
версию парсера. Она предпочтительнее двух разных реализаций стандарта; production build Ladle
проверяет, что пакет собирается для браузера без Node-only модулей.

### Встроенная схема — `imperium`, набор поставки сокращён до четырёх

`imperium` одновременно первая схема в `shippedSchemes`, значение по умолчанию и fallback при
недоступной плагинной схеме. Кроме неё в поставке остаются `nord`, `oled` и `sage`.

**Сохранить `base`, `neutral`, `obsidian`, `terminal` и проверочную `check`.** Отвергнуто владельцем
продукта: эти варианты больше не нужны в пользовательском выборе и создают визуальный шум. Алиасы и
миграция старых идентификаторов тоже отвергнуты явно; неизвестная сохранённая схема проходит обычный
путь отсутствующей схемы и приводит к fallback на `imperium`.

### CSS Modules вместо одного файла стилей

Решение владельца продукта. До переноса стили кита лежали одним растущим `src/styles.css`, и файл был
общим на всё: сломать чужой компонент правкой своего селектора можно было незаметно.

Что это даёт сверх соседства файла с компонентом: **имена классов хешируются**, и селектор снаружи по
внутренностям кита не работает вовсе. Раньше «не цепляйтесь за наши классы» было договорённостью, и
её нарушал сам `shell.css` (селекторы `.sv-`); теперь это механизм, а тест оболочки следит, чтобы
попытка не вернулась.

Цена: сборщик браузерных ассетов плагина обязан уметь CSS Modules, иначе у автора плагина нет дороги,
которая есть у нас ([ui-extension-model.md](ui-extension-model.md)).

### Hover-reveal различает pointer и keyboard явно

Браузерный `:focus-visible` оставался бы более короткой CSS-записью, но его результат зависит от
эвристик браузера и пользовательских настроек: проверка в Chromium показала `:focus-visible` на кнопке
и после указательного click. Поэтому reveal-слои не угадывают происхождение focus сами, а читают
единый корневой `data-sovereign-input-modality`.

Локальные флаги внутри `Tooltip`, Tree или конкретной строки сообщения отвергнуты: они дублировали бы
один контракт, расходились между потребителями и снова оставляли следующий hover-компонент без
исправления.

### Почему tooltip всегда единый

**Один публичный `Tooltip`.** Подсказка — сквозной interaction-контракт, а не декоративный кусок
конкретного экрана. Единая реализация уже закрывает различия pointer и keyboard, доступное описание,
idle-overflow и узкие flex-контейнеры; локальная копия неизбежно разойдётся хотя бы по одному из этих
правил.

**Структурированный `content` не создаёт новый тип подсказки.** Иногда одной строки недостаточно:
статическая справка может состоять из нескольких секций, разделённых линией. Поэтому `content`
принимает `ReactNode`, но trigger, CSS-показ, позиционирование и ARIA-связь остаются теми же. Для
интерактивных элементов используется отдельный примитив меню/слоя, а не усложнение tooltip.

### `Modal` не перенесён

В списке среза он был. В чужом ките это легаси-дубликат `Dialog`: без портала, без фокус-трапа, со
сырым `z-index` и ссылкой на несуществующий токен тени. Наш `Dialog` с вариантом `drawer` закрывает
обе его роли — вопрос по центру и длинный список у края.

**Перенести `Modal` рядом с `Dialog`.** Отвергнуто: это второй способ делать то же самое, причём
строго худший, и выбор между ними пришлось бы объяснять каждому, кто откроет кит.

### Каталог компонентов на Ladle

Восемь примитивов перенесены вперёд своих срезов: настоящий потребитель у них появится в срезах 6–10.
До тех пор проверить их нечем, кроме чтения кода, — а вид, клавиатура и поведение на четырёх схемах и
трёх масштабах чтением кода не проверяются.

Первый из них дошёл до потребителя в срезе 6 ([roadmap.md](roadmap.md)): форма входа собрана целиком
из кита — перенесённые вперёд `Field` и `Input` плюс `Button`, `Notice`, `Panel`, `Heading` и `Text` —
и своих компонентов в `apps/web` ей не понадобилось. Перенос этим подтвердился: правка потребовалась
ровно одна, `autoComplete` у поля ввода.

**Обойтись без каталога и ждать потребителя.** Отвергнуто: примитив, ни разу не открытый в браузере,
приезжает в свой срез с дефектами, которые там будут выглядеть как дефекты среза. Каталог окупился на
первой же истории: `Field` понимал пустую строку в `error` как безымянный отказ, то есть красил пустую
форму в красное и вешал `aria-describedby` на пустой элемент. Ни тест разметки, ни линтер этого не
видели — вызывающий писал ровно то, что написал бы любой другой.

**Storybook.** Отвергнуто: тяжелее и со своей сборкой; Ladle работает на Vite, который у нас уже
есть. Цена в любом случае одна — dev-зависимость в ките, ещё один режим запуска и цель в `make`.

### Три типографические роли вместо Unbounded и одной гарнитуры для всего

Source Serif 4 несёт голос агента и связный смысловой текст, Onest — реплику человека, служебные
строки, плотные контролы и навигацию, IBM Plex Mono — команды, пути, аргументы, вывод, логи и другой
технический материал. В реальной сессии граница проходит внутри одного ответа: проза агента остаётся
serif, встроенный код и блок выполнения становятся mono, а переведённое состояние машины — sans.
Так авторский голос, интерфейсное действие и машинный факт различаются без аватаров и без опоры на
один цвет. Source Serif 4 и Onest поставляются локальными variable-пакетами Fontsource; IBM Plex
Mono намеренно импортируется только статическими начертаниями 400 и 500, потому что variable-пакета
Fontsource для него нет. Это сохраняет одинаковый вид локального демона без CDN и не запрашивает
несуществующую ось начертания.

**Сохранить Unbounded, IBM Plex Sans и JetBrains Mono.** Отвергнуто: Unbounded слишком громко
маркирует любой заголовок как футуристичный, а прежняя тройка не отделяла достаточно ясно голос,
управление и машинный регистр.

**Одна sans-serif-гарнитура для всего.** Отвергнуто: она универсальна, но не придаёт связному ответу
агента собственного спокойного голоса. Serif во всём интерфейсе и monospace во всём продукте также
отвергнуты: оба преждевременно навязывают один тип содержимого.

### Открытая лента и публичная граница поднятого композера

Общая карточка вокруг чата убрана: она повторяла границу центральной поверхности и одинаково
обрамляла разговор, метаданные и действие ввода. Открытая лента оставляет главным связный ответ,
компактные полосы статистики, контекста, очередей и действий отделяет тонкими линиями, а композер
поднимает как одну самостоятельную поверхность.

Рамка, радиус, фон, тень и внутренний отступ композера принадлежат публичному `RaisedSurface`.
Прикладной CSS владеет только размещением его обёртки и внутренним flex-раскладом контролов. Это
частный случай общей границы: семейство шрифта, радиус, возвышение, градиенты и фильтры не задаются в
`apps/web`; их поставляет UI kit, чтобы хост и браузерный UI плагина собирались из одного визуального
контракта.

Композер остаётся компактным даже при длинном черновике: поле растёт до двенадцати строк, после чего
прокручивается только само `textarea`; поверхность, toolbar и соседняя история не получают overflow.
Toolbar занимает одну строку и делится на свободную сжимаемую левую зону и прижатый вправо ряд:
круговой контекст, `NextTurnPicker`, постоянно присутствующий Stop и `SplitButton` отправки. Stop
доступен только во время активного турна. Основная часть `SplitButton` запускает обычный тур в
свободной сессии и `steer` в занятой; меню всегда содержит `append`, а во время турна добавляет
`follow-up` и `next-turn`. Выбор альтернативы не сохраняется режимом для следующего Enter. Имена
иконок (`SendIcon`, `StopIcon` и именованные иконки сообщений) приходят из UI-кита, а доступные
подписи и tooltip задаёт приложение.

`NextTurnPicker` в нижнем ряду объединяет модель и reasoning в одну кнопку. Открытие идёт каскадом
провайдер → модель, с ленивой загрузкой групп; затем отдельный пункт выбирает уровень рассуждений.
Каскад раскрывается вверх (`side="top"`) и возвращает фокус на триггер. Группа провайдера и её
модели сохраняют роли дерева, поэтому тесты взаимодействия проверяют реальные `ModelPickerMenu`, а
stylesheet-тест проверяет только границу overflow.

**Оформить `.sessions-composer` напрямую в приложении.** Отвергнуто: получилось бы два источника
истины — публичные токены и прикладная копия геометрии поверхности. Первая смена радиуса или уровня
возвышения разошлась бы между встроенным экраном и плагином.

**Оставить одну поднятую карточку на весь чат.** Отвергнуто: она делает историю и действие ввода
одним объектом, повторяет уже существующую центральную поверхность и возвращает декоративную
вложенность, от которой системные вью уже отказались.

### Плоские эффекты и контекстная плотность вместо декоративной стилизации

Навигация и повторяемые строки используют компактную высоту, а связный текст сохраняет отдельные
ширину и межстрочный интервал. Четыре поверхности Imperium различаются небольшим сдвигом светлоты,
границей и тенью только у действительно поднятого слоя; другие схемы меняют цвет, но не геометрию.

**Равномерно уменьшить весь интерфейс.** Отвергнуто: это увеличивает число строк, но превращает
главный результат — ответ агента — в плотный технический лог.

**Градиенты, свечение, стекло, backdrop blur и неон.** Отвергнуто: характер Sovereign создают
палитра, типографические роли и точная композиция. Декоративные эффекты конкурируют с содержанием,
размывают границы поверхностей и делают инструмент похожим на знакомый launcher или AI SaaS.

### Новые цветовые схемы `oled` и `sage`

Добавлены две флагманские схемы 2026 года: ультратёмная `oled` (`#000000` с цианово-маджентовым неоном) и органическая природная `sage` (шалфей и глиняная терракота).

**Не добавлять `oled` и `sage`.** Отвергнуто: `oled` даёт чисто чёрный фон `#000000`, а `sage` —
спокойную природную гамму; обе темы остаются в актуальном сокращённом наборе.

### Кастомные `Select`, `Combobox` и `MultiSelect` вместо нативного `<select>`

**Оставить нативный `<select>`.** Отвергнуто: нативный выпадающий элемент вызывает стандартное белое
системное окно ОС, выбивающееся из тёмных схем. Кастомные выпадающие списки полностью адаптируются
под токены активной схемы и поддерживают поиск, клавиатуру и выбор тегов.

Они сохраняют различия своих нативных моделей: `Select` выбирает один пункт из списка, `Combobox`
фильтрует доступный для выбора набор текстом, а `MultiSelect` меняет выбор без закрытия списка и
показывает выбранное отдельными тегами. Поэтому у всех трёх один паттерн `combobox`/`listbox`, но
только у множества есть `aria-multiselectable`, а только у поискового поля — `aria-autocomplete`.

**Один универсальный компонент с режимами.** Отвергнуто: режимы смешали бы несовместимые поверхности
и клавиатурные контракты, а вызывающий мог бы получить поиск или удаляемые теги там, где они не
уместны. Три небольших явно названных компонента проще проверить и описать.

### Общий portal для всплывающих поверхностей

Все popup-компоненты используют один внутренний слой для portal и viewport geometry. Причиной стал
`Select` на странице Appearance: его список имел высокий `z-index`, но находился внутри
`SettingsRow.rowControl`, который сам создавал stacking context. Следующие строки с тем же уровнем
рисовались позже и перекрывали список, хотя локальный `z-index` был больше.

**Поднимать активную строку Settings.** Отвергнуто: исправляет только одну композицию и снова
ломается у следующего `overflow`, transform или stacking context.

**Оставить portal и расчёт координат каждому компоненту.** Отвергнуто: `Menu`, `Tree` и `Popover`
уже имели три расходящиеся реализации. Единый слой оставляет предметным компонентам их ARIA,
клавиатуру и focus lifecycle, но централизует portal, flip, viewport clamp, resize и scroll.

**Внешняя библиотека позиционирования.** Отвергнуто: для четырёх сторон, flip и viewport clamp новая
runtime-зависимость не оправдана. Решение пересматривается, если понадобятся virtual anchors,
сложные collision boundaries или стрелки поверхности.

### `ModelPicker` — двойной выбор с ленивой подгрузкой, отдельный примитив

Экран создания сессии выбирает модель каскадом: провайдер → его модели. Моделей на все провайдеры
сразу больше тысячи, и спрашиваются они по одному провайдеру, а не пачкой. Этот каскад и стал
поводом вынести пикер в кит, а не строить на месте в `apps/web`.

**Оставить два `Select` подряд (провайдер, потом модель).** Отвергнуто: человек выбирает одну
сущность, но вынужден сначала заполнить отдельное служебное поле провайдера. Двойная выборка в
одном попапе, где шапка группы — она же кнопка её раскрытия, оставляет одно поле модели и одну
прокручиваемую область для большого каталога.

**Собрать пикер в `apps/web`, а не в ките.** Отвергнуто: единственный потребитель сейчас один, но
поверхность у пикера нетривиальная — согласованная клавиатура (стрелки по шапкам и опциям,
`Enter` и пробел, `ArrowRight`/`ArrowLeft` для раскрытия), ARIA (`combobox`/`tree`/`treeitem`,
`aria-activedescendant`, `aria-expanded`) и ленивая подгрузка с состояниями `loading` и
`failureReason`. Оставь это на месте — и плагин, которому понадобится такой же выбор, не сможет его
воспроизвести, а копия в плагине разойдётся с образцом при первой же правке. То же правило, по
которому в ките живут `Select`, `Combobox` и `MultiSelect`.

**Построить поверх `Accordion`.** Отвергнуто: у аккордеона состояние uncontrolled (`defaultExpandedIds`
как начальный набор, дальше компонент владеет им сам) и нет колбэка раскрытия. А здесь раскрытие
группы — это запрос к демону за её опциями (`onExpandGroup`), и без контроля над состоянием позвать
его нельзя. Поэтому у пикера своё состояние раскрытия, а провайдеры — раскрываемые `treeitem`, не
аккордеонные секции. Сам popup построен на `Popover`: его управляемый режим принимает готовый trigger,
роль содержимого и `open`/`onOpenChange`, поэтому ModelPicker сохраняет единое закрытие по Escape и
клику снаружи без второй реализации popup lifecycle.

Как и остальные примитивы выбора, пикер доменно нейтрален: имя `ModelPicker` — дань первому
потребителю, но ни про провайдеров, ни про модели он не знает. Группы и опции приходят данными, и
тот же пикер годится для любого двухуровневого выбора с ленивой подгрузкой второго уровня.

### Уведомления через провайдер и хук

Состояние уведомлений принадлежит ближайшему `ToastProvider`: он выводит свой `ToastContainer`, а
потребитель вызывает `useToast().toast` или `dismiss`. Такому вызову не надо вручную передавать
стек через дерево приложения, а управляемый `ToastContainer` остаётся для случая, когда состоянием
владеет вызывающий. Автоматическое закрытие по умолчанию ограничивает шум; `durationMs <= 0` оставлен
для статуса, который требует явного подтверждения человеком.

**Глобальный singleton вне React.** Отвергнуто: он смешал бы независимые деревья React и сделал бы
невозможным локальный жизненный цикл провайдера в тесте или встроенном интерфейсе плагина.

### Блок кода устройства не стал примитивом кита

Вход по коду устройства показывает три вещи разом: сам код, адрес, куда его вводить, и ожидание
подтверждения ([models-and-providers.md](models-and-providers.md)). Соблазн завести на это отдельный
`DeviceCode` есть — вид узнаваемый и повторяется у каждого провайдера с таким входом.

**Отвергнуто.** Это композиция `Code`, `Link` и `Progress` **одного экрана**, а не самостоятельная
единица интерфейса. Плагину, заменяющему вью провайдеров
([ui-extension-model.md](ui-extension-model.md)), нужны именно части: свою компоновку он строит сам —
иначе замена вью означает повторение нашей раскладки под чужим именем. Примитив же зафиксировал бы
нашу компоновку в публичном контракте, и первое же расхождение (провайдер показывает код без срока,
или срок без адреса) пришлось бы закрывать пропсами-исключениями.

В кит из этого экрана добавлена одна `Link`: ссылки в ките не было вовсе, и собрать её из имеущегося
нельзя — это тег, а не композиция.

### `Form` появился после второго кейса, а не после первого

Enter в поле, подтверждающий действие, нужен в двух местах: форма входа в провайдера и форма
создания проекта. После первого кейса сырой `<form onSubmit>` в `login-view.tsx` ещё оправдывался:
примитив ради одного использования — абстракция ради абстракции, и кит держался тонким. После
второго кейса то же поведение пришлось писать заново ручными `onKeyDown` на каждом `Input` формы
проекта — это уже второй знак, что жест повторяется, и примитив окупается. `Form` тонкая: она
только гасит нативную перезагрузку страницы, зовёт колбэк и по необязательному `label` называет
нативную форму для скринридера, без геометрии и состояния. Своего
`className` у неё нет (имя модуля хешируется, как у всех примитивов), поэтому раскладку формы
держит внутренний контейнер вызывающего.

### DOM-тесты сложных интерактивных компонентов

`@testing-library/react` и `jsdom` лежат в devDependencies `ui-kit`, а срезом 7 — и `web`, теми же
диапазонами: лок-файл один, и две версии jsdom в нём были бы ошибкой, а не выбором. Они исполняют реальный
React-рендер и события клавиатуры в изолированном `// @vitest-environment jsdom` тесте: так проверяются
`aria-activedescendant`, пропуск недоступных пунктов и фактическое перемещение DOM-фокуса в `Tree`.

Про фокус дерева тест утверждает две вещи сразу, и обе — про `document.activeElement`, а не про
разметку. Стрелка **обязана** увести настоящий фокус на соседний `treeitem`. Перерисовка —
**обязана не** уводить его никуда: в тестах рядом с деревом стоит поле ввода, оно получает фокус, и
после того как узлы приехали пропом или узел под фокусом из набора исчез, фокус остаётся в поле, а
переезжает только право на `Tab` (`tabindex="0"` на оставшемся узле).

**Оставить только серверный рендер и тесты чистой логики.** Отвергнуто: серверная разметка не меняет
состояние и не имеет фокуса, поэтому не ловит ни одну из двух ошибок — ни roving tabindex, который
переехал, пока настоящий фокус остался на прежнем `treeitem`, ни `useEffect`, который на каждой
дельте стриминга забирал фокус из поля ввода себе. Вторая и была настоящей: срез 10b нашёл её в
`Tree` первым же потребителем.

**Сделать jsdom глобальной средой Vitest.** Отвергнуто: большинство тестов кита проверяет чистые
данные и не нуждается в DOM; окружение выбрано на уровне одного тестового файла, чтобы не менять их
исполнение и стоимость запуска.

### Размётка ответа модели — на `react-markdown`, а не своим рендерером

Три новые зависимости кита на один примитив: `react-markdown`, `remark-gfm`, `rehype-sanitize`.
Установленных пакетов от этого прибавилось четыре — экосистема unified уже лежала в лок-файле
зависимостью каталога компонентов, — но считается решение не по этому числу, а по тому, что кит
берёт на себя чужой парсер.

**Свой минимальный рендерер (ноль зависимостей).** Отвергнуто. Разобрать заголовки, списки и
ограждённые блоки несложно; невозможно — остановиться на этом. Ответ модели содержит вложенные
списки, таблицы, ссылки в скобках, экранированные символы и незакрытые ограждения, и каждый
следующий случай дописывался бы в наш парсер по факту жалобы. Цена ошибки при этом не «некрасиво
показалось»: разбор чужого текста своими руками — это то место, где рождается XSS.

**`marked` + `DOMPurify`.** Отвергнуто. Пакетов столько же, но связка отдаёт строку HTML, и вставлять
её пришлось бы через `dangerouslySetInnerHTML`. Тогда единственной защитой остаётся санитайзер, и
любая его настройка — это правка списка разрешённых тегов вслепую. `react-markdown` строит дерево
React и в DOM строкой не пишет вовсе; сырой HTML он отбрасывает ещё до санитайзера, потому что
`rehype-raw` мы не подключаем. Замка два, и первый — архитектурный, а не список.

**Санитайзер поверх собственной схемы.** Схема по умолчанию (`hast-util-sanitize`) пропускает `irc`
и `xmpp` в `href`; в чате агента ссылка, открывающая стороннее приложение, пользы не имеет, и
список схем сведён к `http`, `https`, `mailto`. Остальное оставлено как есть: сужать схему дальше
значит молча ломать таблицы GFM и классы языка у кода — ровно то, ради чего `remark-gfm` и брался.

### Стриминг текста — `Markdown` с отдельным индикатором состояния

`StreamingText` сохраняет отдельную семантику состояния (`aria-busy`, доступное имя и каретку), но
внутри сразу использует `Markdown`: человек видит форматирование без ожидания `message-end`.

**Прежнее правило: разбирать разметку только после окончания сообщения.** Дельта приходит на каждый
токен, поэтому разбор всего буфера повторяется сотни раз за турн, а незакрытый fenced code block меняет
дерево целиком. Владелец продукта выбрал прямой рендеринг, чтобы оценить его на реальных ответах. Если
стоимость или скачки разметки окажутся заметными, улучшение через debounce или стабильные блоки
оформляется отдельным срезом; этот эксперимент не скрывает форматирование сейчас.

### Ввод чата не стал отдельным примитивом

Роадмап называл в срезе 9 пять примитивов кита, и пятый — «многострочный ввод». Отдельного
`ChatComposer` в ките нет.

**Отвергнуто.** Многострочное поле уже есть — `Textarea`, — и второе было бы ровно тем дубликатом, за
который не перенесён `Modal`: два способа ввести одно и то же расходятся в поведении на первой же
правке. Вместо примитива область выросла на три пропса (`autoGrow`, `maxRows`, `onSubmit`), и
выросла она в сторону, полезной не только чату: поле, которое тянется под содержимое, нужно и
описанию проекта.

Кнопки «отправить» и «остановить» примитивом тоже не стали: это предметные действия **одного
экрана**. Но повторяемая нейтральная композиция primary action + альтернативное `Menu` стала
публичным `SplitButton`; экран передаёт в неё свои подписи, иконку и callback, не зашивая в кит
семантику сессии.

### `Tree` переписан первым потребителем

Дерево лежало в ките с переноса визуала, каталог его показывал, тесты были зелёные. Панель записей
сессии (срез 10b) вскрыла в нём четыре дефекта, и три из них каталогом не видны в принципе — их
видно только тому, кто ставит дерево в живое вью.

**`label` и `toggleLabel` обязательны.** Умолчанием подписи было русское «Иерархия объектов», и на
английском интерфейсе оно уезжало в `aria-label` как есть. Это тот же прецедент, что уже случился с
«Выберите...» у трёх полей выбора, — и он повторился ровно потому, что первый раз был закрыт
правкой одного места, а не правилом.

**Заменить русское умолчание английским.** Отвергнуто: английская строка зашивает язык в кит точно
так же, просто незаметнее — на русском интерфейсе она не бросается в глаза владельцу продукта, и
дырка живёт до жалобы того, кто читает интерфейс скринридером. Кит вообще не знает, на каком языке
говорит вызывающий, значит не имеет права на строку по умолчанию.

**Имя кнопки раскрытия — функция, а не пара строк.** Отвергнуто `expandLabel`/`collapseLabel`: имя
зависит и от состояния, и от узла («Развернуть турн», а не «Развернуть»), а порядок слов
принадлежит языку. Склеивать его в ките значит навязывать русский синтаксис через чёрный ход.

**Раскрытие: два режима без смешанного.** `expandedIds` не задан — набор помнит дерево; задан —
владеет вызывающий, и своего дерево не применяет вовсе. Второй режим и есть настоящая причина
правки: панель записей обязана открыться на ветке, в которой сессия работает сейчас, а путь до
текущего листа знает вью, не кит.

**Смешанный режим — дерево хранит своё раскрытие и заодно слушает проп.** Отвергнуто: это два
источника истины на одно состояние, и расходятся они в первом же сценарии — вызывающий отдал новый
набор, дерево применило поверх него своё, и на экране раскрыто не то, что записано во вью.
Управляемость по образцу `value`/`onChange` вызывающему уже знакома, и вопрос «кто здесь главный»
решается наличием пропа, а не догадкой.

**`onExpandedChange` отдаёт набор целиком и зовётся в обоих режимах.** Отвергнута дельта
(«этот узел раскрылся»): собирать из неё набор пришлось бы каждому вызывающему заново. Молчание в
неуправляемом режиме отвергнуто тоже — вью, которому раскрытие нужно только для того, чтобы
запомнить его между открытиями панели, иначе пришлось бы становиться владельцем целиком.

**Позиция roving tabindex выводится, а не хранится эффектом.** Прежний `useEffect` звал `.focus()`
на каждом обновлении, потому что его зависимость (список видимых узлов) пересчитывалась каждый
рендер. Рядом с живой лентой чата это не мелочь: дерево записей перерисовывается на каждой дельте
турна и забирало бы фокус из поля ввода, пока человек печатает. Эффект убран целиком, право на
`Tab` считается из набора видимых узлов — узел под фокусом, иначе выбранный, иначе первый видимый, —
а `.focus()` зовётся только в ответ на нажатие клавиши или щелчок.

**Чинить эффект, а не убирать.** Отвергнуто: `useMemo` на видимых узлах убирает лишние срабатывания,
но не отвечает на вопрос, почему компонент вообще двигает фокус без действия человека. Исчезнувший
узел должен терять право на `Tab`, а не уводить курсор за собой — это разные вещи, и хранить их
одним состоянием было исходной ошибкой.

**Щелчок по строке больше не сворачивает узел.** Раньше один щелчок делал два дела разом, то есть
выбрать раскрытую папку было нельзя вовсе, не свернув её, — а с клавиатуры те же два дела давно
делались разными клавишами. Раскрывашка стала настоящей `<button>` со своим именем и своим
обработчиком; из обхода `Tab` она исключена, потому что точка входа в дерево одна — узел, а
раскрытие с клавиатуры живёт на стрелках.

### `openTab` перестал быть закрытым типом

Прежде `shellTabs` перечислял вкладки ядра (`"appearance"`, `"diagnostics"`) замкнутым типом, и
`readLayout` отбрасывал незнакомый идентификатор. Вкладки ядра убраны — их место на странице
настроек, — а вкладки плагинов появятся в срезе 12. Закрытый список из нуля значений — это не тип,
а мёртвый код, и описать им идентификаторы вкладок плагинов ядро всё равно не смогло бы.

Теперь `openTab: string | undefined`, `readLayout` хранит любую строку, а проверку «такая вкладка
есть» делает сама оболочка (`tabs.find(...)`): только ей известно, какие вкладки ей передали.
Умозаключение «раскладку записали с вкладкой, которой у нас нет» осталось верным и без закрытого
типа — просто теперь это решает компонент, а не функция чтения.

**Оставить `shellTabs` пустым массивом «до среза 12».** Отвергнуто: пустой замкнутый тип отвергает
любой идентификатор, в том числе тот, что принесёт плагин, — правая панель не открылась бы вовсе.

### Правая панель осталась пустой, а не удалилась

Вкладок ядра у правой панели больше нет, и до среза 12 показывать ей нечего. Удалить панель,
полосу вкладок и проп `tabs` целиком — соблазнительно, но это опубликованный контракт размещения из
[ui-extension-model.md](ui-extension-model.md): плагин вкладывает в правую панель свои вкладки, и
убрать место под них теперь, чтобы вернуть его срезом 12, дороже, чем оставить пустым. Пока вкладок
нет, панель показывает заглушку.

### Граница считает абсолютную ширину от начала жеста

Прежде `PanelResizer` копил приращения между соседними кадрами и применял их к замкнутому в
`onPointerDown` состоянию. Замыкание живёт весь жест и не видит новых пропов, поэтому состояние, от
которого считалась ширина, застывало на моменте нажатия, а приращения накладывались поверх него —
панель дёргалась к стартовой ширине и не оставалась там, куда её потянули.

Теперь в `onPointerDown` берутся две константы на весь жест — `startX` и `startWidth` — и ширина
каждого кадра считается как расстояние от них. Устаревшее замыкание перестаёт быть проблемой не
потому, что его починили, а потому, что от него больше ничего не зависит.

### Возврат панели — плавающая кнопка, а не постоянный рельс

Скрытую панель надо вернуть. Постоянный узкий рельс у края страницы держал бы кнопку возврата всегда
на виду — и постоянно отъедал бы ширину у страницы ради кнопки, которая нужна редко.

Вместо этого кнопка возврата лежит в самой странице (`position: absolute` на `.shell-page`,
которой добавлен `position: relative`) и видна только пока панель скрыта. `z-index` у неё не задаётся
намеренно: кнопка идёт в DOM после содержимого страницы, и порядка документа достаточно, чтобы
лечь поверх него; лишний слой конкурировал бы с меню на `--sovereign-z-overlay`.

**Рельс у края.** Отвергнут владельцем: он постоянно отъедает ширину у страницы ради кнопки, которая
нужна редко.

### Кнопки скрытия и возврата — китовая `Button`, а не своя

Прежде у оболочки был свой `<button class="shell-hide">` с геометрией и цветом, дублирующими кит.
Это нарушает правило «интерфейс строится только из кита»: компонент, сделанный на месте в `apps/web`,
становится тем, что плагин воспроизвести не может. Поэтому китовая `Button` получила `size` и
`iconOnly` (см. `Button`), и обе кнопки скрытия/возврата используют её. Своего CSS у оболочки для
кнопки не осталось вовсе — только позиционирование обёртки возврата; вид рисует кит, как и везде.

### Именованные иконки приходят через UI-кит

Интерфейс будет использовать пиктограммы во многих экранах, поэтому их общим источником выбран
`lucide-react`: пакет совместим с React 19, не требует runtime-зависимостей и допускает
поэлементные импорты. Наружу UI-кит отдаёт собственные компоненты по смыслу действия, а не исходные
имена Lucide. Так толщина линий, размерная сетка и замена конкретного символа остаются одним
решением кита.

Для снятия метки используется `TagX`: поставленная версия Lucide не экспортирует `TagOff`, а крест
поверх тега прямо отличает снятие существующей метки от обычной установки `Tag`.

**Локальные SVG в каждом экране.** Отвергнуты: при росте числа пиктограмм они образуют несколько
несогласованных наборов и дублируют геометрию.

**Прямой импорт Lucide из приложений.** Отвергнут: внешний словарь и настройки разошлись бы по
потребителям, а смена библиотеки потребовала бы правок во всех экранах.
