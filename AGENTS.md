# AGENTS.md

Правила работы с этим репозиторием. Файл читается агентом в начале каждой сессии и является
источником истины по процессу. Если реальность разошлась с этим документом — правится документ.

> Содержание этого файла — точная копия [CLAUDE.md](CLAUDE.md). Документ-источник там же;
> при правках один вовремя обновляется вторым, расхождение считается багом.

## 0. Контекст проекта

- **Проект:** `sovereign_platform_node`
- **Статус:** старт разработки, архитектура не зафиксирована.
- **Способ разработки:** весь код пишут ИИ-агенты. У агента нет памяти между сессиями —
  единственная долговременная память проекта это **репозиторий**: код, `docs/`, история коммитов.

> Описание продукта, границы системы и стек ещё не зафиксированы. Документы по этим темам
> появятся в `docs/` по мере принятия решений.

## 1. Главный принцип

**Знание, не записанное в репозиторий, считается утерянным.**

Если во время работы выяснилось что-то, что понадобится через месяц другому агенту, — это
попадает в `docs/`, а не только в ответ пользователю. Сюда относятся: принятые решения и их
причины, отвергнутые варианты, внешние ограничения, договорённости по API, неочевидные баги
окружения.

Не документируется то, что и так видно из кода или `git log`.

## 2. Документация

Каталог `docs/`. Структура не задана заранее и растёт по факту: документ заводится тогда, когда
есть что в нём написать. Заглушки не создаются — пустой файл создаёт видимость проработанной
темы. Актуальный список документов — в [docs/README.md](docs/README.md), он обновляется тем же
коммитом, что и новый документ.

Правила:

- Один документ — одна тема. Разросшийся файл дробится, а не растёт до 1000 строк.
- Документация живёт в том же коммите, что и изменение кода, которое её вызвало.
- Устаревший документ удаляется или переписывается. Неверная документация хуже её отсутствия.
- Язык документации — русский. Язык кода, идентификаторов и коммитов — английский.

### Решения и отвергнутые варианты

Отдельного журнала решений в репозитории нет. Решение живёт в том документе, который описывает
затронутую тему: как устроено — в основном тексте, почему устроено именно так и что отвергнуто —
в разделе **«Почему так»** в конце того же документа.

- **Решение и его обоснование не расходятся по разным файлам.** Читающий про шину событий видит
  и правила, и причину, по которой отвергнута альтернатива, не открывая второй документ.
- **Отвергнутые варианты записываются с причиной отказа.** Это самая ценная часть: она избавляет
  следующего агента от повторного прохода по тупикам.
- **Решение изменилось — документ переписывается.** История версий и так лежит в `git log`;
  держать в тексте отменённые формулировки значит заставлять читателя выяснять, какая из них
  действующая. Отвергнутый ранее вариант остаётся в «Почему так» именно как отвергнутый.
- Дорогое для отката решение (выбор БД, транспорта, схемы данных, границ модулей, внешней
  зависимости) обязано попасть в «Почему так» — без него правило выглядит произволом.

## 3. Коммиты

- **Маленькие и атомарные.** Один коммит — одно логическое изменение. Рефакторинг, фича и
  форматирование не смешиваются в одном коммите.
- Каждый коммит оставляет репозиторий в рабочем состоянии: собирается, тесты зелёные.
- Формат сообщения — Conventional Commits:

  ```
  <type>(<scope>): <краткое описание в императиве, англ., до 72 символов>

  <необязательное тело: зачем это изменение, какие альтернативы отвергнуты>
  ```

  Типы: `feat`, `fix`, `refactor`, `docs`, `test`, `chore`, `perf`, `build`, `ci`.

- В теле коммита объясняется **почему**, а не «что» — «что» видно из диффа.
- Коммиты, сделанные агентом, помечаются трейлером:

  ```
  Co-Authored-By: Claude Opus 5 <noreply@anthropic.com>
  ```

- Не коммитить: секреты, `.env`, артефакты сборки, локальные конфиги IDE.
- Агент коммитит сам по ходу работы; `push` и создание PR — только по явной просьбе.

## 4. Ветки

- `main` — всегда рабочая, всегда собирается.
- Работа ведётся в ветках `feat/...`, `fix/...`, `docs/...`, `refactor/...`.
- Прямые коммиты в `main` допустимы только для стартового каркаса и правок документации.

## 5. Порядок работы агента

**В начале сессии:**

1. Прочитать `CLAUDE.md`.
2. Прочитать `docs/README.md` и оттуда — документы по затрагиваемой области.
3. В каждом из них прочитать раздел «Почему так»: там причины и уже отвергнутые варианты.
4. Посмотреть `git log --oneline -20` — чем закончилась прошлая сессия.

**Во время работы:**

- Сначала прочитать существующий код, потом писать. Новый код повторяет стиль соседнего.
- Не расширять задачу молча. Замеченное «попутно» либо чинится отдельным коммитом, либо
  выносится в бэклог (`docs/backlog.md`, файл создаётся при первой записи).
- Не изобретать абстракции «на будущее». Только то, что нужно текущей задаче.
- Каждое изменение проверяется запуском: тесты, линтер, сборка. «Должно работать» — не результат.

**В конце сессии:**

- Изменения закоммичены.
- Документация приведена в соответствие коду.
- Незавершённое зафиксировано в `docs/backlog.md`: что сделано, что осталось, где остановились.

## 6. Definition of Done

Задача закрыта, когда всё перечисленное выполнено:

- [ ] Код написан и работает — проверено запуском, а не рассуждением.
- [ ] Есть тесты на новое поведение и на исправленный баг.
- [ ] Линтер и сборка проходят без ошибок и новых предупреждений.
- [ ] Документация обновлена; значимое решение записано в «Почему так» своего документа.
- [ ] Изменения разбиты на атомарные коммиты с осмысленными сообщениями.

## 7. Требования к коду

- Именование по делу: имя объясняет назначение, а не тип. Сокращений нет.
- Комментарии объясняют «почему», а не пересказывают код.
- Ошибки не глушатся. `catch` без обработки — баг.
- Внешние зависимости добавляются осознанно: каждая новая — это запись в «Почему так» того
  документа, чью задачу она решает.
- Публичные интерфейсы модулей описываются в `docs/`.

> Конкретика по стеку (форматтер, линтер, версии, команды запуска) появится в `docs/`, когда
> стек будет выбран.

## 8. Взаимодействие с пользователем

- **Архитектурные решения агент не принимает.** Любая развилка, влияющая на архитектуру,
  сначала выносится на согласование: варианты, разница между ними, чем платим за каждый,
  рекомендация. Реализуется тот вариант, который выбрал владелец продукта.
- **Утверждено только то, что владелец продукта сформулировал явно.** Предложение агента,
  не получившее явного «да», в спецификацию попадает со статусом «обсуждается» и не
  считается основанием для кода.
- Развилки внутри реализации (имя, порядок аргументов, форма вспомогательной функции) агент
  решает сам.
- Работа идёт короткими итерациями. Каждое задание завершается коммитом.
- Отчёт по факту: что сделано, что проверено, что не сделано и почему. Без приукрашивания.
