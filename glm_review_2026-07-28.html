2Документация — полнота и качество

Вердикт: избыточности нет, полнота выдающаяся

Все 23 документа в docs/ привязаны к темам через master-spec.md и README.md, оба источника согласованы. Заглушек нет — каждый документ существует потому, что по теме есть содержание. У каждого нормативного документа есть раздел «Почему так» с перечислением отвергнутых вариантов и причины отказа — это самая ценная часть для ИИ-агента без памяти между сессиями (явно заявленная цель в CLAUDE.md).

Что сделано хорошо

  • Единая модель памяти. Решения и их обоснование живут в одном файле с правилом — это прямо противопоставлено отвергнутому docs/adr/ (74 файла), и спор, почему так, записан честно.
  • Статус каждого раздела явный. master-spec.md разделяет «Утверждено / Обсуждается / Не начато», явно отмечая «справочник по Pi 0.82.1, прочитан по исходникам» — чтобы следующий агент не принял чужой контракт за наш.
  • «Замер верен, решение отменено». В runtime-checks.md (проверки 6, 10, 20) SQLite-замеры остались с честной пометкой, что база отвергнута, но цифры остаются фактом о рантайме. Это образец того, как обращаться с устаревшим решением, не теряя знания.
  • Roadmap зафиксирован до конца платформы (срезы 5–13) — объяснено, почему порядок утверждён сразу, а не по одному срезу (у агента нет памяти, иначе каждая сессия переоткрывает вопрос).
  • Документация — часть Definition of Done (CLAUDE.md §6): без обновления docs задача не закрывается.

4apps/daemon — ядро и супервизор

Самая густая по логике часть: супервизор плагинов с конечным автоматом состояний, перезапуском, воркерами и установкой зависимостей, плюс шина, SSE-стрим, настройки и лок-файл. ~3900 строк кода, ~3200 строк тестов (соотношение хорошее). Здесь же — большая часть найденных багов, что типично: сложность集中ена в одном файле.

High — баги и утечки, которые сработают

Накопление message-listener-ов на воркере при каждой перезагрузке High

apps/daemon/src/plugin-supervisor.ts:424

При остановке воркера в stop() навешивается ещё один worker.on("message", …), ждущий deactivated, поверх постоянного listener-а из launch() (строка 374). Снять ни один из них не успевает — worker.terminate() не порождает cleanup. После N перезагрузок одного плагина на одном воркере копится N+1 listener; Node также начинает печатать MaxListenersExceededWarning после 10.

// launch() ставит постоянный listener
worker.on("message", (message: PluginOutgoing) => { … });
// stop() добавляет ещё один, ожидающий deactivated — без once/off
worker.on("message", (message: PluginOutgoing) => {
  if (message.kind === "deactivated") finish();
});

Лекарство: worker.once("message", …) плюс явный worker.off(...) в finally, либо отслеживать через слабый Map.

stop() не резолвится при досрочном exit воркера — длинный shutdown High

apps/daemon/src/plugin-supervisor.ts:406–432

В stop() промис ожидает либо сообщения deactivated, либо срабатывания таймаута deactivateTimeout (2 с). Если воркер умирает раньше сам — обработчик exit (launch(), строка 376) снимает состояние, но не резолвит ожидающий stop(). Тот честно ждёт свои 2 секунды. На stopAll, который идёт последовательно (строка 576 for…of await), это складывается: 20 упавших плагинов = 40 секунд до отпускания лока.

Глобального дедлайна на stopAll нет, а лок отпускается в .finally (строка 154). SIGTERM на сложной установке будет ждать заметное время. Лекарство: слушать exit внутри stop() и резолвить сразу.

Установка npm install без таймаута — зависший плагин зависает навсегда High

apps/daemon/src/plugin-dependencies.ts:134–166

spawn("npm", ["install", …], { stdio }) ждёт 'close' или 'error'. Если npm повис на сетевом запросе к реестру или на сломанном postinstall (stdin уже ignore, но других защит нет), промис не резолвится никогда. Супервизор считает состояние installing, а installing в apply() (строка 528) считается «alive» — значит, никаких повторов. Один зависший сетевой узел = один навсегда застрявший плагин без восстановления, кроме перезапуска демона.

Лекарство: таймаут на spawn (например, 60–120 с) с интерпретацией таймаута как failed.

bus.subscribe в plugin-events не отписывается High

apps/daemon/src/plugin-events.ts:42

Подписка создаётся, но функция отписки, которую возвращает bus.subscribe(...), не сохраняется и не вызывается. stopAll не закрывает объект events. На shutdown это не страшно (процесс уходит), но это несоответствие с event-stream.ts, который свой unsubscribe хранит и вызывает. Если createPluginSupervisor когда-нибудь будет пересоздан в рантайме (или в тестах), старая подписка останется живой и будет доставлять события в дохлые хэндлы воркеров.

Цепочка applying в main.ts создаёт ложное ощущение безопасности Medium

apps/daemon/src/main.ts:82–95

Комментарий обещает «чтобы два одновременных перечитывания не запустили один плагин дважды». На деле вся защита — это проверка entry.startToken === token в start()/launch(). А цепочка ещё и глотает ошибки в .catch (только логирует), маскируя реальные баги apply/reload. Двойной путь applyPlugins() при каждой смене настроек и при каждом FS-событии ещё и полностью переоткрывает файловую систему вместо диффа против in-memory состояния. Тяжелее, чем нужно.

Debounce-таймеры без .unref() Medium

apps/daemon/src/plugin-watcher.ts:73 · apps/daemon/src/settings.ts:180

В setTimeout(...) не вызывается .unref(). close() чистит оба, поэтому блокирует только если обработчик сигнала не отработал. Но это несоответствие с event-stream.ts:104, где ping-таймер правильно unref-ается. Привести к одному стилю.

Medium — на масштабе

failed считается alive — preferences не переоцениваются до retry Medium

apps/daemon/src/plugin-supervisor.ts:526–536

Если плагин лежит в failed на потолке задержки (60 с), а пользователь переключает его вклад в preferences, apply() ничего не делает — плагин «жив». Изменение применится, только когда догорит таймер retry. Сюрприз для пользователя: переключил — изменений нет до минуты.

O(n) фильтр и JSON.stringify-дифф на горячем пути Medium

apps/daemon/src/event-stream.ts:176 · apps/daemon/src/contribution-registry.ts:111 · apps/daemon/src/settings.ts:151

recent.filter(...) при каждом переподключении клиента (до 1000 событий × N клиентов), и JSON.stringify(nextResolved) !== JSON.stringify(resolved) при каждом применении вкладов. На десятках плагинов незаметно, на сотнях — кадр на каждом apply. Лечится бинарным поиском по индексу и счётчиком ревизий соответственно.

apps/daemon/src/dispatcher.ts:28

Тип method: "GET" | "POST" | "PUT" | "DELETE" — но в коде зарегистрированы только GET/PUT. YAGNI: добавить POST можно одной строкой, когда понадобится. То же про возвращаемое RouteHandler значение — ни один handler его не использует.

Консистентность итерации listener-ов Low

event-bus.ts:41 копирует в массив перед итерацией (с обоснованием в комментарии), а settings.ts:157 итерирует живой Set. Одинаковый риск — разная защита. Три разные формы «вещь или причина отказа» (WriteOutcome, DependencyOutcome, DiscoveredPlugin | RefusedPlugin | undefined) для одной семантики.

Сильные места ядра

  • Паттерн startToken (plugin-supervisor.ts:340–351) корректно отменяет устаревшие асинхронные запуски — главная защита от гонок в supervisor-е.
  • Окно стабильности (:244–247) сбрасывает счётчик попыток, только если плагин продержался stability — иначе редкая ошибка раз в сутки навсегда оставила бы плагин на потолке задержки. Тонкая правильная деталь.
  • Одноразовая обработка протухшего лока (instance-lock.ts:73–81) с честным комментарием про thundering herd.
  • patchPreferences (settings.ts:196–217) перечитывает файл перед записью — сохраняет неизвестные ключи от более новой версии платформы и ручные правки. Атомарная запись с cleanup во finally.
  • Slow-client detection (event-stream.ts:186–198) через writableLength — честный порог в 1 МБ вместо таймаута. Демон не падает от OOM на болтливом потоке.
  • Защита после отправки заголовков (dispatcher.ts:142–149): если ошибка после headersSent, сокет уничтожается, а не пытается дописать 500. Многие серверы делают это неправильно.
  • Защита неймспейса core.* (contribution-registry.ts:142–148): плагин не может выдать себя за ядро в событии.
  • Резервные поля журнала (logger.ts:45–49): плагин не может подделать source или time.

5apps/web + packages/ui-kit — интерфейс

SPA на React со своим роутером, одной SSE-связью с фронтовой шиной и трёхпанельной оболочкой. Кит — палитра/роли/схемы как данные, локализация каталогами. Самое ценное — чистые редьюсеры (plugins/state.ts), самое слабое — ручной React-клей вокруг них.

High — утечки и гонки

PanelResizer теряет window-listener-ы при пропущенном pointerup High

apps/web/src/shell/shell.tsx:105–126

При onPointerDown на window навешиваются pointermove/pointerup, снимаются только в pointerup. Если пользователь переключился на другую вкладку, Alt-Tab-нул, открыл DevTools или паузнул выполнение — pointerup не придет, и listener-ы висят вечно: каждое последующее движение мышью по странице повторно вызывает onResize. Нет ни pointercancel, ни visibilitychange/blur очистки. Лекарство — одна строка: слушать ещё и pointercancel с тем же drop.

Двойной путь setState обходится защитный ref, который сам и ломает High

apps/web/src/plugins/use-plugins.ts:46–50, 77–80

В комментарий сказано: «кадры приходят чаще, чем React успевает отрисовать», поэтому заведён latest.current-зеркало. Но в подписке шины вызывается и apply (пишет в ref), и setState напрямую. Любой будущий setState(...) минуя apply — и зеркало разъезжается с отрисованным состоянием, а это ровно тот баг, ради которого ref заведён. Идиоматичное решение — setState(prev => …), который видит последнюю очередь, и ref вообще не нужен.

Оптимистичные записи без ordering — гонки на быстрых переключениях High

apps/web/src/plugins/use-plugins.ts:101–120 · apps/web/src/App.tsx:192–204

И в switchPlugin, и в записи внешнего вида, локальное состояние обновляется оптимистично, затем .then(setPreferences) перезаписывает серверным ответом. Если пользователь переключил дважды подряд, второй оптимистичный apply выигрывает локально, но первый запрос резолвится первым и затирает второе решение пользователя ответом на первое. Нет ни sequence number, ни per-key in-flight отслеживания. В switchPlugin это «вкладки прыгают туда-сюда», во внешнем виде — «тема не та, что выбрал».

6packages/protocol и packages/sdk — публичный контракт

SDK — самый дорогой в изменении пакет («ломать дороже, чем всё остальное», public-contract.md). Поэтому каждая находка здесь весит больше: ширина экспорта сегодня определяет цену завтрашних правок.

High — утечка внутренних деталей в public API

SDK экспортирует 4 subpath без различения public/internal High

packages/sdk/package.json:6–11

"exports": {
  ".": "./src/index.ts",
  "./testing": "./src/testing.ts",
  "./host": "./src/host.ts",
  "./events": "./src/events.ts"
}

При этом host.ts сам говорит: «Авторам плагинов эта точка входа не нужна», а в events.ts: «её зовёт бутстрап воркера… Автору плагина она не нужна». То есть два из четырёх subpath — daemon-внутреннее соединение, но выглядят они точно так же, как легитимный ./testing. Единственный потребитель ./host и ./events — это apps/daemon/src/plugin-worker.ts. Любой внешне написанный плагин может сделать import { installPluginHost } from "@sovereign/sdk/host" — и с этого момента убрать subpath уже ломающее изменение. Нужно синтаксически различимое место для внутренних швов (./internal/host, отдельный @sovereign/sdk-internal, или relative path внутри монорепы).

z.prettifyError на error-path — хрупкая зависимость от zod@4 минора High

packages/sdk/src/index.ts:78–91

Ошибка валидации схемы события форматируется через z.prettifyError. Это недокументированный API zod 4 (зафиксирован zod@4.4.3). Любой даунгрейд или расхождение версий zod между демоном и плагином — и на error-пути возникает TypeError: z.prettifyError is not a function, который глушит исходную ошибку валидации. Это место, где SDK должен быть максимально стабилен. Заменить на z.flattenError или собственное форматирование.

export * из каждого модуля протокола — новый хелпер становится публичным High

packages/protocol/src/index.ts:6–16

Пакет позиционирован как «единственный источник правды о типах», но export * из 11 модулей означает: любой новый экспорт автоматически попадает в публичный контракт. Сегодня поверхность уже смешивает (а) wire-типы (Health, StreamEvent), (б) daemon-внутренние парсеры (parsePluginManifest, parseConfig, parsePreferences), (в) функции-хелперы (matchVersionRange). Нужно явный allow-list в index.ts, а не firehose.

parseAppearance и parseLocale экспортированы без потребителей High

packages/protocol/src/settings.ts:160, 204

Grep по репозиторию: ни один внешний файл эти функции не использует. Комментарий оправдывает экспорт тем, что «тем же телом они меняются через веб-API» — но веб-API использует parseAppearancePreferences, другую функцию. YAGNI, который станет неудаляемым, как только выпустится. Классический пример «висячего публичного» — попадает под то самое правило public-contract.md, что видимостью не публикуется.

8Сильные стороны (сохранять)

Что в проекте сделано выше среднего и не должно пострадать при правках:

  1. Дисциплина «почему так». Каждое архитектурное решение сопровождается перечислением отвергнутых альтернатив с причиной отказа. Для ИИ-агента без памяти между сессиями (явно декларированная модель работы) это не красота, а функциональная необходимость. Ценность перевешивает барьер русского языка.
  2. Зависимости под линтером. Граница apps↔packages, запрет apps→apps, запрет @earendil-works/* за пределами пакета реализации (контрактный sdk-реэкспорт событий — единственное именованное исключение). Непроверяемое правило считается отсутствующим — и это подкреплено структурой репозитория (отдельный корень plugins/).
  3. Проверка запуском, не рассуждением. runtime-checks.md — 26 проверок возможностей Node, на которых стоят решения. Замеры честно помечаются как «верен, решение отменено» при отходе от них. Это уникальная для «старта разработки» дисциплина.
  4. Потребление внутренних пакетов исходниками. Решило real-проблему (hot-reload без шага сборки) и подкреплено замером (pnpm разворачивает симлинк, типы стираются). tsc --noEmit — отдельная обязательная цель, что явно зафиксировано в runbook.
  5. Чистые редьюсеры в интерфейсе. plugins/state.ts — образец: чистая функция, IO отделено, тесты рядом с логикой. DOM-стека нет, но это сознательное решение с названным порогом в backlog.
  6. Токены как данные. Палитра заморожена (13 ключей), роли выводятся из неё через color-mix, схема приносится плагином как объект. tokenContract мажор даёт честный отказ вместо «чужих цветов».
  7. Аккуратные lifecycle-инварианты. startToken, окно стабильности для retry, одноразовая обработка протухшего лока, slow-client detection по writableLength — тонкие детали, которые обычно пропускают.
  8. Защита от подделки источника. Ядро ставит source/time в журнале; плагин не может занять core.*-неймспейс; идентичность приходит из воркера, а не из кода плагина.
  9. Atomic write с cleanup в finally, перечитывание файла перед записью. Сохраняет неизвестные ключи от более новой версии и ручные правки.
  10. Native-HTML-первый кит и доступность. <details>, role=status/alert, prefers-reduced-motion, стрелки на сепараторе панелей — выше нормы для самописного кита.
